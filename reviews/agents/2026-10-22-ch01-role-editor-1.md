## 총평
1. 작가 지적이 맞다. 장 첫 문단부터 차이를 먼저 말하고, 장 정의는 셋째 절에서 나온다. 둘째 절은 정의되지 않은 에이전트, 하네스, 설정, 실행 장치를 비교 대상으로 쓴다. "뜻은 다음 절"처럼 정의를 미루는 표시가 세 번 나온다.
2. 정의 뒤에도 실행 장치 다섯 기능, 다섯 구성 요소, "하네스가 하는 일 여섯 가지"의 세 목록이 이름이 겹치고, 해명 문단으로 메운다. 핵심 정의인 다섯 구성 요소는 문단 중간 종속절에 묻혀 있다.
3. 하네스가 "프로그램", "실행 체계", "작업 환경"으로 불리고, 기록은 본문, 그림 1-1, 표 1-6이 다르게 연결하며, 프롬프트 정의가 세 번 반복된다.
4. 가장 쉬운 예("같은 모델도 도구를 연결하지 않은 호출에서는 답변만 하고…")가 셋째 절 끝에 묻혀 있다.

## 표, 그림(7건)
- 표 1-1: "자율 수행 영역"이 에이전트의 자율과 헷갈림, 작업 진행과 실행 범위 행은 본문이 아직 말하지 않음
- 표 1-2: 루프 실행 주체 열의 차이가 본문에 없음
- 표 1-3: 본문 적용 위치 칸이 정의 전 용어로 판정, "모델은 제품 안의 구성 요소"
- 그림 1-1: 기억 → 세션 기록, 결과 확인 → 검증 연결이 본문, 표 1-1과 다름
- 표 1-4: 설명 줄이 표에 없는 분류를 더함
- 그림 1-2: "허용, 확인, 거부"와 본문 용어 불일치, "결과 보고 후 완료"
- 표 1-6: 기록 행이 실행 장치의 세션 기록(모순), 컨텍스트 구성에 역할만

## 제안하는 절 순서
0. 장 첫 문단: 같은 모델 예 → 차이는 모델 바깥 → 범위
1. 모델만으로 할 수 없는 일: 토큰과 컨텍스트 → 도구 정의 → 세 한계 → 하네스라고 부름
2. 이 책의 에이전트와 하네스: 모델 + 하네스 → 실행 장치와 설정 → 다섯 구성 요소(독립 문단) → 외부 실행 환경 → 그림 1-1, 표 1-4. 여섯 가지 목록 삭제
3. 에이전트 루프와 종료 조건: 권한 규칙과 권한 모드 정의
4. 같은 명칭, 다른 맥락: 정의 뒤로. 다른 자료의 말이 이 책 정의 어디에 대응하는가
5. 하네스 엔지니어링
6. 세 설계 층(layers와 prompt-context 합침)
7. 소프트웨어 엔지니어링과의 접점
8. 결과를 개선할 수 있는 영역
9. 확인 방법, 10. 원칙과 점검 질문
