## 1. 총평: 가장 큰 문제 셋

**① 이 장의 핵심 이름이 앞 장, 용어 풀이와 다르게 정의되었습니다. 정의가 미뤄지거나 결론 문장 안에 들어가 있고, 처음 배우는 독자가 모르는 말도 풀지 않았습니다. 8장 원인 1과 4가 그대로 남았습니다(P3, 5장, 20.1-1).**
- **다르게 정의된 이름**
  - 격리: 1장 17행은 "격리 환경, 곧 샌드박스"라고 썼습니다. 9장은 격리(방법), 샌드박스(셸 명령에만 거는 기능), 격리된 실행 환경(컨테이너, 가상 머신)으로 나눕니다(6, A1).
  - 승인자: 9장은 "확인 요청에 승인하거나 거절하는 사람"입니다. 6~8장은 "되돌리기 어려운 동작과 작업 단위의 완료를 승인하는 사람"입니다(8).
  - 권한 모드: 9장과 용어 풀이는 "규칙에 없는 요청을 물어볼지…"입니다. 설계서와 1장은 "도구 호출을 승인하는 방식을 정하는 설정"입니다(17, 55).
  - "되돌리기 어려운 동작": 승인 지점 전체를 가리키는 이름이면서, 세 종류 가운데 하나의 이름으로도 쓰였습니다(11).
- **미루거나 묻은 정의**
  - "뒤의 격리와 샌드박스 절에서 정의합니다"는 정의를 미루는 표시입니다(6).
  - 격리, 승인 지점의 정의가 "필요합니다", "둡니다" 같은 결론 문장 안에 있습니다(8, 20).
  - 프롬프트 주입은 정의보다 먼저 쓰였습니다(20).
- **풀지 않은 말**
  - 셸, 운영 체제 수준(도입부, 3)
  - 에이전트 명세서(4)
  - 브랜치, 강제 push, 풀 리퀘스트(PR), commit, push(11)
  - 보안 경계(19), 허용 도메인(20), 컨테이너(21), API(28)
  - 확장 사고, 전처리 훅(29), 사용 크레딧, 워크스페이스(31)
  - 원본 자료, 검증 기준, check.py(37), touch ~/sandbox-probe(48), 비용 기준 문서(51)

**② 제품 동작을 실제보다 단순하게 써서 본문, 표, 그림, 앞 장, 실습이 서로 다른 것을 말합니다. 8장 원인 3이 남았습니다(P6, 7.1, 7.2, 8장).**
- **권한 모드가 빠짐**: 규칙에 없는 명령은 권한 모드가 처리합니다. 3장 77행은 "수동 모드는 묻고, auto 모드는 확인 없이 실행될 수 있다"고 썼습니다. 9장 예제(65행)와 표 9-5는 이 단계를 빼고 "막지 못합니다"라고만 씁니다. "켜면 막는다"(65행)와 표 9-5("허용 도메인에 넣지 않고 확인이 오면 거절")는 같은 장치의 힘을 다르게 씁니다(41, 44).
- **일반화**: "권한 규칙은 명령 문자열만 대조"는 Bash 규칙에만 맞습니다. Edit 규칙은 경로를 대조합니다. 그런데 요약, 그림 9-1의 "*" 줄, 실습 3에 이 일반화가 있습니다(5, 25, 56).
- **파일 수정 허용**: 표 9-5와 19행은 "파일 수정은 허용"이라고 씁니다. 예제 설정 파일에는 Edit 허용이 없고, 실습 4와 5는 파일 수정 확인 화면을 승인하라고 안내합니다(14, 46).
- **사용량 행의 시점**: 확인 표 앞 문장은 사용량 행이 "실습 단계에 없음"이라고 씁니다. 실습 6의 5단계에 /usage가 있습니다(47).
- **요금 화면**: 실습 6과 그림 9-2는 청구액을 "요금 화면"에서 보라고 하며 9장 비용 관리 절로 링크합니다. 그 절에는 요금 화면이 없습니다(33).
- **샌드박스의 기본 쓰기 범위**: 샌드박스는 기본으로 작업 폴더 쓰기를 허용합니다. 그래서 작업 폴더 안의 data/는 금지 규칙이 샌드박스에 합쳐져야 보호됩니다. 이 실무 핵심이 표 9-5의 칸에만 있고 본문에 없습니다(20, 9.4).

**③ 점검 문안을 문장과 표 칸에 덧붙이고 앞뒤를 다시 읽지 않았습니다. 그래서 문단과 칸이 과밀해지고 설명 순서가 거꾸로 되었습니다. 8장 원인 2가 남았습니다(4.4, P2, 9.3-9).**
