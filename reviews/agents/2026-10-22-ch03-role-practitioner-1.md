## 총평(가장 큰 문제 먼저)

1. **작업 단위의 완료 판정이 실제로 돌아가지 않습니다(R6, R14, R17).**
   - 본문, 표 3-2, 그림 3-1은 "작업 2~4는 검사 스크립트(check.py) 통과"로 씁니다. 그런데 수용 시험 1~3은 작업 4가 끝나야 통과하고, project_code 시험은 작업 3이 끝나야 생깁니다.
   - 그래서 작업 2와 작업 3을 마친 시점에는 check.py가 계속 종료 코드 1로 끝납니다.
   - CLAUDE.example.md의 규칙("통과하면 그 단위의 통과 값만 true")을 그대로 따르면 작업 2를 완료 처리할 수 없습니다.
   - 그 사이 수용 시험 1~3이 정상적으로 계속 실패하므로 "같은 시험 세 번 연속 실패하면 중단" 규칙도 걸립니다.
   - 완료 판정은 docs/example-facts.md처럼 작업별로 check.py 출력의 해당 부분을 보도록 써야 합니다(작업 2는 Q-118 공백 명시, 작업 3은 tests 실패 0건과 project_code 시험 1건 이상, 작업 4는 종료 코드 0).
   - 중단 규칙도 "그 작업 단위의 확인 대상 시험"으로 범위를 좁혀야 합니다.
2. **"수정할 수 없다"를 넘치게 말합니다(R1, R13, R16).**
   - 공식 문서상 Edit 금지 규칙은 내장 편집 도구, Claude Code가 알아보는 Bash 파일 명령(sed, tee 등), 리다이렉션에만 적용됩니다. 파일을 스스로 여는 Python 스크립트 같은 하위 프로세스에는 적용되지 않습니다(permissions 문서 경고 상자, OS 수준 차단은 샌드박스).
   - `Bash(git push *)`는 `git -C . push`와 일치하지 않습니다(C3-4, C3-8).
   - 그런데 요약, 49행, 62행, 표 3-5는 "수정하지 못하게 합니다", "강제"로만 씁니다. 조건(편집 도구, 확인 요청 의존)과 Chapter 9의 샌드박스 연결이 필요합니다.
3. **검증 기준 보호 논리에 구멍이 둘 있습니다.**
   - 49행의 예시(수용 시험 한 건 삭제 → check.py 통과)는 바뀐 check.py에서는 성립하지 않습니다(정한 수 5건을 확인함). 실제로 남는 길은 시험 내용을 약하게 바꾸는 것이라 예시를 바꿔야 합니다.
   - "단위 테스트를 수정할 수 있어도 이 길은 남지 않습니다"도 작업 3에서는 틀립니다. 작업 3의 완료 근거(project_code 시험 1건 이상, tests 실패 0건)를 에이전트가 직접 쓰는 단위 테스트가 맡기 때문입니다. 이 경우 검토 하위 에이전트와 commit 확인이 실질적인 방어선이라고 밝혀야 합니다.
4. **장 정비 규칙을 아직 하나도 적용하지 않았습니다.**
   - R12: "CR", "(Change Request)"가 본문 15곳, 표 3-2, 3-5 캡션에 있습니다.
   - R11: `#ref-` 링크 7곳과 장 끝 참고 자료 절이 남아 있습니다. ref-anthropic-2026b 하나가 문서 3개를 묶고 있습니다. bibliography.json에는 sub-agents, commands, memory 키가 없습니다.

5. **제품 동작 서술 가운데 실무에서 걸리는 세부가 있습니다.**

   - 훅이 `python`과 상대 경로 `tests`만 써서, python3만 있는 환경이나 하위 폴더로 이동한 세션에서는 시험 실패가 아니라 명령 오류로 종료 코드 2를 냅니다.
   - 검토 하위 에이전트는 Bash가 없어 git diff를 볼 수 없습니다. 그런데 "변경된 코드"를 무엇으로 아는지 빠져 있습니다.
