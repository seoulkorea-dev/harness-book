## (3) 개정 명세에 넣을 것

### 절 순서와 절 첫 문단(왜 → 무엇 → 어떻게 → 근거)
기존 앵� approval, cost, permissions, principle은 유지합니다. 새 앵커는 isolation과 example 둘입니다. ch02#instruct-enforce 끝, ch02 표 2-2, ch03 표 3-1, ch06 표, ch11이 ch09 앵커를 가리키므로 permissions 절에는 평가 순서와 ask 확인 설명이 남아야 합니다.

| 0 | 장 첫 문단 | 작동 → 한계 → 결과 → 행동 → "승인, 격리, 비용을 다룹니다" (#1). 둘째 문장에 주장을 되풀이하지 않음 |
| 1 | 위험 관리의 세 가지(kinds) | 왜: 허용된 권한 안에서도 사고는 동작 실행, 접근 범위, 지출의 세 경로로 생김. 무엇: 이 책은 방법을 승인, 격리, 비용으로 정리하고 셋 모두 "허용 범위를 정한다"는 같은 원리. 어떻게: 표 9-1(일반 용어, 병기). 근거: 이 책의 정리이므로 각 절의 출처로 안내 |

### 장 틀
CR 적용 절을 포함합니다. 주장 제목, 원리(kinds, approval, permissions, isolation, cost), CR 적용(example), 실패 표, 확인 방법, 원칙 한 문장, 점검 질문 순서이며, 지금은 CR 적용이 permissions 안에 끼어 있어 장 틀 단계 하나가 빠진 상태입니다. 4~8장도 id="example" 절을 둡니다.

### 그림 9-1, 9-2(D-116, 기준 시각 체계 1-1, 1-2, 2-2 형식)
공통: 폭 760(글자 16px 이상) 또는 960(20px 이상), 맨 위에 합니다체 결론 제목과 강조색 가로선, 단색 면과 선. 금지와 거부는 앰버 대신 회색 점선과 글자, 연결선은 직선(꺾을 때 직각), 그림 안 문구는 개조체, 요약은 상자 없이 맨 아래 "*" 한 줄. 제품명, 명령 이름, 예제 파일 이름과 예제 사실은 넣지 않음. 배치가 다른 시안 두 개를 만들어 하나를 고름(D-107).

- 그림 9-1(권한 규칙) 담을 것: (1) 맨 위 결론 제목 예: "동작의 위험에 따라 허용, 확인, 금지를 나누고 접근 범위는 격리로 보완합니다". (2) 도구 호출 요청이 금지, 확인 요청, 허용 순서로 대조되고 어디에도 없으면 권한 모드로 가는 평가 순서(ch02 그림 2-2의 단계 3과 같은 이름과 순서, 그림 1-2의 번호 사용). 금지는 회색 점선, 확인은 사람 확인 지점. (3) 동작의 위험에 따른 규칙 배치는 본문 절에서 설명하는 일반 기준(되돌릴 수 있으면 허용, 사람이 판단해 진행하면 확인 요청, 에이전트가 하지 않고 사람이 직접 하면 금지)만, 2×2 축은 본문에 같은 설명이 있을 때만 유지. 구체 예(push, 원본 자료 수정, commit)는 표 9-2와 CR 적용 절로 이동. (4) 규칙과 별도로 운영 체제 수준 접근 제한(격리)이 바깥에서 감싸는 층이라는 관계를 방향과 이름이 있는 화살표나 영역으로. (5) 표 9-2는 이 구성 요소의 "무엇인가"와 "본문의 절"만 맡음.
- 그림 9-2(비용 기준) 담을 것: 제품 중립으로 "작업 시작 전에 정함"(작업 단위의 크기, 읽힐 자료의 범위, 지출 한도) → "실행 중 확인"(제품의 사용량 화면, 금액은 추정치) → "한도 도달 시 승인자가 계속 여부 결정"의 흐름을 위에서 아래(먼저 일어나는 흐름이 위)로 화살표와 이름을 붙여 보여 줌. 제품 명령(/usage, /status)과 Session은 표 9-3, 9-5와 본문으로. 승인자가 누구인지(주체)가 그림에서 분명해야 함. 맨 아래 한 줄은 "*" 요약.
