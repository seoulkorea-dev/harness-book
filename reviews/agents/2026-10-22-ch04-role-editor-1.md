### 구조 제안
- 첫 문단: 틀은 지키되 "그래서 … 따라서 …" 꼴을 풀고, 프롬프트 엔지니어링 정의를 첫머리에(Chapter 1). limits 둘째 문장은 지우거나 줄임
- elements 첫 문단: 첫 두 문장을 "왜" 한 문장으로, 네 정의는 네 문장이나 표 4-1로
- elements 둘째 문단: 성공 기준 = 완료 기준 문장을 인용 앞으로, 근거가 완료 기준에만 해당함을 밝힘
- elements 셋째 문단: 점선 설명은 표 4-2와 겹치므로 한 문장으로, 괄호 속 절 이름 참조 삭제
- techniques: 왜 → 무엇 → 출처 순서, 목록 항목은 "정의 → 출처의 근거 → 이 책의 쓰임"으로 통일, 표 4-3에 기능적 제약 열(3~5개는 권장, 금지는 권한 규칙, 실행 여부는 도구와 권한)
- limits 마지막 문단(모델 성능): elements 둘째 문단 끝으로, R2 문장 삭제
- example 첫 문단: 예제 이름 첫 등장 → 영향 검토 정의 → 3장과의 시간 순서 → 두 요청 비교 예고
- example-after: 용어 풀이는 요청문 앞으로, 뒤 문단은 "현재 상황 자료와 완료 기준 1의 역할"과 "두 요청의 차이"로 나눔, D-012 결정은 절 끝
- fail → check: 목적 누락, 입력 누락의 확인 항목이 표 4-6에 없음(R14, R17). "검토 범위"와 "현재 상황 반영" 행 추가

권고(비율에 넣지 않음)
- lead "따라서 … 점검해야 합니다"는 원칙 문장과 같은 말, "따라서"를 빼는 편이 나음
- "성공 기준(success criteria)" 원어와 함께
- 구체적 지시와 출력 형식의 관계를 한 구절로
- 여섯 가지 선별 기준(도구나 설정 없이 요청 문장만으로 적용)
- 할 일로 지시 항목의 강제 문장은 표 4-3 기능적 제약 열로
- 링크 표기 "Chapter 2의 지시와 강제"와 "Chapter 2"를 맞춤
- example-before의 "결정 기한"은 정의에 없음
- "이 사실을 모르는 검토는 …"은 의인화
- 요청문의 이름표를 네 요소로 통일할지 검토
- 요약 둘째 항목을 본문 정의와 같게
