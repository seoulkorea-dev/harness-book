Chapter 8 기록과 인계: 결정, 진행, 규칙의 문서화

작업이 이어지는지를 정하는 것은 대화 이력의 길이가 아니라, 결정과 진행 상황이 에이전트가 읽을 수 있는 문서로 남아 있는지입니다.

이 장에서는 세션이 끝나도 작업이 이어지도록 결정, 진행, 규칙을 저장소(코드와 문서를 변경 이력과 함께 보관하는 곳)의 문서로 남기는 기록과 인계를 다룹니다. 세션은 에이전트(Agent)와 대화를 한 번 시작해 끝낼 때까지이며, 컨텍스트(Context)는 모델이 응답을 생성할 때 입력되는 정보 전체이며, 새 세션은 이전 대화가 없는 새 컨텍스트에서 시작합니다. 대화에서만 합의한 내용은 세션이 끝나거나, 대화가 길어져 앞부분을 요약하는 압축이 일어나면 사라질 수 있습니다. 그러면 같은 논의와 같은 실수가 되풀이됩니다. 그래서 이어 갈 정보는 에이전트가 읽을 수 있는 문서로 남겨야 합니다.

남길 기록은 세 종류입니다. 무엇을 왜 정했는지 남기는 결정 기록, 어떤 작업이 어디까지 진행되었는지 남기는 진행 기록, 모든 작업에 적용할 지침을 담는 규칙 문서입니다. 세션을 넘길 때는 이 셋으로 알 수 없는 맥락을 인계 메모로 전달합니다. 에이전트가 실제로 한 일은 하네스(Harness)가 남기는 실행 로그로 확인합니다. Chapter 5가 에이전트가 읽을 정보를 정하고 Chapter 7이 결과를 증거로 판정하는 방법을 정했다면, 이 장은 그 정보와 증거가 세션이 끝난 뒤에도 남도록 기록을 설계합니다.

먼저 세션이 끝난 뒤 남는 것과 기록의 세 종류를 살펴보고, 결정 기록의 형식, 인계 메모 작성, 실행 로그와 추적을 익힌 뒤, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)을 두 세션에 나누어 기록하고 인계하는 예제를 다룹니다.

  • 새 세션과 다른 에이전트는 이전 대화를 읽지 못하므로, 이어 갈 정보는 저장소의 문서로 남깁니다.
  • 기록은 결정 기록, 진행 기록, 규칙 문서의 세 종류로 관리하고, 세션을 넘길 때는 인계 메모를 작성합니다.
  • 하네스가 남기는 실행 로그는 보관 기간, 추적 지점, 확인 방법을 정해 두고, 에이전트가 작업을 마쳤다고 알리는 완료 보고를 받을 때 함께 확인합니다.

세션이 끝난 뒤 남는 것

여러 세션에 걸친 작업에서는 세션과 세션 사이에 작업 상태가 이어지지 않습니다. Claude Code의 장기 실행 글도 이 문제를 다룹니다. 글의 실험에서 에이전트는 분리된 세션으로 일하며, 새 세션은 이전 세션의 기억 없이 시작합니다7. Claude Code 문서도 세션은 서로 독립적이고, 세션마다 새 컨텍스트에서 시작한다고 설명합니다6. 세션 사이에 지식을 전달하는 수단은 둘입니다. 하나는 사람이 작성하는 규칙 문서인 CLAUDE.md이고, 다른 하나는 Claude가 작업 중에 알게 된 내용을 스스로 파일에 적어 두고 다음 세션에 읽는 자동 메모리입니다15.

세션이 끝난 뒤에도 남는 것은 여럿입니다. 대화를 저장한 세션 기록은 로컬 파일로 남지만 기본 30일이 지나면 삭제됩니다34. 자동 메모리는 컴퓨터마다 따로 저장되어, 다른 컴퓨터나 클라우드 환경의 에이전트와 공유되지 않습니다15. 그래서 작업을 이어 가는 기준은 저장소의 문서와 commit(변경을 확정해 저장소의 이력에 남기는 일)으로 둡니다. commit으로 변경 이력이 남고, commit한 변경을 여러 사람과 컴퓨터가 함께 사용하는 원격 저장소에 올려(push) 공유하면 다른 세션과 다른 에이전트, 사람이 같은 파일을 읽기 때문입니다. Codex의 하네스 엔지니어링(Harness Engineering) 글도 에이전트가 실행 중에 접근할 수 없는 지식은 에이전트에게 없는 것과 같다고 밝혔습니다. 문서 도구, 채팅, 사람의 기억에 있는 지식이 여기에 해당합니다19.

버전 주석 (2026년 10월) Claude Code 문서에 따르면 자동 메모리 폴더는 오래된 세션 데이터 정리에서 제외됩니다. v2.1.228 이전에는 메모리 폴더 안의 하위 폴더가 세션 데이터로 취급되어 그 아래의 오래된 파일이 지워질 수 있었습니다34.

지난 대화를 다시 열어 이어 가는 방법도 있습니다. Claude Code는 claude --continue(직전 세션 다시 열기)나 claude --resume(지난 세션을 선택해 다시 열기) 명령으로 지난 세션의 대화를 이어 갈 수 있습니다6. 그러나 새로 시작한 세션이나 다른 에이전트는 그 대화를 읽지 못합니다. 지난 대화의 이력을 복사해 받는 새 세션으로 갈라 시작할 수도 있지만, 그 세션은 원래 세션과 따로 이어집니다. 이어 간 세션도 대화가 길어져 압축되면, 앞부분의 지시를 잃을 수 있습니다6. 반면 프로젝트 루트(프로젝트의 맨 위 폴더)의 규칙 문서는 압축 뒤에 다시 읽힙니다15. 그러면 어떤 문서를 남길지가 다음 문제입니다.

기록의 세 종류

남길 정보는 답하는 질문이 다릅니다. 왜 그렇게 정했는지, 어디까지 했는지, 늘 무엇을 지키는지입니다. 갱신하는 시점도 달라서, 한 문서에 섞으면 새 세션이 어느 내용을 먼저 믿을지 알 수 없습니다. 그래서 기록을 결정 기록, 진행 기록, 규칙 문서의 세 종류로 나눕니다. 결정 기록은 무엇을 왜 정했는지를, 진행 기록은 어떤 작업이 어디까지 진행되었는지를, 규칙 문서는 모든 작업에 적용할 지침을 남깁니다. 이 구분은 Chapter 2의 다섯 구성 요소 가운데 기록(결정 기록과 진행 기록)에, 같은 지시 영역에서 역할과 규칙을 적는 규칙 문서를 더한 것입니다. 세션을 넘길 때 이 셋으로 알 수 없는 맥락을 이어 주는 문서는 인계 메모입니다. 그림 8-1은 위에서 아래로 읽습니다. 위 줄은 세션이 끝나면 대화 이력이 다음 세션으로 넘어가지 않는다는 것을, 가운데 영역은 이전 세션이 남기고 다음 세션이 읽는 기록을 보여 줍니다. 맨 아래 띠는 그 기록을 읽는 차례를 번호로 보여 줍니다. 규칙 문서는 세션을 시작할 때 자동으로 읽히므로 나머지 기록을 읽을 순서를 적어 두기에 알맞고, 인계 메모는 그 순서의 마지막에 읽힙니다.

표 8-2는 세 종류마다 기록하는 정보, 갱신 시점, 해당 파일을 보여 줍니다. 진행 기록의 파일인 작업 단위 목록(tasks.json)은 Chapter 6의 작업 단위 분할에서 작업을 한 세션 안에 끝나는 작업 단위로 나누고, 단위마다 끝났는지를 통과 값(true 또는 false)으로 적은 파일입니다. 규칙 문서는 Chapter 5의 규칙 문서의 관리에서 본 것처럼 같은 실수를 두 번째로 했을 때 항목을 더하고, 사실이나 결정이 변경되어 맞지 않게 된 항목은 수정합니다.

세 종류 가운데 진행 기록의 쓰임은 앞의 실험에 나옵니다. 장기 실행 글의 실험에서 에이전트는 진행 기록 파일과 git 이력으로 작업 상태를 파악했습니다. 세션마다 설명이 포함된 commit을 남기고 진행 요약을 기록하도록 하자, 에이전트는 잘못된 변경을 되돌리고 동작하는 상태를 복구할 수 있었습니다7. commit은 작업 단위마다 하나씩 남깁니다.

결정 기록의 형식

결정을 변경했는데 이전 결정이 왜 변경되었는지 남아 있지 않으면, 다음 세션의 에이전트가 이미 폐기된 결정으로 돌아갈 수 있습니다. 그래서 결정 기록은 결정마다 번호, 날짜, 결정 내용, 대체 관계, 이유를 남기는 표로 작성합니다. 대체 관계는 새 결정이 어느 이전 결정을 대신하는지를 나타내며, 표의 대체 칸에 이전 결정의 번호로 적습니다. 결정을 변경할 때는 이전 결정의 줄을 삭제하지 않고 새 줄을 더합니다.

다음은 변경 요청 사항의 결정 기록 예시이며, 변경 요청 사항은 이 장 끝의 예제에서 다시 다룹니다. 표의 CR은 실습 파일에 적힌 변경 요청 사항의 약어입니다. D-012는 부록 실습에서 사용하는 실습 폴더(expense-practice)의 결정 기록에 실제로 있는 결정으로, 변경 요청 사항을 조건부로 수용하고 프로젝트 코드는 인사 시스템이 하루 한 번 갱신하는 파일(data/projects.csv)에서 읽기로 정했습니다. D-015는 대체 관계를 보이려고 이 장에서 만든 가상의 결정으로, 같은 코드를 인사 시스템에 그때그때 물어보는 방식(API, 다른 프로그램의 기능을 호출하는 창구)으로 변경합니다. D-015의 대체 칸에 D-012가 있으므로, 지금 유효한 결정은 D-015입니다.

| 번호 | 날짜 | 결정 | 대체 | 이유 |
|---|---|---|---|---|
| D-012 | 2026-10-12 | CR 조건부 수용. 프로젝트 코드는 인사 시스템 일 1회 갱신 자료(data/projects.csv) 사용 | | 운영 위원회 결정, 실시간 연동 규격 없음 |
| D-015 | 2026-10-16 | 프로젝트 코드를 인사 시스템 API로 실시간 조회 | D-012 | 인사팀이 조회 API 제공 일정 확정 |

코드가 아닌 작업에도 같은 형식을 적용할 수 있습니다. 원고 작업이라면 결정 기록을 저장소에 두고, 원고를 작성하는 에이전트와 검수하는 에이전트가 작업 전에 읽게 합니다.

인계 메모 작성

결정 기록과 진행 기록이 있어도, 진행 기록의 값만으로는 새 세션이 알 수 없는 것이 있습니다. 진행 기록은 작업 단위가 끝났는지를 담는 상태 값이고, 진행 중인 작업이 왜 멈췄는지, 무엇이 아직 정해지지 않았는지는 담지 않습니다. 그래서 세션을 넘길 때는 그 맥락을 한 문서에 묶어 넘기며, 이 문서를 인계 메모라고 합니다. 인계 메모는 세션을 마칠 때나 중단 규칙에 따라 작업을 멈출 때 그 세션의 에이전트가 작성하며, 다음 다섯 가지 항목을 담습니다.

  • 현재 상태: 최종 commit, 완료된 작업 단위, 진행 중인 작업 단위와 멈춘 이유
  • 읽을 문서: 결정 기록과 진행 기록의 위치(읽는 순서는 규칙 문서를 따름)
  • 미결정 사항: 결정이 필요한 항목과 결정할 사람
  • 다음 작업: 다음 세션이 시작할 작업 단위와 완료 기준
  • 확인 명령: 시작할 때 실행해 현재 상태를 확인할 검사 명령

그림 8-1에서 본 것처럼 읽는 순서는 규칙 문서에 적고, 인계 메모는 그 순서의 마지막에 읽혀 앞의 기록으로 알 수 없는 맥락을 전달합니다. 인계 메모의 읽을 문서 항목은 사람이 인계 메모부터 읽게 했을 때나, 규칙 문서에 순서가 없을 때 나머지 기록을 가리키는 역할을 합니다. 다섯 항목은 이 장에서 정한 구성입니다. 장기 실행 글의 실험에서도 에이전트는 세션을 시작할 때 Git 로그와 진행 기록 파일을 먼저 읽고 작업 상태를 파악했습니다7.

실행 로그와 추적

사람과 에이전트가 작성한 문서만으로는 에이전트가 실제로 무엇을 했는지 확인하기 어렵습니다. Chapter 7의 완료 보고가 근거가 되지 않는 이유에서 본 것처럼 완료 보고는 결과를 만든 에이전트가 스스로 작성한 글이어서 근거가 되지 못하므로, 확인하려면 실제로 한 일의 기록이 필요합니다. 하네스가 기본으로 남기거나, 사용자가 설정하면 남는 실행 기록을 실행 로그라고 합니다. 실행 로그는 세션 기록, 실행 결과, 훅(Hook) 기록, 조직 지표의 네 가지이며, 설정하지 않아도 얻는 것과 설정해야 남는 것으로 나뉩니다.

설정하지 않아도 얻는 것은 세션 기록과 실행 결과입니다. Claude Code는 대화를 진행하는 동안 메시지, 도구 사용, 결과를 로컬의 JSONL(JSON Lines) 파일로 저장합니다. JSONL은 한 줄에 항목 하나를 JSON(항목 이름과 값을 정해진 규칙으로 적는 텍스트 형식)으로 적는 파일 형식입니다. 이 기록으로 세션을 되감거나, 이어 가거나, 갈라서 새로 시작할 수 있습니다6.

실행 결과는 Claude Agent SDK(Claude Code의 에이전트 루프를 Python이나 TypeScript 프로그램에서 실행하게 하는 라이브러리)로 프로그램을 만들 때 받는 값입니다. 모든 결과에 비용, 토큰(Token) 사용량, 턴 수(Agent SDK 문서 기준으로 도구 호출을 주고받은 횟수), 세션 ID와 결과 종류가 담깁니다. 결과 종류는 Chapter 1의 에이전트 루프와 종료 조건에서 본 종료 사유이며, 작업이 오류로 끝나도 이 값으로 비용을 확인하고 세션을 이어 갈 수 있습니다. 세션이 실행 중 오류로 비정상 종료되면 비용이 0으로 채워질 수 있습니다9. 실행 결과는 프로그램이 받는 값이므로, 나중에 확인하려면 프로그램이 저장해야 합니다.

대화형으로 사용할 때는 /usage 명령이 지금 세션의 사용량과 비용 추정치를 화면에 보여 줍니다. /usage는 화면에 보여 주는 명령이어서 네 가지 실행 로그에는 들지 않습니다. 이 금액은 정가 기준 추정치(팀이 관리형 설정으로 계약 요율을 정했다면 그 요율 기준)이고 청구 근거가 아닙니다. 구독 계정에서는 플랜 사용량이 함께 보이고, 세션 금액은 청구와 관계가 없습니다22.

설정해야 남는 것은 훅 기록과 조직 지표입니다. 훅은 정해진 시점에 자동으로 실행되는 명령으로, Chapter 2의 지시 기반 규칙과 강제 적용에서 본 강제 수단이며, 여기서는 기록을 남길 지점으로 사용합니다. Agent SDK 문서는 도구 실행 뒤에 실행되는 PostToolUse 훅을 출력 감사, 곧 도구 출력을 남겨 나중에 점검하는 일에 활용하는 예를 듭니다. 하위 에이전트(Subagent, 특정 작업을 맡도록 따로 정의한 에이전트)가 시작하고 끝날 때 실행되는 SubagentStart와 SubagentStop 훅은 병렬 작업 결과의 추적에 활용합니다. 대화를 압축하기 직전에 실행되는 PreCompact 훅으로는 압축하기 전에 전체 대화를 보관할 수 있습니다9. Agent SDK의 훅은 프로그램 안에서 실행되는 함수이고, Claude Code에서는 설정 파일의 훅으로 같은 시점을 사용할 수 있습니다10.

조직 지표는 사용자별 토큰 사용량과 비용 같은 사용 지표를 조직이 한곳에 모아 보는 기록이며, OpenTelemetry로 보냅니다. OpenTelemetry는 지표와 이벤트를 조직의 관측 시스템(사용 현황과 오류를 모아 보여 주는 시스템)으로 보내는 표준 방식입니다. 이 기능은 기본으로 꺼져 있어 환경 변수(프로그램을 실행할 때 읽는 설정 값)로 켜야 동작합니다35. 비용 문서에 따르면 이 방식은 모든 이용 방식에서 동작하고, 사용자별 토큰과 비용 지표를 조직의 관측 시스템으로 거의 실시간으로 보낼 수 있는 유일한 선택지입니다22. 개인 사용자는 주로 세션 기록과 /usage를 봅니다. 조직 지표를 켜는 환경 변수는 셸이나 사용자 설정 파일에 적거나, 팀이 관리형 설정(조직이 모든 사용자에게 내려 주는 설정)으로 배포합니다. 저장소의 .claude/settings.json에 적은 OpenTelemetry 변수는 적용되지 않습니다. 프롬프트 내용은 따로 켜지 않으면 내보내지 않습니다35.

그림 8-2는 위에서 아래로 읽습니다. 실행 로그 영역의 위 묶음과 아래 묶음은 앞에서 나눈 두 가지, 곧 설정 없이 얻는 로그와 설정해야 남는 로그입니다. 사용자는 완료 보고를 받을 때 이 로그와 대조합니다.

표 8-3은 그림 8-2의 구성 요소를 설명합니다.

실행 로그에서 정할 것은 세 가지입니다.

  • 보관 기간: 세션 기록은 기간이 지나면 삭제되므로, 확인에 필요한 기간만큼 보관하도록 정합니다. Claude Code는 기본 30일이 지난 세션 데이터를 시작할 때 삭제하며22, 이 기간은 사용자 설정 파일(~/.claude/settings.json)에 "cleanupPeriodDays": 90처럼 보관할 날짜 수를 적어 변경합니다34. 세션 기록은 암호화되지 않은 텍스트여서 도구가 읽은 비밀 값(비밀번호, 접근 키)이 그대로 들어갈 수 있으므로, 기간은 확인에 필요한 만큼만 늘립니다.
  • 추적 지점: 세션 기록에 남지 않거나 보관 기간 뒤에도 남겨야 할 동작은 어느 시점에 남길지 정하고 훅으로 구현합니다. 예를 들어 압축 전에 전체 대화를 보관하려면 PreCompact 훅을 사용합니다.
  • 확인 방법: 완료 보고의 주장과 맞춰 볼 로그를 정합니다. 예를 들어 "검사가 통과했다"는 보고는 세션 기록에 검사 명령과 그 출력이 있는지로 확인합니다.

예제: 변경 요청 사항의 기록과 인계

지금까지의 기록을 변경 요청 사항에 적용합니다. 작업 번호는 Chapter 6의 예제: 변경 요청 사항의 작업 단위 나누기에서 나눈 작업 1~5입니다. 세션 1이 작업 2(데이터 모델에 프로젝트 코드 항목 추가)와 작업 3(기존 단위 테스트 갱신)을 마치고, 세션 2가 작업 4(정산 요청 화면에 선택 항목 추가)부터 시작하는 상황입니다. 부록 실습 5, 6과 같은 상황입니다. 실습 폴더에는 기록 말고도, 변경 요청 사항의 수용 기준(사람이 정한 완료 조건)을 적은 변경 요청 사항 문서(docs/CR.md)와, 단위 테스트와 수용 시험을 한 번에 실행하는 검사 스크립트(check.py)가 있습니다. 표 8-4는 실습 폴더의 파일을 기록의 종류, 갱신 주체, 세션 2가 읽는 순서로 정리한 것입니다. 읽는 순서의 번호는 규칙 문서(CLAUDE.md)에 적힌 번호입니다. 그림 8-1의 2(결정 기록과 진행 기록)와 3(인계 메모) 앞에, 기록이 아닌 변경 요청 사항 문서를 먼저 읽게 한 것입니다.

읽는 순서와 수정 범위는 실습 폴더의 규칙 문서에 적혀 있습니다. 결정이 변경되면 사람이 결정 기록에 새 결정과 대체 관계를 적고, 에이전트는 결정 기록을 수정하지 않습니다. 다음은 세션 1을 마칠 때 에이전트가 작성할 인계 메모의 예상 결과입니다.

현재 상태: 최종 commit은 작업 3의 commit. 작업 2, 3 완료(통과 값 true, 단위마다 commit). 진행 중인 작업 없음
읽을 문서: CLAUDE.md의 읽는 순서대로 docs/CR.md, DECISIONS.md, tasks.json
미결정 사항: 작업 5(통합 테스트 시나리오 추가)의 승인. 에이전트가 초안을 작성한 뒤 승인자가 결정
다음 작업: 작업 4. 완료 기준은 화면에서 프로젝트 코드 선택 가능, 목록에 없는 코드 거부
확인 명령: python check.py(종료 코드 1이 정상. tests는 통과, acceptance 시험 1~3만 실패)

확인 명령 줄의 종료 코드는 명령이 끝날 때 돌려주는 값으로, check.py는 모든 시험이 통과하고 정한 조건을 충족하면 0, 그렇지 않으면 1을 돌려줍니다. tests는 단위 테스트를, acceptance는 수용 시험(수용 기준을 충족하는지 확인하는 시험)을 둔 폴더이며, 시험 1~3은 작업 4의 화면 기능을 확인하므로 작업 4 전에는 실패합니다. 미결정 사항의 승인자는 Chapter 6에서 본, 되돌리기 어려운 동작과 작업 단위의 완료를 승인하는 사람입니다. 부록 실습 6은 새 세션에서 "HANDOFF.md를 읽고 이어서 작업해 줘"라고 요청합니다. 규칙 문서의 순서 대신 사람이 인계 메모부터 읽도록 지시한 경우이며, 인계 메모의 읽을 문서 항목이 나머지 기록을 다시 가리킵니다.

인계 메모의 "작업 2, 3 완료"는 통과 값을 근거로 하지만, 작업 2의 확인 방법인 수용 시험 4, 5는 구현 전에도 통과합니다(Chapter 7의 예제: 변경 요청 사항의 검증 설계). 그래서 사용자는 세션 2를 시작하기 전에 git diff HEAD~2 -- expense/store.py expense/service.py를 실행합니다. 출력에서 작업 2와 3이 수정한 두 파일에 project_code 항목이 추가되었는지 직접 확인합니다(부록 실습 5의 확인 방법).

세션 2가 작업 4를 마치고 완료 보고를 내면, 사용자는 검사 출력과 함께 실행 로그를 확인합니다. "작업 4를 마쳤다"는 보고가 사실인지, 사용자 폴더의 .claude/projects/ 아래 세션 기록 파일에서 python check.py 실행과 그 출력을 찾아 확인합니다. 예상 결과는 작업 4 뒤에 실행한 python check.py와 종료 코드 0의 출력이 세션 기록에 있고, 그 출력이 완료 보고에 붙은 출력 원문과 같은 것입니다. /usage로는 이 세션에 든 사용량과 비용 추정치를 확인합니다. 인계 메모로 세션을 이어 가는 실습은 부록 실습의 실습 6에 있습니다.

실패를 예방하는 장치

결정, 진행 상황, 계속 지킬 지시를 문서로 남기지 않거나 실행 로그를 정하지 않으면, 변경 요청 사항을 두 세션에 나누어 구현할 때 다음 실패가 생길 수 있습니다. 표 8-5는 실패 유형과 원인, 방지 장치를 정리합니다.

설정과 결과의 확인 방법

기록이 제 역할을 하는지는 새 세션이 기록만으로 작업을 이어 가는지로 확인합니다. 명령은 부록 실습 1에서 만든 실습 폴더(expense-practice)에서 터미널에 입력합니다. 인계 메모, 진행 기록, 결정 기록 행은 실습 5를 마치고 실습 6의 1단계에서 세션 1을 끝낸 뒤 확인하고, 나머지 행은 실습 6을 진행하며 확인합니다. git log --oneline은 commit 목록을 한 줄에 하나씩 보여 주고, git diff HEAD~2 -- DECISIONS.md는 최근 두 commit 동안 DECISIONS.md가 바뀐 내용을 보여 주므로 출력이 없으면 변경되지 않은 것입니다. grep -l과 Select-String은 세션 기록 파일 가운데 python check.py라는 글자가 든 파일의 이름을 찾습니다. 표 8-6은 확인 항목과 확인 방법, 확인 기준입니다.

설계 원칙과 점검 질문

세션이 끝나도 남아야 할 결정과 진행 상황은 대화가 아니라 저장소의 문서로 남깁니다.

이 원칙은 코드가 아닌 업무에도 적용됩니다. 회의에서 정한 결정은 회의록에, 업무를 넘길 때의 맥락은 인계 문서에 남깁니다. 자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 대화에서만 합의하고 문서로 남기지 않은 결정이 있습니까?
  2. 새 세션이 지난 대화 없이 저장소에 남은 기록만 읽고 다음 작업을 시작할 수 있습니까?
  3. 완료 보고를 받을 때 함께 볼 로그와 보관 기간을 정했습니까?
