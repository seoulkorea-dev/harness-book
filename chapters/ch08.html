Chapter 8 기록과 인계: 결정, 진행, 규칙의 문서화

작업이 이어지는지를 정하는 것은 대화 이력의 길이가 아니라, 결정과 진행 상황이 에이전트가 읽을 수 있는 문서로 남아 있는지입니다.

에이전트(Agent)와 한 번 대화를 시작해 끝낼 때까지를 세션이라고 하며, 새 세션은 새 컨텍스트(Context)에서 시작해 이전 세션의 대화를 알지 못합니다. 어제 대화한 내용을 오늘 새 창에서 이어 가려 해도, 새 창은 어제의 합의를 모릅니다. 대화에서만 합의한 내용은 세션이 끝나거나 대화가 압축되면 사라지고, 같은 논의와 같은 실수가 반복됩니다. 따라서 결정, 진행, 규칙은 저장소의 문서로 기록해야 합니다. 이 장에서는 기록의 종류, 결정 기록의 형식, 인계 메모, 실행 로그를 차례로 다루고, 경비 정산 예제에 적용합니다.

  • 새 세션과 다른 에이전트는 이전 대화를 읽지 못하므로, 이어 갈 정보는 저장소의 문서로 남깁니다.
  • 기록은 결정 기록, 진행 기록, 규칙 문서의 세 종류로 관리하고, 세션을 넘길 때는 인계 메모를 작성합니다.
  • 하네스가 남기는 실행 로그는 보관 기간과 확인 방법을 정해 완료 보고와 함께 확인합니다.

세션이 끝난 뒤 남는 것

여러 세션에 걸친 작업에서는 세션과 세션 사이에 작업 상태가 이어지지 않습니다. Claude Code는 장시간 실행 실험에서 이 문제를 다루었습니다. 에이전트는 분리된 세션으로 일하며, 새 세션은 이전 세션의 기억 없이 시작합니다(Young, 2025). Claude Code 문서도 세션은 서로 독립적이고, 세션마다 새 컨텍스트에서 시작한다고 설명합니다. 세션 사이에 지식을 전달하는 것은 사람이 작성하는 CLAUDE.md와 Claude가 작성하는 자동 메모리입니다(Anthropic, 2026a).

세션이 끝난 뒤에도 남는 것은 여럿입니다. 대화 기록은 로컬 파일로 남지만 기본 30일이 지나면 삭제되고, 자동 메모리는 각자의 컴퓨터에만 남아 다른 사람과 다른 컴퓨터의 에이전트가 읽지 못합니다(Anthropic, 2026c). 이 책은 저장소의 문서와 커밋을 작업을 이어 가는 기준으로 삼습니다. 커밋으로 변경 이력이 남고, 다른 세션과 다른 에이전트, 사람이 같은 파일을 읽기 때문입니다. OpenAI의 코딩 에이전트 Codex로 제품을 개발한 경험을 다룬 글도 에이전트가 실행 중에 접근할 수 없는 지식은 에이전트에게 없는 것과 같다고 밝혔습니다. 문서 도구, 채팅, 사람의 기억에 있는 지식이 여기에 해당합니다(Lopopolo, 2026).

대화 이력에 모두 남아 있다는 의견이 있습니다. Claude Code는 --resume 옵션으로 지난 세션의 대화를 다시 열어 이어 갈 수 있습니다(Anthropic, 2026b). 그러나 다른 에이전트나 새 세션은 그 대화를 읽지 못합니다. 이어 간 세션도 대화가 길어져 압축되면, 앞부분의 지시를 잃을 수 있습니다(Chapter 5). 그러면 어떤 문서를 남길지가 다음 문제입니다.

기록의 세 종류

남길 정보는 답하는 질문이 다릅니다. 왜 그렇게 정했는지, 어디까지 했는지, 늘 무엇을 지키는지입니다. 갱신하는 시점도 달라서, 한 문서에 섞으면 새 세션이 어느 내용을 먼저 믿을지 알 수 없습니다. 그래서 이 책은 기록을 결정 기록, 진행 기록, 규칙 문서의 세 종류로 정리합니다. 결정 기록은 무엇을 왜 정했는지를, 진행 기록은 어떤 작업이 어디까지 진행되었는지를, 규칙 문서는 모든 작업에 적용할 지침을 남깁니다. Chapter 2의 기록 구성 요소에 규칙 문서를 더한 정리이며, 세션을 넘길 때 이 셋을 읽도록 묶는 문서가 인계 메모입니다. 이 책은 세 종류와 인계 메모를 함께 저장소의 기록이라고 부릅니다. 그림 8-1은 세션 사이에 기록이 이어지는 구조를 보여 줍니다.

표 8-2는 세 종류의 내용과 갱신 시점입니다. 규칙 문서를 작성하고 갱신하는 방법은 Chapter 5에서 다루었습니다. 같은 실수가 반복될 때 갱신하는 이유도 Chapter 5의 규칙 문서 유지에 있습니다.

세 종류 가운데 진행 기록의 효과는 실험으로 확인되었습니다. Claude Code의 실험에서 에이전트는 진행 기록 파일과 git 이력으로 작업 상태를 파악했습니다. 세션마다 설명이 포함된 커밋을 남기고 진행 요약을 기록하도록 하자, 에이전트는 잘못된 변경을 되돌리고 동작하는 상태를 복구할 수 있었습니다(Young, 2025). 커밋은 저장소에 변경을 기록하는 단위이며, Chapter 6의 작업 단위마다 하나씩 남깁니다.

결정 기록의 형식

결정을 변경했는데 이전 결정이 왜 변경되었는지 남아 있지 않으면, 다음 세션의 에이전트가 이미 폐기된 결정으로 돌아갈 수 있습니다. 그래서 이 책은 결정 기록을 결정마다 번호, 날짜, 결정 내용, 대체 관계, 이유를 남기는 표로 정리합니다. 대체 관계는 새 결정이 어느 결정을 대체하는지 적는 칸입니다. 결정을 변경할 때는 이전 기록을 삭제하지 않고, 새 결정의 대체 칸에 이전 결정의 번호를 적습니다.

다음은 이 장의 예제에 사용할 결정 기록 예시입니다. D-012는 실습 폴더의 결정 기록에 있는 결정이고, D-015는 대체 관계를 보이기 위해 이 장에서 만든 가상의 변경 결정입니다. D-015의 대체 칸에 D-012가 있으므로, 지금 유효한 결정은 D-015입니다.

| 번호 | 날짜 | 결정 | 대체 | 이유 |
|---|---|---|---|---|
| D-012 | 2026-10-12 | CR 조건부 수용. 프로젝트 코드는 인사 시스템 일 1회 갱신 자료 사용 | | 운영 위원회 결정, 실시간 연동 규격 없음 |
| D-015 | 2026-10-16 | 프로젝트 코드를 인사 시스템 API로 실시간 조회 | D-012 | 인사팀이 조회 API 제공 일정 확정 |

이 책의 저장소도 같은 형식의 결정 기록을 두고, 원고를 작성하는 에이전트와 검수하는 에이전트가 작업 전에 읽게 합니다.

인계 메모 작성

결정 기록과 진행 기록이 있어도, 새 세션은 진행 기록의 값만으로 알 수 없는 것이 있습니다. 진행 기록은 작업 단위가 끝났는지를 담는 상태 값이고, 진행 중인 작업이 왜 멈췄는지, 무엇이 아직 정해지지 않았는지는 담지 않습니다. 그래서 이 책은 세션을 넘길 때 그 맥락을 한 문서로 묶어 넘기는 문서를 인계 메모로 정리합니다. 인계 메모는 다음 다섯 항목을 담습니다.

  • 현재 상태: 최종 커밋, 완료된 작업 단위, 진행 중인 작업 단위와 멈춘 이유
  • 읽을 문서: 규칙 문서, 결정 기록, 진행 기록의 위치와 읽는 순서
  • 미결정 사항: 결정이 필요한 항목과 결정할 사람
  • 다음 작업: 다음 세션이 시작할 작업 단위와 완료 기준
  • 확인 명령: 시작할 때 실행해 현재 상태를 확인할 검사 명령

읽는 순서는 규칙 문서가 정합니다. 규칙 문서는 세션을 시작할 때 자동으로 읽히므로, 무엇을 어떤 순서로 읽을지 적어 두기에 알맞습니다. 인계 메모는 그 순서의 마지막에 읽혀, 앞의 기록으로 알 수 없는 맥락을 전달합니다. 인계 메모의 읽을 문서 항목은 사람이 인계 메모부터 읽게 했을 때나, 규칙 문서에 순서가 없을 때 나머지 기록을 가리키는 역할을 합니다. 다섯 항목은 이 책의 설계이며, 가장 가까운 근거는 앞의 실험에서 에이전트가 세션을 시작할 때 git 로그와 진행 파일을 먼저 읽은 방식입니다(Young, 2025).

실행 로그와 추적

사람과 에이전트가 작성한 문서만으로는 에이전트가 실제로 무엇을 했는지 확인하기 어렵습니다. Chapter 7에서 본 것처럼 완료 보고는 근거가 아니고, 확인하려면 실제로 한 일의 기록이 필요합니다. 이 책은 하네스(Harness)가 남기거나, 설정하면 남는 실행 기록을 실행 로그라고 부릅니다. 실행 로그는 기본으로 남는 것과 설정해야 남는 것으로 나뉩니다.

기본으로 남는 것은 세션 기록과 실행 결과입니다. Claude Code는 대화를 진행하는 동안 메시지, 도구 사용, 결과를 로컬의 JSONL 파일로 저장합니다. JSONL은 한 줄에 한 항목씩 적는 텍스트 파일 형식입니다. 이 기록으로 세션을 되감거나, 이어 가거나, 갈라서 새로 시작할 수 있습니다(Anthropic, 2026b). 실행 결과는 Agent SDK(Chapter 1)로 프로그램을 만들 때 받는 값입니다. 모든 결과에 비용, 토큰(Token) 사용량, 턴 수, 세션 ID와 결과 종류(이 책은 종료 사유라고 부름)가 담겨, 작업이 오류로 끝나도 비용을 확인하고 세션을 이어 갈 수 있습니다(Anthropic, 2026d). 대화형으로 사용할 때는 /usage 명령이 사용량과 비용 추정치를 보여 주며, 이 금액은 정가 기준 추정치이고 청구 근거가 아닙니다(Anthropic, 2026e).

설정해야 남는 것은 훅(Hook) 기록과 조직 지표입니다. 훅은 Chapter 2에서 본 강제 수단이며, 여기서는 기록을 남길 지점으로 사용합니다. Agent SDK 문서는 도구 실행 뒤에 실행되는 PostToolUse 훅을 출력 감사에, 하위 에이전트(Subagent, Chapter 2)의 시작과 종료 훅을 병렬 작업 결과의 추적에 활용하는 예를 듭니다. 대화를 요약하기 직전에 실행되는 PreCompact 훅으로는 요약하기 전에 전체 대화를 보관할 수 있습니다(Anthropic, 2026d). 조직 지표는 OpenTelemetry로 보냅니다. OpenTelemetry는 지표와 이벤트를 조직의 관측 시스템으로 보내는 표준 방식이며, 환경 변수로 켜야 동작합니다(Anthropic, 2026f). 비용 문서에 따르면 이 방식은 모든 이용 방식에서 동작하고, 사용자별 토큰과 비용 지표를 조직의 관측 시스템으로 거의 실시간으로 보낼 수 있는 유일한 선택지입니다(Anthropic, 2026e). 개인 사용자는 주로 세션 기록과 /usage를 보고, 조직 지표는 관리자가 설정합니다. 그림 8-2는 네 가지 실행 로그를 보여 줍니다.

표 8-3은 그림 8-2의 구성 요소를 설명합니다.

이 책은 실행 로그에서 정할 것을 세 가지로 정리합니다.

  • 보관 기간: 세션 기록은 기간이 지나면 삭제되므로, 확인에 필요한 기간만큼 보관하도록 정합니다. Claude Code는 기본 30일이 지난 세션 데이터를 시작할 때 삭제하며(Anthropic, 2026e), 이 기간은 설정 파일의 cleanupPeriodDays 값으로 변경합니다(Anthropic, 2026c).
  • 추적 지점: 기본 기록에 없는 동작을 남기려면 어디서 남길지 정하고 훅으로 구현합니다.
  • 확인 방법: 완료 보고의 주장과 맞춰 볼 로그를 정합니다. 예를 들어 "작업 4를 마쳤고 검사가 통과했다"는 보고는 세션 기록에 검사 명령과 그 출력이 있는지로 확인합니다.

변경 요청의 기록과 인계 예제

지금까지의 기록을 Chapter 3의 경비 정산 시스템 개편 변경 요청(Change Request) CR에 적용합니다. 작업 번호는 Chapter 6의 표 6-4에 있는 작업 1~5입니다. 세션 1이 작업 2(정산 요청 데이터에 프로젝트 코드 항목 추가)와 작업 3(기존 단위 테스트 갱신)을 마치고, 세션 2가 작업 4(정산 요청 화면에 선택 항목 추가)부터 시작하는 상황입니다. 부록 실습 5, 6과 같은 상황입니다. 표 8-4는 CR 폴더의 파일을 기록의 종류, 갱신 주체, 세션 2가 읽는 순서로 정리한 것입니다.

읽는 순서와 수정 범위는 CR 폴더의 규칙 문서에 적혀 있습니다. 결정이 변경되면 사람이 결정 기록에 새 결정과 대체 관계를 적고, 에이전트는 결정 기록을 수정하지 않습니다. 다음은 세션 1을 마칠 때 에이전트가 작성한 인계 메모의 예입니다.

읽을 문서: CLAUDE.md의 읽는 순서대로 docs/CR.md, DECISIONS.md, tasks.json
미결정 사항: 없음. 작업 5(통합 시나리오)는 승인자(변경을 승인하는 사람)가 승인
다음 작업: 작업 4. 완료 기준은 화면에서 프로젝트 코드 선택 가능, 목록에 없는 코드 거부
확인 명령: python check.py(acceptance의 시험 1~3이 아직 실패하는 것이 정상)

확인 명령의 acceptance는 Chapter 3의 수용 시험 폴더이며, 시험 1~3은 작업 4의 화면 기능을 확인하므로 작업 4 전에는 실패합니다. 부록 실습 6은 새 세션에서 "HANDOFF.md를 읽고 이어서 작업해 줘"라고 요청합니다. 규칙 문서의 순서 대신 사람이 인계 메모부터 읽도록 지시한 경우이며, 인계 메모의 읽을 문서 항목이 나머지 기록을 다시 가리킵니다.

세션 2가 작업 4를 마치고 완료 보고를 내면, 사용자는 검사 출력과 함께 실행 로그를 확인합니다. "작업 4를 마쳤다"는 보고가 사실인지, 사용자 폴더의 .claude/projects/ 아래 세션 기록 파일에서 python check.py 실행과 그 출력을 찾아 확인합니다. /usage로 이 세션의 사용량과 비용 추정치도 봅니다. 인계 메모로 세션을 이어 가는 실습은 부록 실습의 실습 6에 있습니다.

실패와 막는 장치

결정과 진행 상황을 문서로 남기지 않으면, CR을 두 세션에 나누어 구현할 때 다음 실패가 생길 수 있습니다. 표의 작업 번호는 표 6-4의 번호입니다. 표 8-5는 실패와 원인, 막는 장치입니다.

확인 방법

기록이 제 역할을 하는지는 새 세션이 기록만으로 작업을 이어 가는지로 확인합니다. 명령과 파일은 실습 폴더(examples/expense-app/) 기준입니다. 표 8-6은 확인할 것과 확인 위치입니다.

원칙과 점검 질문

세션이 끝나도 남아야 할 결정과 진행 상황은 대화가 아니라 저장소의 문서로 남깁니다.

코드가 아닌 업무에도 적용됩니다. 회의에서 정한 결정은 회의록에, 업무를 넘길 때의 맥락은 인계 문서에 남깁니다. 자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 대화에서만 합의하고 문서로 남기지 않은 결정이 있습니까?
  2. 새 세션이 규칙 문서와 인계 메모만 읽고 다음 작업을 시작할 수 있습니까?
  3. 완료 보고를 받을 때 함께 볼 로그와 보관 기간을 정했습니까?
