Chapter 8 기록과 인계: 결정, 진행, 규칙의 문서화

작업이 이어지는지를 정하는 것은 대화 이력의 길이가 아니라, 결정과 진행 상황이 에이전트가 읽을 수 있는 문서로 남아 있는지입니다.

에이전트(Agent)의 세션은 새 컨텍스트(Context)에서 시작하며, 이전 세션의 대화 내용을 기억하지 못합니다. 작업이 이어지는지를 정하는 것은 대화 이력의 길이가 아니라, 결정과 진행 상황이 에이전트가 읽을 수 있는 문서로 남아 있는지입니다. 그래서 대화 안에서만 합의한 내용은 다음 세션에서 사라지고, 같은 논의와 같은 실수가 반복됩니다. 따라서 결정, 진행, 규칙은 저장소의 문서로 기록해야 합니다. 이 장에서는 기록의 세 종류와 결정 기록, 인계 메모의 작성 방법을 다룹니다.

  • 새 세션과 다른 에이전트는 이전 대화를 읽지 못합니다.
  • 기록은 결정 기록, 진행 기록, 규칙 문서의 세 종류로 관리합니다.
  • 작업을 다른 세션에 넘길 때는 인계 메모를 작성합니다.

세션이 끝난 뒤 남는 것

Claude Code가 장시간 실행 실험에서 해결해야 했던 문제는 세션과 세션 사이에 작업 상태가 이어지지 않는 점이었습니다. 에이전트는 분리된 세션으로 일하며, 새 세션은 이전 세션의 기억 없이 시작합니다(Young, 2025). Claude Code 문서도 세션마다 새 컨텍스트에서 시작하며, CLAUDE.md와 자동 메모리가 세션 사이에 지식을 전달한다고 설명합니다(Anthropic, 2026a).

Codex는 에이전트가 실행 중에 접근할 수 없는 지식은 에이전트에게 존재하지 않는 것과 마찬가지라고 밝혔습니다. 문서 도구, 채팅, 사람의 기억에 있는 지식이 여기에 해당합니다(Lopopolo, 2026). 세션이 끝난 뒤에도 남는 것은 저장소에 기록된 문서와 커밋뿐입니다.

대화 이력에 모두 남아 있다는 의견이 있습니다. 대화 이력은 같은 세션 안에서만 유효합니다. Claude Code 문서는 대화에서만 전달한 지시가 컨텍스트 압축 뒤에 사라질 수 있다고 설명합니다. 유지할 지시는 CLAUDE.md에 추가하라고 안내합니다(Anthropic, 2026a).

기록의 세 종류

기록은 내용에 따라 세 종류로 나뉩니다. 결정 기록은 무엇을 왜 정했는지를 남깁니다. 진행 기록은 어떤 작업이 어디까지 진행되었는지를 남깁니다. 규칙 문서는 모든 작업에 적용할 지침을 남깁니다. 그림 8-1은 경비 정산 시스템 개편 변경 요청(Change Request) CR 예제에서 세션 1이 남긴 기록을 세션 2가 읽고 이어 가는 구조를, 표 8-1은 종류별 내용과 갱신 시점을 보여 줍니다.

Claude Code의 실험에서 에이전트는 진행 기록 파일과 git 이력으로 작업 상태를 파악했습니다. 세션마다 설명이 포함된 커밋을 남기고 진행 요약을 기록하도록 하자, 에이전트는 잘못된 변경을 되돌리고 동작하는 상태를 복구할 수 있었습니다(Young, 2025).

실행 로그와 추적

세 종류의 기록은 사람이나 에이전트가 의도해서 남기는 문서입니다. 이와 별도로 하네스(Harness)는 실행 과정을 자동으로 남깁니다. 이 책은 이것을 실행 로그라고 부릅니다. 실행 로그는 무엇을 했는지 사후에 확인하는 근거이고, Chapter 7의 검증에서 증거가 됩니다.

Claude Code는 대화를 진행하는 동안 메시지, 도구 사용, 결과를 하나씩 로컬의 JSONL 파일로 저장합니다. 이 기록으로 세션을 되감거나, 이어 가거나, 갈라서 새로 시작할 수 있습니다. Agent SDK는 루프가 끝날 때 결과에 비용, 토큰(Token) 사용량, 턴 수, 세션 ID를 담습니다. 이 정보는 작업이 오류로 끝나도 남습니다(Anthropic, 2026b).

훅(Hook)은 추적 지점이 됩니다. 문서는 도구 실행 뒤의 PostToolUse 훅을 출력 감사에, 하위 에이전트(Subagent)의 시작과 종료 훅을 병렬 작업 결과의 추적에 활용하는 예를 듭니다. 압축 전의 PreCompact 훅으로는 요약하기 전에 전체 대화를 보관할 수 있습니다.

조직 단위의 추적에는 OpenTelemetry 내보내기가 있습니다. 비용 문서에 따르면 이 방식은 모든 환경에서 동작합니다. 사용자별 토큰과 비용 지표를 조직의 관측 시스템으로 거의 실시간으로 보낼 수 있는 유일한 선택지이기도 합니다(Anthropic, 2026b). 그림 8-2는 하네스가 남기는 네 가지 로그입니다.

표 8-2는 그림 8-2의 구성 요소를 설명합니다.

실행 로그에서 정할 것은 세 가지입니다.

  • 보관 기간: 어떤 로그를 얼마나 보관할지 정합니다. Claude Code는 기본 30일이 지난 세션 데이터를 시작할 때 삭제합니다.
  • 추적 지점: 어떤 동작에서 기록을 남길지 정하고 훅으로 구현합니다.
  • 확인 방법: 완료 보고를 받을 때 함께 볼 로그(비용, 턴 수, 종료 사유)를 정합니다.

결정 기록의 형식

결정 기록은 결정마다 번호, 날짜, 결정 내용, 대체 관계, 이유를 남깁니다. 결정을 변경할 때는 이전 기록을 삭제하지 않고, 새 결정이 어느 결정을 대체하는지 적습니다. 이전 결정이 왜 변경되었는지 남아 있어야, 다음 세션의 에이전트가 이미 폐기된 결정으로 돌아가지 않습니다.

| 번호 | 날짜 | 결정 | 대체 | 이유 |
|---|---|---|---|---|
| D-012 | 2026-10-12 | CR 조건부 수용. 프로젝트 코드는 인사 시스템 일 1회 갱신 자료 사용 | | 운영 위원회 결정, 실시간 연동 규격 없음 |
| D-015 | 2026-10-16 | 프로젝트 코드를 인사 시스템 API로 실시간 조회 | D-012 | 인사팀이 조회 API 제공 일정 확정 |

이 책의 저장소도 같은 형식의 결정 기록을 사용합니다. 설계 인터뷰부터 전체 초안 완성까지의 결정이 DECISIONS.md에 번호순으로 남아 있습니다. 작성 에이전트와 검수 에이전트는 작업 전에 이 문서를 읽습니다.

인계 메모 작성

인계 메모는 작업을 다른 세션이나 다른 에이전트에 넘길 때 작성하는 문서입니다. 결정 기록과 진행 기록이 저장소에 있어도, 새 세션은 어느 문서부터 읽어야 하는지 알지 못합니다. 인계 메모는 다음 항목을 담습니다.

  • 현재 상태: 최종 커밋, 완료된 작업 단위, 진행 중인 작업 단위
  • 읽을 문서: 규칙 문서, 결정 기록, 진행 기록의 위치와 읽는 순서
  • 미결정 사항: 결정이 필요한 항목과 결정할 사람
  • 다음 작업: 다음 세션이 시작할 작업 단위와 완료 기준
  • 확인 명령: 시작할 때 실행해 현재 상태를 확인할 검사 명령

이 책은 작성과 검수를 서로 다른 채팅에서 진행하며, 검수 채팅을 시작할 때 인계 메모를 전달합니다. 인계 메모에는 저장소 주소, 최종 커밋, 읽을 문서, 검수 문서의 형식이 들어 있습니다.

기록과 인계는 세션이 끝나도 남아야 할 결정과 진행 상황을 에이전트가 읽을 수 있는 문서로 옮기는 일입니다.

인계 메모로 세션을 이어 가는 실습은 부록 실습의 실습 6에 있습니다.

실패와 막는 장치

결정과 진행 상황을 문서로 남기지 않으면, CR을 두 세션에 나누어 구현할 때 다음 실패가 생길 수 있습니다. 작업 번호는 Chapter 6의 표 6-4에 있는 다섯 작업 단위를 위에서부터 차례로 가리킵니다. 표 8-3은 실패와 원인, 막는 장치입니다.

확인 방법

기록이 제 역할을 하는지는 새 세션이 기록만으로 작업을 이어 가는지로 확인합니다. 명령과 파일은 실습 폴더(examples/expense-app/) 기준입니다. 표 8-4는 확인할 것과 확인 위치입니다.

원칙과 점검 질문

세션이 끝나도 남아야 할 결정과 진행 상황은 대화가 아니라 저장소의 문서로 남깁니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 대화에서만 합의하고 문서로 남기지 않은 결정이 있습니까?
  2. 새 세션이 인계 메모만 읽고 다음 작업을 시작할 수 있습니까?
  3. 결정을 변경할 때 이전 결정과의 대체 관계를 남기고 있습니까?
