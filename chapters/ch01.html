Chapter 1 하네스란 무엇인가

에이전트(Agent)는 모델과 하네스(Harness)로 이루어집니다. 같은 모델도 어떤 하네스 안에서 일하는지에 따라 답변만 하는 도구가 되기도 하고, 파일을 수정하고 테스트까지 수행하는 에이전트가 되기도 합니다. 결과의 차이를 만드는 것은 모델이 아니라, 모델을 둘러싸고 루프를 실행하며 도구, 정보, 권한을 관리하는 하네스입니다. 따라서 AI 에이전트를 운영하는 관리자는 모델 선택보다 하네스 설계를 먼저 점검해야 합니다. 이 장에서는 하네스의 정의와 하네스가 하는 일, 하네스가 실행하는 에이전트 루프를 살펴봅니다.

  • 에이전트는 모델과 하네스로 이루어지고, 하네스는 모델 바깥의 실행 장치 전체입니다.
  • 하네스는 루프를 실행하고, 도구를 제공하고, 컨텍스트를 관리하며, 권한, 기록, 검증으로 작업을 통제합니다.
  • 프롬프트와 컨텍스트는 하네스 안의 설계 대상입니다.

에이전트와 하네스

이 책은 에이전트를 모델이 도구를 사용해 작업하고, 결과를 확인하며, 목표를 이룰 때까지 반복하는 시스템으로 정의합니다. 에이전트는 모델과 하네스로 이루어집니다. 하네스는 모델을 에이전트로 동작하게 하는, 모델 바깥의 실행 장치 전체입니다.

Claude Code 문서도 같은 관계로 설명합니다. 문서의 용어집은 하네스를 언어 모델을 코딩 에이전트로 만드는 도구, 컨텍스트(Context) 관리, 실행 환경으로 정의합니다. 문서는 Claude Code가 하네스이고, Claude는 그 안의 모델이라고 밝힙니다(Anthropic, 2026a).

같은 모델이 도구가 없는 채팅에서는 답변만 하고, Claude Code 안에서는 파일 수정과 테스트까지 수행합니다. 차이를 만드는 것은 하네스입니다. 하네스가 하는 일은 여섯 가지입니다.

  • 루프 실행: 모델의 판단과 도구 실행을 작업이 끝날 때까지 반복합니다.
  • 도구 제공: 파일 읽기와 수정, 명령 실행 같은 기능을 모델에 제공합니다.
  • 컨텍스트 관리: 루프마다 모델에 넘길 정보를 정합니다.
  • 권한: 도구로 할 수 있는 동작의 범위를 통제합니다.
  • 기록: 결정과 진행 상황, 실행 과정을 남깁니다.
  • 검증: 결과를 받아들이기 전에 확인합니다.

하네스 안의 프롬프트와 컨텍스트

하네스 안에서 관리자가 설계하는 대상은 프롬프트와 컨텍스트입니다. 이 책은 하네스와 그 안의 두 대상을 합쳐 세 설계 층이라고 부릅니다. Anthropic은 에이전트를 모델이 반복 루프 안에서 스스로 도구를 사용하는 시스템으로 정의합니다. 모델은 입력된 토큰(Token)을 바탕으로 다음 토큰을 예측해 결과를 생성합니다. 토큰은 모델이 글을 처리하는 최소 단위입니다. 토큰 사용량을 확인하는 위치는 Chapter 9의 비용 관리에서 다룹니다.

프롬프트는 모델에 주는 지시문입니다. 컨텍스트는 모델이 응답을 생성할 때 입력되는 정보 전체이며, 프롬프트는 그 일부입니다. 프롬프트는 사람이 하네스에 전달하는 요청이고, 컨텍스트는 하네스가 루프마다 모델에 넘기는 정보입니다. 둘 다 하네스 안의 설계 대상입니다. 그림 1-1은 세 설계 층의 포함 관계와 모델의 입력을, 표 1-1은 층별 정의와 설계 질문을 보여 줍니다.

모델은 공급사가 만듭니다. 세 설계 층은 모델을 사용하는 조직이 설계합니다. 그래서 같은 모델을 사용하는 두 조직이 서로 다른 결과를 얻습니다.

에이전트 루프와 종료 조건

하네스의 다섯 구성 요소(Chapter 2)는 에이전트가 일하는 순서 안에서 서로 다른 시점에 작동합니다. Anthropic의 Agent SDK 문서는 Claude Code의 실행 루프를 다섯 단계로 설명합니다(Anthropic, 2026b).

  • 요청 수신: 모델이 요청과 함께 시스템 프롬프트, 도구 정의, 대화 이력을 받습니다.
  • 판단과 응답: 모델이 현재 상태를 판단해 텍스트로 답하거나 도구 호출을 요청합니다.
  • 도구 실행: 하네스가 요청된 도구를 실행하고 결과를 모델에 돌려줍니다.
  • 반복: 판단과 도구 실행을 반복합니다. 이 왕복 한 번을 턴이라고 부릅니다.
  • 결과 반환: 모델이 도구 호출 없이 응답하면 루프가 끝나고, 최종 응답과 토큰(Token) 사용량, 비용, 세션 ID가 반환됩니다.

그림 1-2는 이 루프와 종료 조건을, 표 1-2는 루프의 단계별로 작동하는 구성 요소를 보여 줍니다.

도구 실행 앞에서는 권한이 작동합니다. 문서에 따르면 거부된 도구 호출은 실행되지 않고, 모델은 거부 메시지를 결과로 받습니다. 모델은 다른 방법을 찾거나, 진행할 수 없다고 보고합니다.

루프는 기본적으로 모델이 스스로 끝낼 때까지 계속됩니다. 문서는 범위가 분명한 작업에서는 문제가 없지만, 열린 요청에서는 루프가 오래 실행될 수 있다고 설명합니다. 그래서 하네스는 두 가지 상한을 둡니다. 턴 상한은 도구를 사용한 턴의 수를, 비용 상한은 지출 금액을 제한합니다. 문서는 운영 환경의 에이전트에 비용 상한을 기본으로 두라고 권합니다(Anthropic, 2026b).

상한에 도달하면 루프는 작업을 마치지 못한 채 끝나고, 결과에 종료 사유가 남습니다. 종료 사유는 정상 완료, 턴 상한 도달, 비용 상한 도달, 실행 중 오류 등으로 구분됩니다. 상한에 도달한 결과는 완료로 판정하지 않습니다(Chapter 7의 완료 보고). 관리자는 두 상한의 값과, 상한에 도달했을 때 세션을 재개할지 중단할지를 미리 정합니다. 비용 상한의 기준은 Chapter 9의 비용 관리와 연결됩니다.

Codex도 같은 구조의 루프를 사용합니다. OpenAI는 Codex의 하네스가 모든 Codex 제품에 공통인 에이전트 루프를 제공한다고 설명합니다. 턴이라는 말의 범위는 두 제품이 다릅니다. Agent SDK 문서의 턴은 도구 호출 왕복 한 번이고, OpenAI 글의 턴은 사용자 메시지 하나에 대한 처리 전체입니다. 한 턴 안에서 모델 추론과 도구 호출이 여러 번 반복됩니다. OpenAI는 에이전트가 한 턴에서 수백 번의 도구 호출을 할 수 있다고 설명합니다. 그러면 컨텍스트 윈도(Context Window)를 모두 소진할 수 있습니다(OpenAI, 2026). 두 제품을 함께 운영한다면 턴 상한을 정하기 전에 제품마다 턴이 무엇을 세는지 확인해야 합니다.

프롬프트 엔지니어링과 컨텍스트 엔지니어링

프롬프트 엔지니어링(Prompt Engineering)은 원하는 결과를 얻도록 지시문을 작성하고 구성하는 방법입니다. 컨텍스트 엔지니어링(Context Engineering)은 모델이 응답을 생성하는 동안 필요한 정보를 선별하고 유지하는 전략입니다. 두 정의는 Anthropic이 2025년 9월 공개한 글(Rajasekaran 외, 2025)을 따릅니다. 이 글에서 Anthropic은 컨텍스트 엔지니어링을 프롬프트 엔지니어링이 발전한 단계로 설명합니다. 두 방법은 세 가지 점에서 다릅니다.

  • 대상: 프롬프트 엔지니어링은 지시문을 다룹니다. 컨텍스트 엔지니어링은 시스템 지시, 도구 설명, 외부 자료, 대화 이력을 포함한 입력 전체를 다룹니다.
  • 시점: 프롬프트 작성은 한 번으로 끝나는 작업입니다. 컨텍스트는 모델에 무엇을 넘길지 정할 때마다 다시 선별합니다.
  • 제약: 모델이 한 번에 처리할 수 있는 토큰의 범위를 컨텍스트 윈도(Context Window)라고 합니다. Anthropic은 컨텍스트의 토큰이 늘수록 모델이 정보를 정확히 기억해 내는 능력이 떨어진다고 설명합니다. 컨텍스트 윈도의 사용 현황을 확인하는 위치는 Chapter 5의 한정된 자원에서 다룹니다. 그래서 많은 정보를 제공하는 것보다 필요한 정보를 선별하는 것이 중요합니다.

관리 관점에서 두 층은 관리 대상이 다릅니다. 프롬프트는 요청 한 건의 지시문입니다. 컨텍스트는 규칙 문서, 업무 자료, 대화 이력처럼 조직이 관리하는 자료를 포함합니다.

하네스 엔지니어링

이 책은 하네스 엔지니어링(Harness Engineering)을 에이전트가 신뢰할 수 있는 결과를 내도록 모델 바깥의 작업 환경을 설계하는 일로 정의합니다. 하네스의 구성 요소는 역할, 도구, 권한, 기록, 검증의 다섯 가지입니다. 구성 요소별 설계는 Chapter 2에서 다룹니다.

OpenAI는 2026년 2월 이 용어를 제목으로 한 글(Lopopolo, 2026)에서, 사람이 코드를 직접 작성하지 않는 개발 실험을 소개했습니다. OpenAI 발표에 따르면 이 팀은 5개월 동안 약 100만 줄의 코드와 약 1,500개의 풀 리퀘스트(Pull Request)를 Codex로 생성했습니다. 풀 리퀘스트는 코드 변경을 저장소에 반영하기 전에 검토를 요청하는 단위입니다. 이 실험에서 OpenAI가 밝힌 내용은 네 가지입니다.

  • 엔지니어는 코드를 직접 작성하지 않고, 작업 환경을 설계하고 의도를 문서로 밝히고 피드백 루프를 만드는 일을 맡았습니다.
  • OpenAI는 초기 진행이 느렸던 원인을 Codex의 능력 부족이 아니라 충분히 정의되지 않은 환경에서 찾았습니다.
  • 작업이 실패하면 어떤 능력이 누락되었는지 묻고, 그 능력을 에이전트가 읽을 수 있고 검사로 강제되는 형태로 저장소에 추가했습니다.
  • 에이전트가 실행 중에 읽을 수 없는 지식은 에이전트에게 없는 지식으로 보고, 채팅이나 사람의 기억에 있던 결정을 저장소 문서로 옮겼습니다.

사람의 역할도 남았습니다. 사람은 작업의 우선순위를 정하고, 사용자 의견을 수용 기준으로 정리하고, 결과를 검증했습니다. 수용 기준은 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 이 사례에서 OpenAI가 개선한 대상은 모델이 아니라 저장소 문서, 검사 규칙, 검증 절차 같은 작업 환경이었습니다.

소프트웨어 엔지니어링과의 접점

하네스의 구성 요소는 소프트웨어 엔지니어링의 기존 활동과 대응합니다. 소프트웨어 엔지니어링은 요구 사항 정의, 설계, 개발, 테스트, 배포, 운영으로 이어지는 개발의 전 과정을 다루는 분야입니다. 이 책은 이 분야를 하네스를 이해하는 데 필요한 범위에서만 다룹니다. 표 1-3은 활동별로 대응하는 하네스 설계를 보여 줍니다.

요구 사항을 명확히 정의하는 능력은 에이전트에게 작업을 지시하는 능력으로 이어집니다. 테스트 기준을 정하는 능력은 에이전트의 결과를 검증하는 능력으로 이어집니다.

관리자가 책임질 영역

모델은 공급사가 개선하지만, 하네스는 프로젝트를 운영하는 조직이 설계합니다. 따라서 에이전트 프로젝트의 관리자가 책임질 영역은 모델 바깥의 세 층입니다.

문제가 생기면 관리자는 먼저 원인이 어느 층에 있는지 분류합니다. 표 1-4는 대표적인 증상과 원인이 있는 층, 점검할 항목을 대응시킨 것입니다.

이 책의 작가는 앞선 책 「생성형 AI, 묻고 확인하고 활용하기」를 AI 에이전트와 함께 만들며 73차례 검수를 거쳤습니다. 초기에는 어휘, 조사, 표 번호처럼 같은 종류의 실수를 사람이 매번 찾았습니다. 큰 결정을 집필 중에 여러 번 뒤집는 일도 있었습니다. 해결 방법은 모델 교체가 아니라 작업 환경의 보완이었습니다.

  • 반복된 실수는 자동 검사 규칙으로 만들었습니다.
  • 큰 결정은 번호를 매겨 기록하고, 결정을 변경할 때는 이전 결정을 남겼습니다.
  • 원고 작성과 검수를 서로 다른 에이전트에게 나눠 맡겼습니다.

이후 사람은 판단이 필요한 항목만 검토하는 구조로 작업을 정리했습니다.

모델 성능이 향상되면 하네스가 필요 없다는 의견도 있습니다. 모델 성능의 향상은 한 번의 응답 품질을 높입니다. 그러나 어떤 자료에 접근할지, 어떤 작업을 사람이 승인할지, 무엇을 기록할지는 조직이 정할 일입니다. Anthropic도 모델이 발전해도 컨텍스트를 한정된 자원으로 다루는 일은 계속 중요하다고 밝혔습니다.

같은 모델로 더 나은 결과를 얻는 방법은 모델 바깥의 설계에 있습니다.
