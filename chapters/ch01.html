1장

같은 모델, 다른 점수

에이전트가 기대만큼 일하지 못할 때, 가장 먼저 떠오르는 해법은 더 좋은 모델입니다. 이 장은 그 반사 작용을 멈추는 데서 시작합니다.

개요

코딩 에이전트에 일을 맡겨 본 사람이라면 비슷한 경험이 있을 겁니다. 에이전트가 코드를 쓰고, 스스로 다시 읽어 보고, 괜찮다고 판단하고 끝냅니다. 그런데 막상 실행해 보면 동작하지 않습니다. 이때 우리는 흔히 "모델이 아직 부족하다"고 결론 내리고 다음 모델이 나오기를 기다립니다.

하지만 에이전트는 모델 하나로 이루어져 있지 않습니다. 모델에게 무엇을 보여 줄지 정하는 시스템 프롬프트, 모델이 쓸 수 있는 도구, 모델의 행동 전후에 끼어드는 훅, 작업이 끝났는지 판단하는 규칙이 모두 결과에 영향을 줍니다. 이 바깥 구조 전체를 하네스(harness)라고 부릅니다. 말에 채우는 마구가 말의 힘을 원하는 방향으로 쓰게 하듯, 하네스는 모델의 능력을 원하는 일에 쓰이게 합니다.

이 장에서는 모델을 한 글자도 바꾸지 않고 하네스만 바꿔서 성능을 크게 끌어올린 사례를 먼저 살펴봅니다. 그리고 정반대 방향으로 하네스를 설계한 사례와 비교합니다. 두 사례를 나란히 놓으면, 하네스 엔지니어링이 특정 기법이 아니라 "모델 바깥에서 결과를 설계하는 일" 전체라는 것이 보입니다.

하네스 정의와 구성 요소

이 책은 하네스를 LangChain의 Vivek Trivedy가 정리한 방식대로 정의합니다. 에이전트는 모델과 하네스를 합친 것이고, 하네스는 모델 자신을 뺀 나머지 코드, 설정, 실행 로직 전부입니다. 모델이 "생각하는 부분"이라면, 하네스는 모델이 무엇을 보고, 무엇을 할 수 있고, 언제 멈추고, 결과를 어떻게 확인받는지를 정하는 부분입니다.

하네스는 다시 바깥의 환경과 구분됩니다. 환경은 에이전트가 실제로 건드리는 파일, API, 데이터, 권한입니다. 세 층의 관계는 그림 1-1과 같습니다.

하네스를 이루는 요소는 대체로 여덟 가지로 나눌 수 있습니다.

독자가 이미 쓰는 제품으로 옮기면 이해가 쉽습니다. Claude, GPT는 모델이고, Claude Code, Codex는 그 모델을 감싼 하네스 제품입니다. Thoughtworks의 Birgitta Böckeler는 여기서 한 걸음 더 나눕니다. 제품에 이미 들어 있는 시스템 프롬프트나 코드 검색 기능은 내부 하네스이고, 사용자가 지시 파일, 훅, 스킬 등으로 덧붙이는 부분은 외부 하네스입니다. 이 책이 "내 프로젝트 적용"에서 다루는 대부분은 외부 하네스입니다.

하네스 필요성

모델은 몇 달마다 좋아지는데, 왜 모델 바깥을 따로 설계해야 할까요. 이유는 다섯 가지로 정리됩니다.

첫째, 같은 모델로도 결과가 달라짐. 이 장의 사례에서 LangChain은 모델을 그대로 두고 하네스만 바꿔 점수를 13.7포인트 올렸습니다. 모델을 바꾸는 것만이 성능을 올리는 길이 아닙니다.

둘째, 모델은 스스로 완료를 과신함. 에이전트는 자기 코드를 다시 읽고 괜찮다고 판단한 뒤 멈추는 경향이 있습니다. 이 확인을 모델의 선의에 맡기지 않고 바깥에서 강제하는 장치가 필요합니다.

셋째, 비용과 속도는 하네스가 결정함. 무엇을 컨텍스트에 넣을지, 어느 단계에 추론을 얼마나 쓸지는 모델이 아니라 하네스가 정합니다. 같은 결과를 더 싸고 빠르게 얻는 일은 대부분 하네스의 몫입니다.

넷째, 사고는 권한 설계로 막음. 에이전트가 운영 데이터베이스를 지우는 사고는 모델이 더 똑똑해져서 막히는 것이 아니라, 애초에 지울 수 없게 만든 권한 설계로 막힙니다. 이 이야기는 9장에서 다룹니다.

다섯째, 모델이 바뀌어도 하네스는 남음. 모델은 계속 교체되지만, 하네스에 쌓은 규칙, 검증, 기록은 다음 모델에서도 그대로 쓸 수 있습니다. 다만 1장 사례에서 보듯 새 모델에 맞춘 재조정은 필요합니다.

하네스 용어의 역사

"하네스"는 AI 분야에서 새로 만든 말이 아닙니다. 소프트웨어 테스트에서 먼저 쓰였고, 에이전트 분야로 넘어온 뒤 2026년 초에 "하네스 엔지니어링"이라는 이름으로 빠르게 퍼졌습니다.

연표에서 눈여겨볼 점은 용어보다 관점의 이동입니다. 처음에는 "모델을 시험하는 틀"이었던 하네스가, 이제는 "모델이 일을 잘하게 만드는 설계 대상"이 되었습니다. 이 책은 두 번째 의미로 하네스를 다룹니다.

사례: 모델 고정, 하네스 변경만으로 13.7포인트 향상

3대상 deepagents-cli, 사용 모델 OpenAI gpt-5.2-codex

사례 요약

에이전트 개발 프레임워크를 만드는 회사인 LangChain은 2026년 2월, 자사 코딩 에이전트 deepagents-cli를 개선한 과정을 공개했습니다. 여기서 비교의 대상은 회사가 아니라 deepagents-cli라는 하네스입니다. 핵심은 한 문장입니다. 모델은 OpenAI의 gpt-5.2-codex로 고정하고 하네스만 손봐서, Terminal Bench 2.0 점수를 52.8점에서 66.5점으로 13.7포인트 올렸다는 것입니다. 순위로는 30위권 밖에서 5위권으로 올라섰습니다.

실험 환경

Terminal Bench 2.0은 에이전트의 코딩 능력을 평가하는 벤치마크로, 머신러닝, 디버깅, 생물학 등 여러 분야에 걸친 89개 과제로 이루어져 있습니다. LangChain은 Harbor라는 도구로 실행을 관리했고, Harbor는 Daytona 샌드박스를 띄워 에이전트 루프를 돌린 뒤 검증과 채점까지 수행했습니다. 에이전트의 모든 행동은 지연 시간, 토큰 수, 비용과 함께 LangSmith에 기록되었습니다.

여기서 눈여겨볼 점은 실험 자체도 하나의 하네스 위에서 돌아갔다는 것입니다. 샌드박스, 자동 채점, 행동 기록이 없었다면 "무엇이 나아졌는지"를 말할 근거가 없었을 겁니다. 이 주제는 14장에서 다시 다룹니다.

조절 요소 선별: 세 가지 집중

LangChain은 하네스에 조절 가능한 요소가 많다는 점을 먼저 짚었습니다. 시스템 프롬프트, 도구, 훅이나 미들웨어, 스킬, 서브에이전트 위임, 메모리 등이 모두 후보입니다. 그런데 이들은 의도적으로 탐색 범위를 좁혀 시스템 프롬프트, 도구, 미들웨어 세 가지만 건드렸습니다. 미들웨어는 모델 호출과 도구 호출 앞뒤에 끼어드는 코드로, Claude Code나 Codex에서 말하는 훅과 같은 개념입니다.

기본 프롬프트와 표준 도구, 미들웨어로 시작한 첫 점수가 52.8%였습니다. 이것이 출발선입니다.

개선 방법: 실패 기록 분석 반복 루프

LangChain이 쓴 방법은 단순합니다. 실행 기록(트레이스)을 모으고, 여러 분석 에이전트를 병렬로 띄워 오류를 분석하게 한 뒤, 메인 에이전트가 결과를 종합해 하네스 수정안을 내는 흐름입니다. 이들은 이 과정을 재사용할 수 있도록 에이전트 스킬로 만들었습니다. 사람은 마지막 단계에서 수정안을 검토하고 논의하는 역할을 맡을 수 있었지만 필수는 아니었습니다.

한 가지 경고도 함께 남겼습니다. 특정 과제에만 맞춘 수정은 다른 과제에서 성능을 떨어뜨릴 수 있다는 것입니다. 하네스 개선에도 과적합이 있습니다.

효과 확인 변경 네 가지

첫째, 자기 검증 강제. 가장 흔한 실패 유형은 이 장 첫머리에서 말한 그대로였습니다. 에이전트가 해답을 쓰고, 자기 코드를 다시 읽고, 괜찮아 보인다고 확인한 뒤 멈추는 것입니다. LangChain은 시스템 프롬프트에 계획과 탐색, 구현, 검증, 수정의 네 단계 접근법을 넣었습니다. 특히 검증 단계에서는 테스트를 실행하고, 출력을 끝까지 읽고, 자기 코드가 아니라 원래 요구사항과 비교하라고 안내했습니다. 여기에 더해, 에이전트가 작업을 끝내려는 순간 가로채서 요구사항 대비 검증을 한 번 더 하게 만드는 미들웨어를 붙였습니다. 프롬프트로 권하고, 코드로 강제한 것입니다.

둘째, 환경 정보 사전 주입. 에이전트가 시작할 때 현재 디렉터리와 상하위 디렉터리 구조를 파악하고, Python 같은 도구가 어디에 설치되어 있는지 찾아서 컨텍스트에 넣어 주는 미들웨어를 만들었습니다. 에이전트가 직접 탐색하게 두면 탐색 과정에서 실수가 생기기 때문입니다. 또 결과물이 자동 테스트로 채점된다는 점, 요구사항에 적힌 파일 경로를 정확히 따라야 한다는 점, 정상 경로뿐 아니라 예외 경우도 확인해야 한다는 점을 알려 주었습니다. 시간 제한이 있는 과제에서는 남은 시간을 경고해 검증 단계로 넘어가도록 유도했습니다. LangChain은 하네스 엔지니어의 역할을 "에이전트가 스스로 일을 끝낼 수 있도록 컨텍스트를 준비해 전달하는 것"으로 요약했습니다.

셋째, 반복 실수 루프 차단. 에이전트는 한 번 계획을 정하면 시야가 좁아져서, 잘못된 접근을 조금씩 바꿔 가며 계속 반복하는 경향을 보였습니다. 어떤 기록에서는 같은 방식을 열 번 넘게 반복했습니다. LangChain은 파일별 편집 횟수를 세다가 일정 횟수를 넘으면 "접근 방식을 다시 생각해 보라"는 문구를 컨텍스트에 넣는 미들웨어를 만들었습니다. 흥미롭게도 LangChain은 이것이 현재 모델의 약점을 보완하는 임시 장치이며, 모델이 좋아지면 필요 없어질 가능성이 크다고 스스로 밝혔습니다.

넷째, 단계별 추론 계산량 배분. gpt-5.2-codex는 추론 강도를 low, medium, high, xhigh 네 단계로 조절할 수 있습니다. 가장 높은 xhigh로만 돌렸더니 시간 초과가 잦아 53.9%에 그쳤고, high로만 돌렸을 때는 63.6%였습니다. LangChain은 계획과 검증 단계에는 높은 추론을, 구현 단계에는 한 단계 낮은 추론을 쓰는 방식을 기본으로 삼았고, 이것이 최종 66.5%로 이어졌습니다. 더 많이 생각하게 하는 것이 항상 좋은 것은 아니라는 점을 보여 주는 결과입니다.

같은 하네스, 다른 모델

3대상 deepagents-cli (이전 버전 하네스), 사용 모델 Anthropic Claude Opus 4.6

LangChain은 이전 버전의 하네스로 Claude Opus 4.6을 시험했을 때 59.6%가 나왔다고 밝혔습니다. 경쟁력은 있었지만 Codex보다 낮았는데, LangChain은 그 이유를 Claude에 대해서는 같은 개선 루프를 돌리지 않았기 때문이라고 설명했습니다. 그리고 OpenAI와 Anthropic의 프롬프트 가이드가 서로 다르다는 점을 들어, 하네스는 모델에 맞춰 조정해야 한다고 결론 내렸습니다.

이 대목은 이 책 전체에서 반복될 주제의 예고편입니다. 하네스는 모델과 무관한 범용 장치가 아닙니다. 좋은 컨텍스트 준비, 검증 중심 설계 같은 원칙은 모델을 가리지 않지만, 구체적인 설정은 모델마다 다시 다듬어야 합니다.

대조 사례: 최소 스캐폴드와 모델 자율

ASWE-bench 에이전트

Anthropic은 2024년 10월, 업그레이드된 Claude 3.5 Sonnet이 SWE-bench Verified에서 49%를 기록해 당시 최고 기록이던 45%를 넘었다고 발표하면서 그 에이전트 구성을 함께 공개했습니다. Anthropic은 먼저 SWE-bench가 모델 하나를 평가하는 것이 아니라 모델과 그 주변 스캐폴딩을 합친 에이전트 전체를 평가한다는 점, 그리고 같은 모델이라도 스캐폴딩에 따라 성능이 크게 달라진다는 점을 강조했습니다.

흥미로운 것은 이 에이전트가 택한 방향입니다. deepagents-cli가 미들웨어를 여러 겹 쌓았다면, Anthropic의 SWE-bench 에이전트는 반대로 스캐폴딩을 최소화하고 가능한 한 많은 통제권을 모델에게 주는 쪽을 골랐습니다. 에이전트에는 프롬프트 하나, bash 명령을 실행하는 도구, 파일을 보고 고치는 편집 도구만 주어졌습니다. 모델이 끝났다고 판단하거나 20만 토큰 컨텍스트를 넘을 때까지 계속 실행했고, 단계 사이의 전환을 고정하지 않고 모델이 스스로 판단하게 했습니다.

이 글에는 LangChain 사례와 겹치는 관찰도 있습니다. Anthropic은 채점에 쓰이는 테스트를 모델이 볼 수 없기 때문에, 실제로는 실패했는데도 모델이 성공했다고 여기는 경우가 많았다고 적었습니다. 에이전트가 스스로 완료를 과신하는 문제는 모델 회사와 모델 제공 방식에 상관없이 반복해서 나타나는 패턴이고, 이 책에서도 7장과 11장에서 계속 다룹니다.

대신 Anthropic은 도구 두 개의 설명과 사양을 다듬는 데 많은 노력을 들였다고 밝혔습니다. 통제의 무게를 루프 밖 장치가 아니라 도구 인터페이스에 둔 것입니다. 이 도구 설계 이야기는 4장에서 자세히 다룹니다.

그래서 어느 쪽이 옳다고 말하기는 어렵습니다. 중요한 공통점은 둘 다 모델을 고정한 채 모델 바깥을 설계해서 결과를 바꿨다는 것입니다.

문제 분석: 모델 문제와 하네스 문제 구분

에이전트의 실패를 만났을 때 가장 먼저 할 일은 실패가 어느 층에서 생겼는지 가르는 것입니다. 이 책은 에이전트를 세 층으로 나눠 봅니다.

  • 모델: 추론하고 판단하는 능력 자체
  • 하네스: 모델에게 무엇을 보여 주고, 무엇을 쓰게 하고, 언제 멈추게 하고, 어떻게 확인할지 정하는 구조
  • 환경: 파일 시스템, API, 권한, 데이터처럼 에이전트가 실제로 건드리는 대상

LangChain 사례에서 드러난 실패를 이 기준으로 나눴습니다.

물론 모든 실패가 하네스로 풀리지는 않습니다. 모델이 정말로 모르는 지식이나 풀 수 없는 추론은 하네스로 메울 수 없습니다. 다만 경험상 그 경계는 우리가 처음 생각하는 것보다 훨씬 뒤쪽에 있습니다.

성능 문제를 만나면 모델을 바꾸기 전에 하네스를 먼저 의심한다.

하네스 해법 정리

두 사례에서 쓰인 하네스의 손잡이를 정리했습니다.

내 프로젝트 적용

이제 자신의 에이전트로 같은 질문을 던져 볼 차례입니다. Claude Code든 Codex든 상관없습니다. 다음 순서로 진행합니다.

  1. 과제 묶음 만들기. 최근에 에이전트에게 맡겼던 일 가운데 결과를 확인할 수 있는 과제 열 개를 고릅니다. "테스트가 통과한다", "페이지가 뜬다"처럼 성공 여부를 판정할 수 있어야 합니다.
  2. 기준선 기록. 지금 설정 그대로 열 개를 실행하고, 성공 개수와 실패 모습을 기록합니다. 실패는 "무엇을 하다가 어떻게 끝났는지"를 한 줄로 적습니다.
  3. 실패를 층으로 나누기. 기록한 실패마다 모델, 하네스, 환경 중 어디서 생겼는지 표시합니다. 표 1-4를 참고합니다.
  4. 손잡이 하나만 돌리기. 가장 자주 나온 하네스 실패 하나를 골라 한 가지만 바꿉니다. 예를 들어 지시 파일에 "끝내기 전에 테스트를 실행하고 요구사항과 비교하라"는 절차를 넣습니다.
  5. 같은 열 개를 다시 실행. 기준선과 비교합니다. 나아졌다면 유지하고, 아니라면 되돌립니다. 한 번에 여러 개를 바꾸면 무엇이 효과였는지 알 수 없습니다.

열 개는 통계적으로 충분하지 않습니다. 하지만 이 연습의 목적은 정확한 수치가 아니라, 실패를 보는 눈을 모델에서 하네스로 옮기는 데 있습니다.

체크리스트

  • 에이전트의 실패를 모델, 하네스, 환경 중 어느 층의 문제인지 구분해 보았다
  • 에이전트가 스스로 검증하지 않고 끝내는 경우가 있는지 확인했다
  • 에이전트가 시작할 때 알아야 할 환경 정보를 미리 제공하고 있다
  • 하네스를 바꿀 때 한 번에 하나씩 바꾸고 전후를 비교한다
  • 특정 과제에만 맞춘 수정이 다른 과제를 망치지 않는지 확인한다
  • 다른 모델로 바꿀 때 하네스도 다시 조정해야 한다는 점을 알고 있다
