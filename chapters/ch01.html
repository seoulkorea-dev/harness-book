Chapter 1 하네스란 무엇인가

에이전트는 모델과 하네스로 이루어집니다.

에이전트(Agent)라는 말은 연구 논문, 개발 지침, 제품 문서에서 서로 다른 범위를 가리킵니다. 어떤 곳에서는 모델이 생각과 행동을 번갈아 하는 방법을, 어떤 곳에서는 모델이 스스로 작업 과정을 정하는 시스템을, 어떤 곳에서는 제품 자체를 뜻합니다. 같은 말이 다른 뜻으로 쓰이면, 에이전트를 만든다고 할 때 무엇을 설계하는지가 흐려집니다. 따라서 모델이 혼자 할 수 없는 일과 말의 쓰임 차이를 먼저 확인하고, 이 책에서 사용할 에이전트와 하네스(Harness)의 뜻을 정해야 합니다. 이 장은 모델의 한계에서 출발해 에이전트를 가리키는 여러 형태의 차이, 이 책의 에이전트와 하네스, 하네스 엔지니어링(Harness Engineering)의 정의, 하네스 안의 프롬프트와 컨텍스트(Context), 에이전트 루프를 차례로 살펴봅니다. 마지막으로 결과가 기대와 다를 때 원인이 있는 층을 찾는 방법을 다룹니다.

  • 모델은 명령을 직접 실행하지 않고, 요청 사이의 대화도 기억하지 않으며, 실행 결과도 스스로 확인하지 못합니다. 이 세 가지를 모델 대신 맡는 프로그램이 하네스입니다.
  • 에이전트는 모델과 하네스로 이루어지고, 하네스는 제품이 제공하는 실행 장치와 사용자와 팀이 정하는 설정으로 나뉩니다.
  • 하네스는 루프를 실행하고, 도구를 제공하고, 컨텍스트를 관리하며, 권한, 기록, 검증으로 작업을 통제합니다.
  • 프롬프트와 컨텍스트는 하네스 안의 설계 대상입니다.

모델만으로 할 수 없는 일

하네스가 왜 필요한지 보려면 먼저 모델이 무엇을 받고 무엇을 내놓는지 알아야 합니다. 모델은 글을 토큰(Token) 단위로 처리합니다. 토큰은 모델이 글을 처리하는 최소 단위입니다. 대규모 언어 모델(Large Language Model, LLM)은 입력된 토큰을 바탕으로 다음 토큰을 예측해 결과를 생성하는 모델입니다. 모델이 응답을 생성할 때 입력되는 정보 전체를 컨텍스트라고 하고, 모델이 한 번에 처리할 수 있는 토큰의 범위를 컨텍스트 윈도(Context Window)라고 합니다. 모델은 입력된 컨텍스트를 받아 출력을 만들 뿐이므로, 입력 바깥에서 일어나는 일은 혼자 처리하지 못합니다.

모델 하나만으로는 업무를 끝까지 수행할 수 없습니다. Claude의 API(프로그램이 모델을 호출하는 방식) 문서는 모델과 모델을 호출하는 프로그램의 역할을 나눠 설명합니다(Anthropic, 2026c). 이 설명에서 모델의 한계는 세 가지로 드러납니다.

  • 실행: 모델은 명령을 직접 실행하지 않습니다. 모델은 실행할 명령을 요청하고, 실제 실행은 모델을 호출한 프로그램이 맡습니다.
  • 기억: API는 요청 사이의 상태를 유지하지 않습니다. 대화를 이어 가려면 프로그램이 이전 대화를 다음 요청에 다시 포함해야 합니다.
  • 확인: 모델은 실행 결과를 스스로 받지 못합니다. 프로그램이 결과를 돌려주어야 모델이 다음 판단을 합니다.

도구는 파일 읽기, 명령 실행, 검색처럼 모델 바깥에서 실행되는 기능입니다. 도구 호출은 모델이 특정 도구를 정해진 입력으로 실행해 달라고 요청하는 것입니다. 프로그램은 도구를 실행하고 결과를 모델에 돌려줍니다. 실행이 실패하면 실패 표시와 오류 내용을 결과로 돌려줍니다(Anthropic, 2026c).

실행, 기억, 확인을 모델 대신 맡는 프로그램을 이 책은 하네스라고 부릅니다. 하네스라는 말은 사용하는 곳마다 뜻이 조금씩 달라서, 다음 절에서 쓰임을 비교한 뒤 이 책의 에이전트와 하네스 절에서 뜻을 정합니다. 표 1-1은 모델만 호출할 때와 하네스 안에서 일할 때의 차이를 항목별로 보여 줍니다.

같은 말, 다른 뜻

앞 절에서 하네스라고 부른 프로그램과, 그 프로그램이 움직이는 에이전트는 사용하는 곳에 따라 뜻이 조금씩 다릅니다. 이 절은 쓰임의 차이를 비교하고, 다음 절에서 이 책의 정의를 정합니다.

2022년에 공개된 ReAct 논문은 모델이 생각, 행동, 관찰을 번갈아 하며 문제를 풀게 하는 방법을 제안했습니다(Yao 외, 2023). 모델이 추론을 적고(생각), 도구를 호출하고(행동), 그 결과를 보고(관찰) 다음 생각을 이어 갑니다. 이 반복이 오늘날 에이전트 루프(판단, 도구 실행, 결과 확인을 되풀이하는 흐름, 에이전트 루프와 종료 조건)의 원형입니다. ReAct는 프롬프트로 구현한 방법이어서, 루프를 돌리고 도구를 실행하고 결과를 다시 모델에 입력하는 일은 모델 바깥의 코드가 맡았습니다.

Anthropic은 모델과 도구를 사용하는 시스템을 워크플로(Workflow)와 에이전트로 나눕니다(Schluntz 외, 2024). 워크플로는 미리 정한 코드 경로(프로그램에 미리 적어 둔 처리 순서)에 따라 모델과 도구를 조율합니다. 에이전트는 모델이 자기 작업 과정과 도구 사용을 스스로 정합니다. 워크플로는 단계가 정해진 작업에서 예측 가능하고, 에이전트는 단계를 미리 정하기 어려운 작업에서 유연합니다.

두 방식은 함께 사용할 수 있습니다. 작업의 순서와 사람의 승인 지점은 워크플로처럼 미리 정하고, 각 단계 안의 작업은 에이전트가 판단하게 합니다. 이 책은 이 형태를 결합형이라고 부릅니다. Chapter 3에서 구현하는 경비 정산 시스템 개편 변경 요청(Change Request) CR이 결합형의 예입니다. 변경 요청은 운영 중인 시스템의 기능을 어떻게 변경할지 요청하는 문서이며, 이 책은 이 예제를 줄여서 CR이라고 부릅니다. CR은 일을 다섯 개의 작업 단위로 나눕니다. 작업 단위의 순서와 사람의 승인 지점은 하네스의 설정으로 미리 정하고, 작업 단위 안의 구현 방법은 에이전트가 판단합니다.

하네스라는 말도 사용하는 곳마다 강조점이 다릅니다. 하네스는 원래 말에 채우는 마구이고, 소프트웨어에서는 시험 대상을 실행하고 결과를 확인하는 테스트 하네스라는 말로 사용되어 왔습니다. Codex는 에이전트 루프와 실행 로직을 맡는 모델 바깥의 장치를 하네스라고 부릅니다(OpenAI, 2026). Claude Code는 긴 작업을 여러 세션에 걸쳐 이어 가게 하는 장치로 하네스를 설명하고(Young, 2025), 제품 문서에서는 제품 자체를 하네스로, 모델을 그 안의 구성 요소로 설명합니다(다음 절). 이 책은 Claude Code 문서의 넓은 정의를 따릅니다. 루프 실행이나 세션 기록 하나만으로는 앞 절의 실행, 기억, 확인을 모두 맡지 못하기 때문입니다. 두 제품이 강조한 루프 실행과 세션 기록은 다음 절에서 정하는 하네스의 한 부분으로 봅니다.

표 1-2는 에이전트를 가리키는 네 가지 형태를, 표 1-3은 하네스라는 말의 쓰임을 비교합니다.

이 책의 에이전트와 하네스

이 책에서 에이전트는 모델이 루프 안에서 도구를 사용해 다음 행동을 스스로 정하고, 결과를 확인하며, 목표를 이룰 때까지 반복하는 시스템입니다. 에이전트는 모델과 하네스로 이루어집니다. 하네스는 모델을 에이전트로 동작하게 하는, 모델 바깥의 실행 장치 전체입니다. Claude Code도 에이전트를 모델이 반복 루프 안에서 스스로 도구를 사용하는 시스템으로 설명합니다(Rajasekaran 외, 2025). 앞 절의 결합형도 단계 안의 행동은 모델이 정하므로 이 정의의 에이전트에 들어갑니다.

제품 문서도 같은 관계로 설명합니다. 문서의 용어집은 하네스를 언어 모델을 코딩 에이전트로 만드는 도구, 컨텍스트 관리, 실행 환경으로 정의합니다. 문서는 Claude Code가 하네스이고, Claude는 그 안의 모델이라고 밝힙니다(Anthropic, 2026a).

앞 정의의 실행 장치 전체는 두 부분으로 나뉩니다. 이 책은 제품이 제공하는 부분을 실행 장치, 사용자와 팀이 정하는 부분을 설정이라고 부릅니다. 실행 장치는 제품이 제공하는 부분으로, 루프 실행, 도구 제공, 컨텍스트 관리, 권한 확인, 세션 기록을 맡습니다. 설정은 사용자와 팀이 정하는 부분으로, 규칙 문서, 권한 설정, 자동 검사, 역할 분담처럼 맡길 업무에 맞춰 정하는 값입니다. 설정이 없으면 에이전트는 제품의 기본값으로 동작하고, 맡길 업무에 맞게 설정을 정하면 그 업무를 위한 에이전트가 됩니다. 작업 순서, 승인, 검사처럼 미리 정해야 하는 부분을 설정으로 고정하면 앞 절의 결합형이 됩니다. 이 책에서 하네스의 다섯 구성 요소(역할, 도구, 권한, 기록, 검증)라고 할 때는 설정에서 정하는 항목을 가리킵니다. 실행 장치와 설정에 도구, 권한, 기록처럼 같은 이름이 있는 것은 같은 기능을 두 쪽에서 보기 때문입니다. 실행 장치는 그 기능을 제품이 갖추어 둔 것이고, 설정은 그 기능을 이 업무에서 어떻게 쓸지 팀이 정한 값입니다.

하네스가 실행하는 도구는 모델과 하네스 바깥의 외부 실행 환경에 작용합니다. 외부 실행 환경은 파일 시스템, 데이터베이스, 네트워크, 소프트웨어, 사용자, 기타 외부 서비스처럼 도구가 읽고 변경하는 대상입니다. 도구는 제품에 들어 있는 기본 도구와, MCP(Model Context Protocol)라는 표준 방식으로 연결하는 외부 도구로 나뉩니다(Chapter 2). 그림 1-1은 모델, 하네스, 외부 실행 환경으로 이루어진 에이전트의 구성을 보여 줍니다. 하네스가 먼저 입력과 컨텍스트를 모델에 넘기고, 모델은 그것을 바탕으로 응답이나 도구 호출을 하네스에 돌려줍니다.

표 1-4는 그림 1-1의 구성 요소를 설명합니다.

같은 모델이 도구가 없는 채팅에서는 답변만 하고, Claude Code 안에서는 파일 수정과 테스트까지 수행합니다. 차이를 만드는 것은 하네스입니다. 하네스가 하는 일은 여섯 가지입니다.

  • 루프 실행: 모델의 판단과 도구 실행을 작업이 끝날 때까지 반복합니다.
  • 도구 제공: 파일 읽기와 수정, 명령 실행 같은 기능을 모델에 제공합니다.
  • 컨텍스트 관리: 루프마다 모델에 넘길 정보를 정합니다.
  • 권한: 도구로 할 수 있는 동작의 범위를 통제합니다.
  • 기록: 결정과 진행 상황, 실행 과정을 남깁니다.
  • 검증: 결과를 받아들이기 전에 확인합니다.

여섯 가지는 실행 장치와 설정을 합쳐 하네스 전체가 하는 일로 요약한 것입니다. 루프 실행, 도구 제공, 컨텍스트 관리는 주로 실행 장치가 맡고, 권한, 기록, 검증은 실행 장치의 기능 위에 팀이 설정으로 범위와 기준을 정합니다. 설정의 역할은 컨텍스트 관리를 거쳐 모델에 전달됩니다(표 1-6).

하네스 엔지니어링

하네스의 설정은 맡길 업무마다 팀이 정해야 하므로, 그 설계를 하나의 일로 다룰 이름이 필요합니다. 이 책은 하네스 엔지니어링을 에이전트가 신뢰할 수 있는 결과를 내도록 모델 바깥의 작업 환경을 설계하는 일로 정의합니다. 구성 요소별 설계는 Chapter 2에서 다룹니다.

이 정의가 실제 개발에서 어떤 모습인지는 Codex의 사례에서 볼 수 있습니다. Codex는 2026년 2월 이 용어를 제목으로 한 글(Lopopolo, 2026)에서, 사람이 코드를 직접 작성하지 않는 개발 실험을 소개했습니다. 이 글에 따르면 개발 팀은 5개월 동안 약 100만 줄의 코드와 약 1,500개의 풀 리퀘스트(Pull Request)를 Codex로 생성했습니다. 풀 리퀘스트는 코드 변경을 저장소에 반영하기 전에 검토를 요청하는 단위입니다. 이 실험에서 밝힌 내용은 네 가지입니다.

  • 엔지니어는 코드를 직접 작성하지 않고, 작업 환경을 설계하고 의도를 문서로 밝히고 피드백 루프(결과를 확인하고 그 결과로 다음 작업을 수정하는 반복)를 만드는 일을 맡았습니다.
  • 이 실험은 초기 진행이 느렸던 원인을 Codex의 능력 부족이 아니라 충분히 정의되지 않은 환경에서 찾았습니다.
  • 작업이 실패하면 어떤 능력이 누락되었는지 묻고, 그 능력을 에이전트가 읽을 수 있고 검사로 강제되는 형태로 저장소에 추가했습니다.
  • 에이전트가 실행 중에 읽을 수 없는 지식은 에이전트에게 없는 지식으로 보고, 채팅이나 사람의 기억에 있던 결정을 저장소 문서로 옮겼습니다.

사람의 역할도 남았습니다. 사람은 작업의 우선순위를 정하고, 사용자 의견을 수용 기준으로 정리하고, 결과를 검증했습니다. 수용 기준은 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 이 사례에서 개선한 대상은 모델이 아니라 저장소 문서, 검사 규칙, 검증 절차 같은 작업 환경이었습니다.

하네스 안의 프롬프트와 컨텍스트

앞 절의 사례에서 개선한 작업 환경에는 모델에 넘기는 입력도 들어 있습니다. 하네스가 루프마다 모델에 넘기는 입력은 프롬프트와 컨텍스트이므로, 이 책은 둘을 하네스 안의 설계 대상으로 봅니다. 층마다 답해야 할 설계 질문은 서로 다르므로, 이 책은 프롬프트, 컨텍스트, 하네스를 묶어 세 설계 층이라고 부릅니다. 모델은 공급사가 제공하는 실행 엔진이고, 프롬프트, 컨텍스트, 하네스의 설정은 모델을 사용하는 팀이 설계하는 대상입니다.

프롬프트는 모델에 주는 지시문입니다. 컨텍스트는 모델이 응답을 생성할 때 입력되는 정보 전체이며, 프롬프트는 그 일부입니다. 이 책에서 프롬프트는 사람이 이번 작업에 입력하는 요청을 가리킵니다. 제품이 미리 포함하는 시스템 프롬프트와 규칙 문서는 하네스가 루프마다 모델에 넘기는 컨텍스트의 일부로 다룹니다. 표 1-5는 층별 정의와 설계 질문을 보여 줍니다.

세 층은 모두 팀이 정하는 값이므로, 같은 모델을 사용해도 세 층을 어떻게 설계했는지에 따라 팀마다 결과가 달라집니다.

에이전트 루프와 종료 조건

세 설계 층 가운데 하네스가 실제로 어떻게 작동하는지는 에이전트 루프에서 드러납니다. 하네스의 다섯 구성 요소(Chapter 2)는 루프의 단계마다 서로 다른 시점에 작동합니다. Claude Code의 Agent SDK(Claude Code의 에이전트 루프를 프로그램에서 실행하는 개발 도구) 문서가 설명하는 실행 루프를 이 책은 다섯 단계로 정리합니다(Anthropic, 2026b).

  • 컨텍스트 구성: 하네스가 요청과 함께 시스템 프롬프트, 도구 정의, 대화 이력을 모아 모델에 넘깁니다.
  • 판단과 응답: 모델이 현재 상태를 판단해 텍스트로 답하거나 도구 호출을 요청합니다.
  • 권한 확인: 도구 호출 요청이 있으면, 하네스가 실행 전에 허용(allow), 확인(ask), 거부(deny)를 판단합니다.
  • 도구 실행: 하네스가 요청된 도구를 실행하고 결과를 대화 이력에 추가한 뒤 컨텍스트 구성부터 반복합니다. 이 왕복 한 번을 턴이라고 부릅니다.
  • 최종 응답: 모델이 도구 호출 없이 응답하면 루프가 끝나고, 최종 응답과 토큰 사용량, 비용, 세션 ID가 반환됩니다.

그림 1-2는 다섯 단계와 그 사이의 분기를 보여 줍니다. 그림은 최종 응답 앞에 완료 기준 확인을 하나 더 둡니다. 모델이 도구 호출 없이 응답하면 일을 끝냈다고 판단한 것이지만, 그 판단이 맞는지는 따로 확인해야 하기 때문입니다. Claude Code에서는 훅(Hook, 정해진 시점에 자동으로 실행되는 명령)으로 이 확인을 추가합니다. 모델이 응답을 마치려 할 때 실행되는 Stop 훅이 완료 기준을 검사하고, 미달이면 종료를 막아 모델이 작업을 이어 가게 합니다(Anthropic, 2026d). 완료 기준은 팀이 설정의 검증에서 정합니다(Chapter 7의 완료 기준).

표 1-6은 루프의 단계별로 작동하는 구성 요소를 보여 줍니다.

도구 실행 앞에서는 권한이 작동합니다. Agent SDK 문서에 따르면 거부된 도구 호출은 실행되지 않고, 모델은 거부 메시지를 결과로 받습니다. 모델은 다른 방법을 찾거나, 진행할 수 없다고 보고합니다.

Stop 훅이 없으면 루프는 모델이 스스로 끝낼 때까지 계속됩니다. 문서는 범위가 분명한 작업에서는 문제가 없지만, 열린 요청에서는 루프가 오래 실행될 수 있다고 설명합니다. 그래서 하네스는 두 가지 상한을 둡니다. 턴 상한은 도구를 사용한 턴의 수를, 비용 상한은 지출 금액을 제한합니다. 문서는 운영 환경의 에이전트에 비용 상한을 기본으로 두라고 권합니다(Anthropic, 2026b).

상한에 도달하면 루프는 작업을 마치지 못한 채 끝나고, 결과에 종료 사유가 남습니다. 종료 사유는 정상 완료, 턴 상한 도달, 비용 상한 도달, 실행 중 오류 등으로 구분됩니다. 상한에 도달한 결과는 완료로 판정하지 않습니다(Chapter 7의 완료 보고). 두 상한의 값과, 상한에 도달했을 때 세션을 재개할지 중단할지는 작업을 맡기기 전에 정합니다. 비용 상한의 기준은 Chapter 9의 비용 관리와 연결됩니다.

Codex도 같은 구조의 루프를 사용합니다. Codex는 하네스가 모든 Codex 제품에 공통인 에이전트 루프를 제공한다고 설명합니다. 턴이라는 말의 범위는 두 제품이 다릅니다. Agent SDK 문서의 턴은 도구 호출 왕복 한 번이고, Codex 글의 턴은 사용자 메시지 하나에 대한 처리 전체입니다. 한 턴 안에서 모델 추론과 도구 호출이 여러 번 반복됩니다. Codex는 에이전트가 한 턴에서 수백 번의 도구 호출을 할 수 있다고 설명합니다. 그러면 컨텍스트 윈도를 모두 소진할 수 있습니다(OpenAI, 2026). 두 제품을 함께 운영한다면 턴 상한을 정하기 전에 제품마다 턴이 무엇을 세는지 확인해야 합니다.

프롬프트 엔지니어링과 컨텍스트 엔지니어링

앞에서 프롬프트와 컨텍스트를 하네스 안의 두 설계 층으로 정했습니다. 두 층을 다루는 방법에는 이미 이름이 있고, 두 방법의 범위를 구분해야 하네스 엔지니어링이 무엇을 더 다루는지 분명해집니다. 프롬프트 엔지니어링(Prompt Engineering)은 원하는 결과를 얻도록 지시문을 작성하고 구성하는 방법입니다. 컨텍스트 엔지니어링(Context Engineering)은 모델이 응답을 생성하는 동안 필요한 정보를 선별하고 유지하는 전략입니다. 두 정의는 Claude Code가 2025년 9월 공개한 글(Rajasekaran 외, 2025)을 따릅니다. 이 글에서 Claude Code는 컨텍스트 엔지니어링을 프롬프트 엔지니어링이 발전한 단계로 설명합니다. 두 방법은 세 가지 점에서 다릅니다.

  • 대상: 프롬프트 엔지니어링은 지시문을 다룹니다. 컨텍스트 엔지니어링은 시스템 지시, 도구 설명, 외부 자료, 대화 이력을 포함한 입력 전체를 다룹니다.
  • 시점: 프롬프트 작성은 한 번으로 끝나는 작업입니다. 컨텍스트는 모델에 무엇을 넘길지 정할 때마다 다시 선별합니다.
  • 제약: 컨텍스트 엔지니어링은 컨텍스트 윈도의 한도 안에서 정보를 선별해야 합니다. Claude Code는 컨텍스트의 토큰이 늘수록 모델이 정보를 정확히 기억해 내는 능력이 떨어진다고 설명합니다. 컨텍스트 윈도의 사용 현황을 확인하는 위치는 Chapter 5의 한정된 자원에서 다룹니다. 그래서 많은 정보를 제공하는 것보다 필요한 정보를 선별하는 것이 중요합니다.

두 방법은 모델에 넘기는 입력을 다룹니다. 하네스 엔지니어링은 그 입력을 포함해 루프, 도구, 권한, 기록, 검증까지 다룹니다.

소프트웨어 엔지니어링과의 접점

하네스 설계는 처음부터 새로 배울 일만은 아닙니다. 하네스 설계는 소프트웨어 엔지니어링의 기존 활동과 대응합니다. 소프트웨어 엔지니어링은 요구 사항 정의, 설계, 개발, 테스트, 배포, 운영으로 이어지는 개발의 전 과정을 다루는 분야입니다. 이 책은 이 분야를 하네스를 이해하는 데 필요한 범위에서만 다룹니다. 표 1-7은 활동별로 대응하는 하네스 설계를 보여 줍니다.

요구 사항을 명확히 정의하는 능력은 에이전트에게 작업을 지시하는 능력으로 이어집니다. 테스트 기준을 정하는 능력은 에이전트의 결과를 검증하는 능력으로 이어집니다.

결과를 개선할 수 있는 영역

모델은 공급사가 개선하지만, 하네스의 설정은 에이전트를 사용하는 팀이 정합니다. 따라서 결과를 개선할 때 직접 변경할 수 있는 대상은 모델 바깥의 세 설계 층, 곧 프롬프트, 컨텍스트, 하네스의 설정입니다.

문제가 생기면 먼저 원인이 어느 층에 있는지 분류합니다. 표 1-8은 대표적인 증상과 원인이 있는 층, 점검할 항목을 대응시킨 것입니다.

이 분류는 작가의 작업에서 나왔습니다. 이 책의 작가는 앞선 책 「생성형 AI, 묻고 확인하고 활용하기」를 AI 에이전트와 함께 만들며 73차례 검수(원고를 읽고 수정할 곳을 찾는 점검)를 거쳤습니다. 초기에는 어휘, 조사, 표 번호처럼 같은 종류의 실수를 사람이 매번 찾았습니다. 큰 결정을 집필 중에 여러 번 뒤집는 일도 있었습니다. 해결 방법은 모델 교체가 아니라 작업 환경의 보완이었습니다.

  • 반복된 실수는 자동 검사 규칙으로 만들었습니다.
  • 큰 결정은 번호를 매겨 기록하고, 결정을 변경할 때는 이전 결정을 남겼습니다.
  • 원고 작성과 검수를 서로 다른 에이전트에게 나눠 맡겼습니다.

이후 사람은 판단이 필요한 항목만 검토하는 구조로 작업을 정리했습니다.

모델 성능이 향상되면 하네스가 필요 없다는 의견도 있습니다. 모델 성능의 향상은 한 번의 응답 품질을 높입니다. 그러나 어떤 자료에 접근할지, 어떤 작업을 사람이 승인할지, 무엇을 기록할지는 팀이 정할 일입니다. Claude Code도 모델이 발전해도 컨텍스트를 한정된 자원으로 다루는 일은 계속 중요하다고 밝혔습니다(Rajasekaran 외, 2025).

같은 모델로 더 나은 결과를 얻으려면, 모델을 교체하기 전에 하네스의 설정을 점검합니다. 앞에서 정의한 하네스 엔지니어링을 업무의 질문으로 정리하면, 무엇을 맡기고, 어떤 정보를 주며, 어디까지 허용하고, 어떻게 검증할지를 정하는 일이 하네스 엔지니어링입니다.

확인 방법

하네스가 맡는 일은 제품의 명령과 실행 결과로 확인합니다. /로 시작하는 명령은 Claude Code를 실행한 뒤 입력창에 입력하는 명령이며, 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다. 표 1-9는 이 장에서 다룬 컨텍스트 구성, 권한 확인, 루프의 종료를 확인하는 위치입니다.

원칙과 점검 질문

에이전트의 결과가 기대와 다르면, 모델을 교체하기 전에 하네스의 설정을 먼저 점검합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트에서 제품이 맡는 실행 장치와 팀이 정하는 설정을 구분할 수 있습니까?
  2. 맡긴 작업의 턴 상한과 비용 상한, 상한에 도달했을 때의 처리가 정해져 있습니까?
  3. 최근 겪은 문제를 표 1-8의 증상에 대응하면, 원인은 프롬프트, 컨텍스트, 하네스 가운데 어느 층에 있습니까?
