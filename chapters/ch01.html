1장

같은 모델, 다른 점수

AI 에이전트의 성능은 모델만으로 결정되지 않습니다. 모델을 감싸는 하네스가 결과를 바꿉니다.

개요

이 장은 하네스 엔지니어링을 이해하는 데 필요한 기초 개념과, 하네스가 결과를 바꾼 실제 사례를 다룹니다. 이 장을 마치면 다음 내용을 설명할 수 있습니다.

  • AI 모델이 스스로 할 수 있는 일과 할 수 없는 일
  • 챗봇과 에이전트의 차이
  • 하네스의 정의, 구성 요소, 필요성
  • 에이전트가 작업 하나를 처리하는 단계
  • 모델을 바꾸지 않고 하네스만 바꿔 성능을 올린 사례

AI 모델 기초

이 책에서 모델은 대규모 언어 모델(LLM, Large Language Model)을 뜻합니다. 대규모 언어 모델은 많은 양의 글로 학습한 프로그램으로, 글을 입력받아 글을 출력합니다. OpenAI의 GPT, Anthropic의 Claude가 대규모 언어 모델입니다.

모델에 대해 먼저 알아야 할 사실은 다음과 같이 정리됩니다.

  • 입력과 출력은 글입니다. 모델에 보내는 입력을 프롬프트라고 하고, 모델이 돌려주는 출력을 응답이라고 합니다. 모델은 글을 토큰이라는 단위로 나눠 처리합니다. 토큰은 단어 하나 또는 단어의 일부입니다.
  • 모델은 스스로 행동하지 못합니다. 모델은 파일을 열거나, 명령을 실행하거나, 인터넷에 접속하지 못합니다. 모델이 할 수 있는 일은 입력을 읽고 응답을 만드는 것뿐입니다.
  • 모델은 호출 사이에 기억을 유지하지 않습니다. 모델에 입력을 보내 응답을 받는 한 번의 과정을 호출이라고 합니다. 모델은 이전 호출의 내용을 기억하지 않습니다. 대화를 이어 가려면 이전 대화 내용을 다음 입력에 다시 넣어야 합니다.
  • 한 번에 받을 수 있는 입력의 양에 한도가 있습니다. 이 한도를 컨텍스트 윈도라고 하고, 토큰 수로 표시합니다. 한 번의 호출에서 모델에 전달되는 입력 전체를 컨텍스트라고 합니다.
  • 모델은 회사의 서버에서 실행됩니다. 사용자의 프로그램은 API를 통해 모델을 호출합니다. API는 프로그램끼리 정해진 형식으로 요청과 응답을 주고받는 방법입니다.

에이전트 개념

에이전트는 모델이 도구를 사용해 목표한 작업을 끝까지 처리하는 시스템입니다. 챗봇은 질문 하나에 답변 하나를 돌려주고 끝납니다. 에이전트는 파일을 읽고, 코드를 고치고, 테스트를 실행하는 일을 작업이 끝날 때까지 여러 번 반복합니다.

에이전트의 핵심은 도구 호출입니다. 도구는 파일 읽기, 파일 수정, 명령 실행처럼 에이전트가 할 수 있는 행동 하나하나를 뜻합니다. 모델은 도구를 직접 실행하지 못하므로, 응답 안에 "이 도구를 이 값으로 실행해 달라"는 요청을 정해진 형식으로 적습니다. 이 요청을 도구 호출이라고 합니다. 실제 실행은 모델 바깥의 프로그램이 맡습니다.

하네스 정의

하네스는 에이전트에서 모델을 제외한 나머지 전부입니다. 이 책은 LangChain의 Vivek Trivedy가 정리한 정의를 따릅니다.

에이전트 = 모델 + 하네스

하네스는 모델 자신을 뺀 모든 코드, 설정, 실행 로직을 포함합니다. 하네스가 하는 일은 다음 네 가지로 나뉩니다.

  • 모델에 무엇을 보여 줄지 결정합니다. (입력 구성)
  • 모델이 어떤 행동을 요청할 수 있는지 정합니다. (도구 정의)
  • 모델이 요청한 행동을 실행하고, 결과를 다시 모델에 전달합니다. (도구 실행)
  • 작업을 언제 멈출지, 결과가 맞는지 확인합니다. (종료와 검증)

하네스는 모델과 환경 사이에 있습니다. 환경은 에이전트가 실제로 다루는 대상으로, 파일, 데이터, 외부 서비스의 API, 접근 권한을 포함합니다. 모델은 환경과 직접 연결되지 않고, 하네스를 거쳐서만 환경과 데이터를 주고받습니다.

Claude Code와 Codex는 하네스 제품입니다. Claude Code는 Anthropic의 Claude 모델을, Codex는 OpenAI의 GPT 모델을 호출하는 하네스입니다. Thoughtworks의 Birgitta Böckeler는 하네스를 두 부분으로 나눕니다.

외부 하네스
사용자가 덧붙이는 부분. 지시 파일, 훅, 스킬, 추가 도구 등

하네스 구성 요소

하네스는 여덟 가지 요소로 구성됩니다.

표에 나온 용어를 정리합니다.

시스템 프롬프트
하네스가 모든 호출의 입력 맨 앞에 넣는 기본 지시문
지시 파일
프로젝트 폴더에 두는 규칙 파일. Claude Code는 CLAUDE.md, Codex는 AGENTS.md를 읽습니다.
MCP 서버

서브에이전트
큰 작업의 일부를 맡아 따로 실행되는 하위 에이전트
훅, 미들웨어

린트 검사

샌드박스

트레이스
에이전트의 모델 호출, 도구 실행, 결과를 시간 순서로 남긴 실행 기록

작업 처리 흐름

에이전트는 "모델 호출, 도구 실행, 결과 전달"을 작업이 끝날 때까지 반복합니다. 이 반복을 에이전트 루프라고 합니다. 사용자가 코딩 에이전트에 "테스트가 실패하는 버그를 고쳐 줘"라고 요청하면, 일반적인 하네스는 다음 순서로 처리합니다.

  1. 하네스가 시스템 프롬프트, 지시 파일, 사용자 요청, 사용할 수 있는 도구 목록을 묶어 모델을 호출합니다.
  2. 모델이 "테스트 실행 명령을 실행해 달라"는 도구 호출을 응답합니다.
  3. 하네스가 이 명령이 허용된 범위인지 권한을 확인한 뒤 명령을 실행합니다.
  4. 하네스가 실행 결과(실패한 테스트와 오류 메시지)를 컨텍스트에 추가해 모델을 다시 호출합니다.
  5. 모델이 원인이 되는 파일을 읽는 도구 호출을 응답하고, 하네스가 파일 내용을 전달합니다.
  6. 모델이 파일 수정 도구 호출을 응답하고, 하네스가 파일을 수정합니다.
  7. 모델이 테스트를 다시 실행하는 도구 호출을 응답하고, 하네스가 실행 결과를 전달합니다.
  8. 테스트가 통과하면 모델이 도구 호출 없이 "완료했습니다"라는 응답을 돌려줍니다.
  9. 하네스가 종료 조건을 확인하고 사용자에게 결과를 보고합니다.

이 흐름에서 모델이 한 일은 응답 작성뿐입니다. 명령 실행, 권한 확인, 결과 전달, 종료 판단은 모두 하네스가 했습니다. 따라서 하네스의 설계가 바뀌면 같은 모델로도 결과가 달라집니다.

하네스 필요성

모델의 성능이 높아져도 하네스 설계는 필요합니다. 이유는 다섯 가지입니다.

  • 같은 모델로도 결과가 달라집니다. 이 장의 사례에서 LangChain은 모델을 그대로 두고 하네스만 바꿔 벤치마크 점수를 13.7포인트 올렸습니다.
  • 모델은 스스로 완료를 과신합니다. 에이전트는 자기 코드를 다시 읽고 괜찮다고 판단하면 테스트 없이 작업을 끝냅니다. 테스트 실행 같은 검증은 하네스가 강제해야 합니다.
  • 비용과 속도는 하네스가 결정합니다. 모델 사용 요금은 입력과 출력의 토큰 수에 따라 정해집니다. 컨텍스트에 무엇을 넣고 뺄지, 어느 단계에서 추론을 얼마나 쓸지는 하네스가 정합니다.
  • 사고는 권한 설계로 막습니다. 에이전트가 운영 데이터베이스를 삭제하는 사고는 모델의 성능이 아니라, 삭제 명령을 실행할 수 없게 만든 권한 설계로 막습니다. 9장에서 다룹니다.
  • 모델이 바뀌어도 하네스는 남습니다. 모델은 몇 달 단위로 새 버전이 나옵니다. 하네스에 쌓은 규칙, 검증, 기록은 새 모델에서도 그대로 씁니다. 단, 새 모델에 맞춘 재조정은 필요합니다.

하네스 용어의 역사

하네스는 소프트웨어 테스트 분야에서 먼저 쓰인 용어입니다. 테스트 하네스는 테스트 대상 코드를 실행하고 결과를 확인하는 프로그램 묶음을 뜻합니다. 에이전트 분야에서는 처음에 스캐폴딩(scaffolding)이라는 용어가 주로 쓰였고, 2025년 말부터 하네스가 함께 쓰였습니다. 2026년 2월에는 여러 회사와 개인이 몇 주 사이에 "하네스 엔지니어링"이라는 용어로 글을 발표했습니다.

하네스의 의미는 "모델을 시험하는 틀"에서 "모델이 작업을 잘 수행하도록 설계하는 대상"으로 바뀌었습니다. 이 책은 두 번째 의미로 하네스를 다룹니다. 용어를 처음 쓴 사람이 누구인지는 이 책에서 판정하지 않습니다.

벤치마크 기초

벤치마크는 같은 과제 묶음으로 여러 에이전트의 성능을 비교하는 평가 방법입니다. 점수는 전체 과제 중 성공한 과제의 비율(%)로 표시합니다. 이 장의 사례는 두 가지 벤치마크를 사용합니다.

Terminal Bench 2.0
터미널(명령어 입력 창)에서 수행하는 과제 89개로 구성된 벤치마크. 머신러닝, 디버깅, 생물학 등 여러 분야의 과제를 포함합니다.
SWE-bench Verified
실제 오픈소스 프로젝트의 GitHub 이슈를 에이전트가 해결하는지 평가하는 SWE-bench에서, 사람이 검토해 걸러 낸 과제 묶음

벤치마크가 평가하는 대상은 모델 하나가 아니라 모델과 하네스를 합친 에이전트 전체입니다. 따라서 같은 모델도 하네스에 따라 점수가 달라집니다. 이 책의 모든 점수는 발표 주체가 스스로 측정해 발표한 값입니다.

사례: 모델 고정, 하네스 변경만으로 13.7포인트 향상

3대상 deepagents-cli, 사용 모델 OpenAI gpt-5.2-codex

사례 요약

LangChain은 에이전트 개발 프레임워크를 만드는 회사입니다. LangChain은 2026년 2월, 자사 코딩 에이전트 deepagents-cli를 개선한 과정을 공개했습니다. 모델은 OpenAI의 gpt-5.2-codex로 고정하고 하네스만 수정해, Terminal Bench 2.0 점수를 52.8%에서 66.5%로 13.7포인트 올렸습니다. 순위는 30위권 밖에서 5위권으로 올랐습니다. 이 사례에서 비교 대상은 회사가 아니라 deepagents-cli라는 하네스입니다.

버전 주석 (2026년 9월 29일 확인)

  • Ogpt-5.2-codex: 사례 당시 모델입니다. OpenAI는 2026년 9월 22일 GPT-6 Sol, GPT-6 Luna를 Codex와 API에 공개했습니다. (OpenAI 개발자 커뮤니티 공지)
  • 3Terminal Bench 2.0: 사례 당시 버전입니다. 현재 최신 버전은 Terminal-Bench 4.0입니다. (tbench.ai)
  • 3deepagents-cli: 현재 최신 버전은 0.3.0(2026년 8월 24일)입니다. (PyPI)

실험 환경

LangChain은 Harbor라는 도구로 실험을 관리했습니다. Harbor는 Daytona 샌드박스에서 에이전트를 실행하고, 결과를 검증하고, 점수를 매겼습니다. 에이전트의 모든 행동은 소요 시간, 토큰 수, 비용과 함께 LangSmith에 기록되었습니다. 이 실험도 샌드박스, 자동 채점, 실행 기록이라는 하네스 위에서 실행되었습니다. 이 기록이 개선 여부를 판정하는 근거입니다. 이 주제는 14장에서 다룹니다.

조절 요소 선별: 세 가지 집중

하네스에서 조절할 수 있는 요소는 시스템 프롬프트, 도구, 훅이나 미들웨어, 스킬, 서브에이전트 위임, 메모리 등 여러 가지입니다. LangChain은 이 중 시스템 프롬프트, 도구, 미들웨어 세 가지만 수정했습니다. 미들웨어는 모델 호출과 도구 실행 앞뒤에 실행되는 코드로, Claude Code의 훅과 같은 역할을 합니다. 기본 설정으로 측정한 첫 점수는 52.8%였습니다.

개선 방법: 실패 기록 분석 반복 루프

LangChain은 실행 기록(트레이스)을 모으고, 여러 분석용 에이전트를 동시에 실행해 오류를 분석하게 했습니다. 이어 메인 에이전트가 분석 결과를 종합해 하네스 수정안을 만들었습니다. LangChain은 이 과정을 다시 쓸 수 있도록 에이전트 스킬로 만들었습니다. 사람은 마지막 단계에서 수정안을 검토할 수 있었지만, 검토는 필수 단계가 아니었습니다.

LangChain은 특정 과제에만 맞춘 수정이 다른 과제의 성능을 떨어뜨릴 수 있다고 경고했습니다. 이 현상을 과적합이라고 하며, 하네스 개선에서도 과적합이 발생합니다.

효과 확인 변경 네 가지

  • 자기 검증 강제: 프롬프트에 검증 단계를 넣고, 종료 직전 미들웨어로 요구사항 대비 검증을 강제
  • 환경 정보 사전 주입: 디렉터리 구조, 도구 위치, 채점 방식, 남은 시간을 시작 시 제공
  • 반복 실수 루프 차단: 파일별 편집 횟수가 기준을 넘으면 접근 방식 재검토 문구 추가
  • 단계별 추론 계산량 배분: 계획과 검증은 높은 추론 강도, 구현은 한 단계 낮은 추론 강도. 최종 66.5%

첫째, 자기 검증 강제. 가장 많은 실패는 에이전트가 자기 코드를 다시 읽고 괜찮다고 판단한 뒤 테스트 없이 끝내는 경우였습니다. LangChain은 시스템 프롬프트에 계획과 탐색, 구현, 검증, 수정의 네 단계를 넣었습니다. 검증 단계에서는 테스트를 실행하고, 출력을 끝까지 읽고, 자기 코드가 아니라 원래 요구사항과 비교하도록 지시했습니다. 여기에 에이전트가 작업을 끝내려는 순간 요구사항 대비 검증을 한 번 더 실행하게 만드는 미들웨어를 추가했습니다. 프롬프트는 검증을 권하고, 미들웨어는 검증을 강제합니다.

둘째, 환경 정보 사전 주입. LangChain은 에이전트가 시작할 때 현재 디렉터리와 상위, 하위 디렉터리 구조를 파악하고, Python 같은 도구의 설치 위치를 찾아 컨텍스트에 넣는 미들웨어를 만들었습니다. 에이전트가 이 정보를 직접 찾게 하면 탐색 과정에서 실수가 생기기 때문입니다. 또 결과물이 자동 테스트로 채점된다는 점, 요구사항에 적힌 파일 경로를 정확히 지켜야 한다는 점, 예외 경우도 확인해야 한다는 점을 알렸습니다. 시간 제한이 있는 과제에서는 남은 시간을 경고해 검증 단계로 넘어가게 했습니다.

셋째, 반복 실수 루프 차단. 에이전트는 한 번 정한 계획에서 벗어나지 못하고, 잘못된 접근을 조금씩 바꿔 가며 반복했습니다. 한 기록에서는 같은 방식을 열 번 넘게 반복했습니다. LangChain은 파일별 편집 횟수를 세다가 기준을 넘으면 "접근 방식을 다시 검토하라"는 문구를 컨텍스트에 추가하는 미들웨어를 만들었습니다. LangChain은 이 장치를 현재 모델의 약점을 보완하는 임시 장치로 규정했고, 모델이 개선되면 제거될 수 있다고 밝혔습니다.

넷째, 단계별 추론 계산량 배분. 추론 강도는 모델이 응답 전에 문제를 검토하는 데 쓰는 계산량입니다. gpt-5.2-codex는 추론 강도를 low, medium, high, xhigh 네 단계로 설정할 수 있습니다. 모든 단계를 가장 높은 xhigh로 실행하면 시간 초과가 잦아 점수가 53.9%였고, high로 실행하면 63.6%였습니다. LangChain은 계획과 검증 단계에 높은 추론 강도를, 구현 단계에 한 단계 낮은 추론 강도를 쓰는 방식을 택했고, 최종 점수는 66.5%였습니다. 추론 강도를 최대로 올리면 오히려 점수가 떨어졌습니다.

같은 하네스, 다른 모델

3대상 deepagents-cli (이전 버전 하네스), 사용 모델 Anthropic Claude Opus 4.6

LangChain은 이전 버전의 하네스로 Claude Opus 4.6을 시험한 점수가 59.6%라고 밝혔습니다. 이 점수는 gpt-5.2-codex보다 낮았습니다. LangChain은 Claude에 대해서는 같은 개선 과정을 실행하지 않은 것을 이유로 들었습니다. 또 OpenAI와 Anthropic의 프롬프트 작성 가이드가 서로 다르다는 점을 들어, 하네스는 모델에 맞춰 조정해야 한다고 결론 내렸습니다.

버전 주석 (2026년 9월 29일 확인)

  • AClaude Opus 4.6: 현재도 운영 중인 모델입니다. 최신 Opus는 2026년 9월 22일 공개된 Claude Opus 5.5입니다. (Anthropic 발표)

검증 중심 설계, 필요한 정보의 사전 제공 같은 원칙은 모델과 관계없이 적용됩니다. 구체적인 설정은 모델마다 다시 조정해야 합니다.

대조 사례: 최소 스캐폴드와 모델 자율

ASWE-bench 에이전트

Anthropic은 2024년 10월, 업그레이드된 Claude 3.5 Sonnet이 SWE-bench Verified에서 49%를 기록해 당시 최고 기록인 45%를 넘었다고 발표했습니다. Anthropic은 이 발표에서 에이전트 구성도 함께 공개했습니다. Anthropic은 SWE-bench가 모델 하나가 아니라 모델과 스캐폴딩을 합친 에이전트 전체를 평가한다는 점, 같은 모델도 스캐폴딩에 따라 성능이 크게 달라진다는 점을 강조했습니다. 스캐폴딩은 하네스와 같은 뜻으로 쓰인 용어입니다.

버전 주석 (2026년 9월 29일 확인)

  • AClaude 3.5 Sonnet(claude-3-5-sonnet-20241022): 2025년 10월 28일 퇴역했습니다. Anthropic이 권장하는 대체 모델은 claude-sonnet-4-6입니다. (Anthropic 모델 퇴역 문서)
  • 3SWE-bench Verified: 현재도 운영 중인 벤치마크입니다. (swebench.com)

이 에이전트는 deepagents-cli와 반대 방향을 택했습니다. deepagents-cli가 미들웨어를 여러 겹 쌓았다면, SWE-bench 에이전트는 하네스 장치를 최소화하고 판단을 모델에 맡겼습니다. 에이전트에는 프롬프트 하나, bash 명령 실행 도구, 파일 보기와 수정 도구만 주어졌습니다. 에이전트는 모델이 완료를 판단하거나 입력이 20만 토큰을 넘을 때까지 실행되었고, 작업 단계의 전환도 모델이 판단했습니다.

Anthropic은 채점용 테스트를 모델이 볼 수 없어서, 실제로는 실패했는데 모델이 성공했다고 판단한 경우가 많았다고 밝혔습니다. deepagents-cli 사례와 같은 문제입니다. 에이전트가 작업 완료를 과신하는 문제는 7장과 11장에서 다룹니다.

Anthropic은 두 도구의 설명과 사양을 다듬는 데 가장 많은 노력을 들였다고 밝혔습니다. 이 에이전트는 루프 밖의 장치 대신 도구 설계로 에이전트를 제어했습니다. 도구 설계는 4장에서 다룹니다.

두 설계의 우열은 이 비교로 판정할 수 없습니다. 발표 시점, 모델, 벤치마크가 모두 다르기 때문입니다. 공통점은 두 사례 모두 모델을 고정한 채 모델 바깥을 설계해 결과를 바꿨다는 것입니다.

문제 분석: 모델 문제와 하네스 문제 구분

에이전트가 실패하면 먼저 실패가 어느 층에서 생겼는지 구분합니다. 이 책은 에이전트를 세 층으로 나눕니다.

모델
입력을 읽고 판단해 응답을 만드는 능력 자체
하네스
모델에 무엇을 보여 주고, 어떤 도구를 쓰게 하고, 언제 멈추게 하고, 결과를 어떻게 확인할지 정하는 구조
환경
파일 시스템, API, 권한, 데이터처럼 에이전트가 실제로 다루는 대상

deepagents-cli 사례의 실패를 이 기준으로 나누면 표 1-5와 같이 정리됩니다.

네 건 모두 겉보기 원인은 모델이었지만, 실제 수정은 모두 하네스에서 이루어졌습니다. 모든 실패가 하네스로 해결되지는 않습니다. 모델이 모르는 지식이나 모델이 풀 수 없는 추론은 하네스로 보완할 수 없습니다. 따라서 실패를 만나면 모델 교체보다 하네스 점검을 먼저 합니다.

성능 문제를 만나면 모델을 바꾸기 전에 하네스를 먼저 점검한다.

하네스 해법 정리

두 사례에서 쓰인 하네스 조절 요소를 정리했습니다. 각 요소는 이후 장에서 자세히 다룹니다.

내 프로젝트 적용

자신이 쓰는 에이전트로 같은 방법을 적용합니다. Claude Code와 Codex 모두 적용할 수 있습니다.

  1. 과제 묶음 만들기. 최근 에이전트에 맡긴 일 가운데 성공 여부를 판정할 수 있는 과제 10개를 고릅니다. "테스트가 통과한다", "페이지가 열린다"처럼 결과를 확인할 수 있어야 합니다.
  2. 기준선 기록. 현재 설정으로 10개를 실행하고, 성공 개수와 실패 내용을 기록합니다. 실패는 "무엇을 하다가 어떻게 끝났는지"를 한 줄로 적습니다.
  3. 실패를 층으로 나누기. 기록한 실패마다 모델, 하네스, 환경 중 어디서 생겼는지 표시합니다. 표 1-5를 참고합니다.
  4. 조절 요소 하나만 바꾸기. 가장 자주 나온 하네스 실패 하나를 골라 한 가지만 바꿉니다. 예: 지시 파일에 "끝내기 전에 테스트를 실행하고 요구사항과 비교하라"는 규칙 추가
  5. 같은 10개를 다시 실행. 기준선과 비교합니다. 성공 개수가 늘면 유지하고, 아니면 되돌립니다. 한 번에 여러 가지를 바꾸면 어떤 변경이 효과를 냈는지 알 수 없습니다.

과제 10개는 통계적으로 충분한 수가 아닙니다. 이 연습의 목적은 정확한 수치가 아니라, 실패 원인을 모델이 아니라 하네스에서 찾는 방법을 익히는 것입니다.

체크리스트

  • 모델은 글을 입력받아 글을 출력할 뿐, 스스로 행동하지 못한다는 점을 설명할 수 있다
  • 챗봇과 에이전트의 차이를 설명할 수 있다
  • 에이전트 = 모델 + 하네스의 의미를 설명할 수 있다
  • 에이전트 루프의 단계를 순서대로 설명할 수 있다
  • 에이전트의 실패를 모델, 하네스, 환경 중 어느 층의 문제인지 구분했다
  • 에이전트가 검증 없이 작업을 끝내는 경우가 있는지 확인했다
  • 하네스를 바꿀 때 한 번에 하나씩 바꾸고 전후를 비교한다
  • 모델을 바꿀 때 하네스도 다시 조정해야 한다는 점을 알고 있다
