Chapter 6 착수: 맡길 업무 선정과 작업 단위 분할

업무의 크기를 줄이는 것만으로는 위임의 결과가 정해지지 않고, 완료 여부를 확인할 수 있는 작업 단위로 업무를 나누었는지에 따라 결과가 달라집니다.

이 장에서는 에이전트(Agent)에게 업무를 맡기기 전에 하는 준비, 곧 맡길 업무의 선정과 작업 단위 분할을 다룹니다. 세션은 에이전트와 대화를 한 번 시작해 끝낼 때까지입니다. Chapter 1에서 본 것처럼 컨텍스트(Context)는 모델이 응답을 생성할 때 입력되는 정보 전체입니다. 이전 세션을 이어 가지 않고 새로 시작한 세션의 컨텍스트에는 지난 대화가 없습니다. 한 세션에서 다룰 수 있는 정보의 양도 컨텍스트 윈도(Context Window), 곧 모델이 한 번에 처리할 수 있는 토큰(Token, 모델이 텍스트를 나누어 처리하는 단위)의 범위로 제한됩니다. 그래서 범위가 큰 업무를 한 번에 맡기면 중간 상태를 추적하기 어렵고, 어디까지 끝났는지 검증하기도 어렵습니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다. 맡길 업무를 작업 단위로 나누는 일을 작업 단위 분할이라고 합니다.

준비는 세 단계입니다. 맡길 업무를 네 가지 기준으로 선정하고, 선정한 업무를 작업 단위로 나누어 목록에 기록하며, 필요하면 일부 작업을 하위 에이전트(Subagent)에 나눠 맡깁니다. 하위 에이전트는 Chapter 2에서 본 것처럼 특정 작업을 맡도록 따로 정의한 에이전트입니다. 작업 단위는 누가 수행하고 누가 완료를 확정하는지에 따라 세 종류로 나눕니다. Chapter 5가 에이전트가 읽을 정보를 정했다면, 이 장은 그 에이전트에게 업무를 어떤 단위로 건넬지를 정합니다.

먼저 선정 기준과 작업 단위 분할을 살펴보고, 여러 에이전트에 나눠 맡기는 방법을 익힌 뒤, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)의 작업 단위를 나누는 예제를 다룹니다.

  • 맡길 업무는 검증 가능성, 자료 접근성, 복구 가능성, 협의와 승인 조건의 네 기준으로 선정합니다.
  • 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나누고, 목록 파일에 단위마다 작업, 완료 기준, 확인 방법, 통과 값(끝났는지를 적는 true 또는 false)을 기록합니다.
  • 사람이 수행하거나 완료를 확정할 단위는 따로 정해, 에이전트가 그 단위에서 멈추게 합니다.
  • 하위 에이전트에 나눠 맡길 때는 맡기는 방식, 넘길 정보와 도구, 결과 확인, 비용 상한을 정하고, 요약으로 돌아온 결과는 근거와 대조합니다.

맡길 업무의 선정

모든 업무가 에이전트에 맡기기에 적합하지는 않습니다. 결과를 확인할 수 없거나 되돌릴 수 없는 업무를 그대로 맡기면, 잘못된 결과를 받아들이거나 복구하기 어려울 수 있습니다. 판단에 필요한 자료를 에이전트가 읽을 수 없거나 다른 조직의 결정을 기다려야 하는 업무는 에이전트가 끝까지 진행하지 못합니다. 그래서 맡길 업무는 네 가지 기준으로 선정합니다.

  • 검증 가능성: 완료 여부를 검사나 대조로 확인할 수 있는지를 봅니다.
  • 자료 접근성: 판단에 필요한 자료를 에이전트가 읽을 수 있는지를 봅니다.
  • 복구 가능성: 결과가 잘못되었을 때 이전 상태로 되돌릴 수 있는지를 봅니다.
  • 협의와 승인 조건: 다른 조직과의 협의나 결재를 기다리지 않고 끝낼 수 있는지를 봅니다.

네 기준을 모두 충족하는 업무부터 맡깁니다. 일부 기준을 충족하지 못한 업무도 위임 대상에서 제외할 필요는 없습니다. 자료를 정리해 주거나 확인 방법을 먼저 정해 기준을 채우고, 채울 수 없는 부분만 사람이 맡도록 업무를 나눕니다. 확인 방법은 구현 전에는 실패하고 구현 뒤에 통과해야 완료의 근거가 됩니다. 표 6-1은 기준마다 충족하지 못할 때의 조치를 정리합니다.

맡기기로 한 업무를 어떤 크기로 나눌지는 다음 절에서 봅니다.

작업 단위 분할

선정한 업무도 범위가 크면 한 세션 안에 끝나지 않아, 세션이 넘어갈 때 어디까지 끝났는지 확인하기 어렵습니다. 그래서 업무를 앞에서 정의한 작업 단위로 나누고, 단위마다 네 항목을 목록 파일에 적습니다.

  • 작업: 그 단위에서 할 일입니다. 목록에서는 단위를 가리키는 번호(id)와 함께 적습니다.
  • 완료 기준: 단위가 끝났다고 판정하는 조건입니다.
  • 확인 방법: 완료 기준을 확인하는 검사나 기록입니다.
  • 통과 값: 단위가 끝났는지를 적는 칸입니다. 새로 등록한 미완료 단위는 false이고, 완료를 확인한 단위는 true입니다.

에이전트가 세션마다 읽는 규칙 문서에는 통과 값이 false인 첫 단위부터 하나씩 처리하라고 적습니다. 이 목록 파일을 작업 단위 목록이라고 하며, Chapter 2와 3의 변경 요청 사항 예제에서 사용한 tasks.json이 그 예입니다. 작업 단위 목록은 Chapter 2에서 본 진행 기록, 곧 작업이 어디까지 진행되었는지 남긴 기록에 해당합니다.

이 방식을 뒷받침하는 공개 사례로 Claude Code의 장기 실행 글이 있습니다. 글은 여러 세션에 걸쳐 웹 애플리케이션을 개발한 실험에서 관찰한 실패 양상 두 가지를 보고합니다7.

  • 한 번에 전체 구현: 에이전트가 애플리케이션 전체를 한 번에 구현하려 했습니다. 구현 도중 컨텍스트 윈도가 가득 차, 다음 세션은 반쯤 구현되고 기록되지 않은 기능에서 시작했습니다.
  • 이른 완료 판단: 일부 기능이 구현된 뒤 시작한 세션의 에이전트가 진행된 내용을 보고 프로젝트 전체가 완료되었다고 판단했습니다.

글이 택한 방식은 기능 목록과 상태 기록을 두고 하나씩 진행하는 점진적 방식입니다. 실험에서는 첫 세션의 에이전트가 요구 사항을 200개가 넘는 기능 목록으로 작성하고, 모든 기능을 "실패" 상태(이 장의 통과 값 false에 해당)로 표시했습니다. 이후 세션의 에이전트에게는 한 번에 기능 하나만 작업하도록 지시했고, 글은 이 점진적 방식이 에이전트가 한 번에 너무 많은 작업을 시도하는 문제를 해결하는 데 결정적이었다고 설명합니다7.

작업 단위의 크기는 다음 세 가지로 정합니다.

  • 한 세션의 범위: 기능 하나나 변경 하나처럼, 한 세션 안에 끝나 컨텍스트 윈도를 채우지 않을 만큼으로 나눕니다.
  • 확인할 수 있는 범위: 완료 기준과 확인 방법을 한 줄씩 적을 수 있을 만큼으로 나눕니다. 확인 방법을 적을 수 없으면 단위가 너무 크거나, 사람이 판단할 부분이 섞였을 수 있습니다.
  • 주체가 갈리는 곳: 다른 조직과의 합의처럼 사람이 수행할 부분은 에이전트가 수행할 부분과 섞지 않고 따로 뗍니다.

작업 단위를 모두 에이전트가 수행하고 검사로 끝낼 수 있는 것은 아닙니다. 그래서 작업 단위는 누가 수행하는지와 누가 완료를 확정하는지에 따라 세 종류로 나눕니다. 사람 가운데 되돌리기 어려운 동작과 작업 단위의 완료를 승인하는 사람을 승인자라고 합니다.

  • 합의가 필요한 단위: 다른 조직과 협의해야 끝나는 단위입니다.
    • 담당: 사람(승인자)이 수행합니다.
    • 확인: 합의 결과를 적은 결정 기록(무엇을 왜 정했는지 남긴 문서)으로 확인합니다.
    • 통과 값 변경: 승인자가 변경합니다.
  • 검사로 확인하는 단위: 에이전트가 수행하고 검사로 완료를 확인하는 단위입니다.
    • 담당: 에이전트가 수행합니다.
    • 확인: 확인 방법에 적힌 검사의 출력으로 확인합니다.
    • 통과 값 변경: 에이전트가 검사를 통과한 뒤 변경합니다.
  • 판단이 필요한 단위: 검사로 결과를 확인할 수 없어 사람이 판단하는 단위입니다.
    • 담당: 에이전트가 초안을 작성하고 승인자가 승인합니다.
    • 확인: 승인자의 승인으로 확인합니다.
    • 통과 값 변경: 승인자가 변경합니다.

합의가 필요한 단위는 표 6-1의 협의와 승인 조건을 충족하지 못한 부분을 떼어 수행까지 사람에게 맡긴 것이고, 판단이 필요한 단위는 검증 가능성을 충족하지 못한 부분을 떼어 완료 확정만 사람에게 맡긴 것입니다. 작업 단위 목록에는 종류를 적는 항목이 없으므로, 사람이 맡는 단위와 그 단위에서 에이전트가 할 일은 규칙 문서에 적습니다. 통과 값이 false인 첫 단위가 합의가 필요한 단위라면 다음 단위로 건너뛰지 않고 멈추게 하고, 판단이 필요한 단위라면 초안까지 작성한 뒤 승인을 기다리게 합니다.

작업 단위 하나는 네 단계로 처리합니다. 통과 값이 false인 첫 단위를 선택하고, 수행하고, 확인 방법대로 완료 기준을 확인한 뒤, 기준을 충족하면 통과 값을 true로 변경합니다. 완료 기준에 미달하면 같은 단위를 다시 수행하고, 같은 시험이 반복해 실패하면(Chapter 3의 예제에서는 세 번 연속) 중단하고 인계 메모(다음 세션이 이어받을 상황을 적은 기록)를 남깁니다.

그림 6-1의 왼쪽은 작업 단위 목록과 세 종류이고, 오른쪽은 단위 하나의 처리 순서입니다. 목록에서 오른쪽으로 가는 실선은 다음에 처리할 단위를 가리키고, 두 점선은 같은 단위를 다시 수행하는 경로와 다음 단위로 넘어가는 반복을 가리킵니다.

표 6-2는 그림 6-1의 구성 요소를 정리합니다.

그림 6-1은 목록의 단위를 하나씩 처리하는 순서를 보여 주고, 단위 하나를 검증하는 과정과 하네스(Harness)가 정한 수정 권한은 Chapter 3의 그림 3-1이 보여 줍니다. 한 세션이 끝난 뒤 다음 세션이 어디서 시작하는지는 Chapter 8의 인계 메모 작성에서 다룹니다.

작업 단위로 나누는 데에도 드는 수고가 있습니다. 단위마다 완료 기준과 확인 방법을 정해야 하고, 단위가 너무 작으면 목록을 관리하는 일이 늘어납니다. 그 대신 한 단위가 실패하면 실패한 단위만 다시 작업하면 되고, 어느 부분에서 실패했는지 목록으로 확인할 수 있습니다.

여러 에이전트에 나눠 맡기기

작업 단위를 하나씩 처리하는 동안 테스트 실행, 많은 파일을 읽는 자료 조사, 긴 로그 분석처럼 읽고 출력하는 양이 많은 작업이 주 대화(사람과 에이전트가 주고받는 세션의 대화)의 컨텍스트 윈도를 채울 수 있습니다. 이 문제는 Chapter 5의 미리 제공하는 정보와 필요할 때 찾는 정보에서 본 하위 에이전트 기법으로 줄일 수 있습니다. 이런 작업은 작업 단위 전체든 그 안의 하위 작업이든 다른 에이전트에 맡기고 결과의 요약만 받을 수 있습니다. 이 절은 하위 에이전트에 나눠 맡기는 방식의 작동, 비용, 나눠 맡길 때 정할 네 가지를 차례로 다룹니다.

일을 맡는 쪽은 하위 에이전트이고, 맡기는 쪽을 주 에이전트라고 합니다. 주 에이전트는 주 대화에서 사람과 일하는 에이전트입니다.

정의 파일(.claude/agents/ 폴더에 이름, 도구, 지시를 적은 파일)로 만든 하위 에이전트는 자기 컨텍스트 윈도에서 새 대화로 시작합니다. 이 하위 에이전트는 에이전트가 세션마다 읽는 규칙 문서(CLAUDE.md)는 읽지만 주 대화의 기록은 보지 않으며, 정의 파일에서 omitClaudeMd를 true로 정하면 규칙 문서도 읽지 않습니다23. 그래서 주 에이전트는 필요한 정보를 요청에 직접 담습니다. 주 대화를 물려받아 시작하는 포크(Fork)는 예외입니다. Claude Code는 포크 모드가 켜져 있으면 주 에이전트가 하위 작업을 포크로 스스로 시작할 수 있고, 포크 모드는 기본으로 켜져 있습니다. 포크를 사용하지 않으려면 환경 변수 CLAUDE_CODE_FORK_SUBAGENT를 0으로 두거나, 권한 설정의 금지 목록에 Agent(fork)를 적습니다23.

버전 주석 (2026년 10월) Claude Code 문서는 포크 모드가 v2.1.302부터, 대화형 터미널 세션에서는 v2.1.232부터 기본으로 켜져 있다고 안내합니다23.

하위 에이전트의 작업이 끝나면 그 최종 응답이 요약으로 주 에이전트에 돌아옵니다. 그래서 주 대화의 컨텍스트에는 하위 작업의 전체 기록 대신 요약이 더해집니다9. 하위 에이전트를 부르는 것도 도구 호출이므로, 맡긴 요청도 그 도구 입력으로 주 대화의 기록에 남습니다. 그래서 나눠 맡겨도 주 대화의 컨텍스트는 맡긴 요청과 돌아온 요약만큼 늘어납니다. 돌아온 요약은 하위 에이전트가 스스로 정리한 보고이므로, 주 에이전트는 요약만으로 완료를 판단하지 않고 근거를 확인합니다.

하위 에이전트는 실행하는 동안 자기 컨텍스트에서 따로 토큰을 사용하므로, 나눠 맡기면 전체 비용이 늘어날 수 있습니다23. Claude Code의 비용 문서는 하위 에이전트의 요청도 사용량에 포함된다고 설명합니다22.

비용 상한은 Chapter 1에서 본 것처럼 추정 지출 금액에 두는 한도입니다. Claude Agent SDK(Claude Code의 에이전트 루프를 프로그램에서 실행하게 하는 라이브러리) 문서는 SDK로 실행할 때 지정하는 비용 상한에 하위 에이전트의 지출도 합산된다고 설명합니다9. 비용 상한은 SDK 옵션이나 비대화형 실행(claude -p의 --max-budget-usd)에서 지정합니다. 이 명령 줄 옵션은 -p 실행에서만 사용할 수 있어 대화형 세션에는 이 상한이 없고, 상한과 비교하는 금액은 Claude Code가 계산한 추정치라 실제 청구와 다를 수 있습니다26. 구독 요금제에서는 금액 상한 대신 요금제의 사용 한도가 적용되고, 하위 에이전트의 요청도 그 한도에 합산됩니다22.

버전 주석 (2026년 10월) Agent SDK 문서는 Claude Code v2.1.217 이상에서 비용 상한에 이르면 새 하위 에이전트를 만들 수 없다고 안내합니다. 상한은 모델 응답이 도착한 뒤 비교하므로, 실제 지출은 상한에 이른 응답과 실행 중이던 하위 에이전트의 지출만큼 상한을 넘을 수 있습니다9.

그림 6-2에서 내려가는 화살표는 주 에이전트가 맡길 작업과 필요한 정보를 넘기는 방향이고, 올라가는 화살표는 하위 에이전트의 최종 응답이 요약으로 돌아오는 방향입니다. 맨 아래 비용 띠는 하위 에이전트의 지출이 전체 비용에 합산된다는 뜻입니다.

표 6-3은 그림 6-2의 구성 요소를 정리합니다.

나눠 맡길 때는 맡기는 방식, 넘길 정보와 도구, 결과 확인, 비용 상한의 네 가지를 정합니다.

  • 맡기는 방식: 여러 작업을 차례로 맡길지 동시에 맡길지의 순서입니다.
    • 정하는 방법: 앞 단위의 결과를 사용하면 순차로, 의존성이 없고 같은 파일을 수정하지 않으면 병렬로 맡깁니다. 파일을 수정하는 작업을 병렬로 맡길 때는 작업 폴더를 나누어 실행 환경을 격리합니다.
  • 넘길 정보와 도구: 하위 에이전트가 작업에 사용할 정보와 기능입니다.
    • 정하는 방법: 필요한 정보와 돌려받을 보고 형식(근거 파일, 검사 출력)을 요청에 담고, 맡긴 작업에 필요한 최소한의 도구만 지정합니다(Chapter 2의 도구 사용 범위와 제약).
  • 결과 확인: 돌아온 요약을 받아들이는 기준입니다.
    • 정하는 방법: 요약만으로 판단하지 않고, 검사 출력이나 바뀐 파일 같은 근거를 완료 기준과 대조합니다.
  • 비용 상한: 나눠 맡긴 작업까지 합친 전체 지출의 상한입니다.
    • 정하는 방법: 맡길 작업의 수와 작업마다 예상되는 사용량으로 상한을 정하고, -p 실행이나 SDK에서는 상한 옵션에 적습니다. 상한을 둘 수 없는 대화형 세션에서는 맡길 작업의 수를 미리 정하고, Chapter 3처럼 완료 판정과 중단 규칙으로 종료 조건을 정합니다.

Claude Code에서 여러 에이전트를 사용하는 기능에는 하위 에이전트 외에 에이전트 팀(Agent Team)도 있습니다. Claude Code 용어집에 따르면 하위 에이전트는 한 세션 안에서 일하고 맡긴 쪽에만 보고하지만, 에이전트 팀은 사용자가 팀에 속한 각 에이전트(팀원)와 직접 대화할 수 있습니다8. Claude Code의 비용 문서는 에이전트 팀에서 토큰 사용량이 팀 크기에 거의 비례한다고 안내합니다22. 용어집은 에이전트 팀을 기본으로 꺼져 있는 실험 기능으로 설명합니다8. 그래서 이 장은 하위 에이전트만 다루었습니다.

예제: 변경 요청 사항의 작업 단위 나누기

앞의 세 절을 변경 요청 사항에 적용합니다. 변경 요청 사항은 가상 프로젝트인 경비 정산 시스템 개편에 재무팀이 보낸 요청입니다. 직원이 경비를 돌려받으려고 올리는 정산 요청 화면에 프로젝트 코드(경비가 속한 프로젝트의 식별 번호)를 선택하는 항목을 추가해 달라는 내용입니다. Chapter 4의 예제: 변경 요청 사항의 영향 검토 요청하기에서 요청한 영향 검토를 거쳐 이 요청을 수용하기로 했다고 가정합니다.

Chapter 3의 예제는 변경 요청 사항을 다섯 작업 단위로 나눈 상태에서 구현 에이전트를 설계했습니다. 이 절은 그 다섯 단위가 앞의 선정 기준과 분할 방법으로 어떻게 정해지는지 보이고, 하위 에이전트에 나눠 맡길지를 판단합니다. 구현은 Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성에서 설계한 구현 에이전트가 주 에이전트로서 맡습니다.

먼저 표 6-1의 네 기준으로 판정합니다.

  • 검증 가능성: 일부만 충족합니다. 데이터 모델, 단위 테스트, 화면의 변경은 검사로 확인할 수 있습니다. 통합 테스트 시나리오(여러 기능을 이어서 확인하는 시험 절차)에 무엇을 포함할지는 검사로 확인할 수 없으므로, 이 부분은 에이전트가 초안을 작성하고 승인자가 승인하는 판단이 필요한 단위로 뗍니다.
  • 자료 접근성: 코드와 자료가 모두 저장소 안에 있어 충족합니다.
  • 복구 가능성: 작업 단위마다 변경을 확정(commit)해 Git(파일의 변경 이력을 저장하는 도구)의 기록으로 남기므로, 이전 상태로 되돌릴 수 있어 충족합니다.
  • 협의와 승인 조건: 프로젝트 코드 조회 방식은 연동 규격이 없어 인사팀과 합의해야 하므로 충족하지 못합니다. 합의는 승인자가 맡는 합의가 필요한 단위로 뗍니다.

검사로 확인할 수 있는 나머지 세 부분은 에이전트가 맡습니다. 다른 사람이 보는 원격 저장소에 commit을 올리는 push는 되돌리기 어렵지만, 이 예제에서는 에이전트에게 금지하고 사람이 직접 하므로 에이전트가 맡는 업무의 복구 가능성에는 들어가지 않습니다.

기준을 적용한 결과, 변경 요청 사항은 다섯 작업 단위로 나뉩니다. 작업 1은 합의가 필요한 단위, 작업 2, 3, 4는 검사로 확인하는 단위, 작업 5는 판단이 필요한 단위입니다. 다섯 단위의 확인 방법에는 Chapter 3의 예제에서 정한 시험과 파일이 나옵니다.

  • 수용 기준: 완료 기준 가운데 사람이 업무의 요구로 정한 조건입니다. 변경 요청 사항 문서(docs/CR.md)에 등록 화면의 코드 선택(1), 목록에 없는 코드 거부(2), 목록 화면의 코드 표시(3), 코드가 없는 기존 요청의 표시(4), 원본 자료(data/projects.csv) 보존(5)의 다섯 가지가 있습니다.
  • 수용 시험: 수용 기준을 자동으로 확인하는 시험 코드(acceptance/ 폴더)입니다. 시험 번호는 수용 기준의 번호와 같고, 사람이 작성하며 에이전트는 수정하지 않습니다.
  • 단위 테스트: 프로그램의 부품 하나가 정해진 대로 동작하는지 확인하는 시험(tests/ 폴더)이며, 에이전트가 수정합니다. 확인 방법의 tests는 이 시험을 가리킵니다.
  • 검사 스크립트(check.py): 단위 테스트와 수용 시험을 한 번에 실행하는 프로그램입니다. 두 시험의 실패와 건너뜀이 0건이고 수용 시험 5건이 모두 실행되며, 이름에 project_code가 든 단위 테스트가 1건 이상일 때만 종료 코드(명령이 끝날 때 돌려주는 값) 0으로 끝납니다. project_code는 코드에서 프로젝트 코드 항목을 가리키는 이름입니다.
  • 결정 기록 D-012: 결정 기록(DECISIONS.md)의 12번 결정이며, 프로젝트 코드는 인사 시스템이 하루 한 번 갱신하는 data/projects.csv를 사용한다는 결정입니다.
  • commit 확인: 사람이 commit을 승인하기 전에 바뀐 파일과 변경 내용을 보는 일입니다.

작업 1은 합의를 마쳐 목록에서 이미 통과 값이 true이므로, 에이전트는 작업 2부터 시작합니다.

표 6-4는 다섯 단위를 작업 단위 목록(tasks.json)과 같은 순서와 문구로 보여 줍니다. 담당 열은 목록에 없고 표에서 더한 것입니다. 목록에서는 확인 방법(결정 기록, 사람 승인)과, 규칙 문서의 작업 순서 절에 적은 작업 5의 통과 값을 변경하지 않는다는 지시가 사람이 확정하는 단위를 알려 줍니다.

작업 5는 두 주체가 나누어 맡습니다. 완료 기준 가운데 시나리오 초안 작성은 에이전트가 맡고, 통과 값을 true로 변경하는 승인은 승인자가 맡습니다. 에이전트가 초안을 작성해도 승인 전에는 통과 값이 false로 남습니다.

작업 4를 마치기 전에는 수용 시험 1, 2, 3이 실패하므로 check.py는 종료 코드 1로 끝납니다. 그래서 작업 2, 3의 완료는 check.py 출력에서 그 단위의 확인 방법에 적힌 시험의 결과로 판단합니다. 작업 3은 tests로 시작하는 줄의 실패 0건과 project_code 시험 1건 이상으로 봅니다. 수용 시험은 실패한 시험의 이름만 FAIL로 시작하는 줄에 나오므로(예: FAIL: test_1_form_offers_project_codes), 작업 2는 test_4와 test_5로 시작하는 시험이 FAIL 줄에 없으면 통과입니다.

작업 2의 확인 방법(수용 시험 4, 5 통과)은 구현 전에도 통과합니다. 이 시험들이 보는 것은 기존 요청이 이전처럼 표시되는지와 원본 자료(data/projects.csv)가 변경되지 않는지이고, 새 항목이 생겼는지는 보지 않기 때문입니다. 구현 전 상태(기준 상태)를 확인하는 부록의 실습 1. 실습 저장소와 기준 상태에서도 수용 시험은 4, 5만 통과합니다. 작업 3의 확인 방법은 이름에 project_code가 든 단위 테스트가 1건 이상인지도 보므로, 그런 시험이 0건인 기준 상태에서는 실패합니다. 이 확인은 시험의 이름만 세므로, 그 시험이 무엇을 확인하는지는 사람이 commit 확인에서 봅니다.

작업 2의 확인 방법은 구현 전에도 통과하므로, 그 방법만으로는 작업 2의 완료를 증명하지 못합니다. 작업 2의 통과 값이 false인 것은 시험이 실패해서가 아니라 단위를 아직 수행하지 않았기 때문입니다. 이 사례에서는 검토 하위 에이전트의 수용 기준 대조와, commit 확인 때 사람이 보는 변경 차이로 작업 2의 구현을 보완해 확인합니다. 확인 방법을 구현 전에는 실패하는 검사로 만드는 방법은 Chapter 7의 완료 기준을 검사로 변환에서 다룹니다.

작업 단위 목록은 에이전트가 읽고 통과 값을 변경할 수 있는 파일로 저장합니다. 장기 실행 글의 실험에서는 기능 목록을 JSON(항목 이름과 값을 정해진 규칙으로 적는 텍스트 형식) 파일로 저장하고, 에이전트에게 상태 항목만 수정하라고 지시했습니다. 글은 몇 차례 시도한 끝에, 모델이 Markdown 파일보다 JSON 파일을 부적절하게 변경하거나 덮어쓸 가능성이 낮다고 보고 JSON을 택했다고 설명합니다7.

파일 형식은 변경을 막는 장치가 아닙니다. 권한 규칙(Permission Rule, 도구 호출을 허용, 확인 요청, 금지로 나눠 정한 규칙)은 파일을 읽는 Read와 수정하는 Edit에 경로 패턴을 적어 적용하므로, tasks.json 안에서 통과 값만 수정하도록 제한하는 용도로는 사용하기 어렵습니다13. 정해진 시점에 자동으로 실행되는 명령인 훅(Hook)으로 도구 호출을 검사해 차단할 수도 있습니다10. 이 사례는 통과 값 밖의 항목이 수정되어도 사람이 commit 전에 찾아 되돌릴 수 있으므로, 수정할 수 있는 항목(통과 값)과 변경 주체를 규칙 문서에 지시로 적고 commit 전에 목록의 변경 차이를 검토합니다.

다음은 변경 요청 사항의 작업 단위 목록(tasks.json)에서 작업 2, 3의 두 줄을 그대로 옮긴 발췌입니다. 원본 파일은 단위마다 한 줄로 적고, 앞뒤의 대괄호와 나머지 단위의 줄은 생략했습니다. 중괄호 한 쌍이 작업 단위 하나이고, 콜론 앞은 항목 이름, 뒤는 값입니다. 통과 값은 "통과" 항목에 true 또는 false로 적습니다.

  {"id": "작업 2", "작업": "데이터 모델에 프로젝트 코드 항목 추가", "완료 기준": "정산 요청 데이터에 항목 추가, 기존 데이터 유지", "확인 방법": "python check.py의 수용 시험 4, 5 통과", "통과": false},
  {"id": "작업 3", "작업": "기존 단위 테스트 갱신", "완료 기준": "변경된 데이터 모델의 테스트 반영(project_code 시험 추가, 기존 시험 통과)", "확인 방법": "python check.py의 tests 실패 0건, project_code 시험 1건 이상", "통과": false},

다음은 나눠 맡길지의 판단입니다. 작업 2, 3, 4는 앞 단위의 결과를 이어서 사용합니다. 작업 3은 작업 2가 변경한 데이터 모델에 맞춰 테스트를 수정하고, 작업 4는 그 데이터 모델의 항목을 화면에서 선택하게 합니다. 그래서 세 단위를 병렬로 맡기지 않습니다.

앞 결과를 넘겨 하위 에이전트에 순차로 맡길 수도 있습니다. 이 사례는 단위마다 사람이 주 대화에서 commit을 확인하므로, 순차로 나눠 맡겨도 주 대화에서 할 일은 줄지 않고 비용과 확인할 요약만 늘어납니다. 그래서 구현 에이전트가 통과 값이 false인 첫 단위부터 직접 차례로 수행하게 했습니다. 이것은 이 사례의 운영 선택이며, 단위 사이에 의존성이 없고 수정하는 파일이 겹치지 않으면 하위 에이전트에 병렬로 맡길 수도 있습니다.

이 사례에서 하위 에이전트는 구현을 나눠 맡지 않고, Chapter 3의 검토 하위 에이전트로 변경 내용을 변경 요청 사항 문서의 수용 기준과 대조하는 데만 사용합니다(Chapter 3의 표 3-2). 앞의 네 가지 가운데 넘길 정보는 바뀐 파일 목록과 변경 내용(git status, git diff 출력)이고, 도구는 읽기 도구(Read, Grep, Glob)만 지정했습니다. 결과 확인을 위해 검토 하위 에이전트는 수용 기준마다 근거 파일과 줄 번호를 보고합니다. 주 에이전트와 사람은 보고에 적힌 근거를 직접 열어 확인합니다. 검토 하나만 나눠 맡기고 대화형으로 진행하므로, Chapter 3에서 정한 대로 이 사례는 비용 상한을 따로 두지 않았습니다.

구현 에이전트는 작업 단위를 마칠 때마다 그 단위의 변경을 commit하며, commit은 사람이 확인한 뒤 실행됩니다. 이 예제의 예상 결과에서는 작업 4까지 마치면 check.py가 종료 코드 0으로 끝나고, 작업 5는 에이전트가 초안을 작성한 뒤 승인자가 승인할 때까지 통과 값 false로 남습니다. 작업 단위 목록으로 구현을 진행하는 실습은 부록의 실습 5. 작업 단위로 구현에 있습니다.

실패를 예방하는 장치

변경 요청 사항을 작업 단위로 나누지 않거나 담당, 목록의 수정 범위, 확인 방법을 잘못 정하면 표 6-5의 실패가 생길 수 있습니다. 표 6-5는 실패마다 원인과 방지 장치를 정리하며, 작업 번호는 표 6-4의 번호입니다.

설정과 결과의 확인 방법

작업 단위가 끝났는지는 에이전트의 보고만으로 판단하지 않고, 파일과 검사 출력으로 확인합니다. 작업 단위 하나의 검증 방법은 Chapter 3의 설정과 결과의 확인 방법과 같고, 여기서는 목록과 commit 기록으로 진행 상태를 확인하는 방법을 더합니다. 명령은 터미널에서 부록 실습 1에서 만든 실습 폴더(expense-practice)로 이동한 뒤 실행하며, tasks.json은 실습 5에서 reference/tasks.example.json을 복사해 만든 파일입니다.

통과 값의 변경은 단위를 마친 뒤 commit하기 전에 git diff HEAD -- tasks.json으로 봅니다. 에이전트가 commit 확인을 요청하면, 그 요청에 답하기 전에 다른 터미널 창에서 이 명령을 실행합니다. 이 명령은 HEAD(마지막 commit)에 있는 파일과 비교합니다. commit하지 않았고 추적도 하지 않는 파일은 오류 없이 아무것도 출력하지 않아 변경이 없는 것처럼 보이므로, 목록을 만든 직후 첫 단위를 시작하기 전에 tasks.json을 commit해 둡니다(부록의 실습 5. 작업 단위로 구현).

스테이징은 commit할 변경을 git add로 미리 올려 두는 일입니다. git diff HEAD는 스테이징 여부와 관계없이 마지막 commit과 지금 파일을 비교합니다. 인자 없는 git diff는 스테이징하지 않은 변경만, git diff --cached는 스테이징한 변경만 보여 줍니다. git add를 한 번도 하지 않은 새 파일은 세 명령 어디에도 나오지 않으므로 git status로 봅니다. 출력에서 -가 붙은 줄은 변경 전, +가 붙은 줄은 변경 후의 내용입니다. tasks.json은 단위마다 한 줄이므로, 마친 단위의 줄이 -와 +로 한 번씩 나오고 두 줄의 차이가 "통과"의 값뿐이면 기준을 충족합니다. git log --oneline은 commit마다 한 줄로 commit의 짧은 식별 번호와 메시지를 보여 줍니다. 실습 시작 상태와 작업 단위 목록 추가 commit 뒤로 작업 단위마다 commit이 하나씩 있어야 합니다. commit 기록은 단위별 진행을 보여 줄 뿐이므로, commit 개수만으로 완료를 판단하지 않습니다. 표 6-6은 확인할 항목과 확인 기준을 정리합니다.
