Chapter 6 착수: 맡길 업무 선정과 작업 단위 분할

위임의 성패를 정하는 것은 업무의 크기가 아니라, 업무를 결과를 확인할 수 있는 단위로 나누었는지입니다.

에이전트(Agent)는 맡은 업무를 한 세션 안에서 처리하려고 하며, 세션이 끝나면 진행 중이던 상태를 기억하지 못합니다. 그래서 한 번에 큰 업무를 맡기면, 중간에 멈춘 작업과 완료되지 않은 기능이 기록 없이 남습니다. 따라서 착수 전에 맡길 업무를 선정하고, 완료 기준을 갖춘 작업 단위로 분할해야 합니다. 이 장에서는 맡길 업무의 선정 기준, 작업 단위 분할, 여러 에이전트에 나눠 맡기는 방법을 차례로 다루고 경비 정산 예제에 적용합니다.

  • 맡길 업무는 결과 확인, 자료 접근, 되돌림, 합의 필요의 네 기준으로 선정합니다.
  • 작업 단위는 한 세션에 끝나고 완료 여부를 확인할 수 있는 크기로 나누고, 목록에 완료 기준, 확인 방법, 통과 값을 기록합니다.
  • 서로 독립적인 작업 단위만 하위 에이전트에 나눠 맡기고, 요약으로 돌아온 결과를 확인합니다.

맡길 업무의 선정

모든 업무가 에이전트에 맡기기에 적합하지는 않습니다. 결과를 확인할 수 없거나 되돌릴 수 없는 업무를 맡기면, 잘못된 결과를 받아들이거나 복구하지 못합니다. 읽을 자료가 없거나 다른 조직과 합의해야 하는 업무는 에이전트 혼자 끝낼 수 없습니다. 그래서 이 책은 맡길 업무를 네 가지 기준으로 선정합니다. 표 6-1은 기준별 확인 질문과 기준을 충족하지 못할 때의 처리 방법입니다.

네 기준을 모두 충족하는 업무부터 맡깁니다. 일부 기준을 충족하지 않는 업무도 위임 대상에서 제외할 필요는 없습니다. 충족하지 못한 부분을 사람이 맡도록 업무를 나누면 됩니다. 맡기기로 한 업무도 한 번에 주면 실패하는 까닭은 다음 절에서 봅니다.

작업 단위 분할

선정한 업무도 한꺼번에 맡기면 실패합니다. 에이전트는 업무를 한 세션에서 끝내려 하고, 세션이 끝나면 어디까지 했는지 잃기 때문입니다. 그래서 업무를 작업 단위로 나눕니다. 이 책은 작업 단위를 한 세션에 끝나고 완료 여부를 확인할 수 있는 업무의 조각으로 정리합니다. 단위마다 작업, 완료 기준, 확인 방법, 통과 값을 목록 파일에 적고, 통과 값이 false인 첫 단위부터 하나씩 처리합니다. 통과 값은 단위가 끝났는지를 true 또는 false로 적는 칸이며, 처음에는 모두 false(아직 끝나지 않음)입니다. 통과 값이 false인 첫 단위가 사람이 맡을 단위이면, 합의나 승인이 끝난 뒤에 이어 갑니다. Chapter 2와 Chapter 3의 경비 정산 예제에 사용한 작업 단위 목록(tasks.json)이 이 목록입니다.

업무를 작업 단위로 나눠 하나씩 처리하는 방식의 근거는 긴 작업을 여러 세션에 걸쳐 진행한 실험입니다. Claude Code는 여러 세션에 걸쳐 웹 애플리케이션을 개발하는 실험에서 에이전트의 실패 양상 두 가지를 보고했습니다(Young, 2025). 첫째, 에이전트는 애플리케이션 전체를 한 번에 구현하려고 했습니다. 구현 도중 컨텍스트(Context)가 소진되어, 다음 세션은 반쯤 구현되고 기록되지 않은 기능에서 시작했습니다. 둘째, 일부 기능이 구현된 뒤 시작한 세션은 진행된 내용을 보고 프로젝트 전체가 완료되었다고 판단했습니다.

이 실험의 해결 방법은 작업 단위 분할이었습니다. 첫 세션에서 요구 사항을 200개가 넘는 기능 목록으로 작성하고, 모든 기능을 "실패" 상태로 표시했습니다. 이후 세션은 한 번에 기능 하나만 작업했습니다. Claude Code는 이 점진적 방식이 에이전트가 한 번에 너무 많은 작업을 시도하는 문제를 해결하는 데 결정적이었다고 밝혔습니다(Young, 2025).

완료 여부를 확인하는 방법은 단위마다 다르므로, 이 책은 작업 단위를 담당과 확인 방법에 따라 세 종류로 정리합니다. 합의가 필요한 단위는 사람(승인자, Chapter 3에서 변경을 승인하는 사람)이 맡고, 합의 결과를 결정 기록으로 제공합니다. 확인할 수 있는 단위는 에이전트가 맡고, 검사로 완료를 확인합니다. 판단이 필요한 단위는 에이전트가 작성하고 승인자가 승인하며, 통과 값도 사람이 변경합니다.

확인할 수 있는 단위는 표 6-1의 네 기준을 모두 충족하는 기본형이고, 합의가 필요한 단위는 합의 필요 기준을, 판단이 필요한 단위는 결과 확인 기준을 검사로 채울 수 없는 경우를 사람에게 둔 것입니다. 단위 하나는 수행한 뒤 완료 기준을 확인하고 통과 값을 true로 변경하며, 완료 기준에 미달하면 같은 단위를 다시 수행합니다. 그림 6-1은 작업 단위 목록과 작업 단위 하나를 처리하는 순서를 보여 줍니다.

표 6-2는 그림 6-1의 구성 요소를 설명합니다.

목록의 단위를 하나씩 처리하는 순서는 그림 6-1이, 하네스(Harness)가 정한 수정 권한과 작업 단위 하나의 검증은 Chapter 3의 그림 3-1이 맡습니다. 한 세션이 끝난 뒤 다음 세션이 어디서 시작하는지는 Chapter 8의 인계 메모에서 다룹니다.

여러 에이전트에 나눠 맡기기

작업 단위를 하나씩 처리하다 보면 테스트 실행, 많은 파일을 읽는 자료 조사, 긴 기록을 줄이는 로그 분석처럼 출력이 많은 작업이 주 대화의 컨텍스트 윈도(Context Window)를 채웁니다(Chapter 5). 작업 단위가 나뉘어 있으면, 서로 독립적인 단위(한 단위의 결과가 다른 단위의 입력이 되지 않는 단위)는 다른 에이전트에 맡기고 결과의 요약만 받을 수 있습니다. 이 책은 작업 단위를 여러 에이전트에 배분하고 결과를 모으는 일을 오케스트레이션(Orchestration)이라고 부릅니다. 맡는 쪽은 Chapter 2에서 정의한 하위 에이전트(Subagent)이고, 이 장에서는 맡기는 쪽을 주 에이전트라고 부릅니다. 주 에이전트는 주 대화에서 사람과 일하는 에이전트이며, 경비 정산 예제에서는 Chapter 3의 구현 에이전트입니다.

하위 에이전트는 부모 대화를 물려받는 포크 방식을 빼면, 자기 컨텍스트 윈도에서 새 대화로 시작하고, 주 대화를 보지 않습니다. 작업이 끝나면 최종 응답만 요약으로 주 에이전트에 돌아옵니다(Anthropic, 2026). 그래서 출력이 많은 작업을 맡기면, 주 대화의 컨텍스트에는 하위 작업의 전체 기록 대신 요약만큼만 더해집니다.

나눠 맡기면 비용은 늘어납니다. Anthropic의 비용 문서와 Agent SDK(Chapter 1) 문서는 하위 에이전트의 요청도 사용량에 포함되고, 비용 상한도 하위 에이전트의 지출을 포함한다고 설명합니다(Anthropic, 2026).

버전 주석 (2026년 10월) Agent SDK 문서는 Claude Code v2.1.217 이상에서 비용 상한에 이르면 새 하위 에이전트를 만들 수 없다고 안내합니다(Anthropic, 2026).

여러 에이전트를 사용하는 기능에는 하위 에이전트 외에 에이전트 팀(Agent Team)도 있어, 이 책이 다루는 범위를 정해 둡니다. 두 기능은 보고 방식이 다릅니다. Claude Code 용어집은 하위 에이전트가 한 세션 안에서 일하고 맡긴 쪽에만 보고하는 반면, 에이전트 팀의 팀원은 각자 컨텍스트 윈도를 갖고 사용자가 팀원과 직접 대화할 수 있다고 설명합니다. 비용 문서는 여러 인스턴스가 각자의 컨텍스트로 일하는 에이전트 팀에서 토큰(Token) 사용량이 팀 크기에 거의 비례한다고 설명합니다. 에이전트 팀은 기본으로 꺼져 있는 실험 기능이며, 이 책은 하위 에이전트만 다룹니다(Anthropic, 2026). 그림 6-2는 하위 에이전트에 나눠 맡길 때 오가는 정보와 비용을 보여 줍니다.

표 6-3은 그림 6-2의 구성 요소를 설명합니다.

나눠 맡길 때 정할 것은 네 가지입니다.

  • 나눠 맡길 작업: 앞 단위의 변경을 이어받지 않아 서로 독립적이고, 결과만 돌려받으면 되는 작업 단위를 선택합니다. 일반 하위 에이전트는 주 대화를 보지 않으므로, 앞 단위의 변경을 이어받는 작업은 맡기기 어렵습니다.
  • 넘길 정보와 도구: 일반 하위 에이전트는 주 대화를 보지 않으므로 필요한 정보를 요청에 담고, 맡긴 작업에 필요한 최소한의 도구만 지정합니다(Chapter 2의 도구 노출 범위).
  • 결과 확인: 돌아오는 것은 요약이므로, Chapter 7의 완료 기준으로 확인합니다.
  • 비용 상한: 나눠 맡길 작업의 수와 함께 전체 비용 상한을 정합니다. 하위 에이전트의 지출도 상한에 포함되므로, 상한은 나눠 맡긴 작업까지 합쳐 정합니다(Chapter 9의 비용 관리).

변경 요청의 작업 단위 분할 예제

앞의 세 절을 한 사례에 적용합니다. Chapter 4의 영향 검토를 거쳐 경비 정산 시스템 개편 변경 요청(Change Request) CR을 수용하기로 했다고 가정합니다. CR은 정산 요청 화면에 프로젝트 코드 선택 항목을 추가하는 변경이며, 이 변경을 구현하는 에이전트는 Chapter 3에서 설계했습니다.

먼저 표 6-1의 기준을 적용합니다. 코드와 자료가 모두 저장소 안에 있어 자료 접근은 충족되고, 변경은 commit 단위로 되돌릴 수 있으며 push는 사람이 하므로 되돌림도 충족됩니다. 프로젝트 코드 조회 방식은 연동 규격이 없어 인사팀과의 합의가 필요하므로 승인자가 맡습니다. 통합 시나리오의 범위는 검사로 확인할 수 없는 판단이므로 에이전트가 작성하고 승인자가 승인합니다. 나머지는 검사로 확인할 수 있어 에이전트가 맡습니다. 표 6-4는 이 결과를 작업 단위 목록과 같은 순서와 문구로 보여 줍니다. 수용 시험과 검사 스크립트(check.py)는 Chapter 3에서 정의했고, 확인 방법의 tests는 check.py가 실행하는 단위 테스트(tests/ 폴더)를 가리킵니다. 작업 1은 합의를 마쳐 목록에서 이미 통과 값이 true이므로, 에이전트는 작업 2부터 시작합니다.

작업 2와 작업 3의 시험(수용 시험 4, 5와 단위 테스트)은 구현 전에도 통과합니다. 실습 1의 기준 상태 기록에서 단위 테스트는 실패 0건이고, 수용 시험은 넷째와 다섯째만 통과합니다(부록 실습의 실습 1). 두 시험은 새 기능이 생겼는지가 아니라 변경이 기존 동작을 깨지 않았는지를 확인하기 때문입니다. 통과 값이 false인 것은 시험이 실패해서가 아니라 단위를 아직 수행하지 않았기 때문입니다. 추가한 항목이 실제로 쓰이는지는 작업 4의 수용 시험 1, 2, 3이 확인합니다.

작업 단위 목록은 에이전트가 읽고 통과 값을 갱신할 수 있는 파일로 저장합니다. 앞의 실험은 기능 목록을 JSON 형식으로 저장했고, 에이전트가 상태 항목만 수정하도록 지시했습니다. JSON은 항목 이름과 값을 정해진 형식으로 적는 파일 형식입니다. 모델이 Markdown 파일보다 JSON 파일을 부적절하게 변경하거나 덮어쓰는 일이 적었기 때문입니다(Young, 2025). 다음은 CR 목록의 일부(작업 2, 3)입니다.

[
  {
    "id": "작업 2",
    "작업": "데이터 모델에 프로젝트 코드 항목 추가",
    "완료 기준": "정산 요청 데이터에 항목 추가, 기존 데이터 유지",
    "확인 방법": "python check.py의 수용 시험 4, 5 통과",
    "통과": false
  },
  {
    "id": "작업 3",
    "작업": "기존 단위 테스트 갱신",
    "완료 기준": "변경된 데이터 모델의 테스트 반영",
    "확인 방법": "python check.py의 tests 실패 0건",
    "통과": false
  }
]

다음은 나눠 맡길지의 판단입니다. 작업 2, 3, 4는 서로 독립적이지 않습니다. 작업 3은 작업 2가 변경한 데이터 모델에 맞춰 테스트를 수정하고, 작업 4는 그 데이터 모델의 항목을 화면에서 선택하게 합니다. 그래서 이 책의 설계는 세 단위를 하위 에이전트에 나눠 맡기지 않고, 구현 에이전트가 통과 값이 false인 첫 단위부터 차례로 수행하게 합니다. 하위 에이전트는 Chapter 3의 검토 하위 에이전트처럼, 변경 내용을 수용 기준과 읽기 전용으로 대조하는 데 사용합니다(표 3-3). 단위가 서로 이어지는 CR에서는 나눠 맡기지 않는 것이 이 장의 기준에 맞는 선택입니다. 구현 에이전트는 작업 단위를 마칠 때마다 그 단위의 변경을 commit하며, commit은 사람이 확인한 뒤 실행됩니다.

그래도 나누는 수고를 줄이고 싶을 수 있습니다. 작업 단위 분할 자체에 대해, 큰 업무를 한 번에 맡기는 편이 효율적이라는 의견이 있습니다. 한 번에 맡긴 업무가 실패하면, 어느 부분에서 실패했는지 확인할 단위가 없습니다. 작업 단위로 나누면 실패한 단위만 다시 작업합니다.

작업 단위 목록으로 구현을 진행하는 실습은 부록 실습의 실습 5에 있습니다.

실패와 막는 장치

CR을 작업 단위로 나누지 않거나 담당을 잘못 정하면 다음 실패가 생길 수 있습니다. 표 6-5는 실패와 원인, 막는 장치입니다. 표의 작업 번호는 표 6-4의 번호입니다.

확인 방법

작업 단위가 끝났는지는 에이전트의 보고가 아니라 파일과 검사 출력으로 확인합니다. 작업 단위 하나의 검증 방법은 Chapter 3의 확인 방법과 같고, 여기서는 목록 쪽 확인만 다룹니다. 명령은 실습 폴더(examples/expense-app/)에서 실행합니다. git log는 commit 기록을, git diff는 마지막 commit 뒤에 바뀐 내용을 보여 주므로, 통과 값의 변경은 단위를 마친 뒤 commit하기 전에 git diff tasks.json으로 봅니다. 표 6-6은 확인할 것과 확인 위치입니다.

원칙과 점검 질문

맡길 업무는 한 세션에 끝나고 완료 여부를 확인할 수 있는 작업 단위로 나누어 맡깁니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 맡기려는 업무의 각 작업 단위에 완료 기준과 확인 방법이 있습니까?
  2. 작업 단위 가운데 다른 조직과 합의가 필요해 사람이 맡아야 할 단위는 무엇입니까?
  3. 세션이 중간에 끝나도 어느 단위까지 끝났는지 파일로 알 수 있습니까?
