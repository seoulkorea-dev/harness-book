Chapter 6 착수: 맡길 업무 선정과 작업 단위 분할

에이전트(Agent)는 맡은 업무를 한 세션 안에서 처리하려고 하며, 세션이 끝나면 진행 중이던 상태를 기억하지 못합니다. 위임의 성패를 정하는 것은 업무의 크기가 아니라, 업무를 결과를 확인할 수 있는 단위로 나누었는지입니다. 그래서 한 번에 큰 업무를 맡기면, 중간에 멈춘 작업과 완료되지 않은 기능이 기록 없이 남습니다. 따라서 착수 전에 맡길 업무를 선정하고, 완료 기준을 갖춘 작업 단위로 분할해야 합니다. 이 장에서는 맡길 업무의 선정 기준과 작업 단위 분할 방법을 다룹니다.

  • 맡길 업무는 결과 확인, 자료 접근, 되돌림, 합의 필요의 네 기준으로 선정합니다.
  • 작업 단위는 한 세션에 끝나고 완료 여부를 확인할 수 있는 크기로 나눕니다.
  • 작업 단위 목록은 완료 기준과 상태를 함께 기록합니다.

맡길 업무의 선정

모든 업무가 에이전트에 맡기기에 적합하지는 않습니다. 이 책은 맡길 업무를 네 가지 기준으로 선정합니다. 표 6-1은 기준별 확인 질문과 기준을 충족하지 못할 때의 처리 방법입니다.

네 기준을 모두 충족하는 업무부터 맡깁니다. 일부 기준을 충족하지 않는 업무도 위임 대상에서 제외할 필요는 없습니다. 충족하지 못한 부분을 사람이 맡도록 업무를 나누면 됩니다.

작업 단위 분할

Anthropic은 여러 세션에 걸쳐 웹 애플리케이션을 개발하는 실험에서 에이전트의 실패 양상 두 가지를 보고했습니다(Young, 2025). 첫째, 에이전트는 애플리케이션 전체를 한 번에 구현하려고 했습니다. 구현 도중 컨텍스트(Context)가 소진되어, 다음 세션은 반쯤 구현되고 기록되지 않은 기능에서 시작했습니다. 둘째, 일부 기능이 구현된 뒤 시작한 세션은 진행된 내용을 보고 프로젝트 전체가 완료되었다고 판단했습니다.

Anthropic의 해결 방법은 작업 단위 분할이었습니다. 첫 세션에서 요구 사항을 200개가 넘는 기능 목록으로 작성하고, 모든 기능을 "실패" 상태로 표시했습니다. 이후 세션은 한 번에 기능 하나만 작업했습니다. Anthropic은 이 점진적 방식이 에이전트가 한 번에 너무 많은 작업을 시도하는 문제를 해결하는 데 결정적이었다고 밝혔습니다(Young, 2025).

작업 단위의 크기 기준은 두 가지입니다. 한 세션 안에 끝나야 하고, 완료 여부를 확인할 수 있어야 합니다. 그림 6-1은 CR-07을 작업 단위로 나눈 목록과, 한 작업 단위를 처리하는 순서입니다.

표 6-2는 그림 6-1의 구성 요소를 설명합니다.

여러 에이전트에 나눠 맡기기

작업 단위를 나누면 일부를 다른 에이전트에 맡길 수 있습니다. 이 책은 작업 단위를 여러 에이전트에 배분하고 결과를 모으는 일을 오케스트레이션이라고 부릅니다. Claude Code에서는 하위 에이전트(Subagent)가 맡은 작업을 처리합니다.

하위 에이전트는 자신의 컨텍스트 윈도(Context Window)에서 일합니다. 새 대화로 시작하고, 주 에이전트의 대화를 보지 않습니다. 작업이 끝나면 최종 응답만 주 에이전트에 돌아옵니다(Anthropic, 2026). 그래서 테스트 실행이나 로그 처리처럼 출력이 많은 작업을 맡기면, 주 대화의 컨텍스트가 늘지 않습니다.

나눠 맡기면 비용은 늘어납니다. Agent SDK의 비용 상한은 하위 에이전트의 지출을 포함하고, 상한에 이르면 새 하위 에이전트를 만들 수 없습니다. 비용 문서는 여러 인스턴스가 각자의 컨텍스트로 일하는 에이전트 팀에서 토큰(Token) 사용량이 팀 크기에 거의 비례한다고 설명합니다. 팀원이 계획 모드로 실행되면 일반 세션보다 약 7배의 토큰을 사용한다고 안내합니다(Anthropic, 2026).

하위 에이전트와 에이전트 팀은 보고 방식이 다릅니다. 용어집에 따르면 하위 에이전트는 한 세션 안에서 일하고 주 에이전트에게만 보고합니다. 에이전트 팀의 팀원은 각자 컨텍스트 윈도를 갖고, 사용자가 팀원과 직접 대화할 수 있습니다. 그림 6-2는 하위 에이전트에 나눠 맡길 때 오가는 정보와 비용입니다.

표 6-3은 그림 6-2의 구성 요소를 설명합니다.

나눠 맡길 때 정할 것은 네 가지입니다.

  • 나눠 맡길 작업: 서로 독립적이고, 결과만 돌려받으면 되는 작업 단위를 선택합니다.
  • 넘길 정보: 하위 에이전트는 주 에이전트의 대화를 보지 않으므로, 필요한 정보를 요청에 담습니다.
  • 결과 확인: 돌아오는 것은 요약이므로, Chapter 7의 완료 기준으로 확인합니다.
  • 비용 상한: 나눠 맡길 작업의 수와 함께 전체 비용 상한을 정합니다.

변경 요청의 작업 단위 분할 예제

Chapter 4의 변경 요청 영향 검토 예제에서 다룬 CR-07을 수용하기로 했다고 가정합니다. 이 변경을 구현하는 에이전트는 Chapter 3에서 설계했습니다. 정산 요청 화면에 프로젝트 코드 선택 항목을 추가하는 변경입니다. 표 6-4는 이 변경을 작업 단위로 분할한 결과입니다.

첫 번째 작업 단위는 연동 규격이 없어 다른 조직과의 합의가 필요하므로 PM이 맡습니다. 나머지 작업 단위는 합의 결과를 입력으로 받아 에이전트가 수행합니다. 마지막 작업 단위는 에이전트가 작성하지만, 통합 테스트의 범위를 정하는 판단이므로 PM이 승인합니다.

작업 단위 목록은 에이전트가 읽고 상태를 갱신할 수 있는 파일로 저장합니다. Anthropic은 기능 목록을 JSON 형식으로 저장했고, 에이전트가 상태 항목만 수정하도록 지시했습니다. 모델이 Markdown 파일보다 JSON 파일을 부적절하게 변경하거나 덮어쓰는 일이 적었기 때문입니다(Young, 2025).

[
  {
    "id": "CR-07-2",
    "작업": "데이터 모델에 프로젝트 코드 항목 추가",
    "완료 기준": "정산 요청 데이터에 항목 추가, 기존 데이터 유지",
    "확인 방법": "데이터 변환 시험 통과",
    "통과": false
  },
  {
    "id": "CR-07-3",
    "작업": "정산 요청 화면에 선택 항목 추가",
    "완료 기준": "화면에서 프로젝트 코드 선택 가능",
    "확인 방법": "화면 시험 통과",
    "통과": false
  }
]

큰 업무를 한 번에 맡기는 편이 효율적이라는 의견이 있습니다. 한 번에 맡긴 업무가 실패하면, 어느 부분에서 실패했는지 확인할 단위가 없습니다. 작업 단위로 나누면 실패한 단위만 다시 작업합니다.

위임은 업무를 결과를 확인할 수 있는 단위로 나누는 일에서 시작합니다.
