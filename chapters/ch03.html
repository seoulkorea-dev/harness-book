Chapter 3 하네스로 에이전트 설계하기

에이전트의 동작은 요청 문장뿐 아니라, 업무의 목적부터 승인 지점까지 하네스에 정의한 아홉 항목에 따라 달라집니다.

Chapter 2의 다섯 구성 요소를 모두 정해도, 에이전트(Agent)에게 업무를 맡기기에는 아직 부족합니다. 결과를 어디에 쓸지, 어떤 자료로 시작할지, 언제 멈출지, 어디서 사람이 확인할지는 업무마다 다르기 때문입니다. 에이전트는 하네스(Harness)에 정의된 규칙 문서, 도구, 권한을 바탕으로 작업하므로, 정의하지 않은 값은 모델의 추측이나 제품의 기본값으로 채워질 수 있습니다.

업무마다 정할 값을 한 문서에 모은 것이 에이전트 명세서입니다. 명세서는 다섯 구성 요소(Chapter 2의 다섯 요소가 만드는 흐름)에 목적, 입력, 종료 조건, 승인 지점의 네 업무 항목을 더한 아홉 항목으로 이루어집니다. 명세서의 값은 Claude Code가 읽는 하네스 설정 파일로 옮겨야 작동합니다.

이 장에서는 먼저 명세서가 왜 필요한지 살펴보고, 네 업무 항목과 검증 기준의 보호를 차례로 살펴봅니다. 이어서 명세서를 설정 파일로 옮기는 방법을 익히고, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)을 구현하는 에이전트의 명세서를 작성합니다.

  • 에이전트 명세서는 다섯 구성 요소(역할, 도구, 권한, 기록, 검증)에 목적, 입력, 종료 조건, 승인 지점을 더한 아홉 항목의 값을 적는 문서입니다.
  • 수용 기준을 판정하는 시험과 스크립트(검증 기준)는 사람이 작성하고, 에이전트가 수정해 통과한 것처럼 꾸미지 못하게 금지 규칙과 사람의 확인으로 보호합니다.
  • 명세서의 값은 규칙 문서, 권한 규칙과 훅을 담은 설정 파일, 하위 에이전트 정의처럼 Claude Code가 읽고 적용하는 하네스 설정 파일로 옮깁니다.

에이전트 명세서가 필요한 이유

명세서는 업무를 맡길 때마다 정할 값을 누락하지 않게 합니다. 정할 항목을 기억에 의존하면 누락이 생기기 쉽습니다. 그래서 항목을 목록으로 정리해 두고, 업무마다 값을 채웁니다. 업무에 필요한 항목과 값을 기록한 문서를 에이전트 명세서라고 합니다.

명세서의 아홉 항목은 Chapter 2의 다섯 구성 요소인 역할, 도구, 권한, 기록, 검증을 포함합니다. 나머지 목적, 입력, 종료 조건, 승인 지점은 맡기는 업무 자체를 정하므로 업무 항목이라고 합니다. 표 3-1처럼 업무 항목이 비면 그 항목에 해당하는 실패가 생길 수 있습니다.

결과의 쓰임을 정하는 목적

목적은 결과를 누가 어디에 사용하는지 정합니다. "보고서를 정리해 줘"라는 요청만으로는 정리의 범위와 깊이가 정해지지 않습니다. 보고서를 팀 회의의 결정에 사용하는지, 외부에 보내는지에 따라 담을 내용이 달라지기 때문입니다.

목적은 결과를 사용하는 사람, 장소, 시점을 한 문장으로 적습니다. "다음 주 팀 회의에서 도입 여부를 결정할 수 있게"처럼 적으면, 에이전트는 결정에 필요한 내용부터 작업 범위를 정할 수 있습니다.

목적이 비어 있으면 에이전트는 결과의 쓰임을 모른 채 작업 범위를 추측할 수 있습니다.

작업에 사용할 자료를 정하는 입력

입력은 에이전트가 작업에 사용할 자료를 정합니다. 입력은 세션을 시작할 때 처음 읽을 자료와 작업 중에 필요할 때 찾을 자료로 나눕니다. 처음 읽을 자료는 규칙 문서에 읽는 순서로 적고, 필요할 때 찾을 자료는 위치만 알려 줍니다. 두 자료를 나누는 기준은 Chapter 5의 미리 제공하는 정보와 필요할 때 찾는 정보에서 다룹니다.

작업이 여러 세션에 걸치면 이전 세션의 진행 상황도 입력입니다. Claude Code 문서에 따르면 세션은 새 컨텍스트(Context) 창으로 시작하므로15, 다음 세션은 진행 기록과 인계 메모를 읽고 시작합니다.

입력이 비어 있으면 에이전트는 필요한 자료를 추측하거나 찾지 못할 수 있습니다. 이전 세션의 진행 상황을 읽지 않으면, 이미 끝난 작업을 다시 할 수도 있습니다.

작업을 멈출 때를 정하는 종료 조건

종료 조건은 에이전트가 언제 작업을 멈추는지 정합니다. 종료 조건에는 세 가지 값이 들어갑니다.

  • 완료 기준: 작업이 끝났는지 판정하는 기준입니다. 완료를 판정할 명령과 그 기대 출력으로 적습니다.
  • 중단 규칙: 같은 실패가 몇 번 반복되면 멈출지 정한 규칙입니다.
  • 실행 상한: 루프가 도는 횟수(턴 상한)와 추정 지출 금액(비용 상한)에 두는 한도입니다.

"테스트 명령이 실패 0건으로 끝나면 완료, 같은 테스트가 세 번 연속 실패하면 멈추고 사람에게 알림"처럼 적으면, 에이전트는 끝낼 때와 멈출 때를 따로 판단할 수 있습니다.

종료 조건이 비어 있으면 에이전트는 끝난 작업을 이어 가거나, 같은 실패를 끝없이 되풀이할 수 있습니다.

실행 상한에는 조건이 있습니다. 턴이 무엇을 세는지는 Chapter 1에서 본 것처럼 문서마다 다릅니다. Claude Code에서 턴과 비용의 상한을 정하는 명령 줄 옵션(--max-turns, --max-budget-usd)은, 대화 없이 요청 하나를 실행하고 끝내는 -p 실행에서만 사용할 수 있습니다26. --max-budget-usd의 비용은 Claude Code가 계산한 추정치라 실제 청구와 다를 수 있고, 지출이 상한을 넘을 수도 있습니다. 사람이 지켜보는 대화형 세션이라면 상한 대신 완료 기준과 중단 규칙으로 종료 조건을 정할 수 있습니다.

사람이 확인할 동작을 정하는 승인 지점

승인 지점은 실행 전에 사람이 확인할 동작을 정합니다. 저장소 반영, 외부 발송, 배포처럼 되돌리기 어려운 동작이 대상입니다.

승인 지점은 권한 규칙(Permission Rule)으로 구현합니다. 확인 요청 규칙을 두면 실행 전에 사람에게 묻고, 금지 규칙을 두면 그 동작은 사람이 직접 실행합니다. 어느 동작에서 사람이 개입할지는 업무가 정하므로, 다섯 구성 요소의 권한과 따로 업무 항목에 둡니다. 같은 저장소 반영이라도 개인 실험 저장소에서는 확인 없이 허용하고, 팀이 함께 사용하는 저장소에서는 사람이 확인하게 할 수 있습니다.

승인 지점이 비어 있으면 되돌리기 어려운 동작이 사람의 확인 없이 실행될 수 있습니다.

승인 지점과 함께 정할 것이 하나 더 있습니다. 완료를 판정하는 기준을 누가 수정할 수 있는가입니다.

검증 기준의 수정 권한

검증 기준은 정하는 것만으로는 충분하지 않고, 그 기준을 누가 수정할 수 있는지도 정해야 합니다. 완료를 판정하는 시험을 에이전트가 수정할 수 있으면, 기능을 구현하지 않고 실패하는 시험을 수정해서 통과시킬 수 있기 때문입니다. 시험은 결과가 맞는지 자동으로 확인하는 코드입니다.

완료 기준 가운데 사람이 업무의 요구로 정한 것을 수용 기준(Acceptance Criteria)이라고 합니다. 수용 기준을 자동으로 판정하는 시험과, 그 시험을 실행하는 작은 프로그램(스크립트)을 묶어 검증 기준이라고 합니다. 수용 기준은 충족해야 할 조건이고, 검증 기준은 그 조건의 충족 여부를 판정하는 파일입니다.

검증 기준은 사람이 작성하고, 에이전트의 수정은 금지 규칙으로 막습니다. 금지 규칙으로 막을 수 없는 경우는 사람이 결과를 받아들이기 전에 바뀐 파일을 확인해 보완합니다.

검증 기준을 보호하지 않으면, 에이전트가 실패하는 시험을 수정해 통과시키고 완료를 보고할 수 있습니다.

시험 수를 세는 검사에도 빈틈이 있습니다. 시험 파일을 지우면 실행 건수가, 일부를 건너뛰게 하면 건너뜀 수가 달라져 검사가 실패합니다. 그러나 시험 안에서 결과를 비교하는 줄만 지워 내용을 약하게 만들면 건수는 그대로입니다. 검사가 건수를 확인하는 것과 별도로, 시험의 수정을 권한 규칙으로 금지하는 이유가 이것입니다.

명세서를 옮길 하네스 설정 파일

명세서의 값은 Claude Code가 정해진 위치에서 자동으로 읽어 들이는 파일로 옮겨야 작동합니다. 명세서는 사람이 읽는 문서여서 Claude Code가 그대로 적용하지 않기 때문입니다. 이런 파일을 하네스 설정 파일이라고 하며, 이 장에서는 세 가지를 다룹니다.

  • 규칙 문서(CLAUDE.md): 에이전트가 세션을 시작할 때 읽는 지시입니다15.
  • 설정 파일(.claude/settings.json): Claude Code가 적용하는 권한 규칙과 훅(Hook)을 담습니다. 저장소에 함께 두면 팀이 같은 설정을 사용합니다.
  • 하위 에이전트(Subagent) 정의: .claude/agents/ 폴더의 파일이며, 하위 에이전트의 역할과 도구를 담습니다.

진행 기록, 결정 기록, 인계 메모, 검증 기준처럼 에이전트가 읽거나 실행하는 저장소의 다른 파일도 명세서의 값을 담습니다. 표 3-2는 명세서 항목마다 옮길 파일을 정리합니다.

권한 규칙은 허용(allow), 확인 요청(ask), 금지(deny)의 세 목록에 둡니다. 규칙은 도구 이름 뒤 괄호에 대상을 적습니다. Edit 규칙은 파일을 수정하거나 새로 작성하는 Claude Code의 내장 편집 도구(Edit, Write, NotebookEdit) 전체에 적용되고, Bash 규칙은 명령 실행 도구(Bash)에 적용됩니다. 파일 경로 규칙은 Edit(경로)로 적으며, Write(경로) 규칙은 어떤 수정과도 일치하지 않습니다13.

Edit(./docs/**)는 docs/ 폴더 아래 모든 파일의 수정을, Bash(git push *)는 git push로 시작하는 명령을 가리킵니다. 경로의 **는 하위 폴더를 포함한 모든 파일과 일치하고, 명령의 *는 아무 문자열과 일치합니다. ./는 Claude Code의 현재 작업 폴더를 기준으로 한 경로입니다13. 이 장의 예제는 Claude Code를 시작한 폴더에서 작업한다고 전제합니다.

괄호 없이 도구 이름만 적는 금지 규칙은 그 도구를 모델의 컨텍스트에서 없애, 모델이 그 도구를 볼 수 없게 합니다13. 웹 페이지를 가져오는 WebFetch와 웹을 검색하는 WebSearch는 Claude Code의 기본 도구이므로, 웹 접근을 제외하려면 이 형식으로 막습니다27.

하위 에이전트 정의의 도구 줄(tools)에는 맡긴 일에 필요한 도구만 적습니다. 검토를 맡은 하위 에이전트가 코드를 수정할 수 있으면 자기가 수정한 결과를 자기가 검토하게 되므로, 읽기 도구만 적습니다. 도구 줄을 생략한 하위 에이전트는 하위 에이전트에 허용되는 도구를 모두 물려받습니다22. 그래서 도구를 제한하지 않으면 검토 하위 에이전트가 코드를 수정할 수 있습니다.

편집 뒤 훅으로 검사를 실행할 때는 종료 코드로 결과를 알립니다. 종료 코드는 명령이 끝날 때 돌려주는 값이며, 0은 성공, 0이 아닌 값은 실패를 뜻합니다. Claude Code 문서는 PostToolUse 훅이 종료 코드 2로 끝나면 오류 출력을 모델에 보여 주지만, 이미 실행된 도구는 막지 못한다고 설명합니다10. 따라서 편집 뒤 훅은 실패를 알려 다시 작업하게 하는 장치이고, 파일의 수정 금지는 권한 규칙이 맡습니다.

설정 파일에도 한계가 있습니다. Edit 금지 규칙은 Claude Code의 편집 도구와 Claude Code가 알아보는 파일 명령에 적용되고, 에이전트가 실행한 스크립트가 파일을 직접 여는 경우에는 적용되지 않습니다13. 허용한 테스트 명령과 훅은 에이전트가 작성한 시험 코드를 묻지 않고 실행하므로, 그 코드가 금지한 파일을 직접 수정해도 금지 규칙은 막지 못합니다. 도구 이름만 적은 금지 규칙도 그 도구만 막으므로, curl처럼 웹 주소의 내용을 가져오는 셸 명령은 허용 목록 밖에서 권한 모드(Permission Mode)에 따라 처리됩니다.

명령 규칙은 문자열을 비교하므로, git -C . push처럼 다르게 작성한 명령은 Bash(git push *)와 일치하지 않습니다13. 이런 명령은 권한 모드가 처리합니다. 사람에게 묻는 수동 모드(설정 값 default)에서는 실행 전에 확인을 요청하므로, 사람이 그 자리에서 거절할 수 있습니다. Claude Code가 호출을 자동으로 판단하는 auto 모드는, 문서에 따르면 작업 중인 저장소로의 push를 기본으로 허용합니다. 강제 push와, 기본 브랜치가 아니면서 production, gh-pages처럼 배포 대상을 나타내는 이름의 브랜치로의 push는 이 허용에 들지 않습니다11. 그래서 auto 모드에서는 다르게 작성한 push 명령이 확인 없이 실행될 수 있습니다. 수동 모드로 진행하려면 claude --permission-mode default로 시작하거나, 설정 파일의 permissions.defaultMode에 default를 적습니다11.

버전 주석 (2026년 10월) Claude Code 문서에 따르면 시작 옵션이나 설정 파일로 모드를 정하지 않은 경우, v2.1.283 이상의 대화형 터미널과 VS Code 세션은 auto 모드로 시작하고, 이전 버전은 요금제에 따라 다릅니다. claude -p와 Agent SDK는 default로 시작합니다11.

규칙 문서의 지시도 지켜진다는 보장이 없습니다. Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 다루며, 지시를 엄격하게 따른다는 보장은 없다고 설명합니다15. 그래서 어기면 되돌리기 어려운 동작은 권한 규칙이나, 도구 실행 전에 막는 PreToolUse 훅으로 처리합니다10. 이런 빈틈은 사람이 결과를 받아들이기 전에 바뀐 파일 목록을 확인해 찾습니다.

예제: 변경 요청 사항의 에이전트 명세서 작성

이 절은 명세서를 변경 요청 사항에 적용합니다. 경비 정산 시스템 개편은 가상 프로젝트이고, 변경 요청 사항은 재무팀이 2026년 10월 5일에 요청한 변경 한 건입니다. 정산 요청 화면에 프로젝트 코드(경비가 속한 프로젝트의 식별 번호) 선택 항목을 추가해, 월말 결산에서 프로젝트별 경비를 집계하려는 것입니다.

대상은 정산 요청을 등록하고 목록으로 보여 주는 작은 웹 앱이며, 따로 설치할 것 없이 Python만 있으면 실행됩니다. 앱 코드는 expense/ 폴더와 app.py에 있고, 시험 코드는 tests/와 acceptance/ 폴더에 있습니다. 등록할 수 있는 프로젝트 코드 목록은 인사 시스템이 하루 한 번 갱신하는 원본 자료(data/projects.csv)이고, 앱은 이 파일을 읽기만 합니다.

변경 요청 사항은 다섯 작업 단위로 나뉩니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다. 작업 2의 데이터 모델은 정산 요청 한 건을 어떤 항목으로 저장할지 정한 코드입니다. 작업 3의 단위 테스트는 프로그램의 부품 하나가 정해진 대로 동작하는지 확인하는 시험이고, 작업 5의 통합 테스트 시나리오는 여러 기능을 이어서 실행해 확인하는 시험 절차입니다.

  • 작업 1: 인사팀과 프로젝트 코드 조회 방식을 합의합니다. 사람이 맡고, 합의 결과는 결정 기록(DECISIONS.md)의 12번 결정(D-012)으로 확인합니다.
  • 작업 2: 정산 요청의 데이터 모델에 프로젝트 코드 항목을 추가합니다. 에이전트가 맡습니다.
  • 작업 3: 바뀐 데이터 모델에 맞춰 단위 테스트(tests/ 폴더)를 갱신합니다. 에이전트가 맡습니다.
  • 작업 4: 정산 요청 화면에 프로젝트 코드 선택 항목을 추가하고, 프로젝트 코드 목록에 없는 코드는 거부합니다. 에이전트가 맡습니다.
  • 작업 5: 프로젝트별 집계를 확인하는 통합 테스트 시나리오의 초안을 작성합니다. 에이전트가 초안을 작성하고, 사람이 승인해 완료를 확정합니다.

사람이 정한 수용 기준은 다섯 가지이고, 변경 요청 사항 문서(docs/CR.md)에 있습니다.

  1. 정산 요청 등록 화면에서 프로젝트 코드 목록의 코드를 선택할 수 있습니다.
  2. 프로젝트 코드 목록에 없는 코드로 등록하면 거부하고, 거부 사유에 입력한 코드를 표시합니다.
  3. 목록 화면에 프로젝트 코드를 표시합니다.
  4. 프로젝트 코드가 없는 기존 정산 요청도 이전처럼 목록 화면에 나옵니다.
  5. 등록 처리는 원본 자료(data/projects.csv)를 변경하지 않습니다.

수용 시험은 acceptance/ 폴더에 기준마다 하나씩 다섯 건이 있고, 시험 번호는 수용 기준의 번호와 같습니다. 수용 시험은 사람이 작성하고 에이전트는 수정하지 않습니다. 단위 테스트는 데이터 모델이 변경되면 함께 수정해야 하므로 에이전트가 수정합니다.

검사 스크립트(check.py)는 두 시험을 명령 한 번으로 실행하며, 다음 세 조건을 모두 충족하면 종료 코드 0으로 끝납니다. 이 예제의 검증 기준은 수용 시험과 검사 스크립트입니다.

  1. 두 시험에서 실패한 시험과 실행하지 않고 넘어간 시험(건너뜀)이 0건입니다.
  2. 수용 시험이 정한 수(5건)만큼 실행됩니다.
  3. 이름에 project_code가 든 단위 테스트가 1건 이상 있습니다. project_code는 코드에서 프로젝트 코드 항목을 가리키는 이름입니다.

검사 스크립트는 폴더마다 결과를 한 줄씩 출력합니다. 구현 전에 실행하면 tests와 acceptance로 시작하는 두 줄은 다음과 같고, 종료 코드는 1입니다.

tests: 실행 3건, 실패 0건, 건너뜀 0건, project_code 시험 0건
acceptance: 실행 5건, 실패 3건, 건너뜀 0건(정한 수 5건)

이 예제에는 에이전트가 둘입니다. 구현 에이전트는 작업 단위를 처리하며 코드를 수정하는 주 에이전트이고, 검토 하위 에이전트는 바뀐 내용을 수용 기준과 대조해 보고만 합니다. 두 에이전트와 사람은 다음 파일과 명령으로 일을 이어 갑니다.

  • 진행 기록(tasks.json): 작업 단위마다 확인 방법과 통과 값을 적은 파일입니다. 확인 방법은 완료 기준을 무엇으로 판정할지 적은 칸이고, 통과 값은 그 확인 방법을 충족했는지를 true 또는 false로 적은 칸입니다. 작업 1은 합의가 이미 결정 기록(D-012)에 있어 통과 값이 처음부터 true입니다. 작업 2~4의 통과 값은 구현 에이전트가, 작업 5의 통과 값은 사람이 변경합니다.
  • 인계 메모(HANDOFF.md): 구현 에이전트가 세션을 마칠 때 남깁니다.
  • git status와 git diff: 저장소에서 바뀐 파일 목록과 바뀐 내용을 보여 주는 명령입니다.
  • git commit과 git push: commit은 바뀐 파일을 저장소의 기록으로 남기는 명령이고, push는 그 기록을 다른 사람이 보는 저장소에 올리는 명령입니다. 사람이 commit을 승인하기 전에 바뀐 파일을 보는 일을 commit 확인이라고 합니다.

표 3-3과 표 3-4는 명세서의 아홉 항목에 정한 값입니다. 표 3-3은 다섯 구성 요소의 값이고, 표 3-4는 업무 항목의 값입니다.

표의 값 가운데 다섯 가지를 풀이합니다.

  • 검증 기준의 보호: 수용 시험과 검사 스크립트는 사람이 작성하고, 구현 에이전트의 편집 도구로는 수정하지 못하게 금지 규칙으로 막습니다. 작업 4는 사람이 작성한 수용 시험으로 완료를 판정하므로, 단위 테스트를 변경하는 것만으로는 완료로 보이게 할 수 없습니다.
  • 작업 단위별 판정: 구현 에이전트는 작업 단위를 마칠 때 검사 스크립트를 실행하고, 확인 방법을 충족하면 통과 값을 true로 변경합니다. 작업 2와 3을 마친 시점에는 작업 4가 맡은 수용 시험 1, 2, 3이 아직 실패하므로, 검사 스크립트 전체는 종료 코드 1로 끝납니다. 그래서 확인 방법은 출력 가운데 그 작업 단위가 맡은 시험의 결과로 판정합니다. 작업 3은 tests로 시작하는 줄의 실패 0건과 project_code 시험 1건 이상으로 판정합니다. 작업 4까지 마치면 검사 스크립트가 종료 코드 0으로 끝나며, 이것이 목표 상태입니다.
  • 중단 규칙: 작업 단위를 마칠 때 실행한 검사 스크립트에서 그 단위의 확인 방법에 든 시험(확인 대상 시험)이 세 번 연속 실패하면 중단하고 인계 메모를 작성합니다. 파일을 수정할 때마다 실행되는 편집 뒤 훅의 실패는 세지 않습니다.
  • 완료의 확정: 통과 값을 변경한 뒤 구현 에이전트는 검토 하위 에이전트에게 대조를 요청합니다. 사람은 검토 보고와 바뀐 파일을 보고 commit을 승인하거나 수정을 요청하며, 수정을 요청받으면 구현 에이전트는 통과 값을 false로 되돌리고 다시 작업합니다.
  • 세션 나누기: 구현은 두 세션에 나누어 진행합니다(첫 세션은 작업 2, 3, 두 번째 세션은 작업 4). 두 번째 세션은 인계 메모와 진행 기록을 읽고 시작합니다. 사람이 지켜보는 대화형 세션이므로 턴 상한과 비용 상한은 두지 않습니다.

그림 3-1은 표 3-3과 표 3-4의 값을 하네스에 적용했을 때 주체별로 수정할 수 있는 파일과, 작업 단위 하나의 검증 흐름을 보여 줍니다. 위쪽 두 영역은 수정할 수 있는 파일과 수정할 수 없는 파일이고, 아래는 검증 흐름입니다. 그림의 승인자는 되돌리기 어려운 동작과 작업 단위의 완료를 승인하는 사람입니다. 규칙 문서도 하네스의 설정에 속하지만, 설정 폴더(.claude/) 밖에 두는 지시이므로 그림에서는 설정 폴더와 따로 적었습니다.

검증 흐름에서 실선은 정상 흐름, 점선은 되돌아가거나 멈추는 경로입니다. 훅은 파일을 수정하는 도구(Edit, Write)가 실행될 때마다 단위 테스트를 자동으로 실행하고, 검사 스크립트는 구현 에이전트가 작업 단위를 마칠 때 실행합니다.

표 3-5는 그림 3-1의 구성 요소와 주요 역할을 정리합니다.

표 3-3과 표 3-4의 값 가운데 권한 규칙과 훅은 설정 파일(.claude/settings.json)로 옮깁니다. 아래는 그 파일의 내용입니다. 실습 파일에는 python 명령이 없는 환경에서 사용하는 python3 허용 규칙 두 줄이 더 있으며, 여기서는 생략했습니다. 그런 환경에서는 훅 명령의 python도 python3로 변경합니다.

{
  "permissions": {
    "allow": [
      "Bash(python -m unittest *)",
      "Bash(python check.py)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(./data/**)",
      "Edit(./acceptance/**)",
      "Edit(./check.py)",
      "Edit(./CLAUDE.md)",
      "Edit(./DECISIONS.md)",
      "Edit(./.claude/**)",
      "Bash(git push *)",
      "WebFetch",
      "WebSearch"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "cd \"$CLAUDE_PROJECT_DIR\" && python -m unittest discover tests -q || exit 2" }
        ]
      }
    ]
  }
}

허용 목록의 python -m unittest는 단위 테스트를, python check.py는 검사 스크립트를 실행하는 명령입니다. 별표가 없는 Bash(git status)는 git status와 정확히 같은 명령만 허용합니다. 훅의 matcher에 적은 Edit|Write는 파일 수정 도구(Edit) 또는 파일 작성 도구(Write)가 실행된 뒤를 뜻하며, |는 "또는"입니다. type이 command인 항목은 command에 적은 셸 명령을 실행합니다.

훅 명령은 먼저 cd로 세션을 시작한 폴더로 이동하고, 이동에 성공했을 때만(&&) tests 폴더의 단위 테스트를 찾아 실행합니다. $CLAUDE_PROJECT_DIR은 세션을 시작한 폴더의 경로를 담아 Claude Code가 전달하는 환경 변수입니다. 훅의 명령은 Claude Code의 현재 작업 폴더에서 실행되고, 작업 폴더는 Claude Code가 cd로 옮기면 따라 바뀝니다10. 하위 폴더에서는 tests 폴더를 찾지 못하므로, 먼저 세션을 시작한 폴더로 이동하게 했습니다. 명령 끝의 || exit 2는 테스트가 실패하면 종료 코드 2로 끝내라는 뜻이며, 단위 테스트를 실행하는 Python의 시험 모듈(unittest)은 결과를 오류 출력에 작성하므로 실패 내용이 모델에 전달됩니다.

검토 하위 에이전트는 별도 파일(.claude/agents/reviewer.md)에 정의하고, 도구를 읽기 도구인 Read(파일 읽기), Grep(내용 검색), Glob(이름 패턴으로 파일 찾기)로 제한합니다. 아래는 그 파일의 내용입니다.

---
name: reviewer
description: 변경 요청 사항(docs/CR.md)의 변경 내용을 수용 기준과 대조해 보고하는 검토 에이전트

근거 파일과 줄 번호를 함께 보고해 줘. 파일은 수정하지 마.

정의 파일에서 두 줄의 --- 사이는 이름(name), 설명(description), 도구(tools)를 정하는 설정이고, 그 아래는 검토 하위 에이전트에게 주는 지시입니다. 검토 하위 에이전트는 명령을 실행할 수 없어 git diff를 직접 실행하지 못합니다. 그래서 규칙 문서의 작업 순서에 "확인 방법을 충족하면 commit 전에 reviewer 하위 에이전트에게 바뀐 파일 목록과 변경 내용(git status, git diff 출력)을 넘겨 수용 기준 대조를 요청한다"라고 적습니다. 검토 보고는 수용 기준과 코드를 읽고 비교한 결과이고, 실제로 동작하는지는 단위 테스트와 검사 스크립트의 실행 결과가 보여 줍니다.

이 예제의 확인 방법에도 빈틈이 있어, 사람이 commit 확인에서 보완합니다. 작업 2의 확인 방법(수용 시험 4, 5 통과)은 기존 요청의 표시와 원본 자료의 보존이라는 기존 동작만 시험하므로, 구현 전에도 통과합니다. 작업 3은 이름에 project_code가 든 시험이 있으면 충족되므로, 아무것도 확인하지 않는 시험이라도 통과합니다. 그래서 작업 2는 데이터 모델의 변경을, 작업 3은 시험이 바뀐 데이터 모델을 실제로 확인하는지를 사람이 직접 봅니다. tasks.json도 에이전트가 수정할 수 있는 파일이므로, 작업 5의 통과 값과 확인 방법 문구가 그대로인지도 commit 확인에서 봅니다.

목록에 없는 코드를 거부하는지 보는 수용 시험에서 비교하는 줄을 지우면, 검사 스크립트는 통과하고 거부 기능은 없는 채로 완료가 보고될 수 있습니다. 그래서 수용 시험의 수정은 금지 규칙으로 막습니다.

설정과 결과의 확인 방법

명세서를 하네스 설정 파일로 옮긴 뒤에는, 파일이 실제로 적용되었는지 Claude Code의 화면과 검사 출력으로 확인합니다. 표 3-6은 변경 요청 사항을 구현하는 에이전트의 확인 방법입니다. /permissions와 /hooks는 실습 폴더에서 Claude Code를 실행한 뒤 대화 입력창에 입력하는 명령이며, Claude Code 문서에 따르면 각각 권한 규칙과 훅 설정을 보여 줍니다24. python check.py는 터미널에서 실습 폴더(expense-practice)로 이동한 뒤 실행합니다. 종료 코드는 출력에 나오지 않으므로, 명령 바로 뒤에 Git Bash와 macOS, Linux에서는 echo $?로, PowerShell에서는 $LASTEXITCODE로 확인합니다. 직접 실행하는 순서는 확인 방법 칸에 적은 부록 실습에 있습니다.
