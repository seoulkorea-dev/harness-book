Chapter 3 하네스로 에이전트 설계하기

같은 모델과 같은 제품이라도, 맡길 업무에 맞게 하네스(Harness)의 설정을 정해야 그 업무를 위한 에이전트(Agent)가 됩니다. 에이전트의 동작을 정하는 것은 요청 문장이 아니라, 목적부터 승인 지점까지 하네스의 설정에 정해 둔 항목입니다. 그래서 항목 하나가 비어 있으면 그 부분은 모델의 추측이나 제품의 기본값으로 채워집니다. 따라서 에이전트를 만들기 전에 명세서로 항목을 모두 정해야 합니다. 이 장에서는 에이전트 명세서를 작성하고, 작은 웹 서비스에 기능을 추가하는 에이전트를 설계해 제품 파일로 옮기는 방법을 다룹니다.

  • 에이전트 명세서는 목적, 역할, 입력, 도구, 권한, 기록, 검증, 종료 조건, 승인 지점의 아홉 항목입니다.
  • 명세서는 업무 한 건에 적용해 항목마다 값을 정합니다. 에이전트가 수정할 수 있는 파일과 수정할 수 없는 파일을 나누면 검증 기준을 보호할 수 있습니다.
  • 명세서의 항목은 규칙 문서, 권한 설정, 하위 에이전트, 훅 같은 제품 파일로 옮깁니다.

에이전트 명세서

에이전트 명세서는 맡길 업무를 하네스의 설정으로 옮기기 전에 정할 항목의 목록입니다. 명세서는 아홉 항목으로 구성합니다. 표 3-1은 항목별로 정할 내용과 자세히 다루는 장을 보여 줍니다.

종료 조건은 명세서에서 누락되기 쉬운 항목입니다. Agent SDK 문서는 상한이 없으면 열린 요청에서 루프가 오래 실행될 수 있다고 설명합니다(Anthropic, 2026). 명세서의 각 항목은 다음 절의 예제처럼 업무 한 건에 적용해 채웁니다.

기능 추가 에이전트: CR 구현

이 절은 명세서를 작은 웹 서비스의 기능 추가에 적용합니다. 소재는 가상 프로젝트인 경비 정산 시스템 개편의 미니 웹 앱입니다. 앱은 정산 요청을 등록하고 목록으로 보여 주며, Python 표준 라이브러리만으로 동작합니다.

추가할 기능은 경비 정산 시스템 개편 변경 요청(Change Request) CR입니다. CR은 재무팀이 2026년 10월 5일 요청한 변경으로, 정산 요청 화면에 프로젝트 코드 선택 항목을 추가합니다. 요청 사유는 프로젝트별 경비 집계를 월말 결산에 반영하는 것입니다. CR의 영향 검토는 Chapter 4, 작업 단위 분할은 Chapter 6, 결정 기록은 Chapter 8에서 이어집니다.

이 변경은 한 번의 응답으로 끝나지 않습니다. 데이터 구조, 화면, 테스트를 차례로 수정하고, 수정할 때마다 기존 기능이 깨지지 않았는지 확인해야 합니다. 그래서 명세서의 아홉 항목이 모두 필요합니다. CR의 수용 기준은 다섯 가지입니다.

  • 등록 화면에서 프로젝트 코드 목록의 코드를 선택할 수 있습니다.
  • 목록에 없는 코드로 등록하면 거부하고 사유를 표시합니다.
  • 목록 화면에 프로젝트 코드를 표시합니다.
  • 프로젝트 코드가 없는 기존 요청도 목록에 그대로 표시합니다.
  • 프로젝트 코드 원본 파일은 변경하지 않습니다.

표 3-2는 이 업무에 명세서를 적용한 결과입니다.

그림 3-1은 이 명세서를 하네스로 옮긴 구조입니다. 사람, 구현 에이전트, 검토 하위 에이전트(Subagent)의 역할과, 에이전트가 수정할 수 있는 파일과 수정할 수 없는 파일, 작업 단위 하나의 검증 흐름을 보여 줍니다.

표 3-3은 그림 3-1의 구성 요소를 설명합니다.

이 설계에서 가장 중요한 결정은 검증 기준을 보호하는 것입니다. 에이전트는 단위 테스트를 수정할 수 있습니다. 화면과 데이터 구조가 변경되면 기존 테스트도 함께 수정해야 하기 때문입니다. 반면 수용 시험과 검사 스크립트는 사람이 작성하고, 에이전트는 수정할 수 없습니다. 실패하는 시험을 수정해서 완료를 만드는 길을 막기 위해서입니다.

종료 조건과 승인 지점도 명세서에서 정합니다. 작업 단위는 검사 스크립트가 통과하면 끝나고, 같은 시험이 세 번 연속 실패하면 에이전트는 중단하고 인계 메모를 남깁니다. commit은 실행 전에 확인을 받고, push는 사람만 실행합니다. 작업은 두 세션으로 나누고, 두 번째 세션은 인계 메모를 읽고 시작합니다(Chapter 8의 인계 메모).

제품 파일로 옮기기

명세서의 항목은 Claude Code의 파일로 옮겨야 실제로 작동합니다. 표 3-4는 항목별로 옮길 파일을 보여 줍니다.

다음은 권한과 훅(Hook)을 정한 설정 파일입니다. 코드 원본, 수용 시험, 검사 스크립트, 규칙 문서의 수정을 금지해서, 에이전트가 검증 기준 자체를 변경하지 못하게 합니다.

{
  "permissions": {
    "allow": [
      "Bash(python -m unittest *)",
      "Bash(python check.py)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(./data/**)",
      "Edit(./acceptance/**)",
      "Edit(./check.py)",
      "Edit(./CLAUDE.md)",
      "Edit(./DECISIONS.md)",
      "Edit(./.claude/**)",
      "Bash(git push *)",
      "WebFetch",
      "WebSearch"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python -m unittest discover tests -q || exit 2" }
        ]
      }
    ]
  }
}

훅은 파일 편집 도구가 실행된 뒤마다 단위 테스트를 실행합니다. 테스트가 실패하면 종료 코드 2로 끝나도록 해서, 실패 내용이 모델에 전달되게 합니다. Claude Code 문서는 PostToolUse 훅이 종료 코드 2로 끝나면 오류 출력을 모델에 보여 준다고 설명합니다(Anthropic, 2026b).

다음은 검토 하위 에이전트의 정의 파일입니다. 도구를 읽기 도구로 제한해서, 검토 에이전트가 코드를 수정하지 못하게 합니다.

---
name: reviewer
description: CR 변경 내용을 수용 기준과 대조해 보고하는 검토 에이전트
tools: Read, Grep, Glob
---
docs/CR.md의 수용 기준을 읽고, 변경된 코드와 테스트가
기준마다 충족, 미충족, 확인 불가 가운데 어디에 해당하는지
근거 파일과 줄 번호를 함께 보고해 줘. 파일은 수정하지 마.

이 구성을 직접 만들어 보는 실습은 부록 실습의 실습 1(기준 상태)과 실습 5(작업 단위로 구현)에 있습니다.

에이전트 설계는 명세서의 아홉 항목을 정하고, 각 항목을 하네스의 설정으로 옮기는 일입니다.
