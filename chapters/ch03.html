Chapter 3 하네스로 에이전트 설계하기

에이전트의 동작을 정하는 것은 요청 문장이 아니라, 목적부터 승인 지점까지 하네스에 정해 둔 항목입니다.

같은 모델과 같은 제품이라도, 맡길 업무에 맞게 하네스(Harness)의 설정을 정해야 그 업무를 위한 에이전트(Agent)가 됩니다. 정할 항목은 목적에서 시작해 승인 지점으로 끝나는 아홉 가지입니다. 항목 하나가 비어 있으면 그 부분은 모델의 추측이나 제품의 기본값으로 채워집니다. 따라서 에이전트를 만들기 전에 명세서로 아홉 항목을 모두 정합니다. 이 장에서는 에이전트 명세서를 작성하고, 작은 웹 서비스에 기능을 추가하는 에이전트를 설계해 제품 파일로 옮기는 방법을 다룹니다.

  • 에이전트 명세서는 목적, 역할, 입력, 도구, 권한, 기록, 검증, 종료 조건, 승인 지점의 아홉 항목입니다.
  • 명세서는 업무 한 건에 적용해 항목마다 값을 정합니다. 검증 기준(수용 시험, 검사 스크립트)을 에이전트가 수정할 수 없는 파일에 두면, 실패하는 시험을 수정해서 완료를 만드는 길을 막을 수 있습니다.
  • 명세서의 항목은 규칙 문서, 권한 설정, 하위 에이전트, 훅 같은 제품 파일로 옮깁니다.

에이전트 명세서

에이전트 명세서는 맡길 업무를 하네스의 설정으로 옮기기 전에 정할 항목의 목록입니다. 명세서는 아홉 항목으로 구성합니다. 표 3-1은 항목별로 정할 내용과 자세히 다루는 장을 보여 줍니다.

종료 조건은 명세서에서 누락되기 쉬운 항목입니다. Agent SDK 문서는 상한이 없으면 열린 요청에서 루프가 오래 실행될 수 있다고 설명합니다(Anthropic, 2026). 명세서의 각 항목은 다음 절의 예제처럼 업무 한 건에 적용해 채웁니다.

기능 추가 에이전트: CR 구현

이 절은 명세서를 작은 웹 서비스의 기능 추가에 적용합니다. 소재는 가상 프로젝트인 경비 정산 시스템 개편의 미니 웹 앱입니다. 앱은 정산 요청을 등록하고 목록으로 보여 주며, Python 표준 라이브러리만으로 동작합니다. 앱 코드는 expense/ 폴더와 app.py, 단위 테스트는 tests/ 폴더에 있습니다. 등록할 수 있는 프로젝트 코드는 data/ 폴더의 목록 파일에 있으며, 이 장에서는 이 파일을 원본 자료라고 부릅니다.

추가할 기능은 경비 정산 시스템 개편 변경 요청(Change Request) CR이 요구하는 기능입니다. 경비 정산 시스템 개편은 가상 프로젝트의 이름이고, CR은 이 프로젝트에 들어온 변경 요청 한 건입니다. CR은 재무팀이 2026년 10월 5일 요청한 변경으로, 정산 요청 화면에 프로젝트 코드 선택 항목을 추가합니다. 요청 사유는 프로젝트별 경비 집계를 월말 결산에 반영하는 것입니다. 영향 검토는 변경이 기존 기능과 자료에 미치는 영향을 미리 살피는 일이고, 작업 단위는 결과를 따로 확인할 수 있게 나눈 작업 한 덩어리입니다. CR은 작업 1부터 작업 5까지 다섯 작업 단위로 나뉘며, 작업 5는 프로젝트별 집계를 확인하는 통합 시나리오의 초안이라 사람이 승인합니다. CR의 영향 검토는 Chapter 4, 작업 단위 분할은 Chapter 6, 결정 기록은 Chapter 8에서 이어집니다.

이 변경은 한 번의 응답으로 끝나지 않습니다. 데이터 구조, 화면, 테스트를 차례로 수정하고, 수정할 때마다 기존 기능이 깨지지 않았는지 확인해야 합니다. 그래서 명세서의 아홉 항목이 모두 필요합니다. 수용 기준(Acceptance Criteria)은 사람이 정한 완료 조건이고, 수용 시험(acceptance/의 시험)은 그 조건을 충족하는지 확인하는 시험입니다. 수용 시험은 사람이 작성합니다. CR의 수용 기준은 다섯 가지입니다.

  • 등록 화면에서 프로젝트 코드 목록의 코드를 선택할 수 있습니다.
  • 목록에 없는 코드로 등록하면 거부하고 사유를 표시합니다.
  • 목록 화면에 프로젝트 코드를 표시합니다.
  • 프로젝트 코드가 없는 기존 요청도 목록에 그대로 표시합니다.
  • 원본 자료(data/projects.csv)는 변경하지 않습니다.

표 3-2는 이 업무에 명세서를 적용한 결과입니다. 검사 스크립트(check.py)는 단위 테스트와 수용 시험을 한 번에 실행하는 파일입니다. 이 장에서는 수용 시험과 검사 스크립트처럼 완료를 판정하는 파일을 검증 기준이라고 부릅니다.

그림 3-1은 이 명세서를 하네스로 옮긴 구조입니다. 사람, 구현 에이전트, 검토 하위 에이전트(Subagent)의 역할과, 에이전트가 수정할 수 있는 파일과 수정할 수 없는 파일, 작업 단위 하나의 검증 흐름을 보여 줍니다. 작업 단위의 통과 값은 tasks.json에 작업 단위마다 적는 검사 통과 여부이고, 설정 폴더는 권한과 훅(Hook), 하위 에이전트 정의를 두는 .claude/ 폴더입니다. 훅은 파일을 편집할 때마다 자동으로 실행되고, check.py는 구현 에이전트가 작업 단위를 마칠 때 실행합니다.

표 3-3은 그림 3-1의 구성 요소를 설명합니다.

이 설계에서 가장 중요한 결정은 검증 기준을 보호하는 것입니다. 에이전트는 단위 테스트를 수정할 수 있습니다. 화면과 데이터 구조가 변경되면 기존 테스트도 함께 수정해야 하기 때문입니다. 반면 수용 시험과 검사 스크립트는 사람이 작성하고, 에이전트는 수정할 수 없습니다. 실패하는 시험을 수정해서 완료를 만드는 길을 막기 위해서입니다.

종료 조건과 승인 지점도 명세서에서 정합니다. 작업 단위는 검사 스크립트가 통과하면 끝나고, 같은 시험이 세 번 연속 실패하면 에이전트는 중단하고 인계 메모를 남깁니다. commit은 실행 전에 확인을 받고, push는 사람만 실행합니다. 작업은 두 세션으로 나누고, 두 번째 세션은 인계 메모를 읽고 시작합니다(Chapter 8의 인계 메모).

제품 파일로 옮기기

명세서의 항목은 Claude Code의 파일로 옮겨야 실제로 작동합니다. 표 3-4는 항목별로 옮길 파일을 보여 줍니다.

다음은 권한과 훅을 정한 설정 파일입니다. 수용 시험, 검사 스크립트, 원본 자료의 수정을 금지해서, 에이전트가 검증 기준과 그 기준이 판정하는 자료를 변경하지 못하게 합니다. 규칙 문서(CLAUDE.md), 결정 기록(DECISIONS.md), 설정 폴더(.claude/)도 금지해서, 에이전트가 자기 규칙을 변경하지 못하게 합니다. 검사 스크립트는 수정만 금지하고 실행(python check.py)은 허용합니다.

권한 규칙(Permission Rule)은 허용(allow), 확인 요청(ask), 금지(deny)의 세 목록에 둡니다. 각 규칙은 도구 이름 뒤 괄호에 대상을 적습니다. Edit(./data/**)는 data/ 아래 파일의 수정, Bash(git push *)는 git push로 시작하는 명령을 가리키며, *는 아무 문자열과 일치합니다. Claude Code 문서는 괄호 없이 도구 이름만 적은 금지 규칙(WebFetch, WebSearch)이 그 도구를 모델의 컨텍스트(Context)에서 없앤다고 설명합니다(Anthropic, 2026e). 규칙의 평가 순서와 한계는 Chapter 9에서 다룹니다.

{
  "permissions": {
    "allow": [
      "Bash(python -m unittest *)",
      "Bash(python check.py)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(./data/**)",
      "Edit(./acceptance/**)",
      "Edit(./check.py)",
      "Edit(./CLAUDE.md)",
      "Edit(./DECISIONS.md)",
      "Edit(./.claude/**)",
      "Bash(git push *)",
      "WebFetch",
      "WebSearch"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python -m unittest discover tests -q || exit 2" }
        ]
      }
    ]
  }
}

훅은 파일 편집 도구가 실행된 뒤마다 단위 테스트를 실행합니다. 종료 코드는 명령이 끝날 때 돌려주는 값이며, 0은 성공, 0이 아닌 값은 실패를 뜻합니다. 명령 끝의 || exit 2는 앞의 테스트가 실패하면 종료 코드 2로 끝내라는 뜻이며, 이렇게 해야 실패 내용이 모델에 전달됩니다. Claude Code 문서는 PostToolUse 훅이 종료 코드 2로 끝나면 오류 출력을 모델에 보여 주지만, 이미 실행된 도구는 막지 못한다고 설명합니다(Anthropic, 2026b).

다음은 검토 하위 에이전트의 정의 파일입니다. 도구를 읽기 도구로 제한해서, 검토 에이전트가 코드를 수정하지 못하게 합니다.

---
name: reviewer
description: CR 변경 내용을 수용 기준과 대조해 보고하는 검토 에이전트
tools: Read, Grep, Glob
---
docs/CR.md의 수용 기준을 읽고, 변경된 코드와 테스트가
기준마다 충족, 미충족, 확인 불가 가운데 어디에 해당하는지
근거 파일과 줄 번호를 함께 보고해 줘. 파일은 수정하지 마.

정의 파일에서 두 줄의 --- 사이는 이름(name), 설명(description), 도구(tools)를 정하는 설정이고, 그 아래는 검토 에이전트에게 주는 지시입니다. Claude Code 문서에 따르면 도구 줄을 생략한 하위 에이전트는 사용할 수 있는 도구를 모두 물려받습니다(Anthropic, 2026b). 그래서 읽기만 해야 하는 검토 에이전트는 도구 줄에 읽기 도구만 적습니다. 검토를 요청하는 시점은 규칙 문서(CLAUDE.md)의 작업 순서에 "작업 단위를 마치기 전에 reviewer 하위 에이전트에게 수용 기준 대조를 요청한다"로 적습니다.

실패와 막는 장치

명세서의 항목이 비어 있거나 제품 파일로 옮겨지지 않으면, CR 구현에서 실패가 생길 수 있습니다. 표 3-5는 CR 구현에서 생길 수 있는 다섯 가지 대표 실패와 원인이 되는 명세서 항목, 실패를 막는 장치입니다. 막는 장치에는 강제와 지시를 함께 적었습니다.

강제는 에이전트의 판단과 관계없이 작동하는 권한 규칙과 도구 제한입니다. 지시는 규칙 문서(CLAUDE.md)에 적어 에이전트가 따르게 하는 것으로, 중단 규칙, 완료 기준, 기록, 검토를 요청하는 시점이 여기에 해당합니다. Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 다루며, 지시를 엄격하게 따른다는 보장은 없다고 설명합니다(Anthropic, 2026d). 반드시 막아야 하는 동작은 권한 규칙이나 훅으로 둡니다(Chapter 2의 지시와 강제).

확인 방법

명세서를 제품 파일로 옮긴 뒤에는, 파일이 실제로 적용되었는지 제품 화면과 검사 출력으로 확인합니다. 표 3-6은 CR 구현 에이전트를 확인하는 위치입니다. 화면 명령의 설명은 Claude Code 문서(Commands)를 따릅니다(Anthropic, 2026c). 직접 실행하는 순서는 표의 실습 열에 적은 부록 실습에 있습니다. 표의 python check.py는 실습 폴더(examples/expense-app/)에서 실행합니다. 수용 시험 5건은 앞의 수용 기준 다섯 가지에 하나씩 대응하며, 구현 전에는 기존 동작에 해당하는 넷째와 다섯째 기준만 통과합니다.

원칙과 점검 질문

명세서의 아홉 항목을 모두 정하고, 검증 기준(수용 시험, 검사 스크립트)은 에이전트가 수정할 수 없는 파일에 둡니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 맡길 업무의 명세서에서 아직 값을 정하지 않은 항목은 무엇입니까?
  2. 에이전트가 검증 기준을 수정할 수 있는 경로가 남아 있습니까?
  3. 명세서의 각 항목이 어느 제품 파일에 옮겨져 있는지 표 3-4처럼 말할 수 있습니까?
