Chapter 2 하네스의 구성 요소

하네스의 품질을 정하는 것은 연결한 도구의 수가 아니라, 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소를 모두 정했는지입니다.

에이전트(Agent)는 주어진 역할 안에서, 연결된 도구를 사용해, 허용된 권한 범위의 작업을 수행합니다. 그런데 하네스(Harness)에 도구만 연결하고 권한, 기록, 검증을 정하지 않으면, 에이전트가 작업을 마쳐도 그 결과를 받아들일 근거가 없습니다. 그래서 하네스를 설계할 때는 구성 요소마다 무엇을 정해야 하는지 먼저 알고, 반드시 지킬 규칙은 지시가 아니라 강제 수단으로 처리해야 합니다. 이 장에서는 하네스의 다섯 구성 요소와 구성 요소별로 정할 것, 그리고 지시와 강제의 구분을 살펴봅니다.

  • 하네스는 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소로 설계합니다.
  • 규칙 문서는 지시이고, 권한 규칙과 훅은 강제입니다.
  • 반드시 지켜야 하는 규칙은 강제 수단으로 처리합니다.

다섯 구성 요소

하네스는 모델에 입력과 컨텍스트(Context)를 넘기고, 모델의 응답이나 도구 호출을 받아 외부 실행 환경에서 실행하며, 이 과정을 목표까지 반복합니다(Chapter 1). 이 장은 그 가운데 사용자가 정하는 설정, 곧 다섯 구성 요소에 초점을 둡니다. 요청과 컨텍스트 설계는 Chapter 4~5, 작업 분할과 실행 흐름은 Chapter 6에서 다룹니다. 구성 요소마다 정하는 대상이 다릅니다.

  • 역할: 에이전트가 맡는 작업의 범위입니다. 에이전트가 할 작업과 사람이 할 작업의 경계를 정합니다. 경계가 없으면 발송이나 배포처럼 사람이 판단할 일까지 에이전트가 진행할 수 있습니다.
  • 도구: 에이전트가 사용할 수 있는 기능입니다. 도구가 없으면 에이전트는 자료를 읽거나 결과를 만들 수 없습니다. 도구가 너무 많으면 컨텍스트를 차지합니다(도구 노출 범위).
  • 권한: 도구로 할 수 있는 동작의 범위입니다. 같은 파일 도구라도 읽기만 허용할지, 수정까지 허용할지를 정합니다.
  • 기록: 다음 작업에 넘길 정보입니다. 새 세션에서 이전 대화가 자동으로 이어진다고 가정할 수 없습니다(Chapter 1, Anthropic, 2026a). 그래서 세션이 끝난 뒤에도 남아야 할 결정과 진행 상황은 파일로 남깁니다.
  • 검증: 결과를 받아들이기 전에 확인하는 절차입니다. 에이전트의 완료 보고만으로는 결과가 맞는지 알 수 없으므로, 확인 방법을 미리 정합니다.

그림 2-1과 표 2-1의 예는 Chapter 3에서 설계하는 경비 정산 시스템 개편 변경 요청(Change Request) CR입니다. CR은 정산 요청 화면에 프로젝트 코드 선택 항목을 추가하는 변경이며, 에이전트는 이 변경을 작업 단위로 나누어 차례로 구현합니다.

그림 2-1은 다섯 구성 요소를 하는 일에 따라 지시(역할, 기록), 실행 수단(도구), 강제(권한, 검증)로 묶고, 구성 요소마다 정할 것, CR에서 채운 방법, 이유와 에이전트 루프에서 주로 작동하는 단계(그림 1-2의 번호)를 보여 줍니다. 다섯 구성 요소와 세 묶음은 이 책의 정리입니다. 구성 요소는 루프의 한 단계에만 고정되지 않고 여러 지점에서 관여할 수 있으므로, 그림의 번호와 빈 원은 주로 작동하는 단계만 가리킵니다.

CR에서 실제로 사용한 파일과 설정은 표 2-1에 정리했습니다.

표 2-1의 CR 열은 부록 실습의 예제 파일(examples/expense-app/reference/)을 기준으로, 2026년 10월에 확인한 Claude Code 문서에 맞춰 작성했습니다. Codex의 구현 방법은 Chapter 10의 제품 단위 비교에서 다룹니다.

하위 에이전트(Subagent)는 특정 작업을 맡도록 별도로 정의한 에이전트입니다. MCP(Model Context Protocol)는 외부 시스템의 기능을 에이전트의 도구로 연결하는 규약이며, 이를 구현한 서버를 MCP 서버라고 합니다. 자동 메모리는 Claude Code가 작업 중에 알게 된 내용을 기기 안의 파일에 스스로 기록하고 다음 세션에 읽는 기능입니다(Anthropic, 2026a). 수용 시험은 수용 기준(결과물이 받아들여지기 위해 충족해야 하는 조건)을 충족하는지 확인하는 시험이며, 사람이 작성하고 에이전트는 수정하지 않습니다. 원본 자료는 프로젝트 코드 목록 파일(data/projects.csv)입니다.

도구 노출 범위

도구를 많이 연결할수록 에이전트가 할 수 있는 일은 늘어나지만, 비용도 함께 늘어납니다. 연결한 도구의 정의는 컨텍스트 공간을 차지하며, Claude Code에서는 /context 화면의 도구 항목으로 그 크기를 확인합니다(Anthropic, 2026c). 도구가 늘어나 기능이 겹치면 에이전트가 어느 도구를 쓸지 모호한 결정 지점이 생기므로, Claude Code는 작업에 필요한 최소한의 도구 집합을 권합니다(Rajasekaran 외, 2025). 문서도 도구를 선별해서 연결하고, 하위 에이전트에는 필요한 최소한의 도구만 지정하라고 안내합니다(Anthropic, 2026b).

Claude Code는 도구 노출을 줄이는 장치를 둡니다. MCP 서버의 도구 정의는 기본적으로 바로 불러오지 않고, 도구 이름과 서버 안내만 컨텍스트에 둔 뒤 필요할 때 불러옵니다. 이 동작은 MCP 규약이 아니라 Claude Code의 기능입니다. 비용 문서는 gh, aws 같은 명령줄 도구가 도구 목록을 추가하지 않아 MCP 서버보다 컨텍스트를 적게 차지한다고 설명하고, 사용하지 않는 서버는 끄라고 안내합니다(Anthropic, 2026b).

노출 범위는 가용성과 권한 평가를 함께 정합니다. 가용성은 작업에 어떤 도구를 제공할지, 곧 모델이 볼 수 있는 도구의 범위를 정하는 것이고, 권한 평가는 모델이 도구를 호출할 때 그 동작을 금지, 확인, 허용 가운데 무엇으로 처리할지 판단하는 것입니다. 권한 규칙(Permission Rule)은 금지, 확인, 허용의 순서로 평가되고, 처음 일치하는 규칙이 결과를 정합니다. 금지 규칙에 일치하는 호출은 실행되지 않고, 도구 이름만 지정한 금지 규칙(예: WebFetch)은 그 도구를 목록에서 제외합니다(Anthropic, 2026a). 권한 규칙 가운데 도구를 목록에서 제외하는 것은 도구 이름만 지정한 금지 규칙뿐이고, 그 밖의 규칙은 호출할 때마다 평가됩니다. Agent SDK 문서에 따르면 모델은 도구 호출을 요청하고, SDK가 요청된 도구를 실행합니다(Anthropic, 2026b). 이 책은 이 실행 주체를 하네스라고 부릅니다. 거부된 호출은 실행되지 않고, 거부 메시지가 도구 결과로 모델에 전달됩니다. 이 문서에 따르면 읽기 전용 도구는 동시에 실행될 수 있고, 상태를 변경하는 도구는 충돌을 막기 위해 차례로 실행됩니다(Anthropic, 2026b). 그림 2-2는 예제 CR 기준의 도구 구성과, 도구가 호출될 때마다 권한 규칙으로 평가되어 실행되거나 거부되는 흐름을 보여 줍니다. 단계 번호는 이 책이 정리한 그림 1-2의 번호를 따르며, 실행 결과와 거부 메시지는 그림 1-2처럼 이력에 쌓여 다음 판단의 입력이 됩니다.

표 2-2는 그림 2-2의 구성 요소를 설명합니다.

도구 노출 범위에서 정할 것은 세 가지입니다.

  • 작업에 연결할 도구: 작업 단위마다 필요한 도구만 연결합니다. CR은 저장소 안의 파일만 다루므로 웹 접근 도구를 제외했습니다.
  • 읽기와 수정의 구분: 조회만 필요한 작업에는 읽기 도구만 허용합니다.
  • 하위 에이전트의 도구: 하위 에이전트에는 맡긴 작업에 필요한 최소한의 도구만 지정합니다.

지시와 강제

구성 요소를 구현하는 수단은 지시와 강제로 나뉩니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단이며, 규칙 문서가 해당합니다. 강제는 에이전트의 판단과 관계없이 도구가 동작을 허용하거나 막는 수단이며, 권한 규칙과 훅(Hook)이 해당합니다.

Claude Code 문서는 권한 규칙을 모델이 아니라 Claude Code가 적용한다고 설명합니다. 프롬프트나 CLAUDE.md의 지시는 에이전트가 시도하는 동작에 영향을 주지만, 허용되는 동작 자체는 정하지 않습니다. 훅은 정해진 시점에 실행되는 셸 명령이며, 에이전트의 판단과 관계없이 적용됩니다(Anthropic, 2026a).

표 2-3의 기준은 규칙을 어겼을 때의 결과입니다. 어겼을 때 다시 작업하면 되는 규칙은 지시로 충분합니다. 원본 자료의 손상이나 외부 발송처럼 되돌리기 어려운 결과를 낳는 규칙은 강제 수단으로 처리합니다. Claude Code 문서도 규칙 문서를 강제 설정이 아닌 컨텍스트로, 권한 규칙과 훅을 모델의 결정과 관계없이 한계를 지키게 하는 수단으로 설명합니다(Anthropic, 2026c).

표 2-4는 CR의 규칙을 지시와 강제로 나눈 것입니다.

규칙 문서만 있는 상태에서는 수용 시험을 수정하려는 시도를 막지 못하고, 금지 규칙을 더하면 같은 시도가 거부됩니다(부록 실습 2, 3). 훅은 시점에 따라 하는 일이 다릅니다. 도구 실행 전에 실행되는 PreToolUse 훅은 호출을 막을 수 있고, 실행 뒤에 실행되는 PostToolUse 훅은 이미 실행된 편집을 막지 못하고 오류를 모델에 알립니다(Anthropic, 2026d). 또 파일 수정 금지 규칙은 파일을 스스로 여는 스크립트를 통한 간접 수정까지 막지는 못합니다. 이런 경우의 보완 수단인 샌드박스(Sandbox)와 권한 규칙의 평가 순서는 Chapter 9에서 다룹니다.

도구만 연결하면 에이전트가 된다는 의견이 있습니다. 도구만 연결된 에이전트는 작업을 수행할 수는 있지만, 원본 자료를 변경하지 않았는지, 수치가 맞는지 확인할 근거를 남기지 않습니다. 권한, 기록, 검증은 사용자가 결과를 받아들이기 위한 근거입니다.

실패와 막는 장치

다섯 구성 요소 가운데 하나를 정하지 않으면, 그 구성 요소에서 실패가 생깁니다. 표 2-5는 CR을 구현하는 에이전트에서 구성 요소별로 생길 수 있는 실패와 막는 장치입니다. 막는 장치는 표 2-1과 표 2-4의 장치와 같은 이름으로 적었습니다. 통합 테스트 시나리오는 여러 기능을 이어서 실행해 확인하는 시험 절차이며, 이 예제에서는 그 범위를 사람이 승인합니다.

확인 방법

구성 요소를 정했는지는 설정 파일을 읽는 것만으로는 알 수 없고, 제품의 화면과 실행 기록으로 확인합니다. 표 2-6은 CR 구현 에이전트에서 구성 요소별로 확인하는 위치입니다. 표의 명령은 Claude Code의 대화 화면에 입력합니다(Anthropic, 2026c).

원칙과 점검 질문

다섯 구성 요소를 모두 정하고, 어기면 되돌리기 어려운 규칙은 규칙 문서가 아니라 권한 규칙과 훅으로 강제합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트의 하네스에서 다섯 구성 요소 가운데 정하지 않은 것은 무엇입니까?
  2. 규칙 문서에만 적어 둔 규칙 가운데 어기면 되돌리기 어려운 규칙은 무엇입니까?
  3. 연결한 도구 가운데 이 작업에 필요하지 않은 도구는 무엇입니까?
