Chapter 2 하네스의 구성 요소

하네스의 품질을 정하는 것은 연결한 도구의 수가 아니라, 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소를 모두 정했는지입니다.

에이전트(Agent)는 맡은 역할에 따라 도구를 사용하고, 허용된 권한 범위 안에서 작업합니다. 에이전트의 결과를 믿고 받아들이려면 도구를 연결하는 것만으로는 부족하고, 권한, 기록, 검증이 함께 설계되어야 합니다. 그래서 하네스(Harness)를 설계할 때는 구성 요소마다 무엇을 정해야 하는지 먼저 알아야 합니다. 반드시 지켜야 하는 규칙은 규칙 문서에 적는 지시로만 두지 않고, 모델의 판단과 관계없이 제품이 적용하는 강제 수단, 곧 권한 규칙(Permission Rule)과 훅(Hook)으로 처리할 때 확실하게 지켜집니다. 이 장에서는 하네스의 다섯 구성 요소와 구성 요소별로 정할 것, 그리고 지시와 강제를 나누는 방법을 살펴봅니다.

  • 하네스는 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소로 설계합니다.
  • 규칙 문서는 지시이고, 권한 규칙과 훅은 강제입니다.
  • 반드시 지켜야 하는 규칙은 강제 수단으로 처리합니다.

다섯 구성 요소

하네스는 모델에 입력과 컨텍스트(Context)를 넘기고, 모델의 응답이나 도구 호출을 받아 외부 실행 환경에서 실행하며, 이 과정을 목표까지 반복합니다(Chapter 1). 이 장은 그 가운데 사용자가 정하는 설정, 곧 다섯 구성 요소에 초점을 둡니다. 설정은 에이전트가 시작할 때 읽는 규칙 문서, 도구별 허용과 금지 목록인 권한 규칙, 정해진 시점에 자동으로 실행할 명령인 훅처럼 사용자와 팀이 파일로 정하는 값입니다. 요청과 컨텍스트 설계는 Chapter 4~5, 작업 단위 분할은 Chapter 6에서 다룹니다. 설정을 다섯으로 나누는 것은 하나가 빠질 때 생기는 실패가 구성 요소마다 다르기 때문입니다(실패와 막는 장치). 구성 요소마다 정하는 대상을 차례로 봅니다.

  • 역할: 에이전트가 맡는 작업의 범위입니다. 에이전트가 할 작업과 사람이 할 작업의 경계를 정합니다. 경계가 없으면 발송이나 배포처럼 사람이 판단할 일까지 에이전트가 진행할 수 있습니다.
  • 도구: 에이전트가 사용할 수 있는 기능입니다. 도구가 없으면 에이전트는 자료를 읽거나 결과를 만들 수 없습니다. 도구가 너무 많으면 컨텍스트를 차지합니다(도구 노출 범위).
  • 권한: 도구로 할 수 있는 동작의 범위입니다. 같은 파일 도구라도 읽기만 허용할지, 수정까지 허용할지를 정합니다.
  • 기록: 다음 작업에 넘길 정보입니다. 새 세션에서 이전 대화가 자동으로 이어진다고 가정할 수 없습니다(Chapter 1, Anthropic, 2026a). 그래서 세션이 끝난 뒤에도 남아야 할 결정과 진행 상황은 파일로 남깁니다.
  • 검증: 결과를 받아들이기 전에 확인하는 절차입니다. 에이전트의 완료 보고만으로는 결과가 맞는지 알 수 없으므로, 확인 방법을 미리 정합니다.

이 장의 예는 Chapter 3에서 설계하는 경비 정산 시스템 개편 변경 요청(Change Request) CR입니다. CR은 정산 요청 화면에 프로젝트 코드 선택 항목을 추가하는 변경이며, 에이전트는 이 변경을 작업 단위로 나누어 차례로 구현합니다. 작업 단위는 작업 1부터 작업 5까지이며, 작업 5는 프로젝트별 집계를 확인하는 통합 시나리오(여러 기능을 이어서 실행해 확인하는 시험 절차)의 초안이라 사람이 승인합니다. 작업 단위의 완료 여부는 작업 단위 목록(tasks.json)에 통과 값(true 또는 false)으로 적습니다.

그림 2-1은 다섯 구성 요소를 하는 일에 따라 세 묶음으로 나눕니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단이고, 강제는 제품이 에이전트의 판단과 관계없이 적용하는 수단이며(자세한 구분은 지시와 강제), 실행 수단은 에이전트가 작업을 수행하는 데 사용하는 도구입니다. 역할은 지시로 묶었지만, 역할의 경계 가운데 되돌리기 어려운 것은 권한 규칙으로 막거나 사람에게 확인을 요청합니다(표 2-4). 검증은 편집 뒤 훅처럼 제품이 모델의 선택과 관계없이 실행하는 확인이 중심이라 강제로 묶었고, 검사 스크립트와 검토 보고는 그 위에서 완료 여부를 판단하는 근거입니다(표 2-1). 그림은 구성 요소마다 정할 것, 이유와 에이전트 루프에서 주로 작동하는 단계(그림 1-2의 번호)를 보여 줍니다. 다섯 구성 요소와 세 묶음은 이 책의 정리입니다. 구성 요소는 루프의 한 단계에만 고정되지 않고 여러 지점에서 관여할 수 있으므로, 그림의 번호는 주로 작동하는 단계만 가리킵니다. 검증은 번호가 있는 단계가 아니라 최종 응답 전의 완료 기준 확인에서 작동하므로 번호 없이 빈 원으로 표시합니다(Chapter 1).

CR에서 실제로 사용한 파일과 설정은 표 2-1에 정리했습니다. 표에 나오는 용어를 먼저 정리합니다. 규칙 문서(CLAUDE.md)는 에이전트가 세션을 시작할 때 읽는 지침 파일입니다. 권한 규칙은 도구로 하는 동작을 허용, 확인, 금지로 나눈 목록이며 설정 파일에 적습니다. 훅은 파일을 수정한 뒤처럼 정해진 시점에 자동으로 실행되는 명령이며, 이 책은 셸 명령을 실행하는 훅만 다룹니다. 하위 에이전트(Subagent)는 특정 작업을 맡도록 별도로 정의한 에이전트입니다. MCP(Model Context Protocol)는 외부 시스템의 기능을 에이전트의 도구로 연결하는 규약이며, 이를 구현한 서버를 MCP 서버라고 합니다. 자동 메모리는 Claude Code가 작업 중에 알게 된 내용을 기기 안의 파일에 스스로 기록하고 다음 세션에 읽는 기능입니다(Anthropic, 2026a). 수용 시험은 수용 기준(결과물이 받아들여지기 위해 충족해야 하는 조건)을 충족하는지 확인하는 시험이며, 사람이 작성하고 에이전트는 수정하지 않습니다. 원본 자료는 프로젝트 코드 목록 파일(data/projects.csv)입니다.

표 2-1의 CR 열은 부록 실습의 예제 파일(examples/expense-app/reference/)을 기준으로, 2026년 10월에 확인한 Claude Code 문서에 맞춰 작성했습니다. Codex의 구현 방법은 Chapter 10의 제품 단위 비교에서 다룹니다.

도구 노출 범위

다섯 구성 요소 가운데 도구와 권한은 에이전트가 할 수 있는 일을 직접 정하므로 따로 자세히 봅니다. 도구를 많이 연결할수록 에이전트가 할 수 있는 일은 늘어나지만, 비용도 함께 늘어납니다. 연결한 도구의 정의는 컨텍스트 공간을 차지하며(Anthropic, 2026b), Claude Code에서는 /context 화면의 도구 항목으로 그 크기를 확인합니다(Anthropic, 2026c). 도구가 늘어나 기능이 겹치면 에이전트가 어느 도구를 쓸지 모호한 결정 지점이 생기므로, Claude Code는 작업에 필요한 최소한의 도구 집합을 권합니다(Rajasekaran 외, 2025). Claude Code 문서도 도구를 선별해서 연결하고, 하위 에이전트에는 필요한 최소한의 도구만 지정하라고 안내합니다(Anthropic, 2026b).

Claude Code는 도구 노출을 줄이는 장치를 둡니다. MCP 서버의 도구 정의는 기본적으로 바로 불러오지 않고, 도구 이름과 서버 안내만 컨텍스트에 둔 뒤 필요할 때 불러옵니다. 이 동작은 MCP 규약이 아니라 Claude Code의 기능입니다. Claude Code의 비용 문서는 gh, aws 같은 명령줄 도구가 도구 목록을 추가하지 않아 MCP 서버보다 컨텍스트를 적게 차지한다고 설명하고, 사용하지 않는 서버는 끄라고 안내합니다(Anthropic, 2026b).

이 책은 도구 노출 범위를 두 단계로 나눕니다. 가용성은 작업에 어떤 도구를 제공할지, 곧 모델이 볼 수 있는 도구의 범위를 정하는 것이며 도구 구성 요소가 맡습니다. 권한 평가는 모델이 도구를 호출할 때 그 동작을 금지, 확인, 허용 가운데 무엇으로 처리할지 판단하는 것이며 권한 구성 요소가 맡습니다. 권한 규칙은 금지, 확인, 허용의 순서로 평가되고, 처음 일치하는 규칙이 결과를 정합니다. 금지 규칙에 일치하는 호출은 실행되지 않고, 도구 이름만 지정한 금지 규칙(예: WebFetch)은 그 도구를 목록에서 제외하며, 그 밖의 규칙은 호출할 때마다 평가됩니다(Anthropic, 2026a). 권한 평가를 호출할 때마다 하는 것은 모델이 도구 호출을 요청만 하고 실행은 하네스가 하기 때문입니다. Agent SDK 문서에 따르면 모델은 도구 호출을 요청하고, SDK가 요청된 도구를 실행합니다(Anthropic, 2026b). 이 실행을 맡는 쪽이 Chapter 1에서 정한 하네스의 실행 장치(제품이 제공하는 부분)이고, 권한 평가는 요청과 실행 사이에서 이루어집니다.

Claude Code 문서에 따르면 확인 규칙에 일치한 호출은 실행 전에 사람에게 확인을 요청하며(Anthropic, 2026a), Agent SDK 문서에 따르면 사람이 거절한 호출도 실행되지 않고 거부 결과가 모델에 전달됩니다(Anthropic, 2026b). 그림 2-2는 1 컨텍스트 구성에서 정해지는 도구 구성(가용성)과, 도구가 호출될 때마다 3 권한 확인에서 금지, 확인, 허용 순서로 대조되는 흐름을 보여 줍니다. 허용에 일치하면 실행하고, 금지에 일치하면 거부 결과를 기록하며, 확인에 일치하면 사람이 승인하거나 거절합니다. 단계 번호와 이름은 이 책이 정리한 그림 1-2와 같고, 이 그림은 도구 호출 한 번의 흐름만 그리므로 5 최종 응답은 생략합니다. 실행 결과와 거부 결과는 이력에 쌓여 다음 판단의 입력이 됩니다.

표 2-2는 그림 2-2의 단계와 요소를 설명합니다.

가용성과 권한 평가를 정리하면, 도구 노출 범위에서 정할 것은 세 가지입니다.

  • 작업에 연결할 도구: 작업 단위마다 필요한 도구만 연결합니다. CR은 저장소 안의 파일만 다루므로 웹 접근 도구를 제외했습니다.
  • 읽기와 수정의 구분: 조회만 필요한 작업에는 읽기 도구만 허용합니다.
  • 하위 에이전트의 도구: 하위 에이전트에는 맡긴 작업에 필요한 최소한의 도구만 지정합니다.

지시와 강제

앞 절의 금지 규칙은 모델이 따르지 않아도 제품이 적용하지만, 규칙 문서에 적은 규칙은 모델이 읽고 따라야 지켜집니다. 그래서 규칙마다 어느 수단에 맡길지 정해야 합니다. 이 책은 규칙을 처리하는 수단을 지시와 강제로 나눕니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단이며, 규칙 문서가 해당합니다. 강제는 에이전트의 판단과 관계없이 제품이 적용하는 수단입니다. 권한 규칙은 동작을 허용하거나 막고, 훅은 정해진 시점에 명령을 실행합니다.

Claude Code 문서는 권한 규칙을 모델이 아니라 Claude Code가 적용한다고 설명합니다. 프롬프트나 CLAUDE.md의 지시는 에이전트가 시도하는 동작에 영향을 주지만, 허용되는 동작 자체는 정하지 않습니다. 셸 명령을 실행하는 훅은 정해진 시점에 실행되며, 권한 규칙과 함께 에이전트의 판단과 관계없이 적용됩니다(Anthropic, 2026a, 2026c).

표 2-3의 앞 두 줄의 기준은 규칙을 어겼을 때의 결과입니다. 어겼을 때 다시 작업하면 되는 규칙은 지시로 충분합니다. 원본 자료의 손상이나 외부 발송처럼 되돌리기 어려운 결과를 낳는 규칙은 강제 수단으로 처리합니다. 셋째 줄은 결과가 아니라 시점이 기준입니다. 파일을 수정할 때마다 실행해야 하는 검사는 모델이 잊어도 실행되도록 훅에 맡깁니다. 이 장에서 반드시 지켜야 하는 규칙은 어기면 되돌리기 어려운 규칙과, 정해진 시점에 빠짐없이 실행할 규칙입니다.

표 2-4는 CR의 규칙을 지시와 강제로 나눈 것입니다. 표의 Edit(./data/**)는 data 폴더 아래 모든 파일의 수정을 뜻하고, PostToolUse는 도구를 실행한 뒤의 시점입니다.

표 2-4의 첫 두 줄은 실습으로 확인할 수 있습니다. 규칙 문서만 있는 상태에서는 수용 시험을 수정하려는 시도를 막지 못하고, 금지 규칙을 더하면 같은 시도가 거부됩니다(부록 실습 2, 3).

훅은 시점에 따라 하는 일이 다릅니다. 도구 실행 전에 실행되는 PreToolUse 훅은 호출을 막을 수 있고, 실행 뒤에 실행되는 PostToolUse 훅은 이미 실행된 편집을 막지 못하고 오류를 모델에 알립니다(Anthropic, 2026d).

금지 규칙에도 한계가 있습니다. 파일 수정 금지 규칙은 파일을 스스로 여는 스크립트를 통한 간접 수정까지 막지는 못합니다. 이런 경우의 보완 수단인 샌드박스(Sandbox)와 권한 규칙의 평가 순서는 Chapter 9에서 다룹니다.

실패와 막는 장치

도구만 연결하고 권한, 기록, 검증을 정하지 않은 에이전트는 작업을 수행할 수는 있지만, 원본 자료를 변경하지 않았는지, 수용 시험을 통과했는지 확인할 근거를 남기지 않습니다. 권한, 기록, 검증은 사용자가 결과를 받아들이기 위한 근거입니다. 그래서 다섯 구성 요소 가운데 하나를 정하지 않으면, 그 구성 요소에서 실패가 생깁니다. 표 2-5는 CR을 구현하는 에이전트에서 구성 요소별로 생길 수 있는 실패와 막는 장치입니다. 막는 장치는 표 2-1과 표 2-4의 장치와 같은 이름으로 적었습니다.

확인 방법

구성 요소를 정했는지는 설정 파일을 읽는 것만으로는 알 수 없고, 제품의 화면과 실행 기록으로 확인합니다. 표 2-6은 CR 구현 에이전트에서 구성 요소별로 확인하는 위치입니다. 표의 /로 시작하는 명령은 프로젝트 폴더에서 Claude Code를 실행한 뒤 대화 입력창에 입력합니다(Anthropic, 2026c). 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다.

원칙과 점검 질문

다섯 구성 요소를 모두 정하고, 어기면 되돌리기 어려운 규칙은 규칙 문서가 아니라 권한 규칙과 훅으로 강제합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트의 하네스에서 다섯 구성 요소 가운데 정하지 않은 것은 무엇입니까?
  2. 규칙 문서에만 적어 둔 규칙 가운데 어기면 되돌리기 어려운 규칙은 무엇입니까?
  3. 연결한 도구 가운데 이 작업에 필요하지 않은 도구는 무엇입니까?
