Chapter 2 하네스의 구성 요소

하네스의 결과를 믿고 받아들이려면 도구를 연결하는 것만으로는 충분하지 않고, 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소를 모두 정해야 합니다.

에이전트(Agent)는 모델이 판단하고, 모델 바깥의 하네스(Harness)가 그 판단을 실행하는 방식으로 일합니다(Chapter 1). 모델이 무엇을 알고 어떤 도구를 사용할 수 있는지, 모델이 요청한 동작을 실행해도 되는지, 결과가 완료 조건을 충족하는지는 모델의 판단만으로 정해지지 않고, 하네스에 정해 둔 값에 따라 달라집니다. 도구만 연결하고 나머지를 정하지 않으면 에이전트는 일을 하지만, 결과를 받아들일 근거가 남지 않습니다. 그래서 하네스를 설계할 때는 구성 요소마다 무엇을 정할지와, 어기면 되돌리기 어려운 규칙을 어떤 수단으로 지키게 할지를 함께 정합니다. 이 장에서는 하네스의 다섯 구성 요소, 도구를 보여 주는 범위와 실행을 허락하는 규칙, 규칙을 지시와 강제로 나누는 방법을 살펴보고, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)에 적용합니다.

  • 하네스의 설정은 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소로 정합니다.
  • 역할, 기록, 도구는 모델이 판단하는 조건을 정하고, 권한과 검증은 판단 결과를 통제합니다.
  • 규칙 문서는 에이전트가 읽고 따르는 지시이고, 권한 규칙과 훅은 모델의 판단과 관계없이 제품이 적용하는 강제입니다.
  • 어기면 되돌리기 어려운 규칙과 정해진 시점마다 실행할 검사는 강제 수단으로 처리합니다.

다섯 구성 요소

하네스는 모델 바깥의 실행 체계이며, 제품이 제공하는 실행 장치와 사용자와 팀이 정하는 설정으로 나뉩니다(Chapter 1의 그림 1-1). 실행 장치는 루프 실행, 도구 제공, 컨텍스트(Context) 관리, 권한 확인, 세션 기록처럼 제품이 미리 갖춘 기능입니다. 설정은 팀이 업무에 맞게 정하는 값이며, 정하지 않은 항목은 제품의 기본값으로 동작합니다. 이 장은 설정을 다룹니다. 실행 장치가 도구를 제공하고 권한을 확인하는 기능이라면, 설정은 그 가운데 어떤 도구를 보여 주고 어떤 동작을 허용할지 정하는 값입니다. 이 책은 설정에서 정하는 항목을 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소로 나누며, 하나가 비면 생기는 실패가 구성 요소마다 다릅니다.

  • 역할: 에이전트가 맡을 작업과 사람이 맡을 작업의 경계입니다. 주로 규칙 문서에 적습니다. 규칙 문서는 에이전트가 세션을 시작할 때마다 읽는 프로젝트 지침 문서이며, Claude Code에서는 CLAUDE.md입니다18. 경계를 정하지 않으면 외부 발송이나 배포처럼 사람이 판단할 일까지 에이전트가 진행할 수 있습니다.
  • 도구: 에이전트가 사용할 수 있는 기능과, 그 가운데 이번 작업에 보여 줄 범위입니다. 도구가 없으면 에이전트는 파일을 읽거나 수정하지 못하고 명령도 실행하지 못합니다. 도구가 너무 많으면 도구 설명이 컨텍스트를 차지하고, 비슷한 도구 사이에서 무엇을 사용할지 선택하기 어려워집니다.
  • 권한: 도구로 할 수 있는 동작의 범위입니다. 권한 규칙(Permission Rule)은 도구로 하는 동작을 허용, 확인 요청, 금지로 나눈 목록이며 설정 파일에 적습니다13. 같은 파일 도구라도 읽기만 허용할지, 수정까지 허용할지를 여기서 정합니다. 범위를 정하지 않으면 원본 자료, 곧 에이전트가 읽기만 하고 변경하면 안 되는 입력 자료나 완료 판정 기준까지 에이전트가 수정할 수 있습니다.
  • 기록: 무엇을 왜 정했는지 남긴 결정 기록과, 어디까지 진행했는지 남긴 진행 기록입니다. 제품의 세션 기록은 대화 자체를 저장해 그 세션을 다시 열 때 쓰이고, 설정의 기록은 다음 세션이 읽도록 결정과 진행을 정리한 파일이라는 점에서 다릅니다. 새 세션은 이전 대화를 담지 않은 컨텍스트로 시작합니다18. 같은 세션 안에서도 컨텍스트가 한도에 가까워지면 자동으로 압축되어, 앞의 대화가 그대로 남지 않을 수 있습니다10. 그래서 남아야 할 결정과 진행 상황은 파일로 남깁니다.
  • 검증: 결과를 받아들이기 전에 확인하는 절차와 완료 기준입니다. 에이전트의 완료 보고만으로는 결과가 기준에 맞는지 알 수 없으므로, 무엇을 실행해 어떤 출력이 나오면 완료로 볼지 미리 정합니다.

다섯 구성 요소는 모델의 판단을 사이에 두고 두 쪽에서 작동합니다. 역할과 기록은 모델이 판단할 때 읽는 정보이고, 도구는 판단 때 선택할 수 있는 수단입니다. 세 구성 요소 모두 판단이 내려지기 전에 그 조건을 정합니다. 권한과 검증은 판단이 나온 뒤에 작동합니다. 권한은 모델이 요청한 동작을 실행해도 되는지 정하고, 검증은 결과가 완료 조건을 충족하는지 확인합니다. 이 책은 이 관계에 따라 다섯 구성 요소를 세 묶음으로 정리합니다. 규칙 문서와 기록 파일로 판단을 안내하는 지시 묶음(역할, 기록), 판단의 선택지가 되는 실행 수단 묶음(도구), 제품이 판단 결과에 적용하는 강제 묶음(권한, 검증)입니다. 지시와 강제의 정확한 뜻은 뒤의 지시와 강제 절에서 정합니다.

그림 2-1은 세 묶음과 다섯 구성 요소, 가운데에 놓인 모델의 판단과 응답을 보여 줍니다. 모델은 하네스 바깥에 있으므로 그림에서도 세 묶음과 따로 둡니다. 지시 묶음과 실행 수단 묶음에서 판단과 응답으로 가는 화살표는 판단의 조건이고, 판단과 응답에서 강제 묶음으로 가는 화살표는 판단 결과의 통제입니다. 카드마다 정할 것, 그 이유, 에이전트 루프에서 주로 작동하는 단계를 적었습니다. 단계 이름은 Chapter 1의 그림 1-2와 같은 이름입니다.

표 2-1은 그림 2-1의 구성 요소와 판단과 응답의 주요 역할, 기능적 제약, 관련 절을 정리한 것입니다.

다섯 구성 요소는 루프의 한 단계에만 묶이지 않습니다. 도구는 판단 전에 목록으로 제공되고, 판단 뒤에는 하네스가 요청된 도구를 실행합니다. 검증도 파일을 수정할 때마다 실행하는 검사와, 작업을 마치기 전에 완료 기준을 확인하는 일로 두 번 작동할 수 있습니다. 그래서 그림 2-1의 카드에 적은 단계는 주로 작동하는 곳만 가리킵니다.

도구 노출 범위

다섯 구성 요소 가운데 도구와 권한은 에이전트가 실제로 할 수 있는 일을 정하므로 더 자세히 봅니다. 도구를 많이 연결할수록 에이전트가 할 수 있는 일은 늘어나지만, 두 가지 비용도 함께 늘어납니다. 하나는 컨텍스트 공간입니다. 연결한 도구의 이름과 설명은 컨텍스트에 들어가 공간을 차지하며19, Claude Code의 대화 입력창에 /context를 입력하면 나오는 화면에서, 도구 항목으로 그 크기를 확인할 수 있습니다20. 다른 하나는 선택의 어려움입니다. Anthropic의 컨텍스트 엔지니어링(Context Engineering) 글은 기능이 겹치는 도구가 많으면 어느 도구를 쓸지 판단하기 어려워진다고 보고, 작업에 필요한 최소한의 도구만 두라고 권합니다4.

Claude Code는 도구가 컨텍스트를 차지하는 양을 줄이는 기능을 둡니다. MCP(Model Context Protocol)는 외부 시스템의 기능을 에이전트의 도구로 연결하는 규약이고, 이를 구현한 프로그램을 MCP 서버라고 합니다. Claude Code는 기본 설정에서 MCP 서버의 도구 설명을 처음부터 불러오지 않고, 도구 이름과 서버 안내만 컨텍스트에 둔 뒤 필요할 때 불러옵니다21. 이렇게 해도 도구 이름과 안내는 컨텍스트에 남고 선택할 대상도 늘어나므로, 사용량과 비용을 줄이는 방법을 다룬 Claude Code 문서는 사용하지 않는 서버를 끄라고 안내합니다19.

이 책은 도구 노출 범위를 가용성과 권한 평가의 두 층으로 나누어 봅니다. 첫째 층인 가용성은, 작업에 어떤 도구를 제공해 모델이 볼 수 있게 할지 정하는 일이며 도구 구성 요소가 맡습니다. 둘째 층인 권한 평가는 모델이 도구를 호출할 때마다 그 동작을 실행해도 되는지 판단하는 일이며 권한 구성 요소가 맡습니다. 같은 명령 실행 도구(Bash)라도 저장소 상태를 보는 git status와 원격 저장소에 올리는 git push는 결과가 다르고, 같은 수정 도구라도 대상 파일에 따라 위험이 다릅니다. 그래서 권한은 도구를 연결할 때 한 번 정하고 끝내지 않고, 호출마다 평가합니다. 모델은 도구 호출을 요청만 하고 실행은 하네스가 맡으므로10, 하네스는 요청과 실행 사이에서 이 평가를 할 수 있습니다.

Claude Code는 권한 규칙을 금지, 확인 요청, 허용의 순서로 대조하고, 처음 일치하는 규칙이 결과를 정합니다. 금지 규칙에 일치한 호출은 실행되지 않습니다. 권한 규칙은 도구 이름만 적거나, 도구 이름 뒤 괄호에 대상을 적습니다. 웹 문서를 가져오는 WebFetch처럼 도구 이름만 적은 금지 규칙은 그 도구를 아예 목록에서 제외하므로, 모델은 그 도구를 볼 수 없습니다. Bash(git push *)처럼 괄호에 대상(git push로 시작하는 명령)을 적은 규칙은 Bash 도구를 목록에 남겨 두고, 일치하는 호출만 거부합니다13. 어느 규칙에도 일치하지 않는 호출은 권한 모드(Permission Mode)가 처리하며, 모드에 따라 사람에게 묻거나 자동으로 승인하거나 거부합니다12. 권한 모드의 값과 선택 기준은 Chapter 10에서 다룹니다.

확인 요청 규칙에 일치한 호출은 실행 전에 사람에게 확인을 요청합니다13. Claude Code를 프로그램에서 쓰게 하는 Agent SDK의 문서는 사람이 거절한 호출도 실행되지 않고, 거부 메시지가 도구 결과로 모델에 전달된다고 설명합니다22. 그림 2-2는 이 흐름을 그림 1-2의 단계 번호로 보여 줍니다. 위쪽 띠는 1 컨텍스트 구성에서 정하는 가용성이고, 아래 줄은 도구 호출 한 번이 3 권한 확인을 거쳐 실행되거나 거부되는 흐름입니다. 실행 결과와 거부 결과는 모두 대화 이력에 추가되어 다음 판단에 쓰입니다.

표 2-2는 그림 2-2의 단계와 요소를 정리한 것입니다. 그림에서 맨 아래 한 줄로만 적은 권한 모드는 3 권한 확인 행에, 카드 하나로 적은 하위 에이전트(Subagent, 특정 작업을 맡도록 따로 정의한 에이전트)의 도구는 1 컨텍스트 구성의 둘째 행으로 풀어 적었습니다.

가용성과 권한 평가를 정리하면, 도구 노출 범위에서 정할 것은 세 가지입니다.

  • 작업에 연결할 도구: 작업에 필요한 도구만 연결하고, 사용하지 않는 도구는 이름만 적은 금지 규칙이나 연결 해제로 목록에서 제외합니다.
  • 읽기와 수정의 구분: 조회만 필요한 작업에는 수정 도구를 금지 규칙으로 막거나 도구 목록에서 제외해, 읽기 도구만 사용하게 합니다.
  • 하위 에이전트의 도구: 하위 에이전트의 정의 파일에 맡긴 작업에 필요한 도구만 적습니다23.

지시와 강제

앞 절의 금지 규칙은 모델이 따르지 않아도 제품이 적용합니다. 반면 규칙 문서에 적은 규칙은 모델이 읽고 따라야 지켜집니다. 같은 규칙이라도 어느 쪽에 맡기느냐에 따라 지켜지는 정도가 다르므로, 규칙마다 처리할 수단을 정해야 합니다. 이 책은 그 수단을 지시와 강제로 나눕니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단이며, 규칙 문서가 해당합니다. 강제는 에이전트의 판단과 관계없이 제품이 적용하는 수단이며, 권한 규칙과 훅(Hook)이 해당합니다. 훅은 도구 실행 전후처럼 정해진 시점에 자동으로 실행되는 명령이고, 이 책은 셸 명령을 실행하는 훅만 다룹니다11.

Claude Code 문서는 권한 규칙을 적용하는 주체가 모델이 아닌 Claude Code라고 설명합니다. 프롬프트나 CLAUDE.md의 지시는 에이전트가 시도하는 동작에 영향을 주지만, 허용되는 동작 자체를 변경하지는 않습니다13. Claude Code의 메모리 문서와 설정 점검 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 규정하고, 일어나면 안 되는 동작에는 권한 규칙이나 훅을 쓰라고 안내합니다18,24.

훅은 시점에 따라 할 수 있는 일이 다릅니다. 도구 실행 전에 실행되는 PreToolUse 훅은 권한 규칙을 대조하기 전에 실행되며, 호출을 막을 수 있습니다. 도구 실행 뒤에 실행되는 PostToolUse 훅은 이미 실행된 편집을 되돌리지 못합니다. 그 대신 훅 명령이 종료 코드 2(Claude Code가 차단 신호로 정한 값)로 끝나면 오류 출력을 모델에 전달해, 모델이 이어서 수정하게 합니다11. 그래서 PostToolUse 훅은 훅에 지정한 도구로 편집할 때마다, 모델이 잊어도 검사가 실행되게 하는 데 사용합니다.

규칙을 어느 수단에 맡길지는 두 질문으로 정합니다. 첫째, 어기면 되돌리기 어려운가. 어기면 원본 자료가 손상되거나 외부로 발송되는 것처럼 되돌리기 어려운 결과가 생기는 규칙은 권한 규칙으로 막습니다. 어겨도 다시 작업하면 되는 규칙은 지시로 충분합니다. 둘째, 모델이 잊어도 정해진 시점마다 실행되어야 하는가. 파일을 수정할 때마다 실행할 검사가 여기에 해당하며, 훅에 맡깁니다. 표 2-3은 두 질문에 따른 처리 수단입니다.

그림 2-1에서 역할은 지시 묶음에 두었지만, 역할의 경계 가운데 되돌리기 어려운 것은 표 2-3의 둘째 줄처럼 권한 규칙으로 막거나 사람에게 확인을 요청합니다. 검증은 강제 묶음에 두었지만, 제품이 강제하는 것은 훅이 정해진 시점마다 검사를 실행하는 부분입니다. 그 검사의 출력과 검토용 하위 에이전트의 보고는 완료를 판단하는 증거이고, 그 증거를 보고 결과를 받아들이는 승인은 사람이 합니다.

강제 수단에도 적용 범위가 있습니다. 파일 수정 금지 규칙은 수정 도구와 Bash의 일반적인 파일 명령에는 적용되지만, 파일을 스스로 여는 Python 스크립트를 실행해 수정하는 경우까지 막지는 못합니다. Bash 규칙은 명령 문자열이 일치할 때만 적용되므로, Bash(git push *)는 폴더 지정 옵션을 추가한 git -C . push처럼 같은 동작을 다르게 표기한 명령과 일치하지 않습니다13. 훅도 실행되지 않거나 실패하면 막지 못합니다. 이런 빈틈을 운영 체제 수준에서 보완하는 격리 환경, 곧 샌드박스(Sandbox)는 Chapter 9에서 다룹니다.

예제: 변경 요청 사항의 하네스 구성 정하기

이 장의 예제는 Chapter 3에서 자세히 설계할 변경 요청 사항입니다. 변경 요청 사항은 정산 요청 화면에 프로젝트 코드, 곧 경비가 속한 프로젝트의 식별 번호를 선택하는 항목을 추가하는 변경입니다. 작업은 미리 다섯 개의 작업 단위로 나누어 두었습니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다. 작업 1(프로젝트 코드 조회 방식 합의)은 사람이 이미 마쳤고, 작업 2~4(데이터 모델, 단위 테스트, 화면 변경)는 에이전트가 하나씩 구현합니다. 작업 5(통합 테스트 시나리오)는 에이전트가 초안을 작성하고 사람이 승인합니다.

표 2-4와 표 2-5를 읽으려면 예제에서 사용하는 기록 파일과 시험, 자료를 알아야 합니다. 진행 기록은 작업 단위 목록 파일(tasks.json)이며, 작업 단위마다 완료 여부를 통과 값(true 또는 false)으로 적습니다. 수용 기준은 결과물이 받아들여지기 위해 충족해야 하는 조건이고, 수용 시험은 그 조건을 확인하는 시험입니다. 수용 시험은 사람이 작성하고 에이전트는 수정하지 않습니다. 예제의 원본 자료는 인사 시스템이 갱신하는 프로젝트 코드 목록 파일(data/projects.csv)입니다. 검사 스크립트(check.py)는 단위 테스트와 수용 시험을 한 번에 실행해 결과를 출력합니다.

표 2-4는 변경 요청 사항에서 다섯 구성 요소를 어떻게 정했는지 보여 줍니다. 표의 운영 기준은 부록 실습의 예제 파일(examples/expense-app/reference/)과 같고, 2026년 10월에 확인한 Claude Code 문서에 맞춰 작성했습니다. 검증 행의 Edit|Write는 수정 도구(Edit)나 파일 작성 도구(Write)를 실행한 뒤라는 뜻입니다. 다른 제품이 같은 구성 요소를 어떤 장치로 구현하는지는 Chapter 10에서 다룹니다.

표 2-4의 검증에는 Chapter 1에서 본 Stop 훅이 없습니다. 예제는 파일을 수정할 때마다 PostToolUse 훅으로 단위 테스트를 실행하고, 작업 단위의 완료는 검사 스크립트의 출력과 사람의 commit 확인으로 판정하기 때문입니다. 완료 판정까지 훅에 맡기려면 Stop 훅을 더합니다(Chapter 7). 표 2-4의 기록은 사람이 정한 파일에 남깁니다. Claude Code에는 작업 중 알게 된 내용을 모델이 스스로 파일에 적어 다음 세션에 읽는 자동 메모리 기능도 있고, 로컬 세션에서는 기본으로 켜져 있습니다18. 그러나 무엇을 남길지를 모델이 정하므로, 예제는 이 기능을 기록 구성 요소로 삼지 않습니다.

표 2-5는 변경 요청 사항의 규칙을 앞 절의 두 질문에 따라 지시와 강제로 나눈 것입니다. 권한 규칙은 도구 이름 뒤 괄호에 대상을 적습니다. Edit(./data/**)는 data 폴더 아래 모든 파일의 수정이고, Bash(git push *)는 git push로 시작하는 명령입니다.

표 2-5의 첫 두 줄은 실습으로 비교할 수 있습니다. 규칙 문서만 있을 때는 수용 시험을 수정하려는 시도를 막지 못할 수 있고(부록 실습 2), 금지 규칙을 더하면 수용 시험과 원본 자료의 수정 시도가 모두 거부됩니다(부록 실습 3). 금지 규칙은 스크립트를 실행해 수용 시험을 지우는 경우까지 막지 못하므로, 예제의 검사 스크립트는 수용 시험이 실제로 몇 건 실행되었는지 다시 세고 0건이면 실패로 봅니다. 시험을 일부만 지우거나 건너뛰게 한 변경, 원본 자료의 변경은 commit 확인 때 git status와 git diff로 acceptance/와 data/가 변경 목록에 없는지 보고 찾습니다. 또 스크립트 실행처럼 허용 목록에 없는 명령은, 권한 모드가 사람에게 묻는 모드라면 실행 전에 사람이 한 번 더 확인합니다.

실패와 막는 장치

구성 요소 가운데 하나를 정하지 않아도 에이전트는 작업을 수행합니다. 그러나 그 구성 요소가 막던 실패가 생길 수 있고, 생겨도 알아차릴 근거가 남지 않습니다. 구성 요소마다 비었을 때 생기는 실패가 다르므로, 표 2-6은 변경 요청 사항에서 구성 요소별로 생길 수 있는 실패와 방지 장치를 정리합니다. 방지 장치는 표 2-4, 표 2-5와 같은 이름으로 적었습니다.

확인 방법

구성 요소가 정한 대로 적용되는지는 설정 파일을 읽는 것만으로는 알 수 없습니다. 설정은 사용자, 프로젝트, 로컬 등 여러 파일에서 합쳐지고24, 훅처럼 적어 둔 장치가 실제로 실행되는지는 동작을 일으켜 봐야 압니다. 그래서 제품의 화면과 실행 결과로 확인합니다. 표 2-7은 변경 요청 사항의 에이전트에서 구성 요소별로 확인하는 방법입니다. 표의 /로 시작하는 명령은 프로젝트 폴더에서 Claude Code를 실행한 뒤 대화 입력창에 입력합니다25. 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다.

훅 목록에 있다는 것과 훅이 실행되었다는 것은 다릅니다. /hooks는 등록된 훅을 보여 주는 읽기 전용 목록이므로, 실행 여부는 일부러 테스트가 실패하는 편집을 해서 대화 화면의 훅 오류로 확인합니다. 성공한 훅의 출력은 대화에 나타나지 않으므로, 실행 기록을 자세히 보려면 claude --debug로 실행합니다26.

원칙과 점검 질문

다섯 구성 요소를 모두 정하고, 어기면 되돌리기 어려운 규칙은 규칙 문서에만 두지 않고 권한 규칙과 훅으로 강제합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트의 하네스에서 다섯 구성 요소 가운데 정하지 않은 것은 무엇입니까?
  2. 지시로만 처리하는 규칙 가운데 원본 손상이나 외부 발송처럼 결과를 되돌릴 수 없는 것은 무엇입니까?
  3. 연결한 도구 가운데 이 작업에 필요하지 않은 도구는 무엇입니까?
