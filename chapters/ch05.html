Chapter 5 컨텍스트 엔지니어링: 에이전트가 읽는 정보 설계

요청 문장을 다듬는 것만으로는 결과가 정해지지 않고, 에이전트가 판단하는 시점에 어떤 정보를 읽고 있는지에 따라 결과가 달라집니다.

컨텍스트(Context)는 모델이 응답을 생성할 때 입력되는 정보 전체이고, 컨텍스트 엔지니어링(Context Engineering)은 모델에 넘길 정보를 선별하고 최신 상태로 유지하는 일입니다(Chapter 1). 에이전트(Agent)는 작업을 시작할 때 읽는 규칙 문서(세션마다 읽히는 프로젝트 지침, Chapter 2)와 요청, 작업 중에 연 파일과 도구 결과를 근거로 판단합니다. 그래서 필요한 자료가 없거나 오래된 자료가 남아 있으면, 같은 요청에도 에이전트가 다른 자료를 근거로 판단해 결과가 달라질 수 있습니다. 따라서 요청 문장과 함께 에이전트가 무엇을 언제 읽게 할지도 정해야 합니다. 이 장에서는 에이전트가 읽는 정보의 종류, 정보를 제공하는 시점, 규칙 문서를 작성하고 관리하는 방법을 익힙니다.

  • 컨텍스트는 한정된 자원이므로 작업에 필요한 자료를 선별해서 제공합니다.
  • 에이전트가 읽는 정보는 제공 경로와 활용 시점에 따라 상시 규칙, 필요할 때 읽는 문서, 작업 입력, 작업 중 수집, 생성 정보의 네 종류로 나뉩니다.
  • 규칙 문서에는 모든 작업에 해당하는 규칙만 짧게 두고, 같은 실수가 반복되면 항목을 더하며, 맞지 않게 된 항목은 수정하거나 삭제합니다.

컨텍스트는 한정된 자원

선별이 필요한 것은 컨텍스트가 한정된 자원이기 때문입니다. 토큰(Token)은 모델이 텍스트를 나누어 처리하는 단위이고, 컨텍스트 윈도(Context Window)는 모델이 한 번에 처리할 수 있는 토큰의 범위입니다(Chapter 1). Anthropic의 컨텍스트 엔지니어링 글은 컨텍스트를 한정된 자원으로 다뤄야 한다고 설명합니다. 글은 그 이유로, 컨텍스트의 토큰이 늘수록 모델이 그 안의 정보를 정확히 떠올리는 능력이 떨어진다는 점을 듭니다4.

그래서 자료를 많이 제공한다고 결과가 항상 나아지는 것은 아닙니다. 관련 없는 자료는 관련 있는 자료가 차지할 자리를 줄이고, 오래된 자료는 지금 상태와 맞지 않는 근거가 됩니다. 정할 것은 자료의 양뿐 아니라 작업과의 관련성, 최신성, 제공 시점입니다.

Claude Code에서는 입력창에서 실행하는 /context 명령이 컨텍스트에서 무엇이 공간을 차지하는지 보여 줍니다25. 관련 없는 작업으로 넘어갈 때는 /clear 명령으로 새 대화를 시작하고, 긴 대화는 /compact 명령으로 요약해 공간을 확보할 수 있습니다25. 컨텍스트가 한도에 가까워지면 Claude Code가 오래된 도구 출력을 먼저 지우고, 필요하면 대화를 자동으로 요약합니다8. 대화를 요약해 공간을 확보하는 일을 압축이라고 하며, 압축은 뒤의 미리 제공하는 정보와 필요할 때 찾는 정보 절에서 긴 작업의 기법으로 다시 봅니다.

에이전트가 읽는 정보의 종류

컨텍스트 윈도에 한도가 있으므로, 어떤 정보가 어떤 경로로 언제 들어가는지 구분해야 선별할 수 있습니다. 이 책은 에이전트가 읽는 정보를 제공 경로와 활용 시점에 따라 네 종류로 정리합니다. 상시 규칙은 규칙 문서처럼 세션(에이전트와 대화를 한 번 시작해 끝낼 때까지)이 시작될 때마다 읽히는 문서입니다. 필요할 때 읽는 문서는 특정 작업이나 파일을 다룰 때 읽히는 문서입니다. 상시 규칙에 위치를 안내한 세부 설계 문서, Skill(기본 설정에서 이름과 설명만 늘 컨텍스트에 있고 본문은 필요할 때 읽히는 지침과 자료의 묶음), 경로별 규칙(지정한 경로의 파일을 다룰 때 읽히는 규칙), 하위 폴더의 규칙 문서가 여기에 속합니다20,29. 작업 입력은 사용자가 입력하는 요청과 요청에 함께 첨부하는 자료입니다. 작업 중 수집, 생성 정보는 에이전트가 파일을 열어 모은 내용과 명령이나 도구를 실행해 얻은 출력입니다.

네 종류는 모두 같은 컨텍스트 윈도에 들어가고, 제품의 시스템 지침과 불러온 Skill도 같은 윈도를 차지합니다8. 같은 문서라도 사용자가 요청에 첨부하면 작업 입력이고, 규칙 문서에 위치만 안내해 두고 에이전트가 필요할 때 읽게 하면 필요할 때 읽는 문서가 됩니다. 분류의 기준이 문서의 종류가 아니라 제공 경로와 활용 시점인 이유입니다. 그림 5-1은 정보가 오는 곳(규칙 문서, 세부 문서, 사용자, 도구 실행)과 네 종류가 컨텍스트 윈도에 들어가는 시점을, 표 5-1은 종류별 대표 자료와 관리 방식을 보여 줍니다.

표 5-1이 종류별 관리 방식이라면, 표 5-2는 그림 5-1의 영역과 선이 맡는 역할과 제약을 정리합니다.

상시 규칙에는 모든 작업에 필요한 내용만 두고, 나머지는 필요할 때 읽는 문서로 분리한 사례가 있습니다. Codex로 제품을 개발한 OpenAI의 팀은 지침을 AGENTS.md 한 파일에 모두 담는 방식이 기대만큼 작동하지 않았다고 밝히고, 약 100줄의 AGENTS.md가 세부 문서의 위치를 안내하는 구성을 쓴다고 설명했습니다2.

미리 제공하는 정보와 필요할 때 찾는 정보

앞 절이 정보를 들어오는 경로와 시점으로 나누었다면, 이 절은 같은 자료를 작업 전에 미리 포함해 둘지, 작업 중에 에이전트가 찾아 읽게 할지 선택하는 방법을 다룹니다. 하나는 작업 전에 관련 자료를 찾아 미리 제공하는 방법입니다. Anthropic의 컨텍스트 엔지니어링 글은 많은 AI 네이티브 애플리케이션이 임베딩 기반 검색(문장의 뜻을 수치로 변환해 비슷한 자료를 찾는 검색)으로 중요한 자료를 모델이 추론하기 전에 찾아 둔다고 설명합니다. 다른 하나는 필요할 때 찾는 방법입니다. 이 방법에서 에이전트는 파일 경로, 저장된 쿼리(미리 저장해 둔 검색 조건), 웹 링크처럼 자료의 위치를 가리키는 짧은 정보(식별자)만 가지고 있다가, 실행 중에 도구로 자료를 불러옵니다4. 상시 규칙은 미리 제공하는 쪽이고, 필요할 때 읽는 문서는 필요할 때 찾는 쪽에 가깝습니다.

같은 글에 따르면 미리 제공하는 방법은 실행 중에 탐색하지 않으므로 빠를 수 있습니다. 이 책의 정리로는, 미리 찾아 둔 범위 밖의 자료가 작업 중에 새로 필요해지면 그 자료는 담겨 있지 않습니다. 필요할 때 찾는 방법은 에이전트가 탐색하며 관련 자료를 단계적으로 좁혀 가지만, 미리 찾아 둔 자료를 사용하는 것보다 느릴 수 있습니다. 도구와 탐색 기준이 없으면 관련 없는 탐색을 이어 가며 컨텍스트를 낭비할 수도 있습니다. 두 방법은 섞어 사용할 수 있습니다. 같은 글은 Claude Code를 혼합 방식의 예로 듭니다. Claude Code는 CLAUDE.md를 작업 전에 컨텍스트에 포함하고, 파일은 이름 패턴으로 찾는 glob과 내용으로 찾는 grep 같은 도구로 필요할 때 찾습니다4. 같은 글은 어느 방법이든 원하는 결과가 나올 가능성을 높이는 신호가 강한 정보를 가장 작게 묶어 선별하는 것을 목표로 듭니다4.

어느 방법을 쓰든 가져온 자료와 대화 기록은 작업이 길어질수록 쌓이므로, 긴 작업에서는 컨텍스트 윈도에 다 담기지 않는 정보를 다뤄야 할 수 있습니다. 같은 글은 이런 작업을 위한 세 가지 기법을 소개합니다. 압축은 한도에 가까운 대화를 요약해 새 컨텍스트로 이어 가는 기법이고, 구조화된 노트는 에이전트가 컨텍스트 밖의 파일에 진행 상황을 적어 두고 나중에 다시 읽는 기법이며, 하위 에이전트(Subagent)는 분리된 컨텍스트에서 일을 맡기고 요약만 돌려받는 기법입니다. 글은 압축이 대화를 길게 주고받는 작업에, 구조화된 노트가 단계별 목표를 정해 두고 조금씩 진행하는 개발에, 하위 에이전트가 여러 갈래를 나누어 동시에 탐색하는 조사와 분석에 맞는다고 설명합니다4. 하위 에이전트는 특정 작업을 맡도록 따로 정의한 에이전트이며(Chapter 2), 새 컨텍스트에서 시작해 주 대화(사람과 에이전트가 주고받는 세션의 대화)의 내용을 보지 못하고, 위임할 때 받은 지시와 규칙 문서(CLAUDE.md)를 근거로 작업합니다. 대화 전체를 이어받는 포크(fork)는 예외입니다23. 그래서 위임할 때는 필요한 내용이나 그 내용이 있는 파일의 위치를 지시에 담습니다. 그림 5-2는 자료를 주는 방법과 세 가지 기법을, 표 5-3은 그림의 구성 요소를, 표 5-4는 기법별 역할과 제약을 보여 줍니다.

Anthropic의 컨텍스트 엔지니어링 글은 지나치게 압축하면 미묘하지만 중요한 맥락을 잃을 수 있다고 설명하고, Claude Code가 작업 중에 할 일 목록을 만들어 두고 다시 보는 것을 구조화된 노트의 예로 듭니다4. Claude Code 문서에 따르면 대화로 준 지시는 압축 뒤 요약에서 누락될 수 있지만, 프로젝트 루트의 규칙 문서(CLAUDE.md)는 압축 뒤에 디스크에서 다시 읽혀 들어갑니다. 반면 경로별 규칙과 하위 폴더의 규칙 문서는 압축 직후에는 다시 읽히지 않고, 그 경로나 폴더의 파일을 다시 열 때 읽힙니다18. 그래서 세션 내내 지켜야 할 지시는 대화로 주기보다 프로젝트 루트의 규칙 문서에 둡니다.

규칙 문서의 작성

규칙 문서는 상시 규칙으로 읽혀 모든 세션의 컨텍스트를 차지하므로, 작성 방법이 결과에 영향을 줍니다. Claude Code는 CLAUDE.md를, Codex는 AGENTS.md를 읽습니다.

버전 주석 (2026년 10월) Claude Code 문서는 v2.1.277 이상에서 저장소에 CLAUDE.md가 없고 AGENTS.md만 있으면 AGENTS.md를 읽는다고 안내합니다. Amazon Bedrock이나 텔레메트리를 끈 일부 세션은 v2.1.281 이상이 필요합니다18. 두 제품의 규칙 문서 비교는 Chapter 10의 규칙 문서 비교에 있습니다.

이 책은 Claude Code 문서의 CLAUDE.md 작성 안내를 다음 네 가지로 정리합니다18.

  • 확인할 수 있을 만큼 구체적으로: "파일을 정돈해 둔다" 대신 "API 처리 파일은 src/api/handlers/에 둔다"처럼 작성합니다.
  • 짧게: Claude Code 문서는 CLAUDE.md 파일 하나를 200줄 미만으로 유지하는 것을 권장 목표로 제시하고, 파일이 길수록 컨텍스트를 더 차지하고 지침을 지키는 비율이 낮아질 수 있다고 설명합니다. 200줄은 제품이 강제하는 제한이 아니며, 이보다 짧다고 지침을 지키는 것이 보장되지도 않습니다.
  • 일관되게: 두 지침이 서로 모순되면 에이전트가 둘 중 하나를 임의로 따를 수 있으므로, 같은 대상에 대한 지침이 겹치지 않게 합니다.
  • 나누어서: 여러 단계로 이루어진 절차는 Skill로, 일부 파일에만 해당하는 지침은 경로별 규칙으로 옮깁니다. 규칙 문서에 @경로로 가져온 파일은 시작할 때 함께 읽혀 상시 규칙이 되므로, 필요할 때 읽게 할 문서는 경로만 글로 적습니다.

뒤의 예제 절에서는 Chapter 3의 예제에서 구현을 맡은 에이전트의 규칙 문서를 이 네 기준에 비추어 봅니다. 규칙 문서를 직접 작성하는 실습은 부록 실습의 실습 2에 있습니다.

규칙 문서의 관리

규칙 문서는 한 번 작성하고 끝나는 문서가 아닙니다. 이 책은 항목을 추가하는 일뿐 아니라, 사실이나 결정이 변경되어 맞지 않게 된 항목을 수정하거나 삭제하는 일도 관리에 포함합니다. 오래된 지침이 남으면 장 첫머리에서 본 것처럼 에이전트가 다른 근거로 판단할 수 있기 때문입니다. Claude Code 문서는 항목을 추가할 시점으로 네 가지를 제시합니다18.

  • 에이전트가 같은 실수를 두 번째로 했을 때
  • 코드 리뷰에서 에이전트가 알았어야 할 내용이 지적되었을 때
  • 지난 세션에 입력한 정정 내용을 다시 입력하고 있을 때
  • 새로 합류한 팀원에게도 같은 설명이 필요할 때

수정하거나 삭제할 항목은 폴더 구조나 명령이 변경되었을 때, 같은 내용이 다른 문서에 생겼을 때, 문서가 권장 길이를 넘었을 때 찾아봅니다.

항목을 추가해도 에이전트가 반드시 따르는 것은 아닙니다. Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 다룬다고 설명하고, 에이전트의 판단과 관계없이 막아야 하는 동작은 도구를 실행하기 전에 작동하는 훅(Hook)으로 막으라고 안내합니다18. 그래서 규칙 문서의 금지 항목 가운데 어겨서는 안 되는 항목은 권한 규칙(Permission Rule)이나 훅으로도 막을지 검토합니다. 지시로 충분한 규칙과 강제가 필요한 규칙의 구분은 Chapter 2의 지시와 강제에서 다루었습니다.

예제: 변경 요청 사항을 구현하는 에이전트가 읽을 정보 정하기

경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)은 재무팀이 정산 요청 화면에 프로젝트 코드 선택 항목을 추가해 달라고 요청한 내용입니다. 이 절에서는 Chapter 3에서 설계한, 변경 요청 사항을 구현하는 에이전트가 무엇을 언제 읽는지를 앞의 네 종류와 작성 기준으로 정합니다. 수용 기준, 수용 시험(acceptance/), 검사 스크립트(check.py), 작업 단위 목록(tasks.json)과 통과 값, 검토 하위 에이전트는 Chapter 3에서 정의했고, 작업 단위로 나누는 방법은 Chapter 6에서 다룹니다. 이 에이전트는 부록 실습 2에서 예시 규칙 문서(examples/expense-app/reference/CLAUDE.example.md)를 본떠 저장소 루트에 작성한 CLAUDE.md를 상시 규칙으로 읽습니다. reference/ 폴더의 예시 파일은 Claude Code가 자동으로 읽지 않습니다. 이 규칙 문서는 목적, 읽는 순서, 작업 순서, 수정 범위, 중단 규칙, 명령의 여섯 절로 이루어지며, 빈 줄을 포함해 32줄입니다. 다음은 그 가운데 이 장과 관련된 두 절의 발췌입니다.

## 읽는 순서
1. docs/CR.md(수용 기준)
2. DECISIONS.md
3. tasks.json
4. HANDOFF.md(있으면)

## 수정 범위
- 수정할 수 있음: expense/, app.py, tests/, tasks.json의 "통과" 값, HANDOFF.md
- 수정하지 않음: data/, acceptance/, check.py, CLAUDE.md, DECISIONS.md, .claude/

읽는 순서 절은 필요할 때 읽는 문서의 위치와 순서만 안내하고, 문서의 내용은 규칙 문서에 옮기지 않습니다. 변경 요청 사항 문서(docs/CR.md)는 표 5-1의 분류로는 작업 입력인 변경 요청서에 해당합니다. 그러나 이 예제에서는 요청에 첨부하지 않고 읽는 순서 절에 위치만 적어 에이전트가 작업 단위마다 직접 열게 하므로, 필요할 때 읽는 문서로 다룹니다. 수정 범위 절은 에이전트가 수정할 수 있는 파일과 수정하지 않을 파일을 나누고, 뒤의 확인 방법 절에서 바뀐 파일 목록과 대조하는 기준이 됩니다. 수정하지 않음의 경로는 권한 설정 예시(reference/settings.example.json)의 금지 규칙에도 들어 있어, 규칙 문서는 지시를 맡고 권한 설정은 도구 호출의 강제를 맡습니다(부록 실습의 실습 3).

앞 절의 네 기준으로 보면, 이 규칙 문서는 수정 범위를 폴더와 파일 이름으로 적어 바뀐 파일과 대조할 수 있고(구체적으로), 32줄로 권장 목표보다 짧습니다(짧게). 또 수정할 수 있음과 수정하지 않음에 겹치는 경로가 없고(일관되게), 수용 기준과 결정의 내용은 각 파일에 두고 위치만 안내합니다(나누어서). 표 5-5는 네 종류의 정보를 이 예제에서 어떻게 정했는지 보여 줍니다.

긴 작업의 기법도 이 예제에 쓰입니다. 규칙 문서의 중단 규칙은 세션을 마칠 때 인계 메모(HANDOFF.md, Chapter 8의 기록의 세 종류)에 현재 상태, 읽을 문서, 미결정, 다음 작업, 확인 명령을 적게 합니다. 이전 세션을 이어 가지 않고(claude --continue) 새로 시작한 세션에는 지난 대화가 컨텍스트에 없으므로, 인계 메모가 다음 세션이 읽을 구조화된 노트 역할을 합니다. tasks.json의 통과 값도 어느 작업 단위까지 끝났는지를 남기는 노트입니다. 수용 기준 대조를 검토 하위 에이전트에게 맡기는 것은 하위 에이전트 기법의 예입니다.

규칙 문서에 위치와 순서만 두고 내용은 각 문서에서 읽게 하는 방식은 이 책의 원고 저장소에도 쓰입니다. 원고를 작성하는 에이전트는 작업을 시작할 때 원고 저장소 루트의 규칙 문서(CLAUDE.md)를 읽고, 거기 적힌 순서대로 인계 메모(HANDOFF.md)와 작가의 결정과 취향을 정리한 문서(AUTHOR_PREFS.md)를 이어서 읽습니다.

실패와 막는 장치

표 5-5가 예제에서 읽을 정보를 정한 결과라면, 표 5-6은 정보가 누락되거나 넘치거나 오래되었을 때 생길 수 있는 실패와 방지 장치를 정리합니다. 행은 상시 규칙(첫째 행), 필요할 때 읽는 문서(둘째, 셋째 행), 작업 입력(넷째 행), 작업 중 수집, 생성 정보(다섯째 행)의 순서이고, 표의 읽는 순서와 수정 범위는 예제 절에서 보인 규칙 문서의 두 절을 가리킵니다. 셋째 행의 결정 기록은 예제 규칙 문서의 읽는 순서에 이미 있습니다. 다섯째 행의 시험 실행 하위 에이전트는 예제의 검토 하위 에이전트가 읽기 전용이라 시험을 실행하지 않으므로 따로 정의해야 합니다.

확인 방법

에이전트가 무엇을 읽고 있는지는 제품의 화면과 대화 기록으로 확인합니다. 규칙 문서가 컨텍스트에 들어 있다는 것과 에이전트가 규칙을 실제로 지킨다는 것은 다른 문제입니다. 그래서 규칙 문서가 보여도 지켜진다고 판정하지 않고, 규칙을 이해했는지는 응답으로, 실제로 지켰는지는 바뀐 파일로 따로 확인합니다. 표 5-7은 변경 요청 사항을 구현하는 에이전트에서 확인할 항목입니다.

원칙과 점검 질문

상시 규칙 문서에는 모든 작업에 필요한 내용만 짧게 두고, 나머지는 필요할 때 읽도록 위치만 안내합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 규칙 문서에 특정 작업에만 필요한 지침이 섞여 있지 않습니까?
  2. 지난 세션에 입력한 정정 내용을 이번 세션에 다시 입력하고 있지 않습니까?
  3. 에이전트가 대체된 결정이나 오래된 자료를 읽고 근거로 삼을 수 있는 경로가 남아 있습니까?
