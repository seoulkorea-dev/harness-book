Chapter 5 컨텍스트 엔지니어링: 에이전트가 읽는 정보 설계

결과를 정하는 것은 요청 문장의 완성도가 아니라, 에이전트가 판단하는 시점에 무엇을 읽고 있는지입니다.

에이전트(Agent)는 작업을 시작할 때 규칙 문서와 요청, 작업 중에 읽은 파일과 도구 결과를 근거로 판단합니다. 그래서 필요한 자료가 없거나 오래된 자료가 남아 있으면, 같은 요청에도 근거가 다른 결과가 나옵니다. 따라서 에이전트가 읽을 자료를 선별하고 최신 상태로 유지해야 합니다. 이 장에서는 에이전트가 읽는 정보의 종류, 정보를 제공하는 시점, 규칙 문서 작성 방법을 익힙니다.

  • 컨텍스트는 한정된 자원이므로 필요한 자료를 선별해서 제공합니다.
  • 에이전트가 읽는 정보는 상시 규칙, 필요할 때 읽는 문서, 작업 입력, 작업 중 생성 정보로 나뉩니다.
  • 규칙 문서는 짧게 유지하고, 같은 실수가 반복될 때 항목을 추가합니다.

컨텍스트는 한정된 자원

컨텍스트 엔지니어링(Context Engineering)은 Chapter 1에서 정리한 대로 모델에 넘길 정보를 선별하고 유지하는 일입니다. 선별이 필요한 것은 컨텍스트(Context, 모델이 응답을 생성할 때 입력되는 정보 전체)가 한정된 자원이기 때문입니다. 모델은 컨텍스트를 토큰(Token, 글을 처리하는 최소 단위) 단위로 처리하고, 한 번에 처리할 수 있는 범위인 컨텍스트 윈도(Context Window)에는 한도가 있습니다(Chapter 1). Claude Code는 컨텍스트를 한정된 자원으로 설명합니다. 토큰이 늘어날수록 모델이 그 안에서 정보를 정확히 찾는 능력이 떨어지는 현상이 있기 때문입니다(Rajasekaran 외, 2025).

자료를 많이 제공할수록 결과가 나아진다는 의견이 있습니다. 컨텍스트가 한정된 자원이라면, 관련 없는 자료는 관련 있는 자료가 차지할 자리를 줄입니다. 정할 것은 자료의 양이 아니라, 작업마다 어떤 자료를 읽게 할지입니다.

Claude Code에서는 입력창에서 실행하는 /context 명령이 컨텍스트에서 무엇이 공간을 차지하는지 보여 줍니다. 관련 없는 작업으로 넘어갈 때는 /clear 명령으로 대화를 비우고, 긴 대화는 /compact 명령으로 요약(압축, 미리 제공하는 정보와 필요할 때 찾는 정보에서 다룸)해 공간을 확보합니다(Anthropic, 2026).

에이전트가 읽는 정보의 종류

컨텍스트 윈도에 한도가 있으므로, 무엇이 언제 들어가는지 구분해야 선별할 수 있습니다. 이 책은 에이전트가 읽는 정보를 읽히는 시점에 따라 네 가지로 정리합니다. 상시 규칙은 규칙 문서처럼 세션(Claude Code를 시작해 이어지는 대화 한 번)이 시작될 때마다 읽히는 문서입니다. 필요할 때 읽는 문서는 특정 작업이나 특정 파일을 다룰 때만 읽힙니다. Skill(필요할 때만 읽히는 지침과 자료의 묶음)과 경로별 규칙(특정 경로의 파일을 다룰 때만 읽히는 규칙)이 여기에 속합니다. 작업 입력은 사용자가 요청과 함께 제공하는 자료입니다. 작업 중 생성 정보는 에이전트가 파일을 열거나 도구를 실행해서 얻은 결과입니다. 네 종류는 모두 컨텍스트 윈도에 들어갑니다. 같은 문서라도 요청과 함께 제공하면 작업 입력이고, 규칙 문서에 위치만 안내해 두고 에이전트가 필요할 때 읽게 하면 필요할 때 읽는 문서가 되므로, 분류의 기준은 문서의 종류가 아니라 읽히는 시점입니다. 그림 5-1은 정보가 오는 곳(규칙 문서, 세부 문서, 사용자, 도구 실행)과 네 종류가 언제 컨텍스트 윈도에 들어가는지를, 표 5-1은 종류별 예와 관리 방법을 보여 줍니다.

표 5-2는 그림 5-1의 구성 요소를 설명합니다.

상시 규칙에는 모든 작업에 필요한 내용만 두고, 나머지는 필요할 때 읽는 문서로 분리하는 구성이 실제로 쓰입니다. Codex로 제품을 개발한 OpenAI의 팀은 처음에 지침 전체를 AGENTS.md 한 파일에 담았다가 실패하자, 약 100줄의 짧은 AGENTS.md가 세부 문서의 위치를 안내하는 구성으로 전환했습니다(Lopopolo, 2026).

미리 제공하는 정보와 필요할 때 찾는 정보

앞의 네 종류는 정보가 읽히는 시점으로 나눈 것이고, 이 절은 자료를 컨텍스트에 어떻게 가져올지를 정합니다. 상시 규칙은 작업 전에 미리 제공하는 쪽이고, 필요할 때 읽는 문서는 필요할 때 찾는 쪽에 가깝습니다. 에이전트에게 자료를 주는 방법은 두 가지입니다. 하나는 작업 전에 관련 자료를 찾아 제공하는 방법입니다. Claude Code는 많은 AI 네이티브 애플리케이션이 어떤 형태로든 임베딩 기반의 사전 검색(문장의 뜻을 수치로 변환해 비슷한 자료를 작업 전에 찾는 검색)으로 중요한 자료를 미리 찾아 둔다고 설명합니다. 다른 하나는 필요할 때 찾는 방법입니다. 에이전트는 파일 경로, 저장된 쿼리(미리 저장해 둔 검색 조건), 웹 링크 같은 가벼운 식별자만 가지고 있다가, 실행 중에 도구로 자료를 불러옵니다(Rajasekaran 외, 2025).

미리 제공하는 방법은 미리 계산해 둔 자료를 가져오므로 빠릅니다. 필요할 때 찾는 방법에서는 에이전트가 탐색하며 관련 자료를 단계적으로 찾지만, 미리 계산된 자료를 가져오는 것보다 느립니다. 도구와 탐색 기준이 없으면 관련 없는 탐색을 이어 가며 컨텍스트를 낭비할 수도 있습니다. 두 방법을 섞을 수도 있습니다. Claude Code는 CLAUDE.md를 작업 전에 컨텍스트에 포함하고, 파일 이름 패턴으로 찾는 glob과 내용으로 찾는 grep 같은 도구로 파일을 필요할 때 찾습니다.

어느 방법이든 찾아 둔 자료와 작업 기록은 작업이 길어질수록 쌓이므로, 결국 컨텍스트 윈도를 넘는 정보를 다뤄야 합니다. Rajasekaran 외(2025)는 이런 작업을 위한 압축, 구조화된 노트, 하위 에이전트(Subagent)의 세 가지 기법을 소개합니다(내용은 표 5-4). 하위 에이전트는 Chapter 2에서 정의한 대로, 주 대화(사람과 에이전트가 주고받는 세션의 대화)와 분리된 자기 컨텍스트에서 이전 대화 없이 시작합니다. 그림 5-2는 자료를 주는 두 방법과 세 가지 기법을, 표 5-3은 그림의 구성 요소를, 표 5-4는 기법별 내용과 적합한 작업을 보여 줍니다.

Rajasekaran 외는 Claude Code가 할 일 목록을 만드는 것을 구조화된 노트의 예로 듭니다. 경비 정산 시스템 개편 변경 요청(Change Request) CR의 인계 메모(HANDOFF.md, Chapter 8의 기록의 세 종류)도 같은 역할을 합니다. 압축에는 주의가 필요합니다. Rajasekaran 외는 지나치게 압축하면 미묘하지만 중요한 맥락을 잃을 수 있다고 설명합니다. 대화로 준 지시도 요약에서 빠질 수 있지만, 프로젝트 루트의 규칙 문서(CLAUDE.md)는 압축 뒤에도 디스크에서 다시 읽혀 들어갑니다. 경로별 규칙과 하위 폴더의 규칙 문서는 해당 파일을 다시 열 때 읽힙니다(Anthropic, 2026). 그래서 계속 지켜야 할 지시는 대화가 아니라 규칙 문서에 둡니다.

규칙 문서 작성

상시 규칙으로 읽히는 규칙 문서(Chapter 2)는 모든 세션의 컨텍스트를 차지하므로, 작성 방법이 결과에 영향을 줍니다. Claude Code는 CLAUDE.md를, Codex는 AGENTS.md를 읽습니다. Claude Code 문서의 CLAUDE.md 작성 안내를 이 책은 네 가지로 정리합니다(Anthropic, 2026).

  • 확인할 수 있을 만큼 구체적으로: "코드를 정리해 줘" 대신 "API 처리 파일은 src/api/handlers/에 둔다"처럼 작성합니다.
  • 짧게: 파일 하나를 200줄 미만으로 유지하는 것을 목표로 합니다. 문서가 길수록 컨텍스트를 더 차지하고 지침 준수율이 낮아집니다.
  • 일관되게: 두 지침이 서로 모순되면 에이전트가 둘 중 하나를 임의로 따를 수 있습니다.
  • 분리: 여러 단계로 이루어진 절차나 일부 파일에만 해당하는 지침은 Skill이나 경로별 규칙으로 분리합니다.

Chapter 3의 CR을 구현하는 에이전트의 규칙 문서는 이 기준으로 예제 절에서 살펴봅니다.

규칙 문서를 직접 작성하는 실습은 부록 실습의 실습 2에 있습니다.

버전 주석 (2026년 10월) Claude Code 문서는 v2.1.277 이상에서 저장소에 CLAUDE.md가 없고 AGENTS.md만 있으면 AGENTS.md를 읽는다고 안내합니다(Anthropic, 2026). 두 제품의 규칙 문서 비교는 Chapter 10의 규칙 문서 비교에 있습니다.

규칙 문서의 관리

규칙 문서는 한 번 작성하고 끝나는 문서가 아닙니다. 이 책은 이미 바뀐 항목을 수정하거나 삭제하는 일도 관리에 포함합니다. 오래된 지침이 남으면 장 첫머리에서 본 것처럼 근거가 다른 결과가 나오기 때문입니다. 항목을 추가할 시점으로 Claude Code 문서는 네 가지를 제시합니다(Anthropic, 2026).

  • 에이전트가 같은 실수를 두 번째로 반복했을 때
  • 코드 리뷰에서 에이전트가 알았어야 할 내용이 지적되었을 때
  • 지난 세션에 입력한 정정 내용을 다시 입력하고 있을 때
  • 새로 합류한 팀원에게도 같은 설명이 필요할 때

항목을 추가해도 에이전트가 반드시 따르는 것은 아닙니다. 규칙 문서는 지시일 뿐 강제가 아닙니다. Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 다룬다고 설명하고, 반드시 막아야 하는 동작은 훅(Hook)으로 처리하라고 안내합니다(Anthropic, 2026). 훅과, 지시로 충분한 규칙과 강제가 필요한 규칙의 구분은 Chapter 2의 지시와 강제에서 다룹니다.

예제: CR 에이전트가 읽는 정보

앞의 작성 기준이 CR에서 어떻게 나타나는지 봅니다. CR을 구현하는 에이전트는 부록 실습의 규칙 문서(examples/expense-app/reference/CLAUDE.example.md)를 상시 규칙으로 읽습니다. 이 규칙 문서는 목적, 읽는 순서, 작업 순서, 수정 범위, 중단 규칙, 명령의 여섯 절로 이루어지며, 빈 줄을 포함해 31줄입니다. 다음은 그 가운데 이 장과 관련된 두 절의 발췌입니다.

## 읽는 순서
1. docs/CR.md(수용 기준)
2. DECISIONS.md
3. tasks.json
4. HANDOFF.md(있으면)

## 수정 범위
- 수정할 수 있음: expense/, app.py, tests/, tasks.json의 "통과" 값, HANDOFF.md
- 수정하지 않음: data/, acceptance/, check.py, CLAUDE.md, DECISIONS.md, .claude/

읽는 순서 절은 필요할 때 읽는 문서의 위치와 순서만 안내하고, 문서의 내용은 규칙 문서에 옮기지 않습니다. 변경 요청서(docs/CR.md)는 표 5-1에서 작업 입력의 예였지만, CR에서는 작업 단위마다 다시 읽는 수용 기준 문서이므로 읽는 순서에 두어 필요할 때 읽는 문서로 다룹니다. CR에서 규칙 문서는 미리 제공되고, 읽는 순서의 문서와 코드 파일은 에이전트가 필요할 때 찾습니다. 수용 기준, 수용 시험(acceptance/), 검사 스크립트(check.py), 작업 단위 목록(tasks.json)과 통과 값, 검토 하위 에이전트는 Chapter 3에서 정의했고, 작업 단위로 나누는 방법은 Chapter 6에서 다룹니다. 표 5-5는 네 종류의 정보와 긴 작업의 기법을 CR에서 어떻게 채웠는지 보여 줍니다.

같은 원리는 이 책의 원고 작업에도 쓰입니다. 규칙 문서가 읽을 문서의 위치를 안내하는 방식은 이 책의 저장소에서도 사용합니다. 원고를 작성하는 에이전트는 작업을 시작할 때 저장소 루트의 작업 안내(CLAUDE.md)를 읽고, 안내에 적힌 인계 메모(HANDOFF.md, 지난 세션의 진행 상황)와 작가의 결정과 취향을 정리한 문서(AUTHOR_PREFS.md)를 이어서 읽습니다.

실패와 막는 장치

표 5-5가 CR에서 정보를 채운 방법이라면, 표 5-6은 정보가 누락되거나 넘칠 때 주요 정보 종류별로 생길 수 있는 실패와 막는 장치입니다. 표의 읽는 순서와 수정 범위는 예제 절에서 보인 규칙 문서의 두 절을 가리킵니다.

확인 방법
