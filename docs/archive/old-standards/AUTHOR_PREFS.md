# 작가 결정과 취향(AUTHOR_PREFS)

에이전트가 읽는 작가의 결정과 취향입니다. editor는 이 문서를 어긴 곳을 필수로 판정합니다. 바뀌면 작가 요청(GitHub 이슈)이나 DECISIONS.md로 갱신합니다.

## 흐름과 이해도(검수의 첫째 필수 기준, D-117)
작가가 처음부터 요구해 온 검수의 핵심입니다. 규칙(문체, 사실, 용어, 번호, 그림 부품)을 모두 지켜도 아래 셋 가운데 하나를 어기면 editor는 필수로 판정합니다(취향이 아니라 작가의 결정).
- 장의 흐름: 절의 순서가 장의 주장을 쌓아 간다. 절마다 앞 절에서 이어지는 이유가 있다.
- 절과 문단의 논리: 절의 첫 문단은 왜(필요성) → 무엇(정의, 이 책의 정리이면 그렇다고 밝힘) → 어떻게 → 근거 순서다. 문단 첫 문장은 앞 문단과 이어진다. 인용은 바로 앞 주장을 뒷받침한다. 정의를 이유 없이 나열하지 않는다.
- 독자 이해도: 하네스를 처음 배우는 대학생과 직장인이 "왜?", "그래서?", "이게 무슨 말?"이라고 멈출 곳이 없다. 예제는 원리를 이해시키는 데 쓰인다.

검수 방법
- 통독과 표: editor와 flow-reviewer는 판정 전에 바뀐 부분만이 아니라 장 전체를 처음부터 끝까지 읽는다. flow-reviewer는 장마다 reviews/flow/<장>-flow.md에 내용 정리표(| 절 | 핵심 내용 한 줄 | 앞 절과 이어지는 이유 | 문맥이 끊긴 곳 | 중복 | 빠진 것 |, D-129)를 만들고, 끊긴 곳은 필수다. 장 PR 설명에 이 표를 링크한다.
- 독자 점검: reader-novice는 장 개정과 흐름 재점검 때 항상 부르고, 독해가 필요한 점검이므로 sonnet으로 실행한다(비용 규칙의 예외).

## 책과 독자
- 독자는 하네스를 처음 배우는 대학생과 직장인이다. 설명은 자세하게, 실행해 볼 수 있는 확인 방법을 둔다.
- 독자를 가리키는 말(독자, 여러분, 당신, 우리)과 관리자 관점 표현을 쓰지 않는다.
- 장 틀: 주장 제목(장 제목 아래 한 줄) → 원리 → 예제 적용 → 실패 표 → 확인 방법 → 원칙 한 문장 → 점검 질문
- 예제: 장마다 첫 등장은 "경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)", 이후 "변경 요청 사항". 약어 CR과 영어 병기는 쓰지 않는다(D-125, 장 정비 때 바꿈). 작업 단위는 "작업 1"~"작업 5". 예제 사실은 docs/example-facts.md를 따른다(R7)
- 기준과 검수 규칙: 원고 기준은 BOOK_STANDARD.md(D-131, D-132), 반복된 지적은 REVIEW_RULES.md(R1~R17)로 승격했다. 원고를 쓰거나 고칠 때 모두 적용하고, 외부 검토는 새 유형만 찾는다(D-127, 이슈 #66). 같은 장 안 링크 금지(D-122), 인용은 책 전체 번호와 부록 끝 참고 문헌(D-131), 표 체계(D-124), 단정 대신 조건을 밝힘(D-126)
- 핵심 정의는 바꾸지 않는다: 에이전트 = 모델 + 하네스, 하네스 = 모델 바깥의 실행 체계(실행 장치 + 설정, D-121), 다섯 구성 요소(역할, 도구, 권한, 기록, 검증)

## 문체와 표기
- 합니다체. 문장은 짧게(lint 기준). 항목 나열은 가운뎃점(·) 대신 쉼표(,), 빗금(/)도 쓰지 않는다.
- 주체 표기는 제품명(Codex, Claude Code)을 기본으로 한다. 제품과 무관한 회사 글(Claude Code 출시 전 글, 모델과 API 문서)은 회사 이름을 남긴다. 인용 괄호(저자, 연도)와 참고 자료는 그대로(D-108).
- 용어는 장마다 첫 등장에 "한글(원어)" 병기.
- 사실은 1차 출처를 확인해 research/에 기록한 뒤 쓴다. 확인하지 못한 사실은 쓰지 않는다.

## 그림
- 단색 면과 선. 그러데이션, 그림자, 3D, 아이콘, 경고 색(앰버)을 쓰지 않는다. 금지와 거부는 회색 점선과 글자로 구분한다.
- 맨 위 결론 제목(합니다체)과 강조색 가로선, 연결선은 직선(꺾을 때 직각).
- 그림 안 문구는 개조체(명사나 명사형으로 끝맺음, "으로", "에", "합니다"로 끝내지 않음). "끝" 대신 종료, 완료.
- 요약과 "그래서 할 일"은 상자로 감싸지 않고 맨 아래 "*" 한 줄(상자는 구성 요소처럼 보임).
- 영역 사이 관계는 방향과 이름이 있는 화살표로, 먼저 일어나는 흐름을 위에(예: 하네스 → 모델 "입력과 컨텍스트"가 먼저).
- 그림 안 문구는 누구의 관점인지(주체)가 분명해야 한다("판단 전" 같은 주체 없는 표식 금지).
- 그림, 그림의 접근성 설명과 캡션에는 제품명과 회사명을 쓰지 않는다(D-095). 비교 그림은 제품 A, 제품 B.
- 그림은 예외 없이 모두 일반 내용으로 그리고 예제(CR) 사실과 예제 파일 이름을 넣지 않는다. 예제에서 어떻게 채웠는지는 표와 본문이 맡는다(D-116, D-115와 D-114를 대체).
- 폭 760(기본, 글자 16px 이상) 또는 960(글자 20px 이상). 본문에 없는 분류를 그림에만 두지 않는다.
- 그림은 명세를 먼저 쓰고 배치가 다른 시안 두 개를 만든 뒤 고른다(D-107). 고른 이유는 AUTHOR_QUEUE.md에 적는다.

## 책 전체 일관성(검수의 필수 요소)
- 장 하나를 따로 보지 않고 책 전체의 흐름으로 본다. 1장에서 작가가 확인하고 고친 결과(그림 체계와 그림에 담는 내용(모두 일반 내용), 표 형식, 장 틀, 용어, 표기)가 기준이며, 2~11장, 시작하며, 마치며, 부록에 같게 적용한다(D-111).
- 같은 종류의 그림, 표, 문장 형식은 장마다 같은 모양이어야 한다. 그림은 FIGURE_STYLE.md 7절의 기준 시각 체계(1장 그림 1-1, 1-2)를 따른다.
- 기준이 바뀌면(예: 1장 그림을 고침) 이미 끝난 장에도 같은 변경을 전파하는 작업을 작업 목록 맨 앞에 넣는다.
- 중간에 작가 확인이 필요한지 스스로 판단한다. 기준이 이미 있으면 묻지 않고 진행하고, 기준이 없거나 작가만 정할 일이면 AUTHOR_QUEUE.md에 묻는다.

## 작업 방식
- 원고와 그림의 작성, 검사, 커밋, push, PR, 병합은 VS Code의 Claude Code(작성 에이전트)가 한다. 검수는 editor가 한다(D-110).
- 병합은 editor "병합 가능"(필수 0), check_all 통과, CI 통과일 때만 한다.
- 지시하지 않은 변경을 하지 않는다. 꼭 필요하면 PR 설명에 따로 적는다.
- 작가만 정할 일(목차, 장의 주장, 핵심 정의, 그림 방침, 문체 규칙의 변경)은 하지 않고, 필요하면 AUTHOR_QUEUE.md에 권장안과 함께 적고 진행을 멈추지 않는다.
- 작가 요청은 GitHub 이슈(라벨 request)로 온다. 다른 일보다 먼저 처리하고, 처리 결과(PR 주소)를 이슈에 남긴 뒤 닫는다.
- 보고에는 검사 출력 원문을 붙이고, 끝에 미결정 목록을 둔다.
