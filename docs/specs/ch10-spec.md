## 절 첫 문단(왜 → 무엇 → 어떻게 → 근거)
- 장 첫 문단: 작동(두 제품 모두 규칙 문서, 권한, 격리, 설정 파일로 하네스(Harness)를 구성) → 한계(같은 정책도 구성 요소마다 설정 위치와 형식이 다르고, 기본으로 켜진 것과 직접 설정할 것이 다름) → 결과(모델 성능만으로 고르면 운영 중에 정책이 설정에 반영되지 않은 것을 뒤늦게 발견) → 행동(구성 요소 단위로 비교) → 범위(네 기준 비교, 선택 기준, CR 정책을 두 제품에 옮기기). 주장 줄 되풀이 삭제. 앞 장 연결: 9장의 권한 규칙과 격리 링크 한 줄
- 요약 세 줄: (1) 정책은 규칙 문서, 권한, 격리, 설정 파일에 나뉘어 적히고 제품은 이 네 기준으로 비교 (2) Claude Code는 도구별 규칙에서, Codex는 운영 체제 수준 격리에서 출발하므로 옮길 때 추가할 것이 다름 (3) 같은 정책도 금지와 확인 요청이 제품마다 다르게 갈리므로 설정 뒤에 거부 여부를 확인
- criteria: 왜(정책 하나가 네 곳에 나뉘어 적힘: 지시는 규칙 문서, 강제는 권한과 격리, 그 값은 설정 파일) → 무엇("이 책은 비교 기준을 이 네 가지로 정리합니다", 2장의 다섯 구성 요소라고 쓰지 않음) → 어떻게(그림 10-1, 해설표 표 10-1에 제품 이름과 본문의 절) → 근거(Claude Code 문서는 2026년 10월 20일, Codex 문서는 2026년 10월 4일 확인, 도입 전 재확인). 각 기준의 앞 장 링크: 규칙 문서 ch05#rule-doc, 지시와 강제 ch02#instruct-enforce, 권한 규칙 ch02#tool-scope, 격리 ch09#isolation, 설정 파일 ch03#files
- rule-docs: 왜(규칙 문서는 읽고 따르는 지시이므로 이름과 범위가 다르면 한 제품에서만 적용) → 무엇(Claude Code: CLAUDE.md, 네 범위(조직, 사용자, 프로젝트, 개인), 상위 폴더부터 작업 폴더까지 이어 붙여 읽음, CLAUDE.md, .claude/CLAUDE.md, CLAUDE.local.md가 하나도 없을 때만 AGENTS.md를 읽음(v2.1.277 이상, 버전 주석). Codex: AGENTS.md, 전역 ~/.codex에서 저장소 루트, 하위 폴더 순, 같은 폴더의 AGENTS.override.md가 있으면 그 파일) → 어떻게(두 제품을 함께 쓰면 AGENTS.md를 공통 규칙으로, CLAUDE.md 첫 줄에 @AGENTS.md를 두고 아래에 Claude Code 전용 지침. 짧은 코드 예 하나) → 근거(S-C10-1, OpenAI 2026). 네 범위는 "회사 공통 규칙과 개인 규칙을 나눠 두는 자리" 한 구절
- permissions: 왜(규칙 문서는 지시라 반드시 지킬 것은 제품이 강제, ch02 상기) → 무엇과 어떻게:
  - Claude Code: 권한 규칙(Permission Rule) 한 줄 상기(도구별 허용, 확인 요청, 금지, ch02#tool-scope, ch09#permissions). 권한 모드(Permission Mode)는 이 장이 정의: 어느 규칙에도 일치하지 않는 요청을 어떻게 처리할지 정하는 설정. 설정값 여섯 가지 이름과, 본문에 쓰는 것만 풀이(default: 처음 쓰는 동작은 확인 요청, plan: 읽기만 하고 계획, bypassPermissions: ch09 정의 상기). 시작 모드는 실행 방식에 따라 다름(터미널과 VS Code v2.1.283 이상 auto, claude -p와 SDK는 default, 프로젝트 설정의 auto와 bypassPermissions는 효력 없음: 버전 주석으로)
  - 샌드박스(Sandbox) 한 줄 상기(ch09#isolation): 기본 꺼짐, /sandbox나 sandbox.enabled로 켬, 셸 명령과 하위 프로세스만, 파일 도구는 밖, 쓰기는 작업 폴더와 임시 폴더, 네트워크는 허용 도메인 목록과 대조하고 목록에 없는 도메인은 확인 요청
  - Codex: 승인 정책(Approval Policy)은 확인을 요청하는 시점을 정함(금지와 다름). 샌드박스 모드 세 가지(read-only, workspace-write, danger-full-access)는 명령이 접근할 파일과 네트워크 범위. 로컬 실행은 운영 체제 수준 샌드박스를 기본 적용, 기본은 네트워크 차단과 작업 공간 안 수정(2026-10-04 기록, 신뢰 여부에 따른 차이는 버전 주석). on-request는 샌드박스 밖이 필요한 동작에서 확인 요청. 금지는 규칙 파일(실험 단계)의 forbidden. "권한 프로필"은 쓰지 않음(이름과 베타 여부 미확인)
  - 결론: 출발점 차이 → 운영에서의 결과(Claude Code로 옮기면 격리를 켜야 하고, Codex로 옮기면 금지를 규칙 파일로 추가). 근거 S-C10-2~4, OpenAI 2026
- choice: 왜(모델 성능은 두 제품 모두 갱신되어 비교 시점마다 바뀌고, 운영 중 반복해서 부딪히는 것은 정책 구현) → 무엇(이 책의 판단: 선택 기준은 정책이 요구하는 구성 요소를 제품이 기본으로 갖추는지, 추가 설정이 필요한지) → 어떻게(정책을 먼저 적고, 항목마다 네 기준 중 어디에 적을지 정하고, 표 10-2에서 기본과 추가 설정을 대조. 두 출발점은 양자택일이 아니라 추가 설정의 양과 위치의 차이) → 근거(반론 "더 좋은 모델" 처리, "매일"은 쓰지 않음)
- example: CR 전체 이름 첫 등장과 ch03#example 링크 → 왜(정책은 결국 설정 파일에 적히고 위치와 형식이 다름) → 무엇(CR의 정책 가운데 제품마다 구현이 갈리는 세 가지: push는 사람만 함, 외부 자료를 읽지 않음, 작업 폴더 밖은 수정하지 않음. 이유는 ch09 표 9-4 링크) → 어떻게(Claude Code: CR 설정(ch03#files)의 해당 deny 세 개와 추가할 sandbox.
