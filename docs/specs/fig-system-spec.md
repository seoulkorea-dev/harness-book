## 그림 2-1 하네스의 다섯 구성 요소(구성형, 그림 1-1 체계)
- 제목: 다섯 구성 요소를 모두 정해야 결과를 받아들일 근거가 생깁니다
- 부제: 구성 요소마다 정할 것, CR에서 채운 방법, 이유, 주로 작동하는 루프 단계
- 영역(머리 띠): 지시(역할, 기록), 실행 수단(도구), 강제(권한, 검증). 세 묶음은 이 책의 설명용 분류(본문에 있음)
- 구성 요소: 묶음(연한 파랑, 사용자가 정함) 안에 정할 것, CR에서 이렇게 채움(강조), 이유. 지금 그림의 문구 유지

- "*" 한 줄: 반드시 지킬 규칙은 권한 규칙과 훅으로 강제, 나머지는 규칙 문서로 안내

## 그림 2-2 도구 가용성과 실행 권한의 흐름(흐름형, 그림 1-2 체계, 이슈 #10 A)
- 캡션: 그림 2-2. 도구 가용성과 실행 권한의 흐름 (CR 기준)
- 제목: 도구 가용성은 미리 정하고, 실행 권한은 호출할 때마다 평가
- 부제: 가용성은 작업에 제공할 도구, 권한 평가는 호출마다 금지, 확인, 허용 판단(CR 기준)
- 흐름: 도구 구성(가용성, 묶음: CR은 내장 도구만, 이름만 지정한 금지(WebFetch, WebSearch)는 목록에서 제외, MCP 서버 연결 안 함, 하위 에이전트 도구 범위 Read, Grep, Glob) → 2 도구 호출 요청(판단과 응답 단계, 요청은 실행 아님) → 3 권한 확인(금지, 확인, 허용 순서, 처음 일치하는 규칙) → 허용(확인 규칙은 사람 승인 후) 4 도구 실행(하네스가 실행, 결과 반환) / 거부 → 거부 결과 기록(실행 없이 사유 전달, 회색 점선 테두리, 경고 색 없음) → 결과나 사유가 다음 판단의 입력(점선 되돌림)

- "*" 한 줄: 목록에서 빠지는 것은 이름만 지정한 금지 규칙, 나머지 규칙은 호출할 때마다 평가
- 표 2-2(F) 행: 도구 구성과 가용성, 모델의 도구 호출 요청, 권한 평가, 실행 결과와 거부 사유, 하위 에이전트

## 그림 3-1 CR 구현 에이전트의 하네스(구성형과 흐름형 조합)
- 제목: 에이전트는 검증 기준을 수정할 수 없고, 검사를 통과해야 다음 작업 단위로 갑니다(지금과 같음)
- 부제: CR 구현 에이전트의 하네스: 주체별 수정 권한과 작업 단위의 검증 흐름
- 영역: 수정할 수 있는 파일(파랑 머리 띠), 수정할 수 없는 파일(회갈 머리 띠, 안에 연한 파랑 묶음 "검증 기준"). 각 영역 아래에 주체별 카드(구현 에이전트 수정/금지, 검토 하위 에이전트 읽기만, 사람 승인(commit 확인, push)/작성(사람만))
- 흐름(단계 상자 1~5): 1 파일 수정(구현 에이전트), 2 단위 테스트(훅, 편집 뒤 자동 실행), 3 check.py 실행(구현 에이전트, 마무리 때), 4 commit 확인(사람), 5 다음 작업 단위. 통과 시, 사람 확인 후, 실패 시 구현 수정(회갈 점선), 같은 시험 세 번 연속 실패 시 중단, 인계 메모 작성(규칙 문서의 지시라 금지와 다른 실선 회갈 테두리)
