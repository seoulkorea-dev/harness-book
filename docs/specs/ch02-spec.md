# Chapter 2 명세

- 장 제목(목차 그대로): 하네스의 구성 요소
- 주장 한 줄(장 제목 아래에 둘 문장): 하네스의 품질을 정하는 것은 연결한 도구의 수가 아니라, 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소를 모두 정했는지입니다. (지금 주장 줄 유지, src/site.json ch02)
- 독자가 이 장을 읽고 할 수 있게 되는 것(세 가지):
  1. 맡길 업무 한 건에 대해 다섯 구성 요소마다 "정할 것"을 채우고, 그것을 어느 파일과 설정에 둘지 말할 수 있다.
  2. 규칙을 지시(규칙 문서)로 둘지 강제(권한 규칙, 훅)로 둘지, 어겼을 때 되돌릴 수 있는지로 판단할 수 있다.
  3. 연결한 도구 가운데 이 작업에 노출할 도구를 고르고, 설정이 실제로 적용되었는지 명령과 화면으로 확인할 수 있다.

## 범위와 개정 방향
- 지금 원고를 바탕으로 깊이를 더한다. 절 구성은 유지한다. 절과 앵커: 다섯 구성 요소(components), 도구 노출 범위(tool-scope), 지시와 강제(instruct-enforce), 실패와 막는 장치(fail), 확인 방법(check), 원칙과 점검 질문(principle).
- 다른 장이 링크하는 앵커(components 4곳, tool-scope 3곳, instruct-enforce 1곳, principle 1곳)는 이름을 바꾸지 않는다.
- 장 틀의 "CR 적용"은 따로 절을 만들지 않는다. "다섯 구성 요소" 절의 구성 요소별 "CR에서 이렇게 채움"과 "지시와 강제" 절의 CR 장치 표가 그 역할을 한다.

## 다섯 구성 요소: 정할 것 → CR에서 이렇게 채움 → 이유
본문 "다섯 구성 요소" 절의 표 2-1을 이 형태로 넓힌다(지금 열: 정할 결정, Claude Code의 구현 → 새 열: 정할 것, CR에서 이렇게 채움, 이유).

| 구성 요소 | 정할 것 | CR에서 이렇게 채움(실제 파일과 설정) | 이유 | 근거 |
|---|---|---|---|---|
| 역할 | 에이전트가 맡을 작업과 사람이 맡을 작업의 경계 | 규칙 문서(CLAUDE.md)의 작업 순서: "통과가 false인 첫 작업 단위만 수행", "작업 5의 통과 값은 변경하지 않는다". 검토는 하위 에이전트(.claude/agents/reviewer.md)에 맡김. 사람은 수용 기준 확정, 작업 5 승인, commit 승인, push | 통합 시나리오 범위와 저장소 반영은 판단이 필요하고 되돌리기 어려우므로 사람에게 둠. 만든 쪽과 검토하는 쪽을 나눔 | CLAUDE.example.md, reviewer.example.md, S31 |
| 도구 | 작업에 쓸 기능과 노출 범위 | 내장 도구(파일 읽기와 수정, 명령 실행)만 쓰고 외부 도구 서버는 연결하지 않음. 웹 접근 도구는 이름만 쓴 금지 규칙(WebFetch, WebSearch)으로 목록에서 뺌. 검토 에이전트의 도구는 Read, Grep, Glob | 수용 기준과 코드가 모두 저장소 안에 있어 웹 자료가 필요 없음. 도구가 많으면 어느 도구를 쓸지 모호해지고 컨텍스트를 차지함. 검토자는 수정할 수 없어야 함 | settings.example.json, S25(이름만 쓴 deny는 도구 제거), S29, S30, S34, S35, S31 |
| 권한 | 허용, 확인 요청, 금지할 동작 | 허용: 단위 테스트, check.py, git status, git diff. 확인: git commit. 금지: data/(원본 자료), acceptance/(수용 시험), check.py, CLAUDE.md, DECISIONS.md, .claude/의 수정과 git push | 검증 기준과 원본 자료를 에이전트가 바꾸지 못하게 하고, 저장소 반영은 사람이 함. 금지는 확인보다 먼저 평가되어 예외를 만들 수 없음. Edit 금지는 스크립트를 통한 간접 수정은 막지 못하므로 샌드박스로 보완(9장) | settings.example.json, S25 |
| 기록 | 세션이 끝난 뒤 남길 결정과 진행 | 결정 기록(DECISIONS.md의 D-012), 작업 단위 목록(tasks.json의 통과 값), 인계 메모(HANDOFF.md, 중단 규칙의 다섯 항목), 작업 단위별 commit(부록 실습 5의 확인 방법) | 새 세션은 이전 대화를 보지 못하므로 파일로 남긴 것만 이어짐. 규칙 문서와 자동 메모리는 시작 때 로드되지만 강제 설정은 아님 | CLAUDE.example.md, tasks.example.json, S26, S34 |
| 검증 | 완료로 인정하는 조건과 확인 방법 | 편집 뒤 훅(PostToolUse, "Edit\|Write", 단위 테스트, 실패 시 종료 코드 2로 오류를 모델에 전달), 검사 스크립트 check.py(단위 테스트와 수용 시험, 실행 0건도 실패), 검토 에이전트의 수용 기준 대조 보고 | 완료 보고는 근거가 아님(7장). 훅은 모델의 선택과 무관하게 실행됨. 다만 PostToolUse는 이미 실행된 편집을 막지 못하고 알릴 뿐임 | settings.example.json, check.py, S28 |

- 기존 본문의 "자동 메모리" 설명과 "Agent SDK 문서에 따르면 내장 도구의 정의는 요청마다 컨텍스트에 들어가고" 문장은 출처를 다시 확인한다. 조사에서 직접 문장을 찾지 못했다(S32). 확인되지 않으면 "/context의 시스템 도구 항목이 차지하는 공간"으로 바꾼다.

## 지시와 강제: CR의 실제 장치
본문 "지시와 강제" 절에 새 표(CR의 규칙과 처리 수단)를 지금 표 2-3 뒤에 둔다. 권한 규칙의 평가 순서, 문자열 대조의 한계, 샌드박스는 Chapter 9(ch09.html#permissions)로 연결한다.

| CR의 규칙 | 지시(규칙 문서 CLAUDE.md) | 강제(권한 설정, 훅) | 왜 강제가 필요한가 |
|---|---|---|---|
| 수용 시험과 검사 스크립트를 수정하지 않음 | 수정 범위 절 "수정하지 않음: acceptance/, check.py" | 금지 규칙 Edit(./acceptance/**), Edit(./check.py) | 실패하는 시험을 고쳐 완료를 만드는 길을 막음 |
| 원본 자료를 수정하지 않음 | 수정 범위 절 "data/" | 금지 규칙 Edit(./data/**) | 원본 손상은 되돌리기 어려움 |
| push는 사람만 | (규칙 문서에 없음) | 금지 규칙 Bash(git push *) | 다른 사람에게 보이는 동작 |
| commit 전 사람 확인 | (규칙 문서에 없음) | 확인 규칙 Bash(git commit *) | 작업 단위의 반영 시점을 사람이 정함 |
| 편집할 때마다 단위 테스트 | 명령 절의 단위 테스트 명령 | PostToolUse 훅(Edit\|Write) | 모델이 잊어도 실행됨 |
| 같은 시험이 세 번 연속 실패하면 중단 | 중단 규칙 | (강제 없음, 지시만) | 되돌릴 수 있는 일이라 지시로 충분 |
| 작업 단위를 마치기 전에 검토 요청 | 작업 순서 | (강제 없음, 지시만) | 검토 누락은 check.py가 다시 잡음 |

- 표 아래 한 문단: 규칙 문서만 있는 상태에서는 수정 시도를 막지 못한다(부록 실습 2의 확인 방법). 금지 규칙을 더하면 거부된다(부록 실습 3). Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로, 권한과 훅을 결정과 무관하게 한계를 강제하는 수단으로 설명한다(S26, S27).
- PreToolUse 훅은 실행 전에 막고, PostToolUse 훅은 실행 뒤에 알린다는 차이를 한 문장으로 둔다(S28). 자세한 내용은 Chapter 9로 연결한다.
