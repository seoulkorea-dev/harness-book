## 절 첫 문단(왜 → 무엇 → 어떻게 → 근거)
- 장 첫 문단: 작동(하네스는 처음부터 완성되지 않고 반복된 실패를 구성 요소로 옮기며 자람, Chapter 2의 다섯 구성 요소 링크) → 한계(그 자리에서 고치면 고친 내용이 남지 않음) → 결과(같은 종류의 실패가 다음 작업에서 다시) → 행동(구성 요소의 변경으로 처리) → 범위(작가의 두 책, 자기 프로젝트 순서). 주장 줄 되풀이 삭제. 장면 한 줄(같은 실수를 사람이 매번 찾음 → 검사 도구)
- failures: 왜(실패를 모아야 같은 종류가 보임) → 무엇(작가가 지난 책 「생성형 AI, 묻고 확인하고 활용하기」의 73차례 검수에서 반복된 실패를 다섯 가지로 정리, 검수 1회는 원고 전체를 검토하고 검수 문서를 쓰는 한 차례) → 어떻게(목록, 항목마다 장면과 피해 한 구절, 책 집필 용어는 풀이: 검수 문서, 앵커) → 근거(작가의 검수 기록, 이 책의 작가 경험 기록 기준)
- mapping: 왜(개별 수정은 같은 실패를 막지 못함) → 무엇(이 책의 정리: 원인 구성 요소를 찾아 그곳에 장치를 둠) → 어떻게(표 11-1: 실패, 원인 구성 요소, 막는 장치, 원인 판단 이유 한 구절) → 근거(검증으로 간 세 건은 기준이 명확해 자동 검사로 옮길 수 있었음. Lopopolo 인용은 "OpenAI의 Codex 개발 글"로 별도 문장, 원문 재확인 실패는 research와 Q-030)
- this-book: 왜(지난 책은 실패 뒤에 장치를 더했으므로, 이 책은 처음부터 둘 수 있었음) → 무엇(2026년 10월 기준 이 책 저장소의 다섯 구성 요소와 장치, 그림 11-1, 표 11-2) → 어떻게(표 11-1의 장치가 어디에 남았는지 한 문장씩: 결정 기록, 자동 검사, 작성과 검수 분리, 앵커 검사) → 근거(저장소 파일). 둘째 부분: 그런데도 작업 중 새 실패가 반복되어 장치를 더함(표 11-3, FAILURES 기준). 검증 흐름은 로컬 검사(check_all: 빌드, 금칙어와 lint 3종), 저장소 반영 때 book-check(PR과 main, 빌드 결과와 커밋 일치 추가), 배포 뒤 verify-site로 나눠 씀
- steps: 왜(사례만으로는 옮기는 방법이 안 보이고, 반복 실패의 비용은 작업 규모와 관계없이 쌓임) → 무엇(이 책은 개선 순서를 네 단계로 정리: 실패 기록, 원인 판단, 장치 추가, 결정 기록) → 어떻게(그림 11-2, 표 11-4. 번호 목록 삭제. 두 번째를 기준으로 하는 이유: 한 번은 우연일 수 있음, 이 책의 판단. 결정 기록에 남기는 이유: 장치가 왜 있는지 잊고 지우지 않도록) → 근거(이 책의 FAILURES와 DECISIONS). 작게 시작하는 예: 코드 없이도 규칙 문서 한 줄, 확인 목록 한 줄. 반론("개인 작업에는 과함")은 둘째 문단
- check: "개선 순서의 결과는 기록과 검사 출력으로 확인합니다", 표 11-5(단계 | 확인할 것 | 이 책 저장소에서 | 확인 기준), 자기 프로젝트에서는 실패 기록과 결정 기록 두 파일부터. check_all 출력 끝 예 한 줄(검사 요약, 통과)
