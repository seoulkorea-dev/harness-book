## 그림 4-1 요청의 네 요소와 결과
- 목적(제목): 목적과 완료 기준은 요청하는 사람만 줄 수 있습니다(지금 결론 유지, 합니다체)
- 부제: 네 요소로 구성한 요청이 결과와 결과 확인으로 이어지는 구조(예제 CR 영향 검토 요청)
- 구성 요소
  | 구성 요소 | 한 줄 역할 |
  |---|---|
  | 예제 요청문(영역) | 다음 주 운영 위원회… / <변경 요청> … / <현재 상황> … / 출력 형식 … / 완료 기준 …(지금 그림의 요약 문구, 요청문 글자에 "CR"을 쓰지 않음) |
  | 목적, 입력, 출력 형식, 완료 기준(카드) | 표 4-1의 "정할 내용"과 같은 문구 |
  | 요청하는 사람만 아는 정보 | 목적, 완료 기준을 연한 파랑으로 강조(범례는 부제나 카드 이름 옆 글자로, 띠 상자 없음) |
  | 모델의 결과, 결과 확인(단계 상자) | 누락된 요소는 추측으로 채움 / 완료 기준으로 판정 |
- 관계: 요청문 → 모델의 결과(입력과 컨텍스트로 전달) → 결과 확인(파랑 실선), 완료 기준 → 결과 확인(회갈 점선 "완료 기준을 확인에 다시 사용")
- "*" 한 줄: 요청을 보내기 전에 네 요소가 모두 있는지 점검
- 캡션: 그림 4-1. 요청의 네 요소와 결과 (예제 CR 영향 검토 요청) / 네 요소가 결과와 결과 확인에 이어지는 구조
- 시안 A: 가운데 요청문 영역, 왼쪽 목적과 입력, 오른쪽 출력 형식과 완료 기준 카드(지시선), 아래 흐름(지금 배치를 다듬은 안). 시안 B: 왼쪽 요청문 영역 안에 네 요소 묶음을 위에서 아래로(요소 이름과 요청문 줄을 한 묶음에), 오른쪽 세로 흐름(모델의 결과 → 결과 확인)

## 그림 4-2 요청을 명확하게 만드는 여섯 방법
- 제목: 요청은 여섯 가지 방법으로 명확해집니다(지금 결론을 합니다체로)
- 부제: 모델이 추측해야 할 부분을 요청에서 줄이는 방법(프롬프트 작성 문서 기준)
- 구성 요소: 여섯 방법(이름과 요점 한 줄, 본문 목록과 같은 이름). 번호 원은 쓰지 않음(그림 1-2의 루프 번호와 혼동 방지, 3장 Q-013과 같음). 새 분류를 두지 않음
- "*" 한 줄: 요청에 없는 조건은 모델이 알 수 없음
- 캡션: 그림 4-2. 요청을 명확하게 만드는 방법 (프롬프트 작성 문서 기준) / 본문 여섯 가지 방법의 요점
- 시안 A: 한 영역 안에 3×2 묶음. 시안 B: 2×3 묶음에 방법마다 짧은 "덜 명확 → 더 명확" 예(표 4-4에서 한 구절)
