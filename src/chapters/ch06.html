Chapter 6 착수: 맡길 업무 선정과 작업 단위 분할

업무의 크기를 줄이는 것만으로는 위임의 결과가 정해지지 않고, 업무를 완료 여부를 확인할 수 있는 작업 단위로 나누었는지에 따라 결과가 달라집니다.

작업 단위는 완료 기준과 확인 방법을 갖춘 업무의 조각이고, 작업 단위 분할은 맡길 업무를 그런 조각으로 나누는 일입니다. 에이전트(Agent)는 맡은 업무를 한 세션 안에서 진행하지만, 세션이 넘어가면 다음 세션에 진행 상황이 충분히 전달되지 않을 수 있습니다. 범위가 큰 업무를 한 번에 맡기면 중간 상태를 추적하기 어렵고, 어디까지 끝났는지 검증하기도 어렵습니다. 따라서 착수 전에 맡길 업무를 선정하고, 완료 기준을 갖춘 작업 단위로 나눕니다. 이 장에서는 맡길 업무의 선정 기준, 작업 단위 분할, 여러 에이전트에 나눠 맡기는 방법을 차례로 다루고 경비 정산 예제에 적용합니다.

  • 맡길 업무는 검증 가능성, 자료 접근성, 복구 가능성, 협의와 승인 조건의 네 기준으로 선정합니다.
  • 작업 단위는 한 세션 안에 끝내는 것을 목표로 하는 크기로 나누고, 목록에 완료 기준, 확인 방법, 통과 값을 기록합니다.
  • 하위 에이전트에 나눠 맡길 때는 넘길 정보와 의존성을 정하고, 요약으로 돌아온 결과는 근거를 확인합니다.

맡길 업무의 선정

모든 업무가 에이전트에 맡기기에 적합하지는 않으므로, 이 책은 맡길 업무를 네 가지 기준으로 선정합니다. 기준마다 맡기기 전에 확인할 질문이 하나씩 있습니다.

  • 검증 가능성: 완료 여부를 검사나 대조로 확인할 수 있는가
  • 자료 접근성: 판단에 필요한 자료를 에이전트가 읽을 수 있는가
  • 복구 가능성: 결과가 잘못되었을 때 이전 상태로 되돌릴 수 있는가
  • 협의와 승인 조건: 다른 조직과의 협의나 승인 없이 끝낼 수 있는가

결과를 확인할 수 없거나 되돌릴 수 없는 업무를 그대로 맡기면, 잘못된 결과를 받아들이거나 복구하기 어려울 수 있습니다. 표 6-1은 기준별 확인 질문과, 기준을 충족하지 못할 때의 조치입니다.

네 기준을 모두 충족하는 업무부터 맡깁니다. 일부 기준을 충족하지 않는 업무도 위임 대상에서 제외할 필요는 없고, 충족하지 못한 부분을 사람이 맡도록 업무를 나누면 됩니다. 맡기기로 한 업무를 어떤 크기로 나눌지는 다음 절에서 봅니다.

작업 단위 분할

선정한 업무도 범위가 크면 중간 상태를 추적하기 어렵고 완료를 검증하기도 어렵습니다. 그래서 업무를 작업 단위로 나눕니다. 이 책은 작업 단위를 한 세션 안에 끝내는 것을 목표로 하고 완료 여부를 확인할 수 있는 업무의 조각으로 정리합니다. 단위마다 작업, 완료 기준, 확인 방법, 통과 값을 목록 파일에 적고, 통과 값이 false인 첫 단위부터 하나씩 처리합니다.

통과 값은 단위가 끝났는지를 true 또는 false로 적는 칸입니다. 새로 등록한 미완료 단위는 false이고, 이미 완료하고 확인한 단위는 true입니다. 통과 값이 false인 첫 단위가 사람이 맡을 단위이면, 합의나 승인이 끝난 뒤에 이어 갑니다. Chapter 2와 Chapter 3의 경비 정산 예제에 사용한 작업 단위 목록(tasks.json)이 이 목록입니다.

업무를 작업 단위로 나눠 하나씩 처리하는 방식의 근거는 긴 작업을 여러 세션에 걸쳐 진행한 실험입니다. Anthropic의 장기 실행 에이전트 글은 여러 세션에 걸쳐 웹 애플리케이션을 개발하는 실험에서 관찰한 실패 양상 두 가지를 보고합니다.

  • 한 번에 전체 구현: 에이전트가 애플리케이션 전체를 한 번에 구현하려 함
    • 결과: 구현 도중 컨텍스트(Context)가 소진되어, 다음 세션은 반쯤 구현되고 기록되지 않은 기능에서 시작함
  • 이른 완료 판단: 일부 기능이 구현된 뒤 시작한 세션이 진행된 내용을 보고 프로젝트 전체가 완료되었다고 판단함
    • 결과: 남은 기능이 구현되지 않은 채 끝남

같은 글이 택한 방식은 기능 목록과 상태 기록을 두고 하나씩 진행하는 점진적 방식입니다. 첫 세션에서 요구 사항을 200개가 넘는 기능 목록으로 작성하고, 모든 기능을 "실패" 상태로 표시했습니다. 이후 세션은 한 번에 기능 하나만 작업했습니다. 글은 이 점진적 방식이 에이전트가 한 번에 너무 많은 작업을 시도하는 문제를 해결하는 데 결정적이었다고 설명합니다.

완료 여부를 확인하는 방법은 단위마다 다르므로, 이 책은 작업 단위를 담당과 확인 방법에 따라 세 종류로 나눕니다.

  • 합의가 필요한 단위: 다른 조직과 협의해야 끝나는 단위
    • 담당: 사람(승인자, Chapter 3에서 변경을 승인하는 사람)
    • 확인: 합의 결과를 결정 기록으로 제공
  • 검사로 확인하는 단위: 표 6-1의 네 기준을 모두 충족하는 기본형
    • 담당: 에이전트
    • 확인: 검사로 완료를 확인
  • 판단이 필요한 단위: 검사로 결과를 확인할 수 없어 사람이 판단하는 단위
    • 담당: 에이전트가 초안을 작성하고 승인자가 승인
    • 확인: 사람의 승인, 통과 값도 사람이 변경

합의가 필요한 단위는 협의와 승인 조건을, 판단이 필요한 단위는 검증 가능성을 검사로 채울 수 없는 경우를 사람에게 둔 것입니다. 사람의 승인도 확인의 한 방법이므로, 세 종류의 경계는 확인을 검사가 하는지 사람이 하는지에 있습니다.

그림 6-1은 왼쪽에 작업 단위 목록과 단위의 세 종류를, 오른쪽에 작업 단위 하나를 처리하는 순서를 둡니다. 단위 하나는 수행한 뒤 완료 기준을 확인하고 통과 값을 true로 변경하며, 완료 기준에 미달하면 같은 단위를 다시 수행합니다.

표 6-2는 그림 6-1의 구성 요소를 정리합니다.

목록의 단위를 하나씩 처리하는 순서는 그림 6-1이, 하네스(Harness)가 정한 수정 권한과 작업 단위 하나의 검증은 Chapter 3의 그림 3-1이 맡습니다. 같은 시험이 반복해 실패할 때의 중단 기준은 Chapter 7에서, 한 세션이 끝난 뒤 다음 세션이 어디서 시작하는지는 Chapter 8의 인계 메모에서 다룹니다.

여러 에이전트에 나눠 맡기기

작업 단위를 하나씩 처리하다 보면 테스트 실행, 많은 파일을 읽는 자료 조사, 긴 기록을 줄이는 로그 분석처럼 출력이 많은 작업이 주 대화의 컨텍스트 윈도(Context Window)를 채웁니다(Chapter 5). 작업 단위가 나뉘어 있으면, 그 가운데 일부를 다른 에이전트에 맡기고 결과의 요약만 받을 수 있습니다. 이 책은 작업 단위를 여러 에이전트에 배분하고 결과를 모으는 일을 오케스트레이션(Orchestration)이라고 부릅니다. 맡는 쪽은 Chapter 2에서 정의한 하위 에이전트(Subagent)이고, 이 장에서는 맡기는 쪽을 주 에이전트라고 부릅니다. 주 에이전트는 주 대화에서 사람과 일하는 에이전트이며, 경비 정산 예제에서는 Chapter 3의 구현 에이전트입니다.

하위 에이전트는 부모 대화를 물려받는 포크 방식을 빼면, 자기 컨텍스트 윈도에서 새 대화로 시작하고 주 대화의 기록을 보지 않습니다. 작업이 끝나면 최종 응답이 요약으로 주 에이전트에 돌아오므로, 주 대화의 컨텍스트는 하위 작업의 전체 기록 대신 요약만큼 늘어납니다. 그래서 위임할 때 필요한 정보가 자동으로 전달된다고 가정하지 않고 요청에 담으며, 돌아온 요약만으로 완료를 판단하지 않고 근거를 확인합니다.

나눠 맡기면 비용이 늘어날 수 있습니다. 비용 문서는 하위 에이전트의 요청도 사용량에 포함된다고 설명하고, Agent SDK(Chapter 1) 문서는 비용 상한이 하위 에이전트의 지출을 포함한다고 설명합니다.

버전 주석 (2026년 10월) Agent SDK 문서는 Claude Code v2.1.217 이상에서 비용 상한에 이르면 새 하위 에이전트를 만들 수 없다고 안내합니다.

여러 에이전트를 사용하는 기능에는 하위 에이전트 외에 에이전트 팀(Agent Team)도 있어, 이 책이 다루는 범위를 정해 둡니다. Claude Code 용어집은 하위 에이전트가 한 세션 안에서 일하고 맡긴 쪽에만 보고하는 반면, 에이전트 팀의 팀원은 각자 컨텍스트 윈도를 갖고 사용자가 팀원과 직접 대화할 수 있다고 설명합니다. 비용 문서는 에이전트 팀에서 토큰(Token) 사용량이 팀 크기에 거의 비례한다고 설명하고, 에이전트 팀은 기본으로 꺼져 있는 실험 기능이라고 안내합니다. 이 책은 하위 에이전트만 다룹니다.

그림 6-2는 위쪽에 주 에이전트가 하는 일을, 아래쪽에 하위 에이전트와 맡기는 작업의 예를, 맨 아래에 비용을 둡니다. 내려가는 화살표는 작업 단위와 필요한 정보이고, 올라가는 화살표는 최종 응답의 요약입니다.

표 6-3은 그림 6-2의 구성 요소를 정리합니다.

나눠 맡길 때 정할 것은 네 가지입니다. 비용 상한은 Chapter 9의 비용 관리에서, 완료 기준은 Chapter 7의 완료 기준에서 자세히 다룹니다.

  • 맡기는 방식: 순차로 맡길지, 병렬로 맡길지
    • 정할 것: 앞 단위의 결과를 사용하는 단위는 앞 결과를 넘겨 순차로 맡김. 병렬로 맡기려면 단위 사이의 의존성, 같은 파일 수정의 충돌, 실행 환경의 격리를 확인
  • 넘길 정보와 도구: 하위 에이전트가 작업에 사용할 정보와 기능
    • 정할 것: 필요한 정보를 요청에 담고, 맡긴 작업에 필요한 최소한의 도구만 지정(Chapter 2의 도구 노출 범위)
  • 결과 확인: 돌아온 요약을 받아들이는 기준
    • 정할 것: 요약만으로 판단하지 않고 검사 출력이나 바뀐 파일 같은 근거를 완료 기준과 대조
  • 비용 상한: 나눠 맡긴 작업까지 합친 전체 지출의 상한
    • 정할 것: 나눠 맡길 작업의 수와 함께 정함

예제: 변경 요청 사항의 작업 단위 나누기

앞의 세 절을 한 사례에 적용합니다. Chapter 4의 영향 검토를 거쳐 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)을 수용하기로 했다고 가정합니다. 변경 요청 사항은 재무팀이 정산 요청 화면에 프로젝트 코드 선택 항목을 추가해 달라고 요청한 내용이며, 이 변경을 구현하는 에이전트는 Chapter 3에서 설계했습니다.

먼저 표 6-1의 기준을 적용합니다.

  • 자료 접근성: 코드와 자료가 모두 저장소 안에 있어 충족
  • 복구 가능성: 작업 단위마다 commit하므로 Git 기록으로 이전 상태를 되돌릴 수 있어 충족(push를 사람이 하는 것은 원격 저장소 반영의 통제이며 복구 가능성과는 별개)
  • 협의와 승인 조건: 프로젝트 코드 조회 방식은 연동 규격이 없어 인사팀과의 합의가 필요하므로 승인자가 맡음
  • 검증 가능성: 통합 시나리오의 범위는 검사로 확인할 수 없는 판단이므로 에이전트가 작성하고 승인자가 승인. 나머지는 검사로 확인하는 단위로 에이전트가 맡음

표 6-4는 이 결과를 작업 단위 목록과 같은 순서와 문구로 보여 줍니다. 수용 시험과 검사 스크립트(check.py)는 Chapter 3에서 정의했고, 확인 방법의 tests는 check.py가 실행하는 단위 테스트(tests/ 폴더)를 가리킵니다. 작업 1은 합의를 마쳐 목록에서 이미 통과 값이 true이므로, 에이전트는 작업 2부터 시작합니다.

작업 5는 두 주체가 나누어 맡습니다. 완료 기준의 "시나리오 초안"은 에이전트가 작성하는 부분이고, 통과 값을 true로 변경하는 승인 완료는 승인자가 맡습니다. 에이전트가 초안을 작성해도 승인 전에는 통과 값이 false로 남습니다.

작업 2와 작업 3의 시험(수용 시험 4, 5와 단위 테스트)은 지금의 실습 자료에서 구현 전에도 통과합니다. 실습 1의 기준 상태 기록에서 단위 테스트는 실패 0건이고, 수용 시험은 넷째와 다섯째만 통과합니다(부록 실습의 실습 1). 두 시험은 새 기능이 생겼는지가 아니라 변경이 기존 동작을 깨지 않았는지를 확인하기 때문입니다. 그래서 두 단위는 확인 방법만으로는 완료를 증명하지 못하고, 통과 값이 false인 것은 시험이 실패해서가 아니라 단위를 아직 수행하지 않았기 때문입니다. 추가한 항목이 실제로 쓰이는지는 작업 4의 수용 시험 1, 2, 3이 확인합니다. 구현 전에는 실패하고 구현 뒤에 통과하는 확인으로 변경하는 일은 Chapter 3의 예제 정비에서 함께 다룹니다.

작업 단위 목록은 에이전트가 읽고 통과 값을 갱신할 수 있는 파일로 저장합니다. 장기 실행 에이전트 글의 실험은 기능 목록을 JSON 형식(항목 이름과 값을 정해진 형식으로 적는 파일 형식)으로 저장하고, 에이전트가 상태 항목만 수정하도록 지시했습니다. 글은 모델이 Markdown 파일보다 JSON 파일을 부적절하게 변경하거나 덮어쓰는 일이 적었다고 설명합니다. 파일 형식은 변경을 막는 장치가 아니므로, 목록에서 수정할 수 있는 항목과 갱신 권한을 정하고 변경 차이를 검토합니다. 다음은 변경 요청 사항 목록의 일부(작업 2, 3)입니다.

[
  {
    "id": "작업 2",
    "작업": "데이터 모델에 프로젝트 코드 항목 추가",
    "완료 기준": "정산 요청 데이터에 항목 추가, 기존 데이터 유지",
    "확인 방법": "python check.py의 수용 시험 4, 5 통과",
    "통과": false
  },
  {
    "id": "작업 3",
    "작업": "기존 단위 테스트 갱신",
    "완료 기준": "변경된 데이터 모델의 테스트 반영",
    "확인 방법": "python check.py의 tests 실패 0건",
    "통과": false
  }
]

다음은 나눠 맡길지의 판단입니다. 작업 2, 3, 4는 서로 이어집니다. 작업 3은 작업 2가 변경한 데이터 모델에 맞춰 테스트를 수정하고, 작업 4는 그 데이터 모델의 항목을 화면에서 선택하게 합니다. 앞 결과를 넘기면 순차로 위임할 수도 있지만, 이 사례에서는 세 단위가 같은 파일을 이어서 수정하므로 구현 에이전트가 통과 값이 false인 첫 단위부터 차례로 수행하게 했습니다. 이는 이 사례의 운영 선택입니다.

하위 에이전트는 Chapter 3의 검토 하위 에이전트처럼, 변경 내용을 수용 기준과 읽기 전용으로 대조하는 데 사용합니다(표 3-3). 구현 에이전트는 작업 단위를 마칠 때마다 그 단위의 변경을 commit하며, commit은 사람이 확인한 뒤 실행됩니다.

작업 단위로 나누는 데에도 비용이 있습니다. 단위마다 완료 기준과 확인 방법을 정하는 수고가 들고, 단위가 너무 작으면 목록을 관리하는 일이 늘어납니다. 그 대신 한 단위가 실패하면 실패한 단위만 다시 작업하면 되고, 어느 부분에서 실패했는지 목록으로 확인할 수 있습니다.

작업 단위 목록으로 구현을 진행하는 실습은 부록 실습의 실습 5에 있습니다.

실패와 막는 장치

변경 요청 사항을 작업 단위로 나누지 않거나 담당을 잘못 정하면 다음 실패가 생길 수 있습니다. 표의 작업 번호는 표 6-4의 번호입니다.

확인 방법

작업 단위가 끝났는지는 에이전트의 보고가 아니라 파일과 검사 출력으로 확인합니다. 작업 단위 하나의 검증 방법은 Chapter 3의 확인 방법과 같고, 여기서는 목록 쪽 확인만 다룹니다. 명령은 실습 폴더(examples/expense-app/)에서 실행합니다.

통과 값의 변경은 단위를 마친 뒤 commit하기 전에 git diff HEAD -- tasks.json으로 봅니다. 이 명령은 마지막 commit과 지금 파일을 비교하고, 스테이징한 변경만 보려면 git diff --cached를, 새로 만든 파일은 git status를 봅니다. commit 기록은 단위별 진행을 보여 줄 뿐이므로, commit 개수만으로 완료를 판단하지 않습니다. 표 6-6은 확인할 항목입니다.

  3. 세션이 중간에 끝나도 어느 단위까지 끝났는지 파일로 알 수 있습니까?
