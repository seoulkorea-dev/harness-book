Chapter 1 모델, 프롬프트, 컨텍스트, 하네스의 관계

대규모 언어 모델(Large Language Model, LLM)은 입력된 정보를 바탕으로 결과를 생성합니다. 결과의 품질을 정하는 것은 모델 하나가 아니라, 모델에 주는 정보와 모델이 일하는 환경 전체입니다. 그래서 같은 모델을 사용해도 지시문, 제공 정보, 작업 환경이 다르면 결과가 달라집니다. 따라서 AI 에이전트(AI Agent) 프로젝트를 관리하는 사람은 모델 선택보다 모델 바깥의 설계를 먼저 점검해야 합니다. 이 장에서는 모델, 프롬프트, 컨텍스트(Context), 하네스(Harness)의 정의와 서로의 관계를 살펴봅니다.

  • 모델 바깥의 설계는 프롬프트, 컨텍스트, 하네스의 세 층으로 나뉩니다.
  • 프롬프트는 한 번 작성하는 지시문이고, 컨텍스트는 단계마다 다시 선별하는 정보 전체입니다.
  • 하네스는 역할, 도구, 권한, 기록, 검증으로 에이전트의 작업 환경을 정하며, 관리자가 책임질 영역입니다.

모델과 세 설계 층

AI 에이전트의 결과는 모델과 세 설계 층이 함께 정합니다. 세 설계 층은 모델 바깥의 프롬프트, 컨텍스트, 하네스입니다. Anthropic은 에이전트를 모델이 반복 루프 안에서 스스로 도구를 사용하는 시스템으로 정의합니다. 모델은 입력된 토큰(Token)을 바탕으로 다음 토큰을 예측해 결과를 생성합니다. 토큰은 모델이 글을 처리하는 최소 단위입니다.

프롬프트는 모델에 주는 지시문입니다. 컨텍스트는 모델이 응답을 생성할 때 입력되는 정보 전체이며, 프롬프트는 그 일부입니다. 이 책은 하네스를 모델 바깥에서 에이전트가 일하는 환경을 이루는 장치 전체로 정의합니다. 그림 1-1은 세 설계 층의 포함 관계와 모델의 입력을, 표 1-1은 층별 정의와 설계 질문을 보여 줍니다.

모델은 공급사가 만듭니다. 세 설계 층은 모델을 사용하는 조직이 설계합니다. 그래서 같은 모델을 사용하는 두 조직이 서로 다른 결과를 얻습니다.

프롬프트 엔지니어링과 컨텍스트 엔지니어링

프롬프트 엔지니어링(Prompt Engineering)은 원하는 결과를 얻도록 지시문을 작성하고 구성하는 방법입니다. 컨텍스트 엔지니어링(Context Engineering)은 모델이 응답을 생성하는 동안 필요한 정보를 선별하고 유지하는 전략입니다. 두 정의는 Anthropic이 2025년 9월 공개한 글(Rajasekaran 외, 2025)을 따릅니다. 이 글에서 Anthropic은 컨텍스트 엔지니어링을 프롬프트 엔지니어링이 발전한 단계로 설명합니다. 두 방법은 세 가지 점에서 다릅니다.

  • 대상: 프롬프트 엔지니어링은 지시문을 다룹니다. 컨텍스트 엔지니어링은 시스템 지시, 도구 설명, 외부 자료, 대화 이력을 포함한 입력 전체를 다룹니다.
  • 시점: 프롬프트 작성은 한 번으로 끝나는 작업입니다. 컨텍스트는 모델에 무엇을 넘길지 정할 때마다 다시 선별합니다.
  • 제약: 모델이 한 번에 처리할 수 있는 토큰의 범위를 컨텍스트 윈도(Context Window)라고 합니다. Anthropic은 컨텍스트의 토큰이 늘수록 모델이 정보를 정확히 기억해 내는 능력이 떨어진다고 설명합니다. 그래서 많은 정보를 제공하는 것보다 필요한 정보를 선별하는 것이 중요합니다.

관리 관점에서 두 층은 관리 대상이 다릅니다. 프롬프트는 요청 한 건의 지시문입니다. 컨텍스트는 규칙 문서, 업무 자료, 대화 이력처럼 조직이 관리하는 자료를 포함합니다.

하네스 엔지니어링

이 책은 하네스 엔지니어링(Harness Engineering)을 에이전트가 신뢰할 수 있는 결과를 내도록 모델 바깥의 작업 환경을 설계하는 일로 정의합니다. 하네스의 구성 요소는 역할, 도구, 권한, 기록, 검증의 다섯 가지입니다. 구성 요소별 설계는 Chapter 4에서 다룹니다.

OpenAI는 2026년 2월 이 용어를 제목으로 한 글(Lopopolo, 2026)에서, 사람이 코드를 직접 작성하지 않는 개발 실험을 소개했습니다. OpenAI 발표에 따르면 이 팀은 5개월 동안 약 100만 줄의 코드와 약 1,500개의 풀 리퀘스트(Pull Request)를 Codex로 생성했습니다. 풀 리퀘스트는 코드 변경을 저장소에 반영하기 전에 검토를 요청하는 단위입니다. 이 실험에서 OpenAI가 밝힌 내용은 네 가지입니다.

  • OpenAI는 이 프로젝트에서 엔지니어가 코드를 작성하는 대신 환경을 설계하고, 의도를 명시하고, 피드백 루프를 구축하는 일을 맡았다고 밝혔습니다.
  • OpenAI는 초기 진행이 느렸던 원인을 Codex의 능력 부족이 아니라 충분히 정의되지 않은 환경에서 찾았습니다.
  • 작업이 실패하면 어떤 능력이 누락되었는지 묻고, 그 능력을 에이전트가 읽을 수 있고 검사로 강제되는 형태로 저장소에 추가했습니다.
  • 에이전트가 실행 중에 읽을 수 없는 지식은 에이전트에게 없는 지식으로 보고, 채팅이나 사람의 기억에 있던 결정을 저장소 문서로 옮겼습니다.

사람의 역할도 남았습니다. 사람은 작업의 우선순위를 정하고, 사용자 의견을 수용 기준으로 정리하고, 결과를 검증했습니다. 수용 기준은 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 이 사례에서 OpenAI가 개선한 대상은 모델이 아니라 저장소 문서, 검사 규칙, 검증 절차 같은 작업 환경이었습니다.

같은 요청, 세 층의 개선

같은 모델에 같은 업무를 맡겨도, 어느 층까지 설계했는지에 따라 결과가 달라집니다. 아래 예제는 가상 프로젝트인 경비 정산 시스템 개편의 주간 보고서 초안 작성을 프롬프트, 컨텍스트, 하네스의 순서로 개선합니다.

프롬프트만 설계한 경우

첫 단계는 요청 문장만 다듬는 것입니다.

이번 주 프로젝트 주간 보고서 초안을 작성해 줘.
진행 현황, 이슈, 다음 주 계획의 세 절로 나눠 줘.
진행 현황은 작업명, 담당자, 진행률 열이 있는 표로 정리해 줘.

예상 결과: 절 구성과 표 형식은 요청과 일치합니다. 작업명과 진행률은 실제 프로젝트와 무관한 예시 값으로 채워집니다. 모델은 이번 주에 실제로 진행된 작업을 알지 못하기 때문입니다.

컨텍스트를 설계한 경우

두 번째 단계는 보고서에 필요한 자료를 함께 제공하는 것입니다.

아래 자료로 이번 주 프로젝트 주간 보고서 초안을 작성해 줘.
절 구성과 표 형식은 지난주 보고서를 따라 줘.
자료에 없는 내용은 작성하지 말고 "확인 필요"로 표시해 줘.

<지난주 보고서>
(지난주 보고서 전문)
</지난주 보고서>
<이번 주 완료 작업>
(작업 관리 도구에서 내려받은 목록)
</이번 주 완료 작업>
<미해결 이슈>
(이슈 관리 도구에서 내려받은 목록)
</미해결 이슈>

예상 결과: 실제 작업과 이슈가 보고서에 반영되고, 형식은 지난주 보고서와 일치합니다. 자료가 없는 항목은 "확인 필요"로 표시됩니다.

이 단계에도 두 가지 한계가 남습니다. 매주 사람이 자료를 모아 붙여 넣어야 합니다. 보고서의 수치가 원본 자료와 일치하는지 확인하는 절차도 없습니다.

하네스를 설계한 경우

세 번째 단계는 에이전트가 일하는 환경을 정하는 것입니다. 표 1-2는 다섯 구성 요소를 이 예제에 적용한 설정입니다.

예상 결과: 사람이 자료를 모으지 않아도 실제 작업이 반영된 초안이 생성됩니다. 수치가 원본과 다르면 발송 전 검증 단계에서 드러납니다. PM은 초안 검토와 발송 승인에만 시간을 사용합니다.

세 단계 모두 같은 모델을 사용합니다. 결과의 차이는 모델이 아니라 어느 층까지 설계했는지에서 나옵니다.

소프트웨어 엔지니어링과의 접점

하네스의 구성 요소는 소프트웨어 엔지니어링의 기존 활동과 대응합니다. 소프트웨어 엔지니어링은 요구 사항 정의, 설계, 개발, 테스트, 배포, 운영으로 이어지는 개발의 전 과정을 다루는 분야입니다. 이 책은 이 분야를 하네스를 이해하는 데 필요한 범위에서만 다룹니다. 표 1-3은 활동별로 대응하는 하네스 설계를 보여 줍니다.

요구 사항을 명확히 정의하는 능력은 에이전트에게 작업을 지시하는 능력으로 이어집니다. 테스트 기준을 정하는 능력은 에이전트의 결과를 검증하는 능력으로 이어집니다.

관리자가 책임질 영역

모델은 공급사가 개선하지만, 하네스는 프로젝트를 운영하는 조직이 설계합니다. 따라서 에이전트 프로젝트의 관리자가 책임질 영역은 모델 바깥의 세 층입니다.

문제가 생기면 관리자는 먼저 원인이 어느 층에 있는지 분류합니다. 표 1-4는 대표적인 증상과 원인이 있는 층, 점검할 항목을 대응시킨 것입니다.

이 책의 작가는 앞선 책 「생성형 AI, 묻고 확인하고 활용하기」를 AI 에이전트와 함께 만들며 73차례 검수를 거쳤습니다. 초기에는 어휘, 조사, 표 번호처럼 같은 종류의 실수를 사람이 매번 찾았습니다. 큰 결정을 집필 중에 여러 번 뒤집는 일도 있었습니다. 해결 방법은 모델 교체가 아니라 작업 환경의 보완이었습니다.

  • 반복된 실수는 자동 검사 규칙으로 만들었습니다.
  • 큰 결정은 번호를 매겨 기록하고, 결정을 변경할 때는 이전 결정을 남겼습니다.
  • 원고 작성과 검수를 서로 다른 에이전트에게 나눠 맡겼습니다.

이후 사람은 판단이 필요한 항목만 검토하는 구조로 작업을 정리했습니다.

모델 성능이 향상되면 하네스가 필요 없다는 의견도 있습니다. 모델 성능의 향상은 한 번의 응답 품질을 높입니다. 그러나 어떤 자료에 접근할지, 어떤 작업을 사람이 승인할지, 무엇을 기록할지는 조직이 정할 일입니다. Anthropic도 모델이 발전해도 컨텍스트를 한정된 자원으로 다루는 일은 계속 중요하다고 밝혔습니다.

같은 모델로 더 나은 결과를 얻는 방법은 모델 바깥의 설계에 있습니다.
