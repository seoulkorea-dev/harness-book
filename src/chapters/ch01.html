Chapter 1 하네스란 무엇인가

에이전트는 모델과 하네스로 이루어집니다.

인공지능 모델(이하 모델)이 도구를 사용해 목표를 이룰 때까지 스스로 일하는 시스템을 에이전트(Agent)라고 합니다. 하네스(Harness)는 모델이 에이전트로 일할 수 있게 하는 모델 바깥의 실행 체계입니다. 이 체계가 필요한 까닭은 모델이 글을 읽고 다음에 할 일을 판단해 글로 답할 뿐, 파일을 열거나 명령을 직접 실행하지 못하기 때문입니다. 예를 들어 "정산 화면 오류를 수정해 줘"라는 요청에서 어느 파일을 살피고 무엇을 수정할지는 모델이 판단합니다. 파일을 열고, 모델이 만든 수정 내용을 저장하고, 테스트를 실행해 결과를 모델에 전달하는 일은 하네스가 맡습니다. 팀이 금지한 변경을 막고, 정한 동작 앞에서 사람의 확인을 받는 일도 하네스가 합니다.

그래서 하네스를 설계하는 일, 곧 하네스 엔지니어링(Harness Engineering)의 핵심은 두 가지입니다. 하나는 도구, 규칙 문서, 기록, 검사처럼 모델이 일하는 데 사용하는 실행 환경을 설계하는 일이고, 다른 하나는 정한 범위를 벗어나는 예외 상황을 통제하는 일입니다. 이 이름은 2026년 2월 개발자 Mitchell Hashimoto의 글과, OpenAI가 코딩 에이전트 Codex로 제품을 만든 경험을 정리한 글에 연이어 쓰였습니다. 이 장은 모델이 혼자 할 수 없는 일에서 출발해 한 요청을 처리하는 과정, 이 책의 에이전트와 하네스의 정의, 에이전트 루프를 차례로 살펴봅니다. 이어서 다른 자료의 같은 명칭이 이 정의의 어디에 해당하는지, 하네스 엔지니어링과 프롬프트(Prompt), 컨텍스트(Context)의 관계, 소프트웨어 엔지니어링과의 접점을 정리하고, 결과가 기대와 다를 때 원인을 찾는 순서와 확인 방법을 다룹니다.

  • 모델은 판단하고 응답을 생성하지만, 명령을 직접 실행하지 않고, 요청 사이의 대화를 기억하지 않으며, 실행 결과를 직접 받지 못합니다.
  • 에이전트는 모델과 하네스로 이루어집니다. 하네스는 모델 바깥의 실행 체계로, 제품이 제공하는 실행 장치와 사용자와 팀이 정하는 설정으로 나뉩니다.
  • 설정에서 정하는 하네스의 다섯 구성 요소는 역할, 도구, 권한, 기록, 검증입니다.
  • 결과가 기대와 다르면 모델을 교체하기 전에 하네스의 설정을 먼저 점검하고, 증상에 따라 프롬프트와 컨텍스트도 함께 봅니다.

모델만으로 할 수 없는 일

하네스가 맡는 일을 이해하려면 먼저 모델이 무엇을 받고 무엇을 내놓는지 알아야 합니다. 모델은 글을 토큰(Token) 단위로 처리합니다. 토큰은 모델이 텍스트를 나누어 처리하는 단위입니다. 이 책은 대규모 언어 모델(Large Language Model, LLM)을 입력된 토큰을 바탕으로 다음 토큰을 예측해 결과를 생성하는 모델로 정의합니다. 모델이 응답을 생성할 때 입력되는 정보 전체를 컨텍스트라고 하고, 이 책은 모델이 한 번에 처리할 수 있는 토큰의 범위를 컨텍스트 윈도(Context Window)라고 부릅니다. 모델은 입력된 컨텍스트를 받아 출력을 만듭니다. 그래서 어떤 파일을 수정해 달라고 요청해도, 그 파일의 내용이 입력에 들어 있지 않으면 모델은 파일을 직접 열어 읽지 못합니다.

모델을 쓰려면 모델을 호출하는 프로그램이 있어야 합니다. 채팅 화면에 질문을 입력할 때도 화면 뒤의 프로그램이 질문을 모델에 보내고, 응답을 받아 화면에 보여 줍니다. Claude의 API(프로그램이 모델을 호출하는 방식) 문서는 모델과 모델을 호출하는 프로그램의 역할을 나눠 설명합니다.

프로그램은 모델에 도구를 제공할 수 있습니다. 도구는 파일 읽기, 명령 실행, 검색처럼 모델 바깥에서 실행되는 기능입니다. 도구 호출(Tool Call)은 모델이 특정 도구를 정해진 입력으로 실행해 달라고 요청하는 것입니다. 프로그램은 도구를 실행하고 결과를 모델에 돌려줍니다. 실행이 실패하면 실패 표시와 오류 내용을 결과로 돌려줄 수 있습니다.

API 문서의 설명을 바탕으로 이 책은 모델이 혼자 할 수 없는 일을 세 가지로 정리합니다.

  • 실행: 모델은 명령을 직접 실행하지 않습니다. 모델은 실행할 도구와 입력을 요청하고, 실제 실행은 모델을 호출한 프로그램이 맡습니다(웹 검색처럼 Anthropic 서버가 실행하는 도구도 있습니다).
  • 기억: 모델은 요청 사이의 대화를 기억하지 않습니다. Claude의 메시지 API는 상태를 저장하지 않아, 프로그램이 요청마다 전체 대화를 보내야 합니다. 채팅에서 앞의 대화를 기억하는 것처럼 보이는 것은 프로그램이 새 요청마다 이전 대화를 다시 담아 보내기 때문입니다. API 문서의 도구 사용 절차에서도 프로그램은 원래 대화, 모델의 응답, 도구 결과를 모두 다시 담아 보냅니다. 대화가 길어져 컨텍스트 윈도의 한도에 가까워지면 프로그램은 이전 대화를 줄입니다. 예를 들어 Anthropic의 코딩 에이전트 Claude Code는 오래된 도구 출력을 먼저 지우고, 필요하면 이전 대화를 요약합니다.
  • 결과 받기: 모델은 도구 실행 결과를 직접 받지 못합니다. 프로그램이 결과를 돌려주어야 모델이 그 결과를 읽고 다음 판단을 합니다.

앞의 세 가지가 모델이 혼자 할 수 없는 일이라면, 업무를 끝까지 맡길 때 모델 바깥에서 정해야 할 일도 세 가지 있습니다. 바로 작업 진행, 실행 범위, 검증입니다. 모델은 요청 하나에 응답 하나를 만들고 멈추므로, 작업이 끝날 때까지 판단과 도구 실행을 반복하게 하는 장치가 있어야 합니다. 모델이 요청한 실행을 어디까지 허용할지도 정해야 합니다. 결과가 기준에 맞는지 확인하는 일(검증)은 작업한 모델의 완료 보고만으로는 충분하지 않고, 모델 바깥에 정해 둔 검사가 판정해야 합니다.

이렇게 모델이 혼자 할 수 없는 일을 맡고, 그 실행이 정한 범위를 벗어나지 않게 통제하는 모델 바깥의 실행 체계를 이 책은 하네스라고 부릅니다. 표 1-1은 모델만 호출할 때와 하네스 안에서 일할 때를 여섯 항목으로 비교합니다. 표의 자율 수행 영역은 모델만 호출했을 때 모델이 혼자 하는 범위이고, 하네스 보완 영역은 하네스가 그 한계를 메우는 방식입니다. 규칙 문서는 작업 규칙을 적어 프로젝트에 두는 파일입니다. 실행 범위를 제한하는 장치 가운데 권한 규칙(Permission Rule)은 뒤의 에이전트 루프와 종료 조건 절에서 다룹니다. 격리 환경은 에이전트가 팀이 정한 폴더 밖의 파일이나 네트워크에 닿지 못하게 막은 실행 공간입니다.

한 요청에서 모델과 하네스가 하는 일

하네스가 어떤 순서로 일하는지는 코딩 에이전트에서 분명하게 드러납니다. 코딩 에이전트는 저장소(코드와 문서를 변경 이력과 함께 보관하는 곳)의 코드를 읽고 수정하며 테스트를 실행하는 에이전트 제품입니다. Anthropic의 Claude Code와 OpenAI의 Codex가 그 예입니다. 코딩 에이전트에 "정산 화면 오류를 수정해 줘"라고 요청했을 때의 처리 과정을 이 책은 다음 순서로 정리합니다.

  1. 하네스가 요청에 시스템 프롬프트(제품이 미리 포함하는 지시), 규칙 문서, 도구 정의(사용할 수 있는 도구의 이름, 설명, 입력 형식)를 더해 모델에 넘깁니다.
  2. 모델은 오류와 관련된 파일을 찾으려고 검색과 파일 읽기 도구를 요청합니다. 하네스는 그 도구를 실행하고 결과를 돌려줍니다.
  3. 모델은 원인을 판단하고, 수정할 내용을 만들어 파일 수정 도구로 요청합니다. 하네스는 그 수정이 허용된 범위인지 확인하고, 사람의 확인이 필요한 동작이면 승인을 받은 뒤 파일에 적용합니다.
  4. 모델은 테스트 실행을 요청합니다. 하네스는 테스트 실행도 같은 방식으로 확인한 뒤 실행하고 출력을 돌려줍니다. 테스트가 실패하면 모델은 출력을 읽고 2~4번 과정을 반복합니다.
  5. 모델이 일을 마쳤다고 응답하면, 팀이 정해 둔 완료 기준(작업이 끝났다고 판정하는 조건, 예: 테스트 전체 통과)이 있을 때 하네스가 그 기준을 확인하는 검사를 실행합니다. 통과하면 결과를 사람에게 전달하고, 미달이면 모델이 작업을 이어 갑니다. 완료 기준이 없으면 모델의 응답이 그대로 결과가 됩니다.

이 과정에서 수정 코드를 작성하는 것은 모델이고, 하네스는 모델이 요청한 동작을 실행하고 결과를 전달합니다. 하네스가 모든 요청을 실행하는 것은 아닙니다. 비밀 값을 담은 환경 변수 파일(.env)을 읽거나, 작업 폴더 밖에 파일을 쓰거나, 원격 저장소에 변경을 올리는(git push) 요청이 팀이 금지한 동작에 해당하면, 하네스는 실행하지 않고 거부합니다. 팀이 사람의 확인을 받도록 정한 동작은 실행 전에 멈추고 승인을 기다립니다. 어떤 규칙으로 정하고 그 규칙이 어디까지 막는지는 뒤의 에이전트 루프와 종료 조건 절에서 다룹니다.

같은 모델도 도구를 연결하지 않은 호출에서는 답변만 하고, 코딩 에이전트 안에서는 파일 수정과 테스트까지 수행합니다. 이 차이는 주로 하네스가 도구를 연결하고 실행하는 데서 생깁니다.

이 책의 에이전트와 하네스

앞의 처리 과정을 바탕으로 장 첫머리에서 사용한 두 용어의 범위를 정확히 정합니다. 이 책에서 에이전트는 인공지능 모델이 루프(Loop) 안에서 도구를 사용해 다음 행동을 스스로 정하고, 결과를 확인하며, 목표를 이룰 때까지 이 과정을 반복하는 시스템입니다. 루프는 앞에서 본 판단, 도구 실행, 결과 확인의 반복을 말합니다. 에이전트는 '모델'과 '하네스'로 이루어집니다. 하네스는 모델이 에이전트로 일할 수 있게 하는 모델 바깥의 실행 체계 전체를 가리킵니다.

실제 제품의 문서에서도 같은 구조를 볼 수 있습니다. Claude Code 용어집은 하네스를 언어 모델을 코딩 에이전트로 만드는 도구, 컨텍스트 관리, 명령을 실행하는 공간을 모두 합친 것으로 설명하고, Claude Code가 하네스이며 모델 Claude는 그 안에 있다고 표현합니다. 이 책은 모델을 하네스 바깥에 두므로, 이 책의 말로 옮기면 Claude Code가 하네스를 제공하고, 모델 Claude는 하네스가 넘긴 입력으로 판단합니다.

모델 바깥의 실행 체계는 누가 정하는지에 따라 '실행 장치'와 '설정'의 두 층으로 나뉩니다.

  • 실행 장치(제품이 제공): 루프 실행, 도구 제공, 컨텍스트 관리, 권한 확인, 세션 기록처럼 에이전트가 움직이는 데 필요한 기본 기능입니다. 모델의 API로 루프를 직접 작성해 하네스를 만들면 이 층도 팀이 정합니다. 세션은 에이전트와 한 번 대화를 시작해 끝낼 때까지를 말하고, 세션 기록은 그 대화를 저장해 나중에 이어 갈 수 있게 합니다.
  • 설정(사용자와 팀이 정함): 규칙 문서(Claude Code에서는 CLAUDE.md, Codex에서는 AGENTS.md), 권한 설정, 자동 검사, 역할 분담처럼 맡길 업무에 맞춰 정하는 값입니다.

에이전트는 설정이 없어도 제품의 기본값으로 동작합니다. 업무에 맞게 설정을 정하면 그 업무에 맞는 에이전트가 됩니다. 이 책은 설정에서 정하는 항목을 하네스의 다섯 구성 요소라고 부릅니다.

  • 역할: 에이전트가 할 작업과 사람이 할 작업의 경계입니다. 주로 규칙 문서에 적습니다.
  • 도구: 맡길 업무에 연결할 도구입니다. 도구를 연결하고 실행하는 방식은 실행 장치가 정하고, 어떤 도구를 쓸지는 설정이 정합니다.
  • 권한: 도구로 할 수 있는 동작의 범위입니다. 실행 장치의 권한 확인이 이 범위를 적용합니다.
  • 기록: 무엇을 왜 정했는지 남긴 결정 기록과, 작업이 어디까지 진행되었는지 남긴 진행 기록입니다. 실행 장치의 세션 기록은 대화를 저장하고 재개하는 기능이어서, 설정의 기록과 대상이 다릅니다.
  • 검증: 결과를 받아들이기 전에 확인하는 방법과 기준입니다. 자동 검사가 대표적입니다.

다섯 구성 요소가 루프의 어느 단계에서 작동하는지는 뒤의 에이전트 루프와 종료 조건 절에서 보고, 구성 요소별 설계는 Chapter 2에서 다룹니다.

하네스가 실행하는 도구는 모델과 하네스 바깥의 '외부 실행 환경'에 작용합니다. 외부 실행 환경은 파일 시스템, 데이터베이스, 네트워크, 소프트웨어, 사용자, 기타 외부 서비스처럼 도구가 읽거나 변경하는 대상 전체입니다. 도구는 제품에 들어 있는 기본 도구와, 외부 도구를 연결하는 표준 방식인 MCP(Model Context Protocol)로 연결한 도구로 나뉩니다(Chapter 2).

정리하면 그림 1-1처럼 에이전트는 모델과 하네스로 이루어지고, 하네스가 도구로 외부 실행 환경에 작용합니다. 하네스가 먼저 입력과 컨텍스트를 모델에 넘기면, 모델은 그것을 바탕으로 응답이나 도구 호출을 하네스에 돌려줍니다.

표 1-2는 그림 1-1의 구성 요소와 구성 요소 사이의 화살표를 주요 역할과 기능적 제약으로 나누어 설명합니다.

에이전트 루프와 종료 조건

앞에서 정한 하네스가 실제로 움직이는 순서가 에이전트 루프입니다. 처음에 본 오류 수정 요청에서 2~4번 과정은 이 루프의 판단과 응답, 권한 확인, 도구 실행을 되풀이한 것입니다. Claude Code의 Agent SDK(Claude Code의 에이전트 루프를 프로그램에서 실행하는 개발 도구) 문서가 설명하는 실행 루프를 이 책은 다섯 단계로 정리합니다.

  • 컨텍스트 구성: 하네스가 요청과 함께 시스템 프롬프트, 도구 정의, 대화 이력을 모아 모델에 넘깁니다.
  • 판단과 응답: 모델이 현재 상태를 판단해 텍스트로 답하거나 도구 호출을 요청합니다.
  • 권한 확인: 도구 호출 요청이 있으면, 하네스가 실행 전에 권한 규칙에 따라 실행할지, 사람에게 확인을 요청할지, 거부할지 판단합니다.
  • 도구 실행: 하네스가 요청된 도구를 실행하고 결과를 대화 이력에 추가한 뒤 컨텍스트 구성부터 반복합니다. Agent SDK 문서는 이 왕복 한 번을 턴이라고 부릅니다.
  • 최종 응답: 모델이 도구 호출 없이 응답하면 Agent SDK의 루프가 끝나고, 결과 메시지에 최종 응답과 토큰 사용량, 비용, 세션 ID가 담깁니다.

그림 1-2는 다섯 단계와 그 사이의 분기를 보여 줍니다. 이 책은 그림에서 최종 응답 앞에 완료 기준 확인을 하나 더 둡니다. 모델이 도구 호출 없이 응답하면 일을 끝냈다고 판단한 것이지만, 그 판단이 맞는지는 따로 확인해야 하기 때문입니다.

Claude Code에서는 훅(Hook, 정해진 시점에 자동으로 실행되는 명령)으로 이 확인을 추가합니다. 모델이 응답을 마치려 할 때 실행되는 Stop 훅이 완료 기준을 검사하고, 미달이면 종료를 막아 모델이 작업을 이어 가게 합니다. Stop 훅이 매번 종료를 막으면 같은 작업이 계속 되풀이됩니다. 그래서 훅에는 이미 한 번 막은 뒤인지 확인하고 다시 막을지 정하는 조건을 함께 둡니다. Claude Code도 Stop 훅이 연이어 여러 번 종료를 막으면 다음 차단을 무시하고 끝냅니다. 훅이 실행되지 않거나 실패하면 종료를 막지 못하므로, 훅이 실제로 불렸는지도 확인해야 합니다. 확인하는 방법은 Chapter 2의 설정과 결과의 확인 방법에서 다룹니다.

루프 안의 확인에 더해, 루프가 끝난 뒤에는 CI(저장소에 변경이 올라올 때 자동으로 검사를 실행하는 장치)나 사람의 검토가 한 번 더 확인합니다. 완료 기준은 팀이 설정의 검증에서 정합니다(Chapter 7의 완료 기준).

권한 확인 단계는 두 가지 설정으로 작동합니다. 권한 규칙은 도구 호출을 허용(allow), 확인 요청(ask), 금지(deny)로 나눠 정한 규칙입니다. 권한 모드(Permission Mode)는 도구 호출을 승인하는 방식을 정하는 설정으로, 권한 규칙에 정해지지 않은 호출을 사람에게 물을지, 자동으로 승인할지, 자동으로 거부할지가 모드에 따라 달라집니다. Claude Code에서 금지 규칙에 맞은 호출은 어느 권한 모드에서도 거부됩니다.

되돌리기 어려운 동작에 확인 요청 규칙을 걸면, 그 자리가 사람이 개입하는 승인 지점이 됩니다. 이 책은 확인 요청을 되돌리기 어려운 동작에 두기를 권합니다. 확인 요청이 지나치게 잦으면 사람이 내용을 보지 않고 승인할 수 있기 때문입니다(Chapter 9의 승인).

Agent SDK 문서에 따르면 거부된 도구 호출은 실행되지 않고, 모델은 거부 메시지를 결과로 받습니다. 모델은 대개 다른 방법을 찾거나, 진행할 수 없다고 보고합니다. 금지 규칙은 규칙이 알아보는 호출만 거부합니다. 예를 들어 Claude Code에서 .env 파일 읽기를 금지하면 내장 파일 도구와 cat, sed 같은 셸의 파일 명령은 거부되지만, 파일 이름을 적지 않고 읽는 명령(grep -r)이나 스크립트가 파일을 직접 여는 실행은 막지 못합니다. 셸 명령에 거는 규칙도 명령 문장을 보고 판단하므로, git push를 금지해도 git -C . push처럼 다르게 작성한 명령은 막지 못합니다. 이런 실행까지 막는 격리 환경은 Chapter 9의 격리에서 다룹니다.

표 1-3은 루프의 단계별로 작동하는 구성 요소를 보여 줍니다.

실행 장치의 세션 기록은 표 1-3의 어느 한 단계에 속하지 않습니다. Claude Code는 작업하는 동안 메시지, 도구 사용, 결과를 하나씩 로컬 파일에 저장합니다. 그래서 루프가 중간에 끝나도 세션 ID로 그 대화를 이어 갈 수 있습니다.

루프를 어떻게 멈출지도 정해야 합니다. 사람이 지켜보며 언제든 멈출 수 있는 대화형 사용과 달리, 프로그램으로 실행하는 루프는 따로 멈추는 장치가 필요합니다. Agent SDK로 루프를 실행할 때 턴 수나 비용에 상한을 두지 않으면, 루프는 모델이 스스로 끝낼 때까지 계속됩니다. Agent SDK 문서는 범위가 분명한 작업에서는 문제가 없지만, 열린 요청에서는 루프가 오래 실행될 수 있다고 설명합니다. 그래서 Agent SDK는 두 가지 상한을 옵션으로 둘 수 있게 하며, 기본값은 둘 다 제한 없음입니다. 턴 상한은 도구를 사용한 턴의 수를, 비용 상한은 추정 지출 금액을 제한합니다. 비용 상한에 닿아도 진행 중인 응답 하나는 끝까지 처리되므로 지출이 상한을 조금 넘을 수 있습니다. 같은 문서는 운영 환경의 에이전트에 비용 상한을 기본으로 두라고 권합니다.

상한에 도달하면 루프는 작업을 마치지 못한 채 끝나고, 결과에 종료 사유가 남습니다. 종료 사유는 정상 완료, 턴 상한 도달, 비용 상한 도달, 실행 중 오류 등으로 구분됩니다. 상한에 도달한 결과는 완료로 판정하지 않습니다(Chapter 7의 완료 보고). 두 상한의 값과, 상한에 도달했을 때 세션을 재개할지 중단할지는 작업을 맡기기 전에 정합니다. 비용 상한의 기준은 Chapter 9의 비용 관리와 연결됩니다.

상한의 단위인 턴은 문서마다 세는 범위가 다릅니다. Agent SDK 문서의 턴은 도구 호출 왕복 한 번입니다. Claude Code 용어집의 턴은 사용자 메시지 하나에서 응답이 끝날 때까지입니다. Codex의 에이전트 루프 글은 에이전트가 한 턴에서 수백 번의 도구 호출을 할 수 있고, 그러면 컨텍스트 윈도를 모두 소진할 수 있다고 설명합니다. 한 턴이 이렇게 길어질 수 있으므로, 턴 상한을 정하기 전에 사용하는 도구의 문서에서 턴이 무엇을 세는지 확인해야 합니다.

같은 명칭, 다른 맥락

에이전트와 하네스라는 말은 논문, 개발 지침, 제품 문서에서도 쓰이고, 자료마다 가리키는 범위가 조금씩 다릅니다. 다른 자료를 읽을 때 그 말이 이 책의 정의 가운데 어디에 해당하는지 알아 두면 범위를 혼동하지 않습니다. 이 절은 에이전트와 가까운 형태들과 하네스라는 명칭의 쓰임을 차례로 정리합니다.

2022년에 공개되고 2023년 학회에서 발표된 ReAct 논문은 모델이 생각, 행동, 관찰을 번갈아 하며 문제를 풀게 하는 방법을 제안했습니다. 모델이 추론을 적고(생각), 도구를 호출하고(행동), 그 결과를 보고(관찰) 다음 생각을 이어 갑니다. 이 책의 정의로 보면 이 반복은 앞에서 본 에이전트 루프의 원형에 해당합니다.

Anthropic은 모델과 도구를 사용하는 시스템을 워크플로(Workflow)와 에이전트로 나눕니다. 워크플로는 미리 정한 코드 경로(프로그램에 미리 적어 둔 처리 순서)에 따라 모델과 도구를 조율합니다. 마케팅 문구를 작성한 뒤 다른 언어로 번역하는 처리처럼 단계가 정해진 일이 그 예입니다. 에이전트는 모델이 자기 작업 과정과 도구 사용을 스스로 정합니다. 앞의 오류 수정처럼 어느 파일을 살필지 미리 정할 수 없는 일이 그 예입니다. 워크플로는 단계가 정해진 작업에서 예측 가능하고, 에이전트는 단계를 미리 정하기 어려운 작업에서 유연합니다.

두 방식은 함께 사용할 수 있습니다. 작업의 순서와 사람의 승인 지점은 워크플로처럼 미리 정하고, 각 단계 안의 작업은 에이전트가 판단하게 합니다. 이 책의 예제가 이 형태이므로, 이 책은 이 형태를 결합형이라고 부릅니다. 결합형도 단계 안의 행동은 모델이 스스로 정하므로 이 책의 에이전트 정의에 들어갑니다.

Chapter 3에서 구현하는 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)이 결합형의 예입니다. 변경 요청 사항은 운영 중인 시스템의 기능을 어떻게 변경할지 요청한 내용입니다. 이 예제는 정산 요청 화면에 프로젝트 코드 선택 항목을 추가해 달라는 재무팀의 요청이며, 일을 조회 방식 합의, 데이터 모델 변경, 단위 테스트 갱신, 화면 변경, 통합 테스트 시나리오 작성의 다섯 작업 단위로 나눕니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다. 작업 단위의 순서는 규칙 문서와 진행 기록으로 안내합니다. 승인 지점은 권한 규칙으로 정합니다. 변경 확정(git commit)은 작업 단위의 결과를 기록으로 확정하는 자리여서 실행 전에 사람의 확인을 받게 하고, 원격 저장소 반영(git push)은 다른 사람이 보는 저장소를 변경하므로 금지해 사람이 직접 합니다. 작업 단위 안의 구현 방법은 에이전트가 판단합니다.

하네스라는 명칭도 쓰이는 맥락마다 강조점이 다릅니다. 하네스는 일반적으로 말에 채우는 장구(마구)를 뜻하고, 소프트웨어에서는 시험 대상을 실행하고 결과를 확인하는 테스트 하네스라는 용어로 사용되어 왔습니다. Codex의 에이전트 루프 글은 에이전트 루프와 실행 로직을 맡는 모델 바깥의 장치를 하네스라고 부르고, 하네스가 모든 Codex 제품에 공통인 에이전트 루프를 제공한다고 설명합니다. Claude Code의 장기 실행 글은 여러 세션에 걸쳐 긴 작업을 이어 가게 하는 주변 체계라는 뜻으로 하네스라는 말을 사용합니다. 앞에서 본 Claude Code 용어집은 제품 전체를 하네스로 표현합니다.

이 책은 하네스의 범위를 Claude Code 용어집처럼 제품 전체로 잡고 팀이 정하는 설정까지 더해 넓게 잡되, 모델은 하네스 바깥에 둡니다. 팀이 정하는 설정까지 하네스에 포함해야 그 설정을 설계 대상으로 다룰 수 있기 때문입니다. 두 글이 강조한 루프 실행과 세션 기록은 이 책의 정의에서 실행 장치에 해당합니다. 표 1-4는 모델과 도구를 사용하는 세 가지 형태를 적용 대상 작업과 함께 비교하고, 표 1-5는 하네스라는 명칭이 자료마다 가리키는 범위를 비교합니다.

하네스 엔지니어링

하네스의 설정은 맡길 업무마다 팀이 정해야 하므로, 그 설계를 하나의 일로 다룰 이름이 필요합니다. 이 책은 하네스 엔지니어링을 에이전트가 신뢰할 수 있는 결과를 내도록 모델 바깥의 작업 환경을 설계하는 일로 정의합니다. 장 첫머리에서 말한 두 핵심은 이 일을 종류별로 나눈 것입니다.

  • 실행 환경 설계: 모델이 일하는 데 사용하는 도구, 규칙 문서, 기록, 검사를 갖추는 일입니다. 테스트를 실제로 실행할 수 있는 개발 환경과, 테스트, 린터(코드가 정한 규칙을 지키는지 검사하는 도구), 로그처럼 모델이 자기 결과를 직접 볼 수 있는 장치도 여기에 들어갑니다. 여기서 실행 환경은 하네스 쪽에서 준비하는 것을 가리키며, 도구가 작용하는 대상인 외부 실행 환경과 구분합니다. 이 일은 다섯 구성 요소 가운데 역할, 도구, 기록과 주로 관련됩니다.
  • 예외 상황 통제: 허용하지 않은 변경, 끝나지 않는 루프, 기준에 못 미친 결과처럼 정한 범위를 벗어나는 상황을 막거나 사람에게 넘기는 일입니다. 이런 상황은 언제 생길지 모르므로, 통제 장치는 상황이 생기기 전부터 루프의 정해진 단계(도구 호출 전, 종료 전)마다 작동합니다. 다섯 구성 요소 가운데 주로 권한과 검증이 맡습니다.

하네스 엔지니어링이라는 이름은 2026년 2월 두 글에 연이어 나왔습니다. 먼저 개발자 Mitchell Hashimoto의 블로그 글은 에이전트가 실수할 때마다 같은 실수를 되풀이하지 않도록 해결책을 설계하는 일을 이 이름으로 부른다고 밝혔습니다. 며칠 뒤 OpenAI가 Codex로 제품을 만든 경험을 정리한 글은 이 용어를 제목으로 삼아, 사람이 코드를 직접 작성하지 않는 개발 실험을 소개했습니다. 이 글에 따르면 개발 팀은 5개월 동안 약 100만 줄의 코드와 약 1,500개의 풀 리퀘스트(Pull Request)를 Codex로 생성했습니다. 풀 리퀘스트는 코드 변경을 저장소에 반영하기 전에 검토를 요청하는 단위입니다. 이 글이 밝힌 내용은 네 가지입니다.

  • 엔지니어는 코드를 직접 작성하지 않고, 작업 환경을 설계하고 의도를 문서로 밝히고 피드백 루프(결과를 확인하고 그 결과로 다음 작업을 수정하는 반복)를 만드는 일을 맡았습니다.
  • 이 글은 초기 진행이 느렸던 원인을 Codex의 능력 부족보다 충분히 정의되지 않은 환경에서 찾았습니다.
  • 작업이 실패하면 어떤 능력이 누락되었는지 묻고, 그 능력을 에이전트가 읽을 수 있고 검사로 강제되는 형태로 저장소에 추가했습니다.
  • 에이전트가 실행 중에 읽을 수 없는 지식은 에이전트에게 없는 지식으로 보고, 채팅이나 사람의 기억에 있던 결정을 저장소 문서로 옮겼습니다.

사람의 역할도 남았습니다. 사람은 작업의 우선순위를 정하고, 사용자 의견을 수용 기준으로 정리하고, 결과를 검증했습니다. 수용 기준은 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 이 글이 보고한 개선 대상은 모델만이 아니었고, 저장소 문서, 검사 규칙, 검증 절차 같은 작업 환경이 중심이었습니다.

하네스 안의 프롬프트와 컨텍스트

하네스를 설계하면 모델에 넘기는 입력도 함께 정해집니다. 하네스가 루프마다 모델에 넘기는 입력은 프롬프트와 컨텍스트입니다. 프롬프트는 모델에 주는 지시문이고, 컨텍스트는 모델이 응답을 생성할 때 입력되는 정보 전체이므로 프롬프트는 컨텍스트의 일부입니다. 이 책은 프롬프트를 사람이 이번 작업에 입력하는 요청으로 좁혀 사용합니다. 사람이 작업마다 직접 작성하는 부분과 하네스가 미리 정해 두는 부분을 나눠 설계하기 위해서입니다. 그래서 제품이 미리 포함하는 시스템 프롬프트와 규칙 문서는 하네스가 넘기는 컨텍스트의 일부로 다룹니다. 시스템 프롬프트는 이름에 프롬프트가 들어가지만, 사람이 작업마다 입력하는 요청이 아니므로 이 책에서는 컨텍스트로 분류합니다.

프롬프트와 컨텍스트는 하네스가 넘기는 입력이지만, 설계할 때 답해야 할 질문이 하네스와 다릅니다. 그래서 이 책은 프롬프트, 컨텍스트, 하네스를 묶어 세 설계 층이라고 부릅니다. 모델은 공급사가 제공하고 팀은 선택하며, 세 설계 층은 모델을 사용하는 팀이 설계합니다. 표 1-6은 모델과 세 설계 층의 정의와 설계 질문을 보여 줍니다.

같은 모델을 사용해도 세 층을 어떻게 설계했는지에 따라 결과가 달라질 수 있습니다. 앞의 오류 수정 요청에서도 규칙 문서에 테스트 실행 명령이 적혀 있는지, 테스트 실행이 권한 규칙으로 허용되는지 거부되는지에 따라, 같은 모델이 테스트로 수정을 확인하기도 하고 확인하지 못하기도 합니다.

프롬프트 엔지니어링과 컨텍스트 엔지니어링

프롬프트와 컨텍스트를 다루는 방법에는 이미 이름이 있고, 두 방법의 범위를 구분해야 하네스 엔지니어링이 무엇을 더 다루는지 분명해집니다. 프롬프트 엔지니어링(Prompt Engineering)은 원하는 결과를 얻도록 지시문을 작성하고 구성하는 방법입니다. 컨텍스트 엔지니어링(Context Engineering)은 모델이 응답을 생성하는 동안 필요한 정보를 선별하고 유지하는 전략입니다. 두 정의는 2025년 9월 공개된 Claude Code의 컨텍스트 엔지니어링 글을 따릅니다. 이 글은 컨텍스트 엔지니어링을 프롬프트 엔지니어링이 발전한 단계로 설명합니다. 두 방법은 대상과 시점에서 다릅니다. 컨텍스트 엔지니어링에는 컨텍스트 윈도의 한도라는 제약도 따릅니다.

  • 대상: 프롬프트 엔지니어링은 지시문을 다룹니다. 컨텍스트 엔지니어링은 시스템 지시, 도구 설명, 외부 자료, 대화 이력을 포함한 입력 전체를 다룹니다.
  • 시점: 컨텍스트 엔지니어링 글은 프롬프트 작성을 따로 떨어진 한 번의 작업으로, 컨텍스트 선별을 모델에 무엇을 넘길지 정할 때마다 되풀이하는 작업으로 대비합니다. 앞의 오류 수정 요청에서도 요청 문장은 처음에 한 번 작성하지만, 모델에 넘길 파일 내용과 테스트 출력은 루프를 돌 때마다 달라집니다.
  • 제약: 컨텍스트 엔지니어링은 컨텍스트 윈도의 한도 안에서 정보를 선별해야 합니다. 같은 글은 컨텍스트의 토큰이 늘수록 모델이 정보를 정확히 기억해 내는 능력이 떨어진다고 설명합니다. 그래서 많은 정보를 제공하는 것보다 필요한 정보를 선별하는 것이 중요합니다. 컨텍스트 윈도의 사용 현황을 확인하는 위치는 Chapter 5의 한정된 자원에서 다룹니다.

두 방법은 모델에 넘기는 입력을 다룹니다. 하네스 엔지니어링은 그 입력을 포함해 루프, 도구, 권한, 기록, 검증까지 다룹니다.

소프트웨어 엔지니어링과의 접점

하네스 엔지니어링이 다루는 범위가 넓어도 처음부터 새로 배울 일만은 아닙니다. 하네스 설계는 소프트웨어 엔지니어링의 기존 활동과 대응시켜 볼 수 있습니다. 소프트웨어 엔지니어링은 요구 사항 정의, 설계, 개발, 테스트, 배포, 운영으로 이어지는 개발의 전 과정을 다루는 분야입니다. 이 가운데 설계와 개발은 에이전트에게 맡기는 작업 자체이고, 나머지 네 활동은 에이전트가 일부를 수행하더라도 그 기준은 사람이 정해 하네스에 담는 일입니다. 표 1-7은 이 네 활동별로 대응하는 하네스 설계를 보여 줍니다.

요구 사항을 명확히 정의하는 능력은 에이전트에게 작업을 지시하는 능력으로 이어질 수 있습니다. 테스트 기준을 정하는 능력은 에이전트의 결과를 검증하는 능력으로 이어질 수 있습니다.

결과를 개선할 수 있는 영역

세 설계 층을 결과 개선의 관점에서 정리합니다. 모델은 공급사가 개선하고, 팀은 모델을 선택할 수 있을 뿐입니다. 반면 하네스의 설정은 에이전트를 사용하는 팀이 정합니다. 그래서 모델 선택 외에 팀이 결과를 개선하려고 직접 변경할 수 있는 대상은 세 설계 층입니다. 곧 프롬프트, 컨텍스트, 그리고 하네스 가운데 팀이 정하는 설정입니다.

문제가 생기면 먼저 원인이 어느 층에 있는지 분류합니다. 표 1-8은 대표적인 증상마다 먼저 점검할 층과 그 층의 점검 항목을 대응시킨 것입니다. 같은 증상이 여러 층에서 생길 수도 있으므로, 표는 점검을 시작할 순서로 읽습니다.

이 분류 가운데 하네스의 기록, 검증, 역할 쪽 행은 이 책을 집필한 작가의 작업에서 나왔습니다. 작가는 앞선 책 「생성형 AI, 묻고 확인하고 활용하기」를 AI 에이전트와 함께 만들며 73차례 검수(원고를 읽고 수정할 곳을 찾는 점검)를 거쳤습니다. 초기에는 어휘, 조사, 표 번호처럼 같은 종류의 실수를 사람이 매번 찾았습니다. 큰 결정을 집필 중에 여러 번 뒤집는 일도 있었습니다. 해결은 작업 환경을 보완하는 방식으로 했습니다.

  • 검증: 반복된 실수는 자동 검사 규칙으로 만들었습니다.
  • 기록: 큰 결정은 번호를 매겨 기록하고, 결정을 변경할 때는 이전 결정을 남겼습니다.
  • 역할: 원고 작성과 검수를 서로 다른 에이전트에게 맡기고, 판단이 필요한 항목은 사람이 맡도록 경계를 정했습니다.

이렇게 보완한 뒤 사람은 판단이 필요한 항목만 검토하는 구조로 작업을 정리했습니다.

이 경험처럼 작업 환경을 보완하는 일은 모델을 더 좋은 것으로 교체해도 남습니다. 모델 성능이 오르면 한 번의 응답 품질은 좋아질 수 있습니다. 그러나 어떤 자료에 접근할지, 어떤 작업을 사람이 승인할지, 무엇을 기록할지는 팀이 정할 일입니다. 이 가운데 어떤 자료를 모델에 넘길지는 컨텍스트 설계와 이어집니다. Claude Code의 컨텍스트 엔지니어링 글은 모델이 발전해도 컨텍스트를 한정된 자원으로 다루는 일은 계속 중요하다고 설명합니다.

결과를 개선하려면, 모델을 교체하기 전에 하네스의 설정을 먼저 점검합니다. 표 1-8의 컨텍스트 행처럼 원인이 모델에 넘어간 입력에 있어도, 어떤 규칙 문서를 입력에 포함할지는 하네스의 설정이 정하기 때문입니다. 요청 문장이 원인인 프롬프트 행은 요청을 수정하는 쪽을 먼저 봅니다. 곧 무엇을 맡기고(역할), 무엇을 쓰게 하며(도구), 어디까지 허용하고(권한), 무엇을 남기며(기록), 어떻게 확인할지(검증)를 팀이 정했는지 확인합니다.

설정과 결과의 확인 방법

하네스가 맡는 일은 Claude Code의 명령과 Agent SDK의 실행 결과로 확인합니다. /로 시작하는 명령은 실습 폴더에서 Claude Code를 실행한 뒤 입력창에 입력하는 명령이며, 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다. 표 1-9는 이 장에서 다룬 컨텍스트 구성, 권한 확인, 루프의 종료, 사용량을 확인하는 위치입니다. 표의 종료 사유 행은 Agent SDK(Python, TypeScript 라이브러리)로 루프를 실행한 경우의 결과 메시지이므로, Claude Code만 사용한다면 그 행은 건너뛰어도 됩니다.

설계 원칙과 점검 질문

에이전트의 결과가 기대와 다르면, 모델을 교체하기 전에 하네스의 설정을 먼저 점검합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트에서 제품이 맡는 실행 장치와 팀이 정하는 설정을 구분할 수 있습니까?
  2. 맡긴 작업에 턴 상한과 비용 상한을 둘 수 있다면, 그 값과 상한에 도달했을 때의 처리가 정해져 있습니까?
  3. 최근 겪은 문제를 표 1-8의 증상에 대응하면, 원인은 프롬프트, 컨텍스트, 하네스 가운데 어느 층에 있습니까?
