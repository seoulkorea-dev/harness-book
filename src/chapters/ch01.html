Chapter 1 하네스란 무엇인가

에이전트는 모델과 하네스로 이루어집니다.

에이전트(Agent)라는 말은 연구 논문, 개발 지침, 제품 문서에서 서로 다른 범위를 가리킵니다. 어떤 곳에서는 모델이 생각과 행동을 번갈아 하는 방법을, 어떤 곳에서는 모델이 스스로 작업 과정을 정하는 시스템을, 어떤 곳에서는 제품 자체를 뜻합니다. 같은 명칭이 다른 맥락에서 쓰이면, 에이전트를 만든다고 할 때 무엇을 설계하는지가 흐려집니다. 따라서 모델이 혼자 할 수 없는 일과 명칭의 쓰임 차이를 먼저 확인하고, 이 책에서 사용할 에이전트와 하네스(Harness)의 뜻을 정해야 합니다. 이 장은 모델의 한계에서 출발해 에이전트를 가리키는 여러 형태의 차이, 이 책의 에이전트와 하네스, 하네스 엔지니어링(Harness Engineering)의 정의, 하네스 안의 프롬프트와 컨텍스트(Context), 에이전트 루프를 차례로 살펴봅니다. 이어서 프롬프트 엔지니어링(Prompt Engineering)과 컨텍스트 엔지니어링(Context Engineering), 소프트웨어 엔지니어링과의 접점을 짚고, 마지막으로 결과가 기대와 다를 때 원인이 있는 층을 찾는 방법을 다룹니다.

  • 모델은 명령을 직접 실행하지 않고, 요청 사이의 대화도 기억하지 않으며, 실행 결과도 스스로 확인하지 못합니다. 이 세 가지를 모델 대신 맡는 프로그램이 하네스입니다.
  • 에이전트는 모델과 하네스로 이루어지고, 하네스는 모델 바깥의 실행 체계로, 제품이 제공하는 실행 장치와 사용자와 팀이 정하는 설정으로 나뉩니다.
  • 하네스는 루프를 실행하고, 도구를 제공하고, 컨텍스트를 관리하며, 권한, 기록, 검증으로 작업을 통제합니다.
  • 프롬프트와 컨텍스트는 하네스 안의 설계 대상입니다.

모델만으로 할 수 없는 일

하네스가 왜 필요한지 보려면 먼저 모델이 무엇을 받고 무엇을 내놓는지 알아야 합니다. 모델은 글을 토큰(Token) 단위로 처리합니다. 토큰은 모델이 텍스트를 나누어 처리하는 단위입니다. 대규모 언어 모델(Large Language Model, LLM)은 입력된 토큰을 바탕으로 다음 토큰을 예측해 결과를 생성하는 모델입니다. 모델이 응답을 생성할 때 입력되는 정보 전체를 컨텍스트라고 하고, 모델이 한 번에 처리할 수 있는 토큰의 범위를 컨텍스트 윈도(Context Window)라고 합니다. 모델은 입력된 컨텍스트를 받아 출력을 만들 뿐이므로, 입력 바깥에서 일어나는 일은 혼자 처리하지 못합니다.

모델 하나만으로는 업무를 끝까지 수행할 수 없습니다. Claude의 API(프로그램이 모델을 호출하는 방식) 문서는 모델과 모델을 호출하는 프로그램의 역할을 나눠 설명합니다. 이 설명을 바탕으로 이 책은 모델의 한계를 세 가지로 정리합니다.

  • 실행: 모델은 명령을 직접 실행하지 않습니다. 모델은 실행할 명령을 요청하고, 실제 실행은 모델을 호출한 프로그램이 맡습니다(웹 검색처럼 Anthropic 서버가 실행하는 도구도 있습니다).
  • 기억: API 문서의 도구 사용 절차에서 프로그램은 새 요청마다 원래 대화, 모델의 응답, 도구 결과를 모두 다시 담아 보냅니다. 대화를 이어 가려면 프로그램이 이전 대화를 다음 요청에 다시 포함해야 합니다.
  • 확인: 모델은 실행 결과를 스스로 받지 못합니다. 프로그램이 결과를 돌려주어야 모델이 다음 판단을 하고, 결과가 기준에 맞는지 따로 확인하는 일(검증)도 모델 바깥에서 정합니다.

도구는 파일 읽기, 명령 실행, 검색처럼 모델 바깥에서 실행되는 기능입니다. 도구 호출은 모델이 특정 도구를 정해진 입력으로 실행해 달라고 요청하는 것입니다. 프로그램은 도구를 실행하고 결과를 모델에 돌려줍니다. 실행이 실패하면 실패 표시와 오류 내용을 결과로 돌려줄 수 있습니다.

실행, 기억, 확인을 모델 대신 맡는 프로그램을 이 책은 하네스라고 부릅니다. 하네스라는 말은 사용하는 곳마다 뜻이 조금씩 달라서, 다음 절에서 쓰임을 비교한 뒤 그다음의 '이 책의 에이전트와 하네스' 절에서 뜻을 정합니다. 표 1-1은 모델이 혼자 수행하는 범위(자율 수행 영역)에서 세 가지 한계가 어떻게 드러나고 하네스가 그 한계를 어떻게 보완하는지(하네스 보완 영역), 그리고 하네스가 더하는 작업 진행과 실행 범위를 보여 줍니다. 표의 규칙 문서는 작업 규칙을 적어 둔 파일이고, 권한 규칙(Permission Rule)과 권한 모드(Permission Mode)는 실행 범위를 정하는 설정입니다.

같은 명칭, 다른 맥락

앞 절에서 하네스라고 부른 프로그램과 에이전트는 같은 명칭이라도 쓰이는 맥락에 따라 가리키는 범위가 조금씩 다릅니다. 이 절은 맥락별 쓰임을 비교하고, 다음 절에서 이 책의 정의를 정합니다.

2022년에 공개되고 2023년 학회에서 발표된 ReAct 논문은 모델이 생각, 행동, 관찰을 번갈아 하며 문제를 풀게 하는 방법을 제안했습니다. 모델이 추론을 적고(생각), 도구를 호출하고(행동), 그 결과를 보고(관찰) 다음 생각을 이어 갑니다. 이 반복이 오늘날 에이전트 루프(판단, 도구 실행, 결과 확인을 되풀이하는 흐름)의 원형으로 볼 수 있으며, 뒤의 에이전트 루프와 종료 조건 절에서 루프를 다섯 단계로 정리합니다. ReAct는 프롬프트(Prompt, 모델에 주는 지시문)로 구현한 방법이어서, 루프를 돌리고 도구를 실행하고 결과를 다시 모델에 입력하는 일은 모델 바깥의 코드가 맡았습니다.

Anthropic은 모델과 도구를 사용하는 시스템을 워크플로(Workflow)와 에이전트로 나눕니다. 워크플로는 미리 정한 코드 경로(프로그램에 미리 적어 둔 처리 순서)에 따라 모델과 도구를 조율합니다. 에이전트는 모델이 자기 작업 과정과 도구 사용을 스스로 정합니다. 워크플로는 단계가 정해진 작업에서 예측 가능하고, 에이전트는 단계를 미리 정하기 어려운 작업에서 유연합니다.

두 방식은 함께 사용할 수 있습니다. 작업의 순서와 사람의 승인 지점은 워크플로처럼 미리 정하고, 각 단계 안의 작업은 에이전트가 판단하게 합니다. 이 책은 이 형태를 결합형이라고 부릅니다.

Chapter 3에서 구현하는 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)이 결합형의 예입니다. 변경 요청 사항은 운영 중인 시스템의 기능을 어떻게 변경할지 요청한 내용입니다. 이 예제는 정산 요청 화면에 프로젝트 코드 선택 항목을 추가해 달라는 재무팀의 요청이며, 일을 조회 방식 합의, 데이터 모델 변경, 단위 테스트 갱신, 화면 변경, 통합 테스트 시나리오 작성의 다섯 작업 단위로 나눕니다. 작업 단위의 순서와 사람의 승인 지점은 하네스의 설정(사용자와 팀이 정하는 값, 뜻은 다음 절)으로 미리 정하고, 작업 단위 안의 구현 방법은 에이전트가 판단합니다.

하네스라는 명칭도 쓰이는 맥락마다 강조점이 다릅니다. 하네스는 일반적으로 말에 채우는 장구(마구)를 뜻하고, 소프트웨어에서는 시험 대상을 실행하고 결과를 확인하는 테스트 하네스라는 용어로 사용되어 왔습니다. Codex의 에이전트 루프 글은 에이전트 루프와 실행 로직을 맡는 모델 바깥의 장치를 하네스라고 부릅니다. Claude Code의 장기 실행 글은 여러 세션에 걸쳐 긴 작업을 이어 가게 하는 주변 체계라는 뜻으로 하네스라는 말을 사용하고, Claude Code 제품 문서는 제품 자체를 하네스로, 모델을 그 안의 구성 요소로 설명합니다. 다음 절에서 정하는 이 책의 정의는 Claude Code 문서의 넓은 범위를 따릅니다. 루프 실행이나 세션 기록 하나만으로는 앞 절의 실행, 기억, 확인을 모두 맡지 못하기 때문입니다. 두 제품이 강조한 루프 실행과 세션 기록은 그 정의에서 하네스 가운데 제품이 제공하는 부분, 곧 실행 장치로 봅니다.

표 1-2는 에이전트와 그 주변의 네 가지 형태를 적용 대상 작업과 함께 비교하고, 표 1-3은 하네스라는 명칭의 쓰임과 각 쓰임이 이 책의 정의에서 차지하는 위치(본문 적용 위치)를 비교합니다.

이 책의 에이전트와 하네스

이 책에서 에이전트(Agent)는 인공지능 모델이 루프(Loop) 안에서 도구를 사용해 다음 행동을 스스로 정하고, 결과를 확인하며, 목표를 이룰 때까지 이 과정을 반복하는 시스템입니다. 에이전트는 '모델'과 '하네스(Harness)'로 이루어집니다. 하네스는 모델이 에이전트로 일할 수 있게 하는 모델 바깥의 실행 체계 전체를 가리킵니다. Claude Code의 컨텍스트 엔지니어링 글도 에이전트를 반복 루프 안에서 스스로 도구를 사용하는 시스템으로 설명합니다. 결합형도 단계 안의 행동은 모델이 스스로 정하므로 이 책의 정의에 들어갑니다.

실제 제품의 문서에서도 같은 구조를 볼 수 있습니다. Claude Code 용어집은 하네스를 언어 모델을 코딩 에이전트로 만드는 도구, 컨텍스트 관리, 실행 환경을 모두 합친 것으로 설명합니다. 즉 Claude Code 자체가 하네스의 역할을 하고, 언어 모델인 Claude는 그 안에서 판단을 맡습니다.

모델 바깥의 실행 체계는 누가 정하는지에 따라 '실행 장치'와 '설정'의 두 층으로 나뉩니다.

  • 실행 장치(제품이 제공): 루프 실행, 도구 제공, 컨텍스트 관리, 권한 확인, 세션 기록(세션은 Claude Code를 실행해 하나의 대화를 이어 가는 단위)처럼 에이전트가 움직이는 데 필요한 기본 기능을 맡습니다.
  • 설정(사용자와 팀이 정함): 규칙 문서(작업 규칙을 적어 프로젝트에 두는 파일, Claude Code에서는 CLAUDE.md), 권한 설정, 자동 검사, 역할 분담처럼 맡길 업무에 맞춰 정하는 값입니다.

에이전트는 설정이 없어도 제품의 기본값으로 동작하지만, 업무에 맞게 설정을 정하면 그 업무에 맞는 에이전트가 됩니다. 작업 순서, 승인, 검사 단계를 설정으로 정하면 앞에서 말한 결합형이 됩니다. 설정 가운데 규칙 문서는 이 작업 순서를 따르도록 안내하고, 권한 규칙과 훅(Hook, 정해진 시점에 자동으로 실행되는 명령)은 정한 범위 밖의 실행을 막습니다. 이 책에서 하네스의 다섯 구성 요소(역할, 도구, 권한, 기록, 검증)라고 할 때는 이 설정에서 정하는 항목을 가리킵니다. 이 가운데 역할은 에이전트가 할 작업과 사람이 할 작업의 경계이며, 주로 규칙 문서에 적습니다.

실행 장치와 설정에 도구, 권한, 기록처럼 같은 이름이 함께 나오는 것은 대부분 같은 기능을 두 쪽에서 보기 때문입니다. 실행 장치는 그 기능이 작동하는 방식이고, 설정은 그 기능을 이 업무에서 어떻게 쓸지 정한 값입니다. 기록은 예외로, 실행 장치에서는 대화를 저장하고 재개하는 세션 기록이고, 설정에서는 결정 기록과 진행 기록이어서 대상이 다릅니다.

하네스가 실행하는 도구는 모델과 하네스 바깥의 '외부 실행 환경'에 작용합니다. 외부 실행 환경은 파일 시스템, 데이터베이스, 네트워크, 소프트웨어, 사용자 화면처럼 도구가 읽거나 변경하는 대상 전체입니다. 도구는 제품에 들어 있는 기본 도구와, MCP(Model Context Protocol)라는 표준 방식으로 연결하는 외부 도구로 나뉩니다(Chapter 2).

정리하면 에이전트는 그림 1-1처럼 모델, 하네스, 외부 실행 환경이 맞물려 돌아가는 구조입니다. 하네스가 먼저 입력과 컨텍스트를 모델에 넘기면, 모델은 그것을 바탕으로 응답이나 도구 호출(Tool Call)을 하네스에 돌려줍니다.

표 1-4는 그림 1-1의 구성 요소와 구성 요소 사이의 화살표를 주요 역할, 기능적 제약, 관련 절로 나누어 설명합니다.

같은 모델도 도구를 연결하지 않은 호출에서는 답변만 하고, Claude Code 안에서는 파일 수정과 테스트까지 수행합니다. 이 차이는 주로 하네스가 도구를 연결하고 실행하는 데서 생깁니다. 하네스가 하는 일을 실행 장치와 설정을 합쳐 요약하면 여섯 가지입니다.

  • 루프 실행: 모델의 판단과 도구 실행을 작업이 끝날 때까지 반복합니다.
  • 도구 제공: 파일 읽기와 수정, 명령 실행 같은 기능을 모델에 제공합니다.
  • 컨텍스트 관리: 루프마다 모델에 넘길 정보를 정합니다.
  • 권한: 도구로 할 수 있는 동작의 범위를 통제합니다.
  • 기록: 결정과 진행 상황, 실행 과정을 남깁니다.
  • 검증: 결과를 받아들이기 전에 확인합니다.

루프 실행, 도구 제공, 컨텍스트 관리는 주로 실행 장치가 맡고, 권한, 기록, 검증은 실행 장치의 기능 위에 팀이 설정으로 범위와 기준을 정합니다. 다섯 구성 요소 가운데 역할은 이 목록에 따로 없습니다. 역할은 규칙 문서에 적혀 컨텍스트 관리를 거쳐 모델에 전달되기 때문입니다.

하네스 엔지니어링

하네스의 설정은 맡길 업무마다 팀이 정해야 하므로, 그 설계를 하나의 일로 다룰 이름이 필요합니다. 이 책은 하네스 엔지니어링을 에이전트가 신뢰할 수 있는 결과를 내도록 모델 바깥의 작업 환경을 설계하는 일로 정의합니다. 구성 요소별 설계는 Chapter 2에서 다룹니다.

이 정의가 실제 개발에서 어떤 모습인지는 Codex의 사례에서 볼 수 있습니다. 2026년 2월 공개된 Codex의 하네스 엔지니어링 글은 이 용어를 제목으로 삼아, 사람이 코드를 직접 작성하지 않는 개발 실험을 소개했습니다. 이 글에 따르면 개발 팀은 5개월 동안 약 100만 줄의 코드와 약 1,500개의 풀 리퀘스트(Pull Request)를 Codex로 생성했습니다. 풀 리퀘스트는 코드 변경을 저장소에 반영하기 전에 검토를 요청하는 단위입니다. 이 글이 밝힌 내용은 네 가지입니다.

  • 엔지니어는 코드를 직접 작성하지 않고, 작업 환경을 설계하고 의도를 문서로 밝히고 피드백 루프(결과를 확인하고 그 결과로 다음 작업을 수정하는 반복)를 만드는 일을 맡았습니다.
  • 이 글은 초기 진행이 느렸던 원인을 Codex의 능력 부족보다 충분히 정의되지 않은 환경에서 찾았습니다.
  • 작업이 실패하면 어떤 능력이 누락되었는지 묻고, 그 능력을 에이전트가 읽을 수 있고 검사로 강제되는 형태로 저장소에 추가했습니다.
  • 에이전트가 실행 중에 읽을 수 없는 지식은 에이전트에게 없는 지식으로 보고, 채팅이나 사람의 기억에 있던 결정을 저장소 문서로 옮겼습니다.

사람의 역할도 남았습니다. 사람은 작업의 우선순위를 정하고, 사용자 의견을 수용 기준으로 정리하고, 결과를 검증했습니다. 수용 기준은 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 이 글이 보고한 개선 대상은 모델만이 아니었고, 저장소 문서, 검사 규칙, 검증 절차 같은 작업 환경이 중심이었습니다.

하네스 안의 프롬프트와 컨텍스트

앞 절의 사례에서 개선한 작업 환경에는 모델에 넘기는 입력도 들어 있습니다. 하네스가 루프마다 모델에 넘기는 입력은 프롬프트와 컨텍스트이므로, 이 책은 둘을 하네스 안의 설계 대상으로 봅니다. 층마다 답해야 할 설계 질문은 서로 다르므로, 이 책은 프롬프트, 컨텍스트, 하네스를 묶어 세 설계 층이라고 부릅니다. 모델은 공급사가 제공하는 실행 엔진이고, 프롬프트, 컨텍스트, 하네스의 설정은 모델을 사용하는 팀이 설계하는 대상입니다.

프롬프트는 모델에 주는 지시문입니다. 컨텍스트는 모델이 응답을 생성할 때 입력되는 정보 전체이며, 프롬프트는 그 일부입니다. 이 책에서 프롬프트는 사람이 이번 작업에 입력하는 요청을 가리킵니다. 제품이 미리 포함하는 시스템 프롬프트와 규칙 문서는 하네스가 루프마다 모델에 넘기는 컨텍스트의 일부로 다룹니다. 표 1-5는 층별 정의와 설계 질문을 보여 줍니다.

같은 모델을 사용해도 세 층을 어떻게 설계했는지에 따라 팀마다 결과가 달라질 수 있습니다.

에이전트 루프와 종료 조건

세 설계 층 가운데 하네스가 실제로 어떻게 작동하는지는 에이전트 루프에서 드러납니다. 하네스의 다섯 구성 요소(Chapter 2)는 루프의 단계마다 서로 다른 시점에 작동합니다. Claude Code의 Agent SDK(Claude Code의 에이전트 루프를 프로그램에서 실행하는 개발 도구) 문서가 설명하는 실행 루프를 이 책은 다섯 단계로 정리합니다.

  • 컨텍스트 구성: 하네스가 요청과 함께 시스템 프롬프트, 도구 정의, 대화 이력을 모아 모델에 넘깁니다.
  • 판단과 응답: 모델이 현재 상태를 판단해 텍스트로 답하거나 도구 호출을 요청합니다.
  • 권한 확인: 도구 호출 요청이 있으면, 하네스가 실행 전에 허용(allow), 확인 요청(ask), 금지(deny)를 판단합니다.
  • 도구 실행: 하네스가 요청된 도구를 실행하고 결과를 대화 이력에 추가한 뒤 컨텍스트 구성부터 반복합니다. Agent SDK 문서는 이 왕복 한 번을 턴이라고 부릅니다.
  • 최종 응답: 모델이 도구 호출 없이 응답하면 루프가 끝나고, Agent SDK의 결과 메시지에 최종 응답과 토큰 사용량, 비용, 세션 ID가 담깁니다.

그림 1-2는 다섯 단계와 그 사이의 분기를 보여 줍니다. 이 책은 그림에서 최종 응답 앞에 완료 기준(작업이 끝났다고 판정하는 조건, 예: 검사 통과) 확인을 하나 더 둡니다. 모델이 도구 호출 없이 응답하면 일을 끝냈다고 판단한 것이지만, 그 판단이 맞는지는 따로 확인해야 하기 때문입니다. Claude Code에서는 훅으로 이 확인을 추가합니다. 모델이 응답을 마치려 할 때 실행되는 Stop 훅이 완료 기준을 검사하고, 미달이면 종료를 막아 모델이 작업을 이어 가게 합니다. 훅이 실행되지 않거나 실패하면 종료를 막지 못하므로, 훅이 실제로 불렸는지 확인해야 합니다. 확인하는 방법은 Chapter 2의 확인 방법에서 다룹니다. 완료 기준은 팀이 설정의 검증에서 정합니다(Chapter 7의 완료 기준).

표 1-6은 루프의 단계별로 작동하는 구성 요소를 보여 줍니다.

도구 실행 앞에서는 권한이 작동합니다. Agent SDK 문서에 따르면 거부된 도구 호출은 실행되지 않고, 모델은 거부 메시지를 결과로 받습니다. 모델은 대개 다른 방법을 찾거나, 진행할 수 없다고 보고합니다.

루프가 끝나는 때는 모델이 응답을 마칠 때만이 아닙니다. 턴 수나 비용에 상한을 두지 않으면 루프는 모델이 스스로 끝낼 때까지 계속됩니다. Agent SDK 문서는 범위가 분명한 작업에서는 문제가 없지만, 열린 요청에서는 루프가 오래 실행될 수 있다고 설명합니다. 그래서 Agent SDK는 두 가지 상한을 옵션으로 둘 수 있게 하며, 기본값은 둘 다 제한 없음입니다. 턴 상한은 도구를 사용한 턴의 수를, 비용 상한은 추정 지출 금액을 제한합니다. 비용 상한에 닿아도 진행 중인 응답 하나는 끝까지 처리되므로 지출이 상한을 조금 넘을 수 있습니다. 같은 문서는 운영 환경의 에이전트에 비용 상한을 기본으로 두라고 권합니다.

상한에 도달하면 루프는 작업을 마치지 못한 채 끝나고, 결과에 종료 사유가 남습니다. 종료 사유는 정상 완료, 턴 상한 도달, 비용 상한 도달, 실행 중 오류 등으로 구분됩니다. 상한에 도달한 결과는 완료로 판정하지 않습니다(Chapter 7의 완료 보고). 두 상한의 값과, 상한에 도달했을 때 세션을 재개할지 중단할지는 작업을 맡기기 전에 정합니다. 비용 상한의 기준은 Chapter 9의 비용 관리와 연결됩니다.

상한의 단위인 턴은 문서마다 세는 범위가 다릅니다. Agent SDK 문서의 턴은 도구 호출 왕복 한 번입니다. Claude Code 용어집의 턴은 사용자 메시지 하나에서 응답이 끝날 때까지입니다. Codex의 에이전트 루프 글은 하네스가 모든 Codex 제품에 공통인 에이전트 루프를 제공한다고 설명합니다. Codex 글의 턴도 사용자 메시지 하나에 대한 처리 전체이며, 한 턴 안에서 모델 추론과 도구 호출이 여러 번 반복됩니다. 같은 글은 에이전트가 한 턴에서 수백 번의 도구 호출을 할 수 있고, 그러면 컨텍스트 윈도를 모두 소진할 수 있다고 설명합니다. 한 턴이 이렇게 길어질 수 있으므로, 턴 상한을 정하기 전에 사용하는 도구의 문서에서 턴이 무엇을 세는지 확인해야 합니다.

프롬프트 엔지니어링과 컨텍스트 엔지니어링

앞에서 프롬프트와 컨텍스트를 하네스 안의 두 설계 층으로 정했습니다. 두 층을 다루는 방법에는 이미 이름이 있고, 두 방법의 범위를 구분해야 하네스 엔지니어링이 무엇을 더 다루는지 분명해집니다. 프롬프트 엔지니어링은 원하는 결과를 얻도록 지시문을 작성하고 구성하는 방법입니다. 컨텍스트 엔지니어링은 모델이 응답을 생성하는 동안 필요한 정보를 선별하고 유지하는 전략입니다. 두 정의는 2025년 9월 공개된 Claude Code의 컨텍스트 엔지니어링 글을 따릅니다. 이 글은 컨텍스트 엔지니어링을 프롬프트 엔지니어링이 발전한 단계로 설명합니다. 이 책은 프롬프트를 이 정의 가운데 사람이 이번 작업에 입력하는 요청으로 좁혀 사용합니다. 두 방법은 대상과 시점에서 다르고, 컨텍스트 엔지니어링에는 컨텍스트 윈도의 한도라는 제약이 따릅니다.

  • 대상: 프롬프트 엔지니어링은 지시문을 다룹니다. 컨텍스트 엔지니어링은 시스템 지시, 도구 설명, 외부 자료, 대화 이력을 포함한 입력 전체를 다룹니다.
  • 시점: 컨텍스트 엔지니어링 글은 프롬프트 작성을 한 번에 끝나는 작업으로 봅니다. 컨텍스트는 모델에 무엇을 넘길지 정할 때마다 다시 선별합니다.
  • 제약: 컨텍스트 엔지니어링은 컨텍스트 윈도의 한도 안에서 정보를 선별해야 합니다. 같은 글은 컨텍스트의 토큰이 늘수록 모델이 정보를 정확히 기억해 내는 능력이 떨어진다고 설명합니다. 그래서 많은 정보를 제공하는 것보다 필요한 정보를 선별하는 것이 중요합니다. 컨텍스트 윈도의 사용 현황을 확인하는 위치는 Chapter 5의 한정된 자원에서 다룹니다.

두 방법은 모델에 넘기는 입력을 다룹니다. 하네스 엔지니어링은 그 입력을 포함해 루프, 도구, 권한, 기록, 검증까지 다룹니다.

소프트웨어 엔지니어링과의 접점

하네스 엔지니어링이 다루는 범위가 넓어도 처음부터 새로 배울 일만은 아닙니다. 하네스 설계는 소프트웨어 엔지니어링의 기존 활동과 대응시켜 볼 수 있습니다. 소프트웨어 엔지니어링은 요구 사항 정의, 설계, 개발, 테스트, 배포, 운영으로 이어지는 개발의 전 과정을 다루는 분야입니다. 이 책은 이 가운데 에이전트에게 맡기는 일과 직접 짝을 이루는 네 활동만 표로 보입니다. 표 1-7은 활동별로 대응하는 하네스 설계를 보여 줍니다.

요구 사항을 명확히 정의하는 능력은 에이전트에게 작업을 지시하는 능력으로 이어질 수 있습니다. 테스트 기준을 정하는 능력은 에이전트의 결과를 검증하는 능력으로 이어질 수 있습니다.

결과를 개선할 수 있는 영역

앞에서 본 구성을 결과 개선의 관점에서 정리합니다. 모델은 공급사가 개선하지만, 하네스의 설정은 에이전트를 사용하는 팀이 정합니다. 따라서 결과를 개선할 때 직접 변경할 수 있는 대상은 모델 바깥의 세 설계 층, 곧 프롬프트, 컨텍스트, 하네스(설정)입니다.

문제가 생기면 먼저 원인이 어느 층에 있는지 분류합니다. 표 1-8은 대표적인 증상마다 먼저 점검할 층과 그 층의 점검 항목을 대응시킨 것입니다. 같은 증상이 여러 층에서 생길 수도 있으므로, 표는 점검을 시작할 순서로 읽습니다.

이 분류 가운데 하네스의 기록, 검증, 역할 쪽 행은 작가의 작업에서 나왔습니다. 이 책의 작가는 앞선 책 「생성형 AI, 묻고 확인하고 활용하기」를 AI 에이전트와 함께 만들며 73차례 검수(원고를 읽고 수정할 곳을 찾는 점검)를 거쳤습니다. 초기에는 어휘, 조사, 표 번호처럼 같은 종류의 실수를 사람이 매번 찾았습니다. 큰 결정을 집필 중에 여러 번 뒤집는 일도 있었습니다. 해결은 작업 환경을 보완하는 방식으로 했습니다.

  • 검증: 반복된 실수는 자동 검사 규칙으로 만들었습니다.
  • 기록: 큰 결정은 번호를 매겨 기록하고, 결정을 변경할 때는 이전 결정을 남겼습니다.
  • 역할: 원고 작성과 검수를 서로 다른 에이전트에게 나눠 맡겼습니다.

이렇게 보완한 뒤 사람은 판단이 필요한 항목만 검토하는 구조로 작업을 정리했습니다.

이 사례처럼 모델을 교체하지 않아도 남는 일이 있습니다. 모델 성능이 오르면 한 번의 응답 품질은 좋아질 수 있습니다. 그러나 어떤 자료에 접근할지, 어떤 작업을 사람이 승인할지, 무엇을 기록할지는 팀이 정할 일입니다. 컨텍스트에 한해서는 Claude Code의 컨텍스트 엔지니어링 글도 모델이 발전해도 컨텍스트를 한정된 자원으로 다루는 일은 계속 중요하다고 설명합니다.

결과를 개선하려면, 모델을 교체하기 전에 하네스의 설정을 점검합니다. 점검할 대상은 표 1-5에서 하네스의 설계 질문으로 둔 역할, 도구, 권한, 기록, 검증입니다. 곧 무엇을 맡기고(역할), 무엇을 쓰게 하며(도구), 어디까지 허용하고(권한), 무엇을 남기며(기록), 어떻게 확인할지(검증)를 팀이 정했는지 확인합니다.

확인 방법

하네스가 맡는 일은 Claude Code의 명령과 Agent SDK의 실행 결과로 확인합니다. /로 시작하는 명령은 실습 폴더에서 Claude Code를 실행한 뒤 입력창에 입력하는 명령이며, 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다. 표 1-9는 이 장에서 다룬 컨텍스트 구성, 권한 확인, 루프의 종료, 사용량을 확인하는 위치입니다. 표의 종료 사유 행은 Agent SDK(Python, TypeScript 라이브러리)로 루프를 실행한 경우의 결과 메시지이므로, Claude Code만 사용한다면 그 행은 건너뛰어도 됩니다.

원칙과 점검 질문

에이전트의 결과가 기대와 다르면, 모델을 교체하기 전에 하네스의 설정을 먼저 점검합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트에서 제품이 맡는 실행 장치와 팀이 정하는 설정을 구분할 수 있습니까?
  2. 맡긴 작업에 턴 상한과 비용 상한을 둘 수 있다면, 그 값과 상한에 도달했을 때의 처리가 정해져 있습니까?
  3. 최근 겪은 문제를 표 1-8의 증상에 대응하면, 원인은 프롬프트, 컨텍스트, 하네스 가운데 어느 층에 있습니까?
