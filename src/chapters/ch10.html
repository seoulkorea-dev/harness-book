Chapter 10 제품 단위 비교: Codex와 Claude Code의 하네스

제품 선택을 정하는 것은 어느 제품의 모델이 우수한지가 아니라, 조직이 운영하려는 하네스를 각 제품이 어떤 방식으로 구현하는지입니다.

Codex와 Claude Code는 모두 규칙 문서, 권한, 격리, 설정 파일로 하네스(Harness)를 구현합니다. 그러나 같은 정책도 이 네 곳의 설정 위치와 형식이 제품마다 다르고, 기본으로 켜진 것과 직접 설정해야 하는 것도 다릅니다. 그래서 모델 성능만으로 제품을 선택하면, 한 제품에서 금지한 push가 다른 제품에서는 확인 요청으로 넘어가는 것처럼 정책이 설정에 반영되지 않은 것을 운영 중에 발견합니다. 따라서 제품은 정책이 적히는 곳을 기준으로 비교해야 합니다. 이 장에서는 Chapter 9의 권한 규칙(Permission Rule)과 격리를 두 제품이 어떻게 구현하는지 비교하고, 선택 기준을 정한 뒤, 같은 정책을 두 제품의 설정으로 옮겨 봅니다.

  • 정책은 규칙 문서, 권한, 격리, 설정 파일에 나뉘어 적히므로, 제품은 이 네 기준으로 비교합니다.
  • Claude Code는 도구별 규칙에서, Codex는 운영 체제 수준 격리에서 출발하므로, 정책을 옮길 때 추가로 설정할 것이 다릅니다.
  • 같은 정책도 제품마다 금지와 확인 요청이 다르게 갈리므로, 설정한 뒤 금지한 동작이 거부되는지 확인합니다.

비교 기준

조직의 정책 하나는 여러 곳에 나뉘어 적힙니다. 에이전트(Agent)가 읽고 따를 지시는 규칙 문서에, 반드시 지킬 규칙은 권한과 격리에 적히고, 그 값은 설정 파일에 저장됩니다(Chapter 2의 지시와 강제). 두 제품은 이 네 곳의 구현이 서로 다릅니다. 그래서 이 책은 제품의 비교 기준을 규칙 문서, 권한, 격리, 설정 파일의 네 가지로 정리합니다. 이 기준은 Chapter 2의 다섯 구성 요소(역할, 도구, 권한, 기록, 검증)와 달리, 정책이 제품의 어디에 적히는지에 따른 정리입니다. 그림 10-1은 정책 하나가 네 기준으로 나뉘고, 기준마다 두 제품의 구현이 다른 구조를 보여 줍니다. 그림에서 제품 A는 Claude Code, 제품 B는 Codex입니다.

표 10-1은 그림 10-1의 구성 요소를 제품의 실제 이름으로 설명합니다. 비교는 Claude Code 문서는 2026년 10월 20일, Codex 문서는 2026년 10월 4일에 확인한 공식 문서 기준입니다. 두 제품 모두 기능이 자주 갱신되므로, 도입을 결정하기 전에 최신 문서를 다시 확인해야 합니다.

규칙 문서 비교

규칙 문서는 에이전트가 읽고 따르는 지시입니다(Chapter 5의 규칙 문서 작성). 그래서 두 제품이 읽는 문서의 이름과 범위가 다르면, 같은 규칙이 한 제품에서만 적용됩니다. 두 제품을 함께 사용하는 조직은 어느 문서가 언제 읽히는지 먼저 확인해야 합니다.

Claude Code는 CLAUDE.md를 세션마다 읽습니다. 문서는 조직, 사용자, 프로젝트, 개인의 네 범위에 둘 수 있어, 회사 공통 규칙과 개인 규칙을 나눠 둘 수 있습니다. 작업 폴더와 그 위 상위 폴더의 문서를 모두 읽고, 서로 덮어쓰지 않고 차례로 이어서 읽습니다. 프로젝트에 CLAUDE.md, .claude/CLAUDE.md, CLAUDE.local.md가 하나도 없고 AGENTS.md만 있으면 AGENTS.md를 읽습니다(Anthropic, 2026a).

Codex는 작업을 시작하기 전에 AGENTS.md를 읽습니다. 전역 범위의 ~/.codex/AGENTS.md부터 저장소 루트, 하위 폴더의 AGENTS.md를 차례로 읽습니다. 같은 폴더에 AGENTS.override.md가 있으면 AGENTS.md 대신 그 파일을 읽습니다(OpenAI, 2026a).

그래서 두 제품을 함께 사용하는 조직은 AGENTS.md를 공통 규칙 문서로 둡니다. Claude Code에 전용 지침이 필요해 CLAUDE.md를 만들면 AGENTS.md는 자동으로 읽히지 않으므로, CLAUDE.md 첫 줄에 @AGENTS.md를 적어 불러오고 그 아래에 전용 지침을 추가합니다(Anthropic, 2026a).

@AGENTS.md

- 검토는 읽기 전용 하위 에이전트에 맡깁니다.
버전 주석 (2026년 10월) Claude Code가 AGENTS.md를 직접 읽는 동작은 v2.1.277 이상에서 지원합니다. 그 이전 버전에서는 CLAUDE.md의 @AGENTS.md 불러오기를 사용합니다(Anthropic, 2026a).

권한과 격리 비교

규칙 문서는 지시이므로, 반드시 지킬 규칙은 제품이 강제해야 합니다(Chapter 2의 지시와 강제). 강제하는 수단은 두 제품 모두 권한과 격리이지만, 무엇을 기본으로 두고 무엇을 추가로 설정하는지가 다릅니다. 이 절은 Claude Code, Codex의 순서로 두 수단을 살펴본 뒤 차이를 정리합니다.

Claude Code: 도구별 규칙과 선택 설정인 샌드박스

Claude Code는 도구별 권한 규칙으로 동작마다 허용, 확인 요청, 금지를 정합니다(Chapter 2의 도구 노출 범위, Chapter 9의 권한 규칙). 어느 규칙에도 일치하지 않는 요청은 권한 모드(Permission Mode)가 처리합니다. 권한 모드는 규칙에 없는 요청을 물어볼지, 허용할지, 거부할지를 정하는 설정이며, 설정값은 default, acceptEdits, plan, auto, dontAsk, bypassPermissions의 여섯 가지입니다(Anthropic, 2026c). default는 파일 수정, 셸 명령, 네트워크 접근 대부분을 실행 전에 묻고, plan은 파일을 읽고 계획만 작성하며 사용자가 승인하기 전에는 수정하지 않습니다. auto는 사용자가 아니라 별도의 분류기 모델이 실행 전에 동작을 검토하며, 명시한 확인 요청 규칙은 auto에서도 묻습니다. bypassPermissions는 확인을 해제합니다(Chapter 9).

규칙이 없어도 Claude Code는 실행한 폴더(작업 폴더) 안에서 동작합니다. 작업 폴더 밖의 파일 수정은 금지가 아니라 승인 대상입니다(Anthropic, 2026b). 샌드박스(Sandbox)는 셸 명령과 그 하위 프로세스의 파일과 네트워크 접근을 운영 체제 수준에서 제한합니다(Chapter 9의 격리와 샌드박스). 샌드박스는 기본으로 꺼져 있고, /sandbox 명령이나 설정 파일의 sandbox.enabled 값으로 켭니다. 켜면 셸 명령이 수정할 수 있는 곳은 작업 폴더와 임시 폴더로 제한되고, 네트워크는 허용한 도메인 목록과 대조됩니다. 허용 목록 밖의 도메인에 연결하는 명령은 샌드박스 안에서 결정을 기다리며, default 모드는 사용자에게 확인을 요청하고 auto 모드는 거부합니다(Anthropic, 2026d).

Codex: 기본 적용되는 샌드박스와 승인 정책

Codex는 승인 정책(Approval Policy)과 샌드박스의 두 계층으로 통제합니다. 승인 정책은 동작 전에 멈추고 확인을 요청하는 시점을 정하며, 동작을 금지하지는 않습니다. 샌드박스 모드는 명령이 접근할 수 있는 범위를 정하며, 읽기 전용(read-only), 작업 공간 수정 허용(workspace-write), 제한 없음(danger-full-access)이 있습니다. 로컬 실행에는 운영 체제 수준 샌드박스가 기본으로 적용되며, 기본값은 네트워크 접근 차단과 작업 공간 안의 수정만 허용입니다. 특정 명령을 금지하려면 규칙 파일에 금지(forbidden) 규칙을 추가합니다(OpenAI, 2026a).

출발점의 차이

권한과 격리의 값은 설정 파일에 저장되며, 설정 파일의 위치와 층위도 두 제품이 다릅니다. Claude Code는 저장소에 두는 프로젝트 설정(.claude/settings.json), 사용자 설정(~/.claude/settings.json), 조직이 배포하는 관리형 설정을 둡니다. 관리형 설정은 조직이 배포하며, 사용자와 프로젝트 설정으로 덮어쓸 수 없습니다(Anthropic, 2026e). Codex는 사용자 설정(~/.codex/config.toml)을 기본으로 하고, 프로젝트의 .codex/ 설정은 사용자가 신뢰한 프로젝트에서만 읽습니다(OpenAI, 2026a).

두 제품의 차이는 출발점에 있습니다. Claude Code는 도구별 규칙에서 출발하고 격리는 추가로 설정하며, Codex는 운영 체제 수준 격리에서 출발하고 금지는 추가로 설정합니다. 그래서 같은 정책을 Claude Code로 옮기면 샌드박스를 켜야 하고, Codex로 옮기면 금지할 명령을 규칙 파일에 적어야 합니다.

버전 주석 (2026년 10월) Claude Code의 시작 권한 모드는 실행 방식에 따라 다르며, 프로젝트의 .claude/settings.json에 지정한 auto와 bypassPermissions는 적용되지 않습니다(Anthropic, 2026c). Codex의 기본 샌드박스와 승인 정책은 프로젝트를 신뢰했는지에 따라 다를 수 있으므로, 도입 시점의 문서에서 확인합니다.

제품 선택 기준

더 좋은 모델을 사용하는 제품을 선택하면 된다는 의견이 있습니다. 그러나 모델은 두 제품 모두 갱신되므로 모델 비교는 시점마다 다시 해야 하고, 운영 중에 반복해서 부딪히는 것은 정책이 설정에 어떻게 구현되는지입니다(이 책의 판단). 그래서 이 책은 선택 기준을, 조직의 정책이 요구하는 것을 제품이 기본 동작으로 갖추는지, 추가로 설정해야 하는지로 정리합니다.

정책을 먼저 적고, 항목마다 네 기준 가운데 어디에 적을지 정한 뒤, 두 제품의 기본 동작과 추가로 설정할 것을 대조합니다. 두 출발점은 둘 중 하나를 선택하는 문제가 아닙니다. 두 제품 모두 격리와 금지를 갖출 수 있으며, 차이는 추가로 설정할 양과 위치입니다. 표 10-2는 정책의 요구별로 확인할 기준과 두 제품의 구현입니다.

CR 정책의 두 제품 설정

정책은 결국 설정 파일에 적히며, 같은 정책도 제품마다 금지와 확인 요청이 다르게 갈릴 수 있습니다. Chapter 3의 경비 정산 시스템 개편 변경 요청(Change Request) CR에서 두 제품의 구현이 갈리는 정책은 두 가지입니다. push는 사람만 실행하고, 웹에서 외부 자료를 읽지 않습니다. 이렇게 정한 이유는 Chapter 9의 표 9-4에 있습니다. 이 절에서는 두 정책을 두 제품의 설정으로 옮깁니다.

Claude Code 설정(.claude/settings.json)

다음은 CR의 설정 파일(Chapter 3의 제품 파일로 옮기기) 가운데 두 정책에 해당하는 금지 규칙과, 이 장에서 추가하는 샌드박스 설정입니다. 설정 전체는 Chapter 9의 표 9-4와 부록 실습에 있습니다.

{
  "permissions": {
    "deny": ["Bash(git push *)", "WebFetch", "WebSearch"]
  },
  "sandbox": {
    "enabled": true
  }
}

Bash(git push *)는 git push로 시작하는 셸 명령을 금지하고, WebFetch와 WebSearch는 웹 도구를 금지합니다. sandbox의 enabled 값은 CR의 예제 파일에는 없고 이 장에서 추가하는 설정입니다. 금지 규칙은 명령 문자열만 대조하므로, git -C . push 같은 다른 형태의 명령과 셸 명령의 네트워크 접근은 샌드박스가 제한합니다(Anthropic, 2026b).

Codex 설정(~/.codex/config.toml)

sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = false

sandbox_mode는 작업 공간 안의 수정만 허용하고, network_access는 샌드박스 안 명령의 네트워크 접근을 차단합니다. approval_policy의 on-request는 샌드박스 밖의 접근이 필요한 명령을 실행하기 전에 확인을 요청하는 정책입니다. push는 원격 저장소에 접속해야 하므로 확인 요청으로 넘어갈 수 있으며, 금지되지는 않습니다(OpenAI, 2026a). CR에서 push는 사람만 실행하므로, 규칙 파일(~/.codex/rules/default.rules)에 금지 규칙을 추가합니다.

prefix_rule(
    pattern = ["git", "push"],
    decision = "forbidden",
)

pattern은 명령의 앞부분을 대조하고, decision의 forbidden은 확인 없이 실행을 거부합니다(OpenAI, 2026a). 두 제품의 예는 설정 층위가 다릅니다. Claude Code의 예는 저장소에 두는 프로젝트 설정이고, Codex의 예는 사용자 설정입니다.

표 10-3은 CR의 두 정책을 두 제품이 어떻게 구현하는지, 설정과 그 결과로 대조한 것입니다.

표 10-3에서 셸 명령의 네트워크 접근은 두 제품 모두 확인 요청이 될 수 있습니다. 확인 요청이 승인되지 않으면 접근은 실행되지 않으므로, 이 정책은 승인자가 거절해야 지켜집니다. 그래서 승인자는 CR에서 외부 접근을 거절한다는 기준을 알고 있어야 합니다(Chapter 9의 승인 지점 설계).

버전 주석 (2026년 10월) Claude Code의 샌드박스는 macOS, Linux, WSL2에서 동작하고 네이티브 Windows에서는 샌드박스 없이 명령을 실행합니다. 설정의 sandbox.failIfUnavailable을 true로 두면 샌드박스를 사용할 수 없을 때 시작을 멈춥니다(Anthropic, 2026d). Codex 문서는 규칙 기능을 실험 단계로 안내합니다.

실패와 막는 장치

CR의 정책을 다른 제품으로 옮길 때 제품의 차이를 확인하지 않으면, 정책이 설정에 반영되지 않습니다. 표 10-4는 실패와 원인, 막는 장치입니다.

확인 방법

같은 정책을 두 제품에 설정한 뒤에는, 제품마다 설정이 읽혔는지와 금지한 동작이 실제로 거부되는지 확인합니다. push와 네트워크 확인은 원격 저장소에 연결되지 않은 연습 폴더(부록 실습)에서 합니다. 표 10-5는 표 10-4의 실패마다 확인할 것과 확인 위치입니다.
