Chapter 10 제품 단위 비교: Codex와 Claude Code의 하네스

제품 선택을 정하는 것은 어느 제품의 모델이 우수한지가 아니라, 조직이 운영하려는 하네스를 각 제품이 어떤 방식으로 구현하는지입니다.

이 장에서는 조직이 허용하고 금지할 동작을 정한 정책을 Codex와 Claude Code에 옮길 때, 두 제품의 하네스(Harness)가 어떻게 다른지 다룹니다. 두 제품은 모두 규칙 문서, 권한, 격리, 설정 파일로 하네스를 구현하지만, 같은 정책도 이 네 곳의 설정 위치와 형식이 제품마다 다르고, 기본으로 켜진 것과 직접 설정해야 하는 것도 다릅니다. 모델 성능만으로 제품을 선택하면, 한 제품에서 금지한 push(확정한 변경을 원격 저장소에 올리는 일)가 다른 제품에서는 확인 요청으로 넘어갈 수 있는 것처럼, 정책이 설정에 반영되지 않은 것을 운영 중에 발견할 수 있습니다. 그래서 제품은 정책이 적히는 곳을 기준으로 비교해야 합니다.

비교 기준은 규칙 문서, 권한, 격리, 설정 파일의 네 가지입니다. 규칙 문서는 에이전트(Agent)가 읽고 따르는 지시를 적는 문서이고, 권한은 동작마다 허용, 확인 요청, 금지 가운데 무엇으로 처리할지 정하는 설정입니다. 격리는 명령이 접근할 수 있는 파일과 네트워크를 에이전트 프로그램 바깥의 운영 체제가 제한하게 하는 일이고, 설정 파일은 권한과 격리의 값을 저장하는 파일입니다. 두 제품 모두 격리 기능을 샌드박스(Sandbox)라고 부릅니다. Chapter 9가 한 제품 안에서 권한 규칙(Permission Rule)과 격리로 위험을 관리했다면, 이 장에서는 그 두 장치를 포함한 네 기준이 두 제품에서 어떻게 구현되는지 비교합니다.

먼저 비교 기준을 살펴보고, 규칙 문서와 권한, 격리를 두 제품에서 비교한 뒤, 제품 선택 기준과 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)의 정책을 두 제품의 설정으로 옮기는 예제를 다룹니다.

  • 정책은 규칙 문서, 권한, 격리, 설정 파일에 나뉘어 적히므로, 제품은 이 네 기준으로 비교합니다.
  • 설정 파일에 아무것도 적지 않으면 Claude Code는 도구 호출마다 실행 여부를 판정하고, Codex는 명령을 운영 체제 수준 격리 안에서 실행합니다. 금지할 명령은 두 제품 모두 직접 적고, Claude Code는 격리도 추가 설정합니다.
  • 같은 정책도 제품마다 금지와 확인 요청이 다르게 갈리므로, 설정한 뒤 금지한 동작이 거부되는지 확인합니다.

비교 기준

조직의 정책 하나는 여러 곳에 나뉘어 적힙니다. 에이전트가 읽고 따를 지시는 규칙 문서(Chapter 5의 규칙 문서의 작성)에, 반드시 지킬 규칙은 권한과 격리(Chapter 9의 격리와 샌드박스)에 적힙니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단이고, 강제는 에이전트의 판단과 관계없이 제품이 적용하는 수단이기 때문입니다(Chapter 2의 다섯 요소가 만드는 흐름). 권한과 격리의 값은 설정 파일(Chapter 3의 설정 파일: 명세서를 어디에 옮기는가)에 저장됩니다. 두 제품은 이 네 곳의 구현이 서로 다릅니다. 그래서 제품의 비교 기준은 규칙 문서, 권한, 격리, 설정 파일의 네 가지로 둡니다. 이 기준은 Chapter 2의 다섯 구성 요소(역할, 도구, 권한, 기록, 검증, Chapter 2의 다섯 요소가 만드는 흐름)와 달리, 정책이 제품의 어디에 적히는지에 따른 정리입니다. 권한과 격리는 한 절에서 함께 비교하고, 설정 파일은 그 절 끝에서 두 제품의 출발점과 함께 정리합니다. 그림 10-1은 정책 하나가 네 기준으로 나뉘고, 기준마다 두 제품의 구현이 다른 구조를 보여 줍니다. 그림에서 제품 A는 Claude Code, 제품 B는 Codex입니다.

표 10-1은 그림 10-1의 구성 요소를 제품의 실제 이름으로 설명합니다. 이 장의 비교는 Claude Code는 2026년 10월 20일, Codex는 2026년 10월 4일에 확인한 공식 문서를 기준으로 합니다. 두 제품 모두 기능이 자주 갱신되므로, 도입을 결정하기 전에 최신 문서를 다시 확인해야 합니다.

규칙 문서 비교

규칙 문서는 에이전트가 세션마다 읽고 따르는 지시이고, 제품마다 읽는 문서의 이름과 위치가 정해져 있습니다. 그래서 두 제품이 읽는 문서의 이름과 범위가 다르면, 같은 규칙이 한 제품에서만 적용됩니다. 두 제품을 함께 사용하는 조직은 어느 문서가 언제 읽히는지 먼저 확인해야 합니다.

Claude Code 문서는 Claude Code가 CLAUDE.md를 세션마다 읽는다고 설명합니다. CLAUDE.md는 조직(조직이 배포), 사용자(~/.claude/CLAUDE.md), 프로젝트(저장소의 CLAUDE.md), 개인(CLAUDE.local.md)의 네 범위에 둘 수 있어, 조직 공통 규칙과 개인 규칙을 나눠 적을 수 있습니다. ~는 사용자의 홈 폴더입니다. 작업 폴더(Claude Code를 실행한 폴더)와 그 위 폴더의 문서를 모두 읽고, 서로 덮어쓰지 않고 차례로 이어서 읽습니다. 작업 폴더나 그 위 폴더에 CLAUDE.md, .claude/CLAUDE.md, CLAUDE.local.md가 하나도 없고(사용자의 ~/.claude/CLAUDE.md와 조직 문서는 세지 않음) AGENTS.md만 있으면 AGENTS.md를 읽습니다.

Codex 문서는 Codex가 작업을 시작하기 전에 AGENTS.md를 읽는다고 설명합니다. 전역 범위의 ~/.codex/AGENTS.md부터 저장소 루트, 하위 폴더의 AGENTS.md를 차례로 읽습니다. 같은 폴더에 AGENTS.override.md가 있으면 AGENTS.md 대신 그 파일을 읽으며, 이 장의 예에서는 사용하지 않습니다.

그래서 두 제품을 함께 사용하는 조직은 AGENTS.md를 공통 규칙 문서로 둡니다. Claude Code에 전용 지침이 필요해 CLAUDE.md를 만들면 기본 설정에서는 AGENTS.md가 자동으로 읽히지 않으므로, CLAUDE.md 첫 줄에 @AGENTS.md를 적어 불러오고 그 아래에 전용 지침을 추가합니다. 다음은 CLAUDE.md의 예시이며, 실습 파일에는 없습니다. 첫 줄의 @AGENTS.md는 AGENTS.md의 내용을 그 자리에 불러오고, ## 줄은 아래 전용 지침의 제목입니다.

@AGENTS.md

## Claude Code 전용
- 검토는 읽기 전용 하위 에이전트에 맡깁니다.
버전 주석 (2026년 10월) Claude Code가 AGENTS.md를 직접 읽는 동작은 v2.1.277 이상에서 지원하며, Amazon Bedrock(Amazon의 클라우드에서 모델을 사용하는 서비스)을 거치거나 사용 정보 전송(텔레메트리)을 끈 세션은 v2.1.281 이상에서 지원합니다. 그 밖의 경우에는 CLAUDE.md의 @AGENTS.md 불러오기를 사용합니다.

권한과 격리 비교

규칙 문서는 지시이므로, 반드시 지킬 규칙은 에이전트의 판단과 관계없이 제품이 적용하는 강제 수단에 둡니다. 강제하는 수단은 두 제품 모두 권한과 격리이지만, 무엇을 기본으로 두고 무엇을 추가 설정하는지가 다릅니다. 이 절은 Claude Code, Codex의 순서로 두 수단을 살펴본 뒤, 설정 파일의 위치와 두 제품의 출발점 차이를 정리합니다.

Claude Code: 도구별 권한 규칙과 추가로 켜는 샌드박스

Claude Code는 도구별 권한 규칙으로 동작마다 허용, 확인 요청, 금지를 정합니다(Chapter 9의 권한 규칙). 어느 규칙에도 일치하지 않는 요청은 권한 모드(Permission Mode)가 처리합니다. 권한 모드는 도구 호출을 승인하는 방식을 정하는 설정으로, 규칙에 없는 요청을 물을지, 허용할지, 거부할지가 모드에 따라 달라집니다. Claude Code 문서는 권한 모드의 설정 값 여섯 가지를 다음과 같이 설명합니다.

  • default: 사람에게 묻는 수동 모드로, 파일 수정, 셸 명령, 네트워크 접근 대부분을 실행 전에 묻습니다.
  • acceptEdits: 작업 폴더 안의 파일 수정은 묻지 않고, 그 밖은 묻습니다.
  • plan: 파일을 읽고 계획만 작성하며, 사용자가 계획을 승인하기 전에는 수정하지 않습니다.
  • auto: 사용자가 아니라 별도의 분류기 모델(동작이 요청 범위를 넘거나, 알 수 없는 외부 시스템에 닿거나, 읽은 내용에 심긴 지시를 따르는지 판정하는 모델)이 실행 전에 동작을 검토합니다. 명시한 확인 요청 규칙은 이 모드에서도 묻습니다.
  • dontAsk: 물어야 할 동작은 모두 거부합니다.
  • bypassPermissions: 확인을 해제하며, 컨테이너나 가상 머신처럼 따로 막아 둔 격리된 실행 환경에서만 사용합니다(Chapter 9의 격리와 샌드박스).

세션을 시작할 때의 권한 모드(시작 모드)는 실행 방식에 따라 다르며, 대화형 터미널과 VS Code 확장은 auto로 시작할 수 있습니다. 이 장의 동작을 수동 모드로 확인하려면 claude --permission-mode default로 시작합니다.

버전 주석 (2026년 10월) 시작 모드는 실행 방식과 버전에 따라 다릅니다. v2.1.283 이상의 터미널과 VS Code 확장은 auto로 시작하고, claude -p와 Agent SDK는 default로 시작합니다. 프로젝트의 .claude/settings.json과 .claude/settings.local.json에 지정한 auto와 bypassPermissions는 적용되지 않고, 사용자 설정에 지정하면 적용됩니다. auto 모드를 사용할 수 없게 한 환경은 default로 시작합니다.

규칙을 적지 않아도 작업 폴더 밖의 파일 수정에는 권한 모드가 적용됩니다. 파일 도구로 작업 폴더 밖을 수정하는 요청은 default와 acceptEdits 모드에서 확인 요청이 되고, auto 모드에서는 분류기가 판단하며, dontAsk 모드에서는 거부됩니다. 셸 명령이 실행한 스크립트는 파일 도구의 규칙을 거치지 않고 파일을 열 수 있으므로, 셸 명령까지 제한하려면 샌드박스가 필요합니다. 샌드박스는 셸 명령과 그 하위 프로세스(명령이 실행시키는 다른 프로그램)의 파일과 네트워크 접근을 운영 체제 수준에서 제한합니다.

Claude Code 문서는 샌드박스가 기본으로 꺼져 있고, /sandbox 명령이나 설정 파일의 sandbox.enabled 값으로 켠다고 설명합니다. 켜면 셸 명령이 수정할 수 있는 곳은 작업 폴더와 임시 폴더로 제한되고, 네트워크 접속은 허용 도메인, 곧 접속을 허락한 주소(example.com 같은 도메인)의 목록과 대조됩니다. 대화형 터미널에서 목록 밖의 도메인에 연결하는 명령은 연결하지 않고 멈추며, default 모드는 승인자에게 확인을 요청하고 auto 모드는 거부합니다. auto 모드에서도 명령 문자열에 접속할 도메인이 적혀 있고 분류기가 그 접속을 승인하면, 그 명령에 한해 연결됩니다.

Codex: 기본 적용되는 샌드박스와 승인 정책

Codex 문서(2026년 10월 4일 확인)에 따르면 Codex는 승인 정책(Approval Policy)과 샌드박스의 두 계층으로 통제합니다. 승인 정책은 동작 전에 멈추고 확인을 요청하는 시점을 정하며, 금지는 규칙 파일에 실행 거부(forbidden)로 적은 규칙이 맡습니다. 규칙 파일은 지시인 규칙 문서와 달리, 명령의 실행을 제품이 강제하는 파일입니다.

샌드박스 모드는 명령이 접근할 수 있는 범위를 정하며, 읽기 전용(read-only), 작업 공간 수정 허용(workspace-write), 제한 없음(danger-full-access)이 있습니다. 작업 공간은 Codex가 작업하는 폴더로, 이 장의 작업 폴더에 해당합니다. Codex를 사용자의 컴퓨터에서 실행하는 로컬 실행에는 운영 체제 수준 샌드박스가 기본으로 적용됩니다. 사용자가 신뢰한다고 표시한 프로젝트(신뢰한 프로젝트)의 기본값은 네트워크 접근 차단과 작업 폴더 안의 수정만 허용입니다.

설정 파일의 위치와 두 제품의 출발점

권한과 격리의 값은 설정 파일에 저장되며, 설정 파일의 위치도 두 제품이 다릅니다. Claude Code는 저장소에 두는 프로젝트 설정(.claude/settings.json), 사용자 설정(~/.claude/settings.json), 관리형 설정을 둡니다. 관리형 설정은 조직이 배포하는 설정으로, 사용자와 프로젝트 설정으로 덮어쓸 수 없어 조직의 정책을 사용자가 변경하지 못하게 합니다(일부 보안 설정은 하위 설정의 더 엄격한 값이 적용됨). Codex는 사용자 설정(~/.codex/config.toml)을 기본으로 하고, 프로젝트의 .codex/ 설정은 사용자가 신뢰한다고 표시한 프로젝트에서만 읽습니다.

두 제품의 차이는 출발점, 곧 설정 파일에 아무것도 적지 않았을 때 제품이 동작을 통제하는 방식에 있습니다. Claude Code는 도구 호출마다 권한 모드로 실행 여부를 판정하고, Codex는 명령을 운영 체제 수준 샌드박스 안에서 실행합니다. Claude Code는 도구별 규칙에서 출발하고 격리는 추가 설정하며, Codex는 운영 체제 수준 격리에서 출발하고 명령별 금지는 별도의 규칙 파일에 둡니다. 그래서 같은 정책을 옮길 때 금지할 명령은 두 제품 모두 각자의 형식(금지 규칙, 규칙 파일)으로 적어야 하고, Claude Code에서는 샌드박스도 켜야 합니다.

버전 주석 (2026년 10월) Codex의 기본 샌드박스와 승인 정책은 프로젝트를 신뢰했는지에 따라 다를 수 있으므로, 도입 시점의 문서에서 확인합니다.

제품 선택 기준

두 제품의 출발점이 다르다면, 무엇으로 선택할지가 남습니다. 선택 기준은 조직의 정책이 요구하는 것을 제품이 기본 동작으로 갖추는지, 추가 설정해야 하는지입니다. 기본 동작은 설정 파일에 아무것도 적지 않아도 제품이 하는 동작이며, 금지 규칙처럼 직접 적어야 하는 것은 모두 추가 설정입니다. 비교는 다음 순서로 합니다.

  1. 조직의 정책을 항목으로 적습니다.
  2. 항목마다 네 기준 가운데 어디에 적을지 정합니다.
  3. 표 10-2에서 항목마다 두 제품의 기본 동작과 추가 설정을 대조하고, 제품별로 추가 설정이 몇 건이며 어느 기준에 몰리는지 비교합니다.

표 10-2로 대조하면, 특정 명령의 금지는 두 제품 모두 추가 설정이고, 모든 셸 명령의 격리는 Claude Code에서만 추가 설정입니다. 두 출발점의 차이는 옳고 그름보다, 추가 설정할 양과 위치에 있습니다. 추가 설정이 적은 제품은 정책을 옮길 때 누락할 설정이 적고, 추가 설정이 몰린 기준은 뒤의 확인 방법 절에서 확인 항목을 늘려 점검합니다.

모델 성능도 선택에 영향을 줍니다. 그러나 모델은 두 제품 모두 갱신되므로 모델 비교는 시점마다 다시 해야 하고, 운영 중에 반복해서 확인할 대상은 정책이 설정에 어떻게 구현되는지입니다.

예제: 변경 요청 사항의 정책을 두 제품에 설정하기

선택 기준을 정했으면 같은 정책을 두 제품의 설정으로 옮깁니다. 정책은 설정 파일에 적히며, 같은 정책도 제품마다 금지와 확인 요청이 다르게 갈릴 수 있습니다. 변경 요청 사항에서 두 제품의 구현이 갈리는 정책은 두 가지입니다. 웹 도구 금지는 Claude Code의 금지 규칙으로 다루고, Codex에서는 같은 정책을 셸 명령의 네트워크 차단으로 비교합니다. push는 사람만 실행하고, 외부 자료를 읽지 않습니다. 원격 저장소에 반영하는 일은 다른 사람에게 보이는 동작이고, 작업은 저장소 안의 자료만으로 하기 때문입니다(Chapter 9의 예제: 변경 요청 사항의 위험 관리).

Claude Code 설정(.claude/settings.json)

다음 상자는 변경 요청 사항의 설정 파일 가운데 두 정책에 해당하는 금지 규칙과, 이 장에서 추가하는 샌드박스 설정을 발췌한 것입니다. deny 세 항목은 부록의 실습 3. 권한 설정에서 만든 .claude/settings.json에 이미 있으므로 다시 적지 않습니다. 샌드박스 설정은 텍스트 편집기로 이 파일을 열어 permissions 블록을 닫는 중괄호 뒤에 쉼표를 찍고 "sandbox": { "enabled": true }를 더합니다. 에이전트에게는 .claude/의 수정이 금지되어 있으므로 사람이 직접 편집합니다. 저장한 뒤 Claude Code를 새로 시작하고, /permissions에 금지 규칙이 그대로 보이면 파일 형식에 오류가 없는 것입니다.

{
  "permissions": {
    "deny": ["Bash(git push *)", "WebFetch", "WebSearch"]
  },
  "sandbox": {
    "enabled": true
  }
}

Bash(git push *)는 git push로 시작하는 셸 명령을 금지하고, WebFetch와 WebSearch는 웹 도구를 금지합니다. sandbox의 enabled 값 true는 셸 명령에 샌드박스를 켭니다. Bash 금지 규칙은 명령 문자열만 대조하므로 폴더를 지정하는 옵션이 들어간 git -C . push 같은 다른 형태의 명령과 일치하지 않습니다. 샌드박스를 켜면 이런 명령도 원격 저장소에 접속할 때 허용 도메인과 대조되므로, 원격 저장소의 도메인이 목록에 없으면 확인 요청이 되거나(default 모드) 차단됩니다(auto 모드). 원격 저장소의 도메인을 허용 도메인에 두면 push는 제한되지 않습니다.

Codex 설정(~/.codex/config.toml)

다음은 셸 명령의 네트워크 접근을 막는 설정을 Codex의 사용자 설정에 적은 것입니다. 샌드박스 모드와 네트워크 차단은 로컬 실행의 기본값과 같지만, 기본값이 변경되어도 같은 값이 적용되도록 직접 적습니다. 사용자 설정은 그 사용자의 모든 프로젝트에 적용되며, 프로젝트의 .codex/ 설정은 신뢰한 프로젝트에서만 읽히므로 이 예에서는 사용자 설정에 둡니다. config.toml에서 [sandbox_workspace_write]처럼 대괄호로 묶은 줄은 그 아래 키를 묶는 표의 이름이고, 첫 표 이름보다 위에 적은 키는 파일 전체에 적용됩니다. 그래서 ~/.codex/config.toml이 이미 있으면 맨 위 두 줄은 파일의 첫 표 이름 줄보다 위에 더하고, 없으면 새로 만듭니다. [sandbox_workspace_write]가 이미 있으면 표 이름은 더하지 않고 그 아래에 network_access = false만 적습니다. Windows에서는 %USERPROFILE%\.codex 폴더입니다.

sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = false

sandbox_mode는 작업 폴더 안의 수정만 허용하고, network_access는 샌드박스 안 명령의 네트워크 접근을 차단합니다. approval_policy의 on-request는 샌드박스 밖의 접근이 필요한 명령을 실행하기 전에 확인을 요청하는 정책으로, 샌드박스 안에서 끝나지 않는 동작을 승인자가 판단하게 하려고 둡니다. push는 원격 저장소에 접속해야 하므로 확인 요청으로 넘어갈 수 있으며, 금지되지는 않습니다. 이 조합의 실제 동작은 도입 시점의 문서와 뒤의 확인 방법 절의 push 확인으로 점검합니다. 변경 요청 사항에서 push는 사람만 실행하므로, 규칙 파일(~/.codex/rules/default.rules)에 금지 규칙을 추가합니다.

prefix_rule(
    pattern = ["git", "push"],
    decision = "forbidden",
)

pattern은 명령의 앞부분을 대조하고, decision의 forbidden은 확인 없이 실행을 거부합니다.

두 제품의 예는 설정 층위가 다릅니다. Claude Code의 예는 저장소에 두는 프로젝트 설정이고, Codex의 예는 사용자 설정입니다. 표 10-3은 변경 요청 사항의 두 정책을 두 제품이 어떻게 구현하는지 설정과 결과로 대조한 것입니다. 결과는 세 가지로 적습니다. 금지는 규칙이 실행을 거부하는 것, 차단은 샌드박스가 접근을 막는 것, 확인 요청은 승인자의 응답에 따라 실행 여부가 정해지는 것입니다.

표 10-3에서 셸 명령의 네트워크 접근은 두 제품 모두 확인 요청이 될 수 있고, Claude Code의 auto 모드에서는 명령에 적힌 도메인을 분류기가 승인하면 연결될 수 있습니다. 확인 요청이 승인되지 않으면 접근은 실행되지 않으므로, 이 정책은 확인 요청을 승인하거나 거절하는 승인자가 거절해야 지켜집니다. 그래서 승인자는 변경 요청 사항에서 외부 자료 접근을 거절한다는 기준을 알고 있어야 합니다(Chapter 9의 승인 지점 설계).

버전 주석 (2026년 10월) Claude Code의 샌드박스는 macOS, Linux, WSL2(Windows 안에서 Linux를 실행하는 기능의 2판)에서 동작하고, Linux와 WSL2에서는 샌드박스를 만드는 bubblewrap과 네트워크 연결을 중계하는 socat을 설치해야 합니다. 네이티브 Windows에서는 샌드박스 없이 명령을 실행합니다. 설정의 sandbox.failIfUnavailable을 true로 두면 샌드박스를 사용할 수 없을 때 시작을 멈춥니다. Codex 문서는 규칙 기능을 실험 단계로 안내합니다(2026년 10월 4일 확인).

실패를 예방하는 장치

변경 요청 사항의 정책을 다른 제품으로 옮길 때 제품의 차이를 확인하지 않으면, 정책의 일부가 설정에 반영되지 않을 수 있습니다. 표 10-4는 실패 유형과 원인, 방지 장치를 정리합니다.

설정과 결과의 확인 방법

같은 정책을 두 제품에 설정한 뒤에는, 제품마다 설정이 읽혔는지와 금지한 동작이 실제로 거부되는지 확인합니다. 확인은 에이전트에게 해당 동작을 해 달라고 대화로 요청하는 방식이며, push와 네트워크 확인은 원격 저장소에 연결되지 않은 실습 폴더(부록 실습 1에서 만든 expense-practice)에서 합니다. 네트워크 확인은 claude --permission-mode default로 시작한 대화형 터미널에서 합니다. auto 모드에서는 명령에 적힌 도메인을 분류기가 승인하면 연결될 수 있기 때문입니다.

확인 시점은 이 장의 설정을 적용한 뒤입니다. 행 2는 샌드박스 설정을 더하기 전에도 한 번 요청해, 설정 전에는 파일 생성이 성공하고(만든 파일은 rm ~/sandbox-probe로 지움) 설정 뒤에는 실패하는지 확인합니다. Claude Code 행은 부록 실습 3을 마친 폴더에 샌드박스 설정을 더하고 Claude Code를 새로 시작한 뒤 확인합니다. Codex 행은 Codex를 설치해 사용하는 경우에만 하고, 설치하지 않았다면 config.toml과 규칙 파일의 내용이 예제 절의 Codex 설정 상자와 같은지 읽어 확인하는 것으로 대신합니다(동작 확인은 아님). 네이티브 Windows(Git Bash, PowerShell)는 샌드박스를 지원하지 않으므로 행 2와 5를 건너뛰거나 WSL2에서 확인합니다. 행 2와 5의 명령은 입력창에서 명령 앞에 !를 입력해 직접 실행하면 샌드박스 밖에서 실행될 수 있으므로 에이전트에게 실행을 요청합니다. 파일이 만들어졌으면 rm ~/sandbox-probe로 지우고, 샌드박스 밖에서 다시 실행할지 물으면 거절합니다. 표 10-5는 확인 항목마다 확인 방법과 확인 기준을 보여 주며, 행의 번호는 표 10-4의 실패 번호와 일치합니다.

설계 원칙과 점검 질문

제품은 모델 성능이 아니라, 조직이 운영하려는 하네스를 구성 요소마다 어떻게 구현하는지로 비교합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 조직의 정책 항목마다 두 제품의 기본 동작과 추가 설정할 것을 구분했습니까?
  2. 같은 정책을 두 제품에 설정했을 때, 금지와 확인 요청이 같은 동작에 적용됩니까?
  3. 비교에 사용한 문서의 확인 날짜는 언제이며, 도입 시점의 문서와 같습니까?
