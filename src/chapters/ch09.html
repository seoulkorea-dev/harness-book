Chapter 9 위험 관리: 승인, 격리, 비용

사고의 크기를 정하는 것은 에이전트의 판단력이 아니라, 에이전트에 허용한 권한의 범위와 승인 지점의 위치입니다.

이 장에서는 에이전트(Agent)에 허용한 권한 안에서 생기는 사고의 크기를 줄이는 위험 관리를 다룹니다. 에이전트는 허용된 권한 안에서 파일을 수정하고 명령을 실행하는데, 그 권한 안에는 되돌리기 어려운 동작도 있고, 금지한 동작이 다른 형태의 명령으로 실행될 수도 있습니다. 권한을 넓게 열어 두면 한 번의 잘못된 판단이 원본 자료의 손상, 외부 발송, 예상하지 못한 지출로 이어질 수 있습니다. 그래서 에이전트에 허용할 범위를 미리 정해야 합니다.

위험 관리는 세 가지입니다. 되돌리기 어려운 동작에 사람의 확인을 두는 승인, 에이전트가 실행한 명령이 접근할 수 있는 파일과 네트워크를 에이전트 프로그램 바깥의 운영 체제가 제한하게 하는 격리, 토큰(Token, 모델이 텍스트를 나누어 처리하는 단위) 사용량과 지출의 범위를 정하는 비용입니다. Chapter 2는 하네스(Harness)에 두는 권한 규칙(Permission Rule)의 종류와 평가 순서를, Chapter 3은 되돌리기 어려운 동작에서 사람이 개입하는 자리인 승인 지점을, 맡길 업무의 값을 정리한 에이전트 명세서의 한 항목으로 정했습니다. 이 장에서는 그 규칙을 동작의 위험에 따라 어디에 두고, 규칙으로 막을 수 없는 경로와 지출의 범위를 무엇으로 정할지를 다룹니다.

먼저 위험 관리의 세 가지를 살펴보고, 승인 지점 설계와 권한 규칙, 격리와 샌드박스(Sandbox), 비용 관리를 익힌 뒤, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)의 위험 관리 예제를 다룹니다.

  • 사고는 동작의 실행, 접근 범위, 지출의 세 경로로 생기며, 승인, 격리, 비용으로 관리합니다.
  • 승인 지점은 되돌리기 어려운 동작에만 두고, 사람이 판단해 진행할 동작은 확인 요청, 사람이 직접 할 동작은 금지로 둡니다.
  • 명령에 거는 권한 규칙은 명령 문자열만 대조하므로, 에이전트가 실행한 명령의 파일과 네트워크 접근은 격리로 보완합니다.
  • 지출은 작업 단위, 읽힐 자료, 지출 한도로 범위를 정하고, 한도에 이르면 사람이 계속 여부를 정합니다.

위험 관리의 세 가지

허용된 권한 안에서도 사고는 세 경로로 생깁니다. 에이전트가 원본 파일을 덮어쓰거나 메시지를 외부로 보내는 것처럼 동작 자체가 사고가 되는 경로, 작업과 관계없는 파일이나 네트워크에 접근하는 경로, 같은 작업을 반복해 지출이 커지는 경로입니다. 그래서 위험 관리는 승인, 격리, 비용의 세 가지로 나눕니다. 세 방법은 모두 에이전트에 허용할 범위를 정하는 일이며, 각각 동작, 접근, 지출의 범위를 정합니다. 격리는 에이전트가 실행한 명령이 정한 범위 밖의 파일과 네트워크에 닿지 못하게, 에이전트 프로그램 바깥의 운영 체제가 막는 일입니다. 격리의 수단은 Claude Code가 셸(명령을 입력해 실행하는 프로그램) 명령에 거는 샌드박스와, 에이전트 전체를 따로 막아 둔 공간에서 실행하는 격리된 실행 환경입니다. 표 9-1은 방법마다 통제 대상과 통제 수단을 보여 줍니다.

승인 지점 설계

되돌리기 어려운 동작은 실행하기 전에 사람이 확인해야 합니다. 그러나 모든 동작에 확인을 두면 확인할 요청이 많아져, 사람이 내용을 보지 않고 승인할 수 있습니다. 그래서 승인 지점은 되돌리기 어려운 동작에만 둡니다. 승인 지점은 되돌리기 어려운 동작에서 사람이 개입하는 자리이며, Chapter 3의 에이전트 명세서의 아홉 항목 가운데 하나입니다. 그 자리에서 승인하거나 거절하는 사람은 Chapter 6에서 본 승인자, 곧 되돌리기 어려운 동작과 작업 단위의 완료를 승인하는 사람입니다. 확인 요청이 오면 Claude Code의 대화 화면에 실행할 동작이 표시되고, 승인자가 승인하거나 거절합니다.

어떤 동작이 되돌리기 어려운지에 대해서는 Anthropic의 프롬프트 작성 문서가 Claude Opus 4.6을 대상으로 한 안내에서 예를 제시합니다. 문서는 에이전트가 다음 세 종류의 동작을 하기 전에 사용자에게 확인하도록 프롬프트에 지시하는 예를 들고, 파일 수정이나 테스트 실행처럼 되돌릴 수 있는 로컬 동작(사용자의 컴퓨터 안에서 끝나는 동작)은 그대로 하도록 권합니다. 아래 목록의 commit은 변경을 확정해 저장소의 이력에 남기는 일이고, push는 확정한 변경을 여러 사람이 함께 사용하는 원격 저장소에 올리는 일입니다.

  • 파괴적인 동작: 파일이나 브랜치(같은 저장소 안에서 갈라 진행하는 변경 이력의 갈래) 삭제, 데이터베이스 테이블 삭제
  • 이력을 되돌리기 어려운 동작: 원격 저장소의 이력을 덮어쓰는 강제 push, 이미 공유한 commit의 수정
  • 다른 사람에게 보이는 동작: 코드 push, 이슈나 풀 리퀘스트(코드 변경을 반영하기 전에 검토를 요청하는 단위)에 댓글 작성, 메시지 발송, 여러 사람이 함께 사용하는 서버와 설정의 변경

문서는 이 확인을 프롬프트로 지시하지만, 되돌리기 어려운 동작은 규칙으로 강제해야 에이전트의 판단과 관계없이 지켜집니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단이고, 강제는 에이전트의 판단과 관계없이 제품이 적용하는 수단이기 때문입니다(Chapter 2의 지시 기반 규칙과 강제 적용).

규칙으로 옮긴 승인 지점은 확인 요청과 금지의 두 가지로 둡니다. 확인 요청은 사람이 그 자리에서 내용을 보고 진행 시점을 정할 동작에 둡니다. 예를 들어 commit은 반영 시점을 사람이 정합니다. 금지는 다른 사람에게 보이거나 되돌리기 어렵고 에이전트가 시도할 이유가 없어, 사람이 직접 할 동작에 둡니다. 예를 들어 push는 사람만 실행합니다(Chapter 2의 예제: 변경 요청 사항의 하네스 구성 정하기).

승인 지점을 되돌리기 어려운 동작에만 두는 것은 에이전트에 맡기는 일을 줄이려는 것이 아닙니다. 검사 실행처럼 되돌릴 수 있는 동작은 허용 규칙에 두어 승인 없이 진행하므로, 사람은 되돌리기 어려운 동작의 확인에 집중할 수 있습니다.

권한 규칙

앞 절에서 나눈 확인 요청과 금지는 권한 규칙으로 옮깁니다. Claude Code 문서는 권한 규칙을 모델이 아니라 Claude Code가 강제한다고 설명합니다. 권한 규칙은 금지(deny), 확인 요청(ask), 허용(allow)의 세 종류이고, 같은 요청에 여러 규칙이 일치하면 금지, 확인 요청, 허용의 순서로 먼저 일치한 규칙을 따릅니다(Chapter 2의 도구 사용 범위와 제약). 규칙에 없는 요청은 권한 모드(Permission Mode)가 처리합니다. 권한 모드는 도구 호출을 승인하는 방식을 정하는 설정이며, 규칙에 없는 요청을 사람에게 물을지, 자동으로 승인할지, 거부할지가 모드에 따라 달라집니다(Chapter 10의 권한과 격리 비교).

규칙은 앞 절의 기준에 따라 배치합니다. 되돌릴 수 있는 동작은 허용, 되돌리기 어렵고 사람이 판단해 진행할 동작은 확인 요청, 되돌리기 어렵고 사람이 직접 할 동작은 금지로 둡니다. 규칙은 도구 이름 뒤 괄호에 대상을 적고, 명령의 *는 아무 문자열과, 경로의 **는 하위 폴더를 포함한 모든 파일과 일치합니다. 예를 들어 Bash(git push *)는 git push로 시작하는 명령을, Edit(./data/**)는 data 폴더 아래 모든 파일의 수정을 가리킵니다.

넓은 금지 규칙은 더 좁은 허용 규칙이 있어도 그 명령을 막습니다. 예를 들어 Bash(git push *)를 금지하면, 원격 저장소 origin의 main 브랜치로 올리는 Bash(git push origin main)를 허용해도 그 명령은 실행되지 않습니다. 규칙이 구체적이어도 평가 순서는 변경되지 않기 때문입니다. 문서는 이 원리를 다른 명령의 예로 설명하며, git 예는 그 원리를 이 장의 예제에 적용한 것입니다. 그러나 셸 명령의 규칙에는 한계가 있어, 다음 절의 격리로 보완합니다.

격리와 샌드박스

권한 규칙 가운데 셸 명령에 대한 Bash 규칙은 에이전트가 작성한 명령의 문자열과 일치하는지만 확인합니다. 예를 들어 git -C . push는 같은 push를 다른 형태로 작성한 명령이지만, 규칙은 글자만 대조하므로 git push 금지 규칙과 일치하지 않습니다. Claude Code 문서는 Bash 규칙이 에이전트가 흔히 작성하는 형태의 명령을 막을 뿐, 그 프로그램의 모든 실행을 막는 보안 장치는 아니라고 설명합니다. 파일 수정 금지 규칙도 파일 편집 도구와 Claude Code가 인식하는 셸 파일 명령(cat, sed, tee 등)에만 적용되고, 에이전트가 만든 스크립트가 파일을 여는 식의 간접 수정에는 적용되지 않습니다.

그래서 앞에서 정의한 격리가 필요합니다. 운영 체제 수준에서 제한한다는 것은 에이전트 프로그램이 명령의 글자를 검사하는 대신, 컴퓨터의 운영 체제가 파일과 네트워크 접근 자체를 막는다는 뜻입니다. 샌드박스는 셸 명령과 그 하위 프로세스(명령이 실행시키는 다른 프로그램)가 접근할 수 있는 파일과 네트워크를 이렇게 제한합니다.

권한 규칙과 샌드박스는 맡는 범위가 다릅니다. 파일 편집 도구는 샌드박스 밖에서 실행되므로, 파일 도구와 Claude Code가 인식하는 셸 파일 명령은 금지 규칙이, 스크립트 같은 하위 프로세스는 샌드박스가 맡습니다. 샌드박스가 기본으로 파일 수정을 허용하는 범위에는 Claude Code를 시작한 작업 폴더가 들어 있어, 작업 폴더 안의 원본 자료는 샌드박스를 켜는 것만으로는 보호되지 않습니다. 파일 수정 금지 규칙의 경로는 샌드박스 설정에 합쳐지므로, 샌드박스를 켜면 금지 규칙을 둔 경로는 스크립트도 수정할 수 없습니다.

프롬프트 주입(Prompt Injection)은 에이전트가 읽은 내용에 심긴 지시로 모델이 의도하지 않은 동작을 하게 만드는 공격입니다. Claude Code 문서는 권한과 샌드박스를 서로를 보완하는 계층으로 보고, 프롬프트 주입으로 모델의 판단이 흔들려도 샌드박스의 제한은 남는다고 설명합니다. 샌드박스는 네트워크 접속을 허용 도메인, 곧 접속을 허락한 주소의 목록 안으로 제한합니다. 목록에 없는 주소로 접속하려 하면, 사람에게 묻는 수동 모드(설정 값 default)에서는 승인자에게 확인을 요청하고, Claude Code가 호출을 자동으로 판단하는 auto 모드에서는 거부합니다. 허용 도메인을 넓게 열면 자료가 밖으로 나가는 경로가 생기므로, 샌드박스도 모든 접근을 막는 장치는 아닙니다.

Claude Code의 샌드박스는 기본으로 꺼져 있고, /sandbox 명령으로 켭니다. 사람의 확인을 해제하는 모드에서는 금지 규칙에 걸리지 않는 동작을 멈출 사람이 없으므로, 실행 환경이 접근을 가둬야 합니다. 확인을 묻지 않고 실행하는 모드(설정 값 bypassPermissions)는 확인 화면과 제품의 안전 확인을 해제하지만, 금지 규칙은 그대로 적용됩니다. 명시한 확인 요청 규칙은 이 모드에서도 묻지만, 규칙에 없는 동작은 묻지 않고 실행됩니다. 그래서 Claude Code 문서는 이 모드를 인터넷이 연결되지 않은 컨테이너(프로그램과 필요한 파일을 묶어 다른 프로그램과 나눠 실행하는 공간)나 가상 머신(컴퓨터 안에 따로 막아 둔 실행 공간)처럼 격리된 실행 환경에서만 사용하라고 안내합니다.

Codex도 승인 정책(Approval Policy)과 샌드박스의 두 계층을 두며, 두 제품의 차이는 Chapter 10의 권한과 격리 비교에서 다룹니다.

버전 주석 (2026년 10월) Claude Code 문서에 따르면 샌드박스는 macOS, Linux, WSL2에서 동작하고 Linux와 WSL2(Windows 안에서 Linux를 실행하는 기능의 2판)에서는 샌드박스를 만드는 프로그램인 bubblewrap과 네트워크 연결을 중계하는 프로그램인 socat을 설치해야 합니다. 네이티브 Windows와 WSL1에서는 샌드박스 없이 명령이 실행되고, 필요한 패키지가 없는 Linux와 WSL2도 기본 설정에서는 샌드박스 없이 실행되므로 뒤의 확인 방법 절에 있는 샌드박스 확인으로 실제로 켜졌는지 점검합니다.

도구 호출 요청은 먼저 규칙과 대조되고(규칙 대조), 허용되거나 승인된 요청만 실행됩니다(도구 실행). 그림 9-1은 위에서 아래로 읽습니다. 가운데 규칙 대조 영역은 왼쪽의 금지부터 차례로 대조해 처음 일치한 규칙이 결과를 정하는 순서를, 아래 도구 실행 영역은 파일 도구는 규칙이 맡고 셸 명령은 격리가 접근을 제한하는 분담을 보여 줍니다.

표 9-2는 그림 9-1의 구성 요소를 설명합니다.

비용 관리

지출도 한번 나가면 되돌릴 수 없습니다. 그래서 비용도 승인, 격리와 같이 허용할 범위를 정하는 일입니다. 지출에 한도를 정해 두고, 한도에 이르면 승인 지점에서처럼 사람이 계속 여부를 정합니다. API(프로그램이 모델을 직접 호출하는 창구)로 사용한 만큼 과금하는 경우 비용은 토큰 사용량에 비례하고, 구독 요금제는 정해진 사용 한도 안에서 사용합니다. Claude Code 문서는 비용을 관리하는 방법으로 토큰 사용량 추적, 팀 지출 한도, 컨텍스트(Context, 모델이 응답을 생성할 때 입력되는 정보 전체) 관리, 모델 선택 등을 안내합니다. 이 방법을 바탕으로 팀이 작업을 시작하기 전에 정할 기준은 작업 단위의 크기, 읽힐 자료의 범위, 지출 한도의 세 가지입니다. 앞의 둘은 문서의 컨텍스트 관리에, 지출 한도는 문서의 팀 지출 한도에 해당하고, 토큰 사용량 추적은 실행 중의 확인에 사용합니다. 모델 선택은 이 장에서 다루지 않습니다.

  • 작업 단위의 크기: 한 세션에 끝나는 크기로 나누면, 실패한 작업을 처음부터 다시 실행하는 범위가 줄어듭니다(Chapter 6의 작업 단위 분할). 하위 에이전트(Subagent, 특정 작업을 맡도록 따로 정의한 에이전트)에 일을 나눠 맡기는 것은 작업 단위 분할과 다릅니다. 하위 에이전트의 요청도 사용량에 포함되므로, 하위 에이전트로 나누는 것은 다시 실행하는 범위를 줄이는 방법이 아닙니다.
  • 읽힐 자료의 범위: 규칙 문서는 세션마다 읽히므로, 짧게 유지하면 세션마다 읽히는 토큰이 줄어듭니다(Chapter 5의 규칙 문서의 작성).
  • 지출 한도: 팀이나 사용자별 한도를 정하고, 한도에 이르면 사람이 계속 여부를 정합니다. 한도의 단위와 도달했을 때 결정할 사람은 팀의 결정 기록에 적어 둡니다. Teams와 Enterprise 요금제는 사용 크레딧을 켠 뒤 조직, 그룹, 개인 단위로, API 콘솔은 워크스페이스 단위로 한도를 정합니다. 실행 한 번의 비용 상한(Chapter 1의 에이전트 루프와 종료 조건에서 본 max_budget_usd)은 프로그램으로 실행한 작업 하나가 넘지 않을 추정 금액이고, 지출 한도는 팀이나 사용자가 지출하는 금액 전체에 두는 한도입니다. 그래서 하나를 정해도 다른 하나를 대신하지 못합니다.

사용량은 제품의 사용량 화면에서 확인합니다. Claude Code는 /usage 첫 화면 위쪽의 Session 항목에서 현재 세션의 토큰 사용량을 보여 줍니다. 이 항목은 API 사용자를 위한 정보이며, 금액은 정가 기준으로 계산한 추정치라 실제 청구액과 다를 수 있습니다. 실제 청구액은 요금 화면에서 확인합니다. API 사용자는 Claude Console의 사용량 화면이, Teams와 Enterprise 요금제는 조직의 지출 보고서가 요금 화면입니다. 구독 요금제 사용자는 같은 화면에서 요금제 사용량을 봅니다.

비용 관리는 시작 전에 기준을 정하고, 실행 중에 사용량을 확인하고, 지출 한도에 이르면 사람이 계속 여부를 정하는 세 단계로 이어집니다. 그림 9-2는 이 흐름을 위에서 아래로 보여 주며, 3에서 계속을 정하면 점선을 따라 2 실행 중 확인으로 돌아갑니다.

표 9-3은 그림 9-2의 구성 요소를 설명합니다.

예제: 변경 요청 사항의 위험 관리

지금까지의 세 방법을 변경 요청 사항에 적용합니다. 변경 요청 사항의 권한 규칙은 Chapter 3의 명세서를 하네스 설정 파일로 옮기기에서 프로젝트의 설정 파일(.claude/settings.json)에 허용, 확인 요청, 금지의 세 목록으로 옮긴 규칙입니다. 표의 data/는 원본 자료로, 인사 시스템이 갱신하는 프로젝트 코드(경비가 속한 프로젝트의 식별 번호) 목록입니다. acceptance/와 check.py는 사람이 작성한 수용 시험과 그 시험을 실행하는 검사 스크립트로 Chapter 3에서 검증 기준이라고 한 파일입니다. CLAUDE.md, DECISIONS.md, .claude/는 규칙 문서, 결정 기록, 설정 폴더입니다. 표 9-4는 그 권한 규칙을 동작별로 정리하고, 앞의 승인 지점 설계 절의 기준에 따라 그렇게 둔 이유를 적은 것입니다. 첫 행의 단위 테스트와 검사 스크립트 실행에는 python 명령이 없는 환경에서 사용하는 python3 형식의 허용 규칙도 포함됩니다.

변경 요청 사항의 승인 지점 가운데 작업 5(통합 테스트 시나리오 추가)는 승인자가 승인하는 작업 단위이고 권한 규칙이 아니므로 표에 없습니다(Chapter 6의 예제: 변경 요청 사항의 작업 단위 나누기). 예제 설정에는 샌드박스 설정이 없습니다. 예제의 금지 규칙은 문자열이 일치하는 명령만 막으므로, git -C . push 같은 다른 형태의 명령이나 스크립트를 통한 간접 수정은 금지 규칙에 걸리지 않습니다. 이런 명령은 허용 목록에도 없어 권한 모드가 처리합니다. Chapter 3에서 본 것처럼 수동 모드에서는 승인자가 확인 화면에서 거절할 수 있지만, auto 모드에서는 확인 없이 실행될 수 있습니다. 사람의 확인과 관계없이 막으려면 /sandbox로 샌드박스를 켭니다. 샌드박스를 켜면 파일 수정 금지 규칙의 경로가 스크립트에도 적용되고, 저장소 주소를 허용 도메인에 포함하지 않으면 다른 형태의 push도 네트워크 접속에서 다시 확인을 거치거나 거부됩니다. 웹 접근 금지 규칙은 WebFetch와 WebSearch 두 도구만 막으므로, curl 같은 셸의 네트워크 명령도 샌드박스의 허용 도메인으로 제한합니다. 지출 한도는 조직이나 워크스페이스에서 정하는 설정이라 예제 설정 파일에는 없습니다. 변경 요청 사항은 사람이 지켜보는 대화형 세션에서 진행하므로 실행 한 번의 비용 상한도 따로 두지 않습니다. 상한 대신 한 세션에 끝나는 작업 단위와, 같은 시험이 세 번 연속 실패하면 멈추는 중단 규칙으로 다시 하는 비용을 줄입니다(Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성). 이 설정의 예상 결과는 data/projects.csv의 수정을 요청하면 실행 전에 거부되고, commit을 요청하면 승인자에게 확인 화면이 뜨는 것입니다. 이 결과는 뒤의 확인 방법 절에서 확인합니다.

설정과 결과의 확인 방법

권한 설정은 규칙을 읽는 것으로 끝내지 않고, 금지한 동작을 실제로 요청해 거부되는지 확인합니다. 요청은 Claude Code 입력창에, 명령은 부록 실습 1에서 만든 실습 폴더(expense-practice)에서 실행하고, Claude Code도 이 폴더에서 시작합니다. 규칙의 ./ 경로는 Claude Code를 시작한 폴더를 기준으로 하기 때문입니다. 권한 규칙을 직접 설정하는 실습은 부록 실습의 실습 3에 있습니다. 적용된 권한 규칙과 금지 동작 행은 실습 3의 4단계를 마친 뒤, 확인 요청 행은 실습 5에서 commit 확인 화면이 나올 때 확인합니다. 사용량 행은 실습 6의 5단계에서 /usage를 입력할 때 확인하고, 샌드박스와 지출 한도 행은 실습 단계에 없으므로 팀에 적용할 때 따로 확인합니다.

샌드박스 행의 touch ~/sandbox-probe는 사용자 폴더(~)에 빈 파일을 만드는 명령으로, 작업 폴더 밖에 파일 생성을 시도해 샌드박스가 막는지 봅니다. 입력창에서 명령 앞에 !를 입력해 직접 실행하면 샌드박스 밖에서 실행될 수 있으므로 에이전트에게 실행을 요청합니다. 실패 뒤 샌드박스 밖에서 다시 실행할지 물으면 거절하고, 파일이 만들어졌다면 삭제한 뒤 /sandbox로 켜져 있는지 확인합니다. 네이티브 Windows(Git Bash, PowerShell)는 샌드박스를 지원하지 않으므로 이 행을 건너뛰거나 WSL2에서 확인합니다. 표 9-6은 확인 항목마다 확인 방법과 확인 기준을 보여 줍니다.

설계 원칙과 점검 질문

권한은 작업에 필요한 범위로 제한하고, 승인 지점은 되돌리기 어려운 동작에만 둡니다.

권한을 제한하고 승인 지점을 나누는 방식은 코드가 아닌 업무에도 적용됩니다. 금액이 큰 지출은 결재를 받고, 외부 발송은 담당자만 하도록 정하는 결재 규정이 같은 구조입니다. 자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 에이전트에 허용한 동작 가운데 되돌리기 어려운 동작은 무엇이며, 확인 요청과 금지 가운데 어디에 두었습니까?
  2. 금지 규칙을 다른 형태의 명령이나 스크립트로 우회하는 경로를 격리가 막고 있습니까?
  3. 지출 한도에 이르렀을 때 계속할지를 누가 결정합니까?
