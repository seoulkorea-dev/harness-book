Chapter 9 위험 관리: 승인, 격리, 비용

사고의 크기를 정하는 것은 에이전트의 판단력이 아니라, 에이전트에 허용한 권한의 범위와 승인 지점의 위치입니다.

에이전트(Agent)는 허용된 권한 안에서 파일을 수정하고 명령을 실행하며, 그 동작에는 되돌리기 어려운 것도 포함됩니다. 사고의 크기를 정하는 것은 에이전트의 판단력이 아니라, 에이전트에 허용한 권한의 범위와 승인 지점의 위치입니다. 그래서 권한을 넓게 열어 두면, 한 번의 잘못된 판단이 원본 자료의 손상이나 외부 발송으로 이어집니다. 따라서 권한은 작업에 필요한 범위로 제한하고, 되돌리기 어려운 동작에는 사람의 승인 지점을 두어야 합니다. 이 장에서는 승인, 격리, 비용의 세 가지 위험 관리 방법을 다룹니다.

  • 위험 관리는 승인, 격리, 비용의 세 가지로 나눕니다.
  • 승인 지점은 되돌리기 어려운 동작에만 둡니다.
  • 권한 규칙과 격리 환경은 서로를 보완하는 통제 수단입니다.

위험 관리의 세 가지

에이전트의 위험은 통제 대상에 따라 세 가지로 관리합니다. 표 9-1은 방법별 통제 대상과 Claude Code의 수단입니다.

승인 지점 설계

Anthropic의 프롬프트 작성 문서는 에이전트가 되돌리기 어려운 동작을 하기 전에 사용자에게 확인하도록 지시하는 예를 제시합니다(Anthropic, 2026a). 이 문서가 확인 대상으로 든 동작은 세 종류입니다.

  • 파괴적인 동작: 파일이나 브랜치 삭제, 데이터베이스 테이블 삭제
  • 되돌리기 어려운 동작: 강제 push, 게시된 커밋의 수정
  • 다른 사람에게 보이는 동작: 코드 push, 이슈나 PR에 댓글 작성, 메시지 발송, 공유 인프라 변경

승인 단계가 많으면 자동화의 의미가 없다는 의견이 있습니다. 승인 지점을 모든 동작에 두면 승인자는 확인 요청을 검토하지 않고 승인하게 되고, 승인 지점은 통제 수단의 기능을 잃습니다. 승인 지점은 위의 세 종류처럼 되돌리기 어려운 동작에만 둡니다. 파일 수정이나 검사 실행처럼 되돌릴 수 있는 동작은 승인 없이 진행하게 합니다.

권한 규칙과 격리

Claude Code의 권한 규칙(Permission Rule)은 세 종류입니다. allow 규칙은 확인 없이 도구 사용을 허용합니다. ask 규칙은 사용할 때마다 확인을 요청합니다. deny 규칙은 사용을 금지합니다. 규칙은 deny, ask, allow 순서로 평가되며, 처음 일치한 규칙이 결과를 정합니다. 더 구체적인 allow 규칙도 deny 규칙의 예외를 만들 수 없습니다(Anthropic, 2026b). 그림 9-1은 동작의 위험에 따른 규칙 배치, 규칙의 평가 순서, 문자열 대조의 한계를 보완하는 장치를 보여 줍니다.

표 9-2는 그림 9-1의 구성 요소를 설명합니다.

다음은 Chapter 3에서 다룬 경비 정산 시스템 개편 변경 요청(Change Request) CR 예제의 설정 가운데 권한 부분입니다. 원본 자료와 수용 시험의 수정, push는 금지하고, 커밋은 확인을 거치게 합니다.

{
  "permissions": {
    "allow": ["Bash(python -m unittest *)", "Bash(python check.py)"],
    "ask": ["Bash(git commit *)"],
    "deny": ["Edit(./data/**)", "Edit(./acceptance/**)", "Bash(git push *)", "WebFetch"]
  }
}

권한 규칙에는 한계가 있습니다. Claude Code 문서는 Bash 규칙이 명령의 문자열과 일치하는지만 확인하므로, 같은 프로그램을 다른 형태로 호출하면 일치하지 않는다고 설명합니다. 예를 들어 git push 금지 규칙은 git -C . push 형태의 명령과 일치하지 않습니다. 문서는 명령 문자열과 관계없이 파일과 네트워크 접근을 제한하려면 샌드박스(Sandbox)를 사용하라고 안내합니다(Anthropic, 2026b).

Claude Code 문서는 권한과 샌드박스를 서로를 보완하는 보안 계층으로 설명합니다. 권한은 어떤 도구를 사용하고 어떤 파일과 도메인에 접근할지를 통제합니다. 샌드박스는 셸 명령과 그 하위 프로세스의 파일 시스템과 네트워크 접근을 운영 체제 수준에서 제한합니다. 모든 권한 확인을 생략하는 bypassPermissions 모드는 컨테이너나 가상 머신처럼 격리된 환경에서만 사용하라고 경고합니다(Anthropic, 2026b).

Codex도 같은 두 계층을 사용합니다. Codex 문서에 따르면 승인 정책(Approval Policy)은 Codex가 동작 전에 멈추고 확인하는 시점을 정합니다. 샌드박스는 명령이 접근할 수 있는 파일과 네트워크를 정합니다(OpenAI, 2026). 두 제품의 차이는 Chapter 10의 권한과 격리 비교에서 다룹니다.

권한 규칙을 직접 설정하는 실습은 부록 실습의 실습 3에 있습니다.

비용 관리

에이전트의 비용은 토큰(Token) 사용량에 비례합니다. Claude Code 문서는 비용 관리 방법으로 토큰 사용량 추적, 팀 지출 한도 설정, 컨텍스트(Context) 관리, 모델 선택을 안내합니다(Anthropic, 2026b). 팀이 정할 비용 관리 기준은 세 가지입니다.

  • 작업 단위의 크기: 한 세션에 끝나는 크기로 나누면, 실패한 작업을 처음부터 다시 실행하는 비용이 줄어듭니다(Chapter 6의 작업 단위 분할).
  • 읽힐 자료의 범위: 상시 규칙 문서를 짧게 유지하면 세션마다 읽히는 토큰이 줄어듭니다.
  • 지출 한도: 팀이나 사용자별 한도를 정하고, 한도에 이르면 승인자가 계속 여부를 결정합니다.

토큰 사용량은 제품의 명령으로 확인합니다. Claude Code는 /usage 명령의 Session 항목에서 현재 세션의 토큰 사용량을 보여 주고, 상태 줄에 계속 표시하도록 설정할 수도 있습니다. 구독 요금제에서는 같은 화면에 요금제 사용량도 표시됩니다. Claude Code 문서는 Session 항목을 API 사용자를 위한 정보로 안내하며, 금액은 정가 기준으로 계산되어 실제 청구액과 다를 수 있습니다. Codex는 /status 명령으로 세션 설정과 토큰 사용량, 남은 컨텍스트 용량을 보여 줍니다(Anthropic, 2026b; OpenAI, 2026). 그림 9-2는 비용 관리 기준과 확인 위치입니다.

표 9-3은 그림 9-2의 구성 요소를 설명합니다.

위험 관리는 권한을 작업에 필요한 범위로 제한하고, 되돌리기 어려운 동작에만 승인 지점을 두는 일입니다.

실패와 막는 장치

권한과 승인 지점, 비용 기준을 정하지 않으면 CR 구현에서 다음 실패가 생길 수 있습니다. 표 9-4는 실패와 원인, 막는 장치입니다.

확인 방법

권한 설정은 규칙을 읽는 것으로 끝내지 않고, 금지한 동작을 실제로 요청해 거부되는지 확인합니다. 표 9-5는 CR 구현 에이전트에서 확인할 것과 확인 위치입니다.

원칙과 점검 질문

권한은 작업에 필요한 범위로 제한하고, 승인 지점은 되돌리기 어려운 동작에만 둡니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 에이전트에 허용한 동작 가운데 되돌리기 어려운 동작은 무엇입니까?
  2. 금지 규칙이 다른 형태의 명령으로 우회될 수 있는 경로가 있습니까?
  3. 지출 한도에 이르렀을 때 계속할지를 누가 결정합니까?
