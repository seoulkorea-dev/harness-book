Chapter 4 프롬프트 엔지니어링: 한 번의 요청 설계

요청 문장의 표현을 다듬는 것만으로는 결과의 품질이 정해지지 않고, 요청에 목적, 입력, 출력 형식, 완료 기준이 담겼는지에 따라 결과가 달라집니다.

프롬프트(Prompt)는 모델에 주는 지시문이며, 이 책은 사람이 이번 작업에 입력하는 요청을 프롬프트라고 부릅니다(Chapter 1). 모델은 학습한 일반 지식에 컨텍스트(Context)를 더해 결과를 생성합니다. 컨텍스트는 요청 문장과 첨부한 자료처럼 모델에 입력되는 정보 전체입니다. 이번 일의 목적, 판단에 사용할 자료, 결과의 형식, 결과를 받아들일 조건은 요청하는 사람이 정하는 것이어서, 요청에 적지 않으면 모델은 그 빈자리를 추측으로 채웁니다. 추측이 의도와 다르면 결과의 범위나 형식이 요청한 사람이 원한 것과 어긋납니다. 요청을 보내기 전에 목적, 입력, 출력 형식, 완료 기준의 네 요소가 모두 들어 있는지 점검하면 이런 어긋남을 줄일 수 있습니다. 프롬프트 엔지니어링(Prompt Engineering)은 원하는 결과를 얻도록 지시문을 작성하고 구성하는 방법입니다. 이 장에서는 그 가운데 요청 한 건을 구성하는 네 요소와 요청을 명확하게 작성하는 방법을 익히고, 프롬프트로 해결되지 않는 문제까지 살펴봅니다.

  • 요청 한 건은 목적, 입력, 출력 형식, 완료 기준의 네 요소로 구성합니다.
  • 구체적 지시, 이유 제공, 예시 제공, 구획 구분, 할 일로 지시, 행동 동사의 여섯 가지 표현 방법은 네 요소를 모델이 오해 없이 읽게 합니다.
  • 자료의 양과 선별, 반복 작업의 일관성, 결과 검증은 프롬프트만으로 해결되지 않습니다.

요청의 네 요소

모델이 추측으로 채우는 부분을 줄이려면 요청에 무엇을 적을지부터 정해야 합니다. 이 책은 요청 한 건에 담을 정보를 목적, 입력, 출력 형식, 완료 기준의 네 요소로 정리합니다. 목적은 결과를 누가 어떤 결정이나 일에 사용하는지입니다. 입력은 판단에 필요한 자료와 그 범위입니다. 자료는 요청에 첨부하고, 에이전트(Agent)처럼 모델이 파일을 직접 읽을 수 있는 환경이면 자료가 있는 위치를 요청에 적습니다. 출력 형식은 결과의 항목, 표 구성, 분량입니다. 완료 기준은 결과를 받아들여도 되는지, 곧 일이 끝났는지를 판정하는 조건입니다.

네 요소 가운데 먼저 정할 것은 목적과 완료 기준입니다. 입력과 출력 형식은 자료를 첨부하고 양식을 지정하는 과정에서 요청에 드러나기 쉽습니다. 목적과 완료 기준은 요청하는 사람에게는 당연해서 적지 않고 보내기 쉬우며, 요청에 없으면 모델은 주변 자료에서 짐작할 수밖에 없습니다. 완료 기준을 먼저 정하는 순서에는 공개 자료의 근거가 있습니다. Anthropic의 프롬프트 엔지니어링 개요 문서는 프롬프트를 다듬기 전에 사용 사례의 성공 기준(Success Criteria)과 그 기준으로 결과를 시험하는 방법을 먼저 갖추라고 안내합니다. 이 안내는 모델을 사용하는 응용 프로그램을 여러 시험 입력으로 반복해 평가하는 경우를 다룹니다. 이 책은 이 순서를 요청 한 건에 적용하며, 요청 한 건의 성공 기준에 해당하는 것이 완료 기준입니다. 목적은 완료 기준처럼 적지 않고 보내기 쉬우므로 함께 먼저 정합니다.

목적과 완료 기준을 요청에 적어야 하는 이유는 최신 모델이 지시를 따르는 방식에도 있습니다. Anthropic의 프롬프트 작성 모범 사례 문서의 도구 사용 절은 최신 모델이 지시를 정밀하게 따르도록 훈련되었다고 설명합니다. 같은 문서의 명확하고 직접적인 지시 절은 과제가 엄밀히 요구하는 범위를 넘는 결과를 원하면, 그 내용을 모델이 모호한 요청에서 짐작하게 두지 말고 명시적으로 요청하라고 안내합니다. 이 책은 두 안내를 바탕으로, 모델이 적힌 지시를 정밀하게 따를수록 요청에 적지 않은 목적과 완료 기준은 결과에 반영되기 어렵다고 봅니다.

그림 4-1은 네 요소로 구성한 요청이 모델의 판단과 응답을 거쳐 결과 확인으로 이어지는 구조를 보여 줍니다. 완료 기준을 적어도 모델이 기준을 충족한다는 보장은 없으므로, 요청하는 사람은 결과를 완료 기준과 다시 대조합니다. 표 4-1은 요소별로 담을 정보와 누락 시 결과를, 표 4-2는 그림 4-1의 구성 요소를 정리합니다.

요청을 명확하게 만드는 방법

네 요소를 정해도 요청 문장이 모호하면 모델이 그 뜻을 다시 추측합니다. 그래서 네 요소를 정한 뒤에는 그 내용을 모델이 다르게 읽지 않도록 적어야 합니다. Anthropic의 프롬프트 작성 모범 사례 문서는 요청을 명확하게 만드는 방법을 여러 가지로 안내합니다. 이 책은 그 가운데 별도 설정 없이 요청 문장만 변경해 적용할 수 있는 여섯 가지를 선별해 다룹니다. 여섯 방법은 네 요소를 대신하지 않고, 정한 네 요소를 모델이 다르게 읽지 않게 적는 방법입니다.

  • 구체적 지시: 네 요소의 내용을 "정리해", "짧게" 같은 막연한 말 대신 항목, 열 이름, 날짜 범위, 글자 수처럼 확인할 수 있는 말로 적습니다. 모범 사례 문서는 원하는 출력 형식과 제약 조건(분량, 범위처럼 결과가 지켜야 할 한계)을 구체적으로 적고, 단계의 순서나 빠짐없는 수행이 중요하면 번호 목록이나 글머리표로 지시하라고 안내합니다.
  • 이유 제공: 개별 지시를 두는 까닭을 함께 적습니다. 목적이 결과 전체의 쓰임이라면, 이유는 "40자 이내" 같은 지시 하나를 두는 까닭입니다. 같은 문서는 지시의 이유나 동기를 알려 주면 모델이 목표를 더 정확히 이해하고 목적에 맞는 응답을 하는 데 도움이 된다고 설명합니다.
  • 예시 제공: 원하는 결과의 본보기를 요청에 함께 포함합니다. 같은 문서는 예시를 출력의 형식, 어조, 구조를 맞추는 가장 믿을 만한 방법 가운데 하나로 소개합니다. 예시는 실제 업무와 가까운 것으로 정하고, 예외 상황까지 담기도록 서로 다르게 선택하라고 안내합니다. 예시끼리 비슷하면 모델이 의도하지 않은 공통점까지 따라 할 수 있기 때문입니다. 개수는 3~5개를 권합니다. 이 개수는 예시를 사용할 때의 기준이며, 모든 요청에 예시가 필요하다는 뜻은 아닙니다.
  • 구획 구분: 지시, 자료, 예시를 태그로 나눕니다. 태그는 <자료>, </자료>처럼 내용의 종류를 표시하는 표지입니다. 같은 문서는 이 표지를 XML 태그라고 부르고, 태그가 지시, 자료, 예시가 섞인 요청을 모호함 없이 읽게 돕는다고 설명합니다. 이 책은 내용을 나타내는 한글 이름을 태그 이름으로 사용하고, 같은 종류의 내용에는 요청마다 같은 이름을 사용합니다.
  • 할 일로 지시: 하지 말아야 할 일 대신 해야 할 일을 적습니다. 같은 문서는 응답 형식을 정할 때 "마크다운을 사용하지 마" 대신 "부드럽게 이어지는 문단으로 작성해"처럼 작성하라는 예를 듭니다. 이 방법은 응답 형식처럼 결과에 나타나는 모양을 정하는 지시에 사용합니다. 에이전트가 파일을 직접 변경할 수 있는 작업에서 원본 자료 수정 같은 동작은 요청 문장의 금지만으로 확실히 막을 수 없으므로 권한 규칙(Permission Rule)으로 강제합니다(Chapter 2의 지시와 강제).
  • 행동 동사: 제안을 원하는지 실행을 원하는지 동사로 구분합니다. 같은 문서는 도구를 사용할 수 있는 작업에서 "변경 사항을 제안해 줄 수 있어?"라고 물으면, 수정을 원했더라도 모델이 제안만 할 때가 있다고 설명합니다. 실행을 원하면 "수정해 줘"처럼 실행을 뜻하는 동사로 요청합니다. 동사로 실행을 요청해도 실제로 실행되는지는 연결된 도구, 권한 규칙과 권한 모드(Permission Mode), 사람의 승인이 정합니다(Chapter 1의 에이전트 루프, Chapter 2의 도구 노출 범위).

그림 4-2는 여섯 방법의 요점을 보여 주고, 표 4-3은 방법마다 그 방법만으로 해결되지 않는 한계(기능적 제약)를 함께 정리합니다.

표 4-4는 여섯 방법을 적용하기 전과 뒤의 업무 요청을 나란히 비교합니다.

프롬프트로 해결되지 않는 문제

네 요소와 여섯 방법은 요청 한 건의 품질을 높이지만, 요청 문장 바깥에 원인이 있는 문제는 요청을 다듬어도 남습니다. Anthropic의 개요 문서도 성공 기준에 못 미치는 결과 가운데 일부는 프롬프트 엔지니어링보다 다른 방법으로 더 쉽게 개선된다고 설명합니다. 예를 들어 지연 시간과 비용은 다른 모델을 선택하는 편이 더 쉽게 개선될 때가 있다고 합니다. 이 책은 같은 관점에서, 업무에서 자주 만나는 다음 세 문제를 프롬프트의 범위 밖으로 정리합니다.

  • 자료의 양과 선별: 토큰(Token)은 모델이 텍스트를 나누어 처리하는 단위이고, 컨텍스트 윈도(Context Window)는 모델이 한 번에 처리할 수 있는 토큰의 범위입니다. 요청마다 자료를 붙여 넣으면 자료가 늘어날수록 컨텍스트 윈도에서 자료가 차지하는 몫이 커집니다. 컨텍스트의 토큰이 늘수록 모델이 그 정보를 정확히 기억해 내는 능력은 떨어집니다. 무엇을 포함할지도 요청할 때마다 사람이 선별해야 합니다. 어떤 정보를 언제 넘길지는 Chapter 1에서 정의한 컨텍스트 엔지니어링(Context Engineering)이 다루고, 규칙 문서와 필요할 때 읽는 문서로 나누는 방법은 Chapter 5에서 다룹니다.
  • 반복 작업의 일관성: 같은 업무를 여러 번, 여러 사람이 요청하면 요청할 때마다 프롬프트가 달라지고 결과도 달라지기 쉽습니다. 여러 사람의 요청에 공통으로 적용할 조건은 에이전트가 세션을 시작할 때마다 읽는 규칙 문서에 두면 요청마다 다시 적지 않아도 됩니다. 규칙 문서도 에이전트가 읽고 따르는 지시이므로 지켜졌는지는 따로 확인합니다. 규칙 문서는 Chapter 2에서 정의했고, 작성 방법은 Chapter 5의 규칙 문서 작성에서 다룹니다.
  • 결과 검증: 요청에 적은 완료 기준은 모델에게 지키도록 요청한 조건입니다. 모델이 충족했다고 보고해도 실제 충족 여부는 따로 확인해야 합니다. Chapter 3은 사람이 정한 완료 기준을 수용 기준이라고 부르고, 그 기준을 확인하는 시험을 수용 시험이라고 부릅니다. 검사 스크립트는 단위 테스트와 수용 시험을 한 번에 실행해 완료를 판정하는 프로그램이며, Chapter 3의 예제는 이 검사 스크립트로 완료 기준이 충족되었는지를 확인합니다. 완료 기준을 검사로 변환하는 방법은 Chapter 7에서 다루고, 요청 한 건의 결과를 사람이 확인하는 방법은 뒤의 확인 방법 절에서 다룹니다.

예제: 변경 요청 사항의 영향 검토 요청하기

프롬프트가 맡는 범위는 요청 한 건이므로, 예제도 요청 한 건으로 봅니다. 영향 검토는 변경을 받아들이면 화면, 데이터, 일정, 작업량에 어떤 영향이 생기는지 미리 따져 보는 일입니다. 예제는 재무팀이 보낸 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)의 영향 검토를 모델에 맡기는 상황입니다. 이 변경 요청 사항은 정산 요청 화면에 프로젝트 코드 선택 항목을 추가해 달라는 요청입니다. Chapter 3은 수용이 정해진 뒤 이 변경을 구현하는 단계를 다루었고, 이 장의 예제는 운영 위원회가 수용 여부를 정하기 전의 단계입니다. 같은 영향 검토를 맡기는 요청 두 개를 나란히 놓고, 네 요소와 여섯 방법이 요청을 어떻게 달라지게 하는지 비교합니다.

네 요소가 누락된 요청

이 변경 요청 사항 검토해 줘.

이 요청에는 네 요소가 모두 없습니다. 누가 어떤 결정에 사용하는지(목적), 판단 자료(입력), 결과의 항목(출력 형식), 받아들일 조건(완료 기준)이 없어서, 모델은 요청 문장만으로 검토 범위를 추측하거나 필요한 자료를 되물어야 합니다. 파일을 직접 읽을 수 있는 에이전트 환경이면 어떤 파일을 읽을지도 모델이 추측합니다.

네 요소를 갖춘 요청

두 번째 요청은 네 요소를 모두 적은 요청입니다. 요청문의 공수는 예상 작업량이고 인일은 한 사람이 하루에 하는 작업량입니다. 연동 규격은 두 시스템이 자료를 주고받는 방식을 정한 문서입니다.

2026-10-12 운영 위원회에서 아래 변경 요청 사항의 수용 여부를 결정해야 해.
결정에 필요한 영향 검토 결과를 정리해 줘.

<변경 요청 사항>
내용: 정산 요청 화면에 프로젝트 코드 선택 항목 추가
요청 부서: 재무팀, 요청일: 2026-10-05
사유: 프로젝트별 경비 집계를 월말 결산에 반영하기 위함
</변경 요청 사항>

<현재 상황>

</현재 상황>

출력 형식: 영향 범위, 예상 공수(인일), 일정 영향, 수용 시 위험, 권고안의 다섯 항목을 표로 정리해 줘.
완료 기준:
1. 구현 세부 사항은 영향 범위 칸에 한 줄로만 적어 줘.
2. 영향 범위, 예상 공수, 일정 영향은 <현재 상황>의 연동 규격 유무를 전제로 추정하고, 어떤 전제로 추정했는지 함께 밝혀 줘.
3. 자료에 근거가 없는 수치에는 "확인 필요"를 표기해 줘. 결정 자료에서 확정값으로 읽히면 안 되기 때문이야.
4. 권고안은 수용, 조건부 수용, 거절 가운데 하나로 정하고 이유를 한 문장으로 적어 줘. 조건부 수용이면 조건도 함께 적어 줘.

두 요청은 네 요소를 갖추었는지에서 갈립니다. 두 번째 요청은 목적(운영 위원회의 수용 여부 결정), 입력(변경 요청 사항과 현재 상황), 출력 형식(다섯 항목의 표), 완료 기준(번호를 매긴 네 조건)을 모두 갖추었습니다. <현재 상황>에 연동 규격이 없다고 적은 것은 이 내용이 공수와 일정 판단을 좌우하기 때문입니다. 요청에 이 내용이 없으면 모델은 인사 시스템과 이미 실시간 연동이 된다고 가정하고, 연동 규격을 마련하는 작업을 제외하고 공수를 적게 추정할 수 있습니다. 완료 기준 1은 목적인 수용 여부 결정에 맞춰 구현 세부 사항의 분량을 정합니다. 완료 기준 2는 연동 규격이 없다는 전제를 결과에 밝히게 하고, 완료 기준 3은 근거 없이 만든 수치가 확정값처럼 보이지 않게 합니다.

두 번째 요청은 여섯 방법 가운데 구체적 지시(다섯 항목의 표, 공수 단위, 번호를 매긴 완료 기준), 구획 구분(<변경 요청 사항>, <현재 상황> 태그), 이유 제공(완료 기준 3의 이유)을 사용했습니다. 완료 기준 3은 할 일로 지시의 예이기도 하며, 근거 없는 수치를 만들지 말라는 금지 대신 "확인 필요"를 표기하라고 적었습니다. 결과를 표로 받는 요청이라 제안과 실행을 구분할 일이 없어 행동 동사는 따로 사용하지 않았습니다. 형식은 다섯 항목으로 지정했으므로 예시는 포함하지 않았습니다.

운영 위원회는 이 영향 검토를 거쳐 변경 요청 사항을 조건부 수용하고, 프로젝트 코드는 인사 시스템이 하루 한 번 갱신하는 자료(data/projects.csv)를 사용하기로 결정합니다(Chapter 8의 결정 기록 D-012). 이 장은 모델이 돌려준 결과를 싣지 않으며, 같은 요청을 직접 보내 받은 결과는 뒤의 확인 방법 절의 항목으로 대조할 수 있습니다.

실패와 막는 장치

예제 절의 두 번째 요청에서 네 요소 가운데 하나가 누락되면 어떤 실패가 생기는지 거꾸로 따져 볼 수 있습니다. 표 4-5는 요소별로 생길 수 있는 실패와 방지 장치를 보여 줍니다. 방지 장치는 모두 두 번째 요청문에 이미 들어 있는 문장입니다. 요청문의 문장은 지시이므로 실패를 줄이지만 막는다고 보장하지는 않으며, 실제로 지켜졌는지는 뒤의 확인 방법 절에서 대조합니다.

확인 방법

방지 장치를 갖춰도 모델이 완료 기준을 지켰는지는 결과를 받아야 알 수 있습니다. 영향 검토는 결정 한 번에 사용하는 결과라서, Chapter 3처럼 검사 스크립트를 만들어 자동으로 판정하지 않습니다. 요청하는 사람이 결과를 완료 기준과 하나씩 대조합니다. 예제 절의 두 번째 요청을 생성형 AI 채팅에 직접 보내고, 받은 결과를 표 4-6의 확인 항목으로 대조해 볼 수 있습니다. 예를 들어 결과의 예상 공수에 수치가 적혀 있으면 그 근거가 <변경 요청 사항>이나 <현재 상황>에 있는지 찾고, 없으면 "확인 필요"가 표기되었는지 봅니다. 기준에 못 미치는 항목이 있으면, 그 항목의 조건이 요청에 없을 때는 더하고 있을 때는 더 구체적으로 적어 다시 보냅니다.
