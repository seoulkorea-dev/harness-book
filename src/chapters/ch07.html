Chapter 7 검증 설계: 완료 보고 대신 증거 받기

결과를 받아들이는 근거는 완료 보고가 아니라, 검사 출력과 산출물처럼 사용자가 직접 확인할 수 있는 증거입니다.

에이전트(Agent)는 작업을 마치면 완료 보고를 작성하며, 그 보고는 에이전트 자신의 판단입니다. 그러나 그 판단이 결과가 실제로 동작한다는 뜻은 아닙니다. 그래서 완료 보고만으로 결과를 받아들이면, 실제로 동작하지 않는 결과가 완료로 처리됩니다. 따라서 작업을 맡기기 전에 어떤 증거로 완료를 판정할지 정해야 합니다. 이 장에서는 완료 기준을 검사로 변환하는 방법, 검증 방법의 선택, 기준표 채점을 차례로 다루고, 경비 정산 예제에 적용합니다.

  • 완료 보고는 결과를 만든 쪽의 판단이므로 판정 근거가 아닙니다.
  • 완료 기준은 작업을 맡기기 전에 통과, 실패로 갈리는 검사로 변환합니다.
  • 기준 항목마다 자동 검사, 출력 확인, 독립 검수 가운데 하나를 선택하고, 판단이 필요한 기준은 기준표로 채점합니다.

완료 보고가 근거가 되지 않는 이유

완료 보고는 일을 한 쪽이 작성한 글이므로, 결과가 실제로 동작한다는 근거가 되지 못합니다. 에이전트는 자기 결과에 오류가 있어도 알아차리지 못한 채 완료를 보고할 수 있습니다. 그래서 이 책은 완료 보고와 증거를 구분합니다. 완료 보고는 에이전트가 작업을 마쳤다고 알리는 글이고, 증거는 검사 출력이나 산출물처럼 사용자(에이전트에게 업무를 맡긴 사람)가 직접 확인할 수 있는 것입니다.

이 구분의 근거는 장시간 실행 에이전트 실험입니다. Claude Code는 이 실험에서 에이전트가 충분한 시험 없이 기능을 완료로 표시하는 경향을 보고했습니다. 에이전트는 단위 테스트(Unit Test)나 개발 서버에 보내는 curl 명령으로 시험했지만, 기능이 처음부터 끝까지 동작하지 않는다는 사실은 알아차리지 못했습니다. 단위 테스트는 프로그램의 부품 하나가 정해진 대로 동작하는지를 확인하는 시험이어서, 부품을 이어 사용하는 흐름 전체는 확인하지 못합니다. 브라우저 자동화 도구로 사람이 사용하는 방식 그대로 시험하라고 명시하자, 에이전트의 결과가 개선되었습니다(Young, 2025).

이 사례는 두 가지를 보여 줍니다. 결과를 만든 에이전트의 판단은 완료의 근거가 되지 않습니다. 사람처럼 시험하라고 명시하면 에이전트의 결과가 나아집니다.

이 책의 작가도 원고 작업을 맡길 때 완료 보고 대신 검사 명령의 출력 원문을 근거로 받습니다. 원고를 수정했다는 보고에는 빌드(원고를 읽을 수 있는 쪽으로 만드는 일), lint, 사이트 검증 명령의 출력이 함께 있어야 합니다. lint는 원고나 코드의 형식 오류를 정해진 규칙으로 자동 검사하는 도구입니다. 저장소에 반영된 뒤에는 CI(Continuous Integration) 도구인 GitHub Actions의 검사 결과로 다시 확인합니다. CI는 저장소에 변경을 반영할 때마다 빌드와 검사를 자동으로 실행하는 방식입니다.

에이전트가 스스로 확인했다고 보고하면 충분하다는 의견이 있습니다. 에이전트도 시험을 실행하기 때문입니다. 그러나 앞의 장시간 실행 에이전트 실험에서 에이전트는 시험을 실행하고도 기능이 동작하지 않는 사실을 알아차리지 못했습니다. "확인했습니다"라는 보고 문장과, 어떤 명령을 실행해 무엇이 출력되었는지를 담은 출력 원문은 다른 정보입니다. 출력 원문으로 판정하려면 무엇을 확인할지가 맡기기 전에 정해져 있어야 하므로, 다음 절은 완료 기준을 검사로 변환하는 방법을 다룹니다.

완료 기준을 검사로 변환

완료 기준이 문장으로만 있으면 판정하는 사람마다 결과가 달라지므로, 맡기기 전에 검사로 정해 둡니다. 완료 기준은 Chapter 6의 작업 단위 목록에 적는 칸이고, 수용 기준(Acceptance Criteria)은 Chapter 3에서 사람이 정한 완료 조건입니다. 이 책은 완료 기준을 통과, 실패로 갈리는 검사로 만드는 일을 변환이라고 정리합니다.

변환한 기준은 누가 판정해도 같은 결과가 나와야 합니다. 표 7-1은 문장으로 작성된 완료 기준을 검사로 변환한 예입니다. 수용 시험(Acceptance Test)은 수용 기준을 충족하는지 확인하는 시험이고, 응답 코드 200은 웹 서버가 요청을 정상으로 처리했다는 뜻입니다. 구조 검사 스크립트는 오류를 찾을 때만 출력하므로, 출력이 비어 있으면 통과입니다.

변환한 기준을 확인하는 방법은 다음 절에서, 판단이 필요한 기준의 채점은 기준표와 채점에서 다룹니다.

검증 방법의 선택

기준을 검사로 변환해도 모든 기준을 같은 방법으로 확인할 수는 없습니다. 이 책은 기준을 확인하는 방법을 누가 판정하는가에 따라 세 가지로 정리합니다. 자동 검사는 스크립트나 테스트가 판정합니다. 출력 확인은 사용자가 명령의 출력이나 산출물을 직접 확인합니다. 독립 검수는 결과를 만들지 않은 다른 에이전트나 사람이 검토합니다.

세 방법을 모두 거치는 것이 아니라, 기준 항목마다 가장 알맞은 방법을 하나 선택합니다. 어느 방법이든 판정에서 통과하면 다음 작업 단위로 넘어가고, 미통과가 나오면 오류 출력을 에이전트에 돌려 같은 작업 단위를 다시 수행하게 합니다(Chapter 6). 그림 7-1은 이 미통과 갈래를 다시 작업이라고 적습니다. 어느 방법이든 판정에 사용한 출력 원문은 사용자가 마지막에 확인합니다. 그림 7-1은 완료를 판정하는 구조를 보여 줍니다.

이 구분은 Claude Code 문서의 안내와 맞습니다. 문서는 에이전트가 실행할 수 있는 검사(테스트, 빌드, 화면 캡처 비교)를 제공하라고 안내합니다. 검사가 없으면 결과가 끝난 것처럼 보이는 것이 유일한 신호가 되고, 사용자가 직접 확인을 반복해야 한다는 이유입니다. 같은 문서는 일을 한 에이전트가 자기 결과를 채점하지 않도록, 새 컨텍스트(Context)에서 검토하게 하는 방법도 안내합니다(Anthropic, 2026b).

표 7-2는 그림 7-1의 구성 요소를 설명합니다.

표 7-3은 세 방법이 각각 어떤 확인에 알맞은지 보여 줍니다.

반복되는 확인을 자동 검사로 옮긴 사례도 있습니다. Codex로 제품을 개발한 팀은 문서 구조를 전용 lint와 CI로 기계적으로 검사했다고 밝혔습니다. 사람은 작업의 우선순위를 정하고 결과를 검증하는 역할을 맡았습니다(Lopopolo, 2026). 이 책의 구분으로 보면, 반복되는 확인은 자동 검사에 맡기고 사람은 판단이 필요한 확인에 시간을 사용하는 구성입니다.

기준표와 채점

표 7-1처럼 코드로 판정하는 검사로 변환할 수 있는 기준만 있는 것은 아닙니다. 문장의 어조나 요약의 충실도처럼 판단이 필요한 기준은 독립 검수로 확인하고, 그 판정 방식을 따로 정해야 합니다. 이 책은 기준 하나를 정답, 오답이나 점수 같은 판정값으로 만드는 일을 채점이라고 부르고, 채점 방법을 코드 기반, 대규모 언어 모델(LLM, Chapter 1) 기반, 사람의 세 가지로 정리합니다. 코드 기반 채점은 자동 검사에 해당하고, LLM 기반 채점과 사람 채점은 결과를 만들지 않은 쪽이 판정하는 독립 검수에 해당합니다. 출력 확인은 채점이 아니라 사용자가 출력 원문과 산출물을 직접 확인하는 별개의 방법입니다.

채점할 때 통과 조건을 항목별로 적은 표를 기준표(Rubric), 기준이 되는 답을 예시 답안이라고 합니다.

Anthropic의 평가 문서는 채점 방법을 세 가지로 나누고, 가장 빠르고 신뢰할 수 있으며 확장하기 쉬운 방법을 선택하라고 안내합니다(Anthropic, 2026a). 코드 기반 채점은 결과가 정답과 정확히 일치하는지, 특정 문구가 들어 있는지를 확인합니다. LLM 기반 채점은 먼저 신뢰도를 시험한 뒤 확대하고, 사람 채점은 가능하면 피하라고 안내합니다. 표 7-4는 세 방법을 비교합니다.

LLM 기반 채점에서는 기준표를 상세하고 명확하게 작성하는 것이 핵심입니다. 평가 문서는 상세하고 명확한 기준표를 작성하라고 안내하고, 답변의 첫 문장에 특정 회사 이름이 없으면 오답으로 처리하는 기준을 예로 듭니다. 판정 결과는 정답과 오답 또는 1~5점처럼 구체적인 형태로 받습니다. 순수한 정성 평가는 빠르게, 대량으로 판정하기 어렵기 때문입니다.

문서의 예제는 기준이 되는 정답을 예시 답안으로 두고, 채점하는 모델이 결과를 예시 답안과 비교하게 합니다. 예제 코드의 주석에는 결과를 만든 모델과 다른 모델로 평가하는 편이 일반적으로 좋다는 안내도 있습니다(Anthropic, 2026a). 결과를 만든 쪽이 자기 결과를 채점하지 않게 하려는 것으로, 앞 절의 독립 검수와 같은 이유입니다. 1~5점처럼 점수로 받으면, 몇 점부터 통과인지도 채점 전에 정합니다. 그림 7-2는 기준표 채점의 흐름을 보여 줍니다.

표 7-5는 그림 7-2의 구성 요소를 설명합니다.

이 책은 기준표로 채점할 때 정할 것을 세 가지로 정리합니다.

  • 채점 방법: 항목마다 코드, LLM, 사람 가운데 가장 빠르고 신뢰할 수 있는 방법을 정합니다.
  • 기준표와 통과 조건: LLM 기반 채점 항목에는 통과 조건과, 있으면 예시 답안을 준비합니다.
  • 사람의 확인 지점: 사람 채점은 비용이 크므로, 되돌리기 어려운 결정에 둡니다(Chapter 6의 맡길 업무의 선정).

변경 요청의 검증 설계 예제

지금까지의 원리를 Chapter 3의 경비 정산 시스템 개편 변경 요청(Change Request) CR에 적용합니다. CR은 정산 요청에 프로젝트 코드를 목록에서 선택해 입력하게 하는 변경이고, 수용 기준은 다섯 가지입니다. 등록 화면에서 목록의 코드를 선택할 수 있어야 하고, 목록에 없는 코드는 거부하고 사유에 입력한 코드를 표시해야 합니다. 목록 화면에 프로젝트 코드를 표시하고, 코드가 없는 기존 요청도 그대로 표시하며, 원본 자료(프로젝트 코드 목록 파일)는 변경하지 않아야 합니다. 표 7-6은 CR의 기준마다 검증 방법과 통과 조건을 정한 결과입니다.

기준마다 방법 하나를 선택하는 것이 기본입니다. 둘째 행과 셋째 행은 같은 수용 기준을 한 번 더 보는 추가 장치입니다. 셋째 행은 수용 시험 1이 화면을 그리는 문서(HTML)에 선택 항목이 있는지만 보기 때문에, 화면에서 직접 선택해 봅니다. 시험은 기준마다 정해진 경우만 확인하므로, 시험이 통과해도 시험이 다루지 않는 경우가 남을 수 있습니다. 그래서 근거 파일과 줄 번호로 기준을 다시 대조합니다. 넷째 행의 통합 시나리오는 수용 기준이 아니라 Chapter 6의 작업 5에서 승인자가 승인하는 단위입니다.

첫째 행의 수용 시험을 실행하는 파일이 Chapter 3의 검사 스크립트 check.py입니다. 보고 대신 출력 원문으로 판정하려면 스크립트가 무엇을 출력하는지가 중요하므로, 핵심 부분을 봅니다. 아래 코드는 따라 입력할 필요 없이 읽기만 하면 됩니다.

import sys, unittest

results = {}
for folder in ("tests", "acceptance"):
    suite = unittest.TestLoader().discover(folder)
    run = unittest.TextTestRunner(verbosity=0).run(suite)
    results[folder] = (run.testsRun, len(run.failures) + len(run.errors))

for folder, (count, failed) in results.items():
    print(f"{folder}: 실행 {count}건, 실패 {failed}건")
sys.exit(0 if all(count > 0 and failed == 0 for count, failed in results.values()) else 1)

코드는 세 덩어리입니다. 첫 덩어리는 단위 테스트 폴더(tests)와 수용 시험 폴더(acceptance)에서 시험을 찾아 실행하고, 폴더마다 실행 건수와 실패 건수를 셉니다. 둘째 덩어리는 판정 근거인 두 건수를 폴더별로 출력합니다. 종료 코드는 명령이 끝날 때 돌려주는 값이며, 0은 성공을 뜻합니다(Chapter 3). 마지막 줄은 두 폴더 모두 실행 건수가 0보다 크고 실패가 0건일 때만 종료 코드 0으로, 아니면 1로 끝냅니다.

실행 건수가 0건인 폴더를 실패로 판정하는 이유가 있습니다. 시험 파일을 찾지 못해 하나도 실행되지 않으면 실패 건수도 0건이 되어, 통과로 보이기 때문입니다.

출력 원문은 다음처럼 읽습니다. 다음은 CR을 구현하기 전의 기준 상태에서 python check.py를 실행한 출력입니다(부록 실습의 실습 1). 구현 전이므로 수용 시험 1~3이 실패하고 종료 코드는 1입니다. 구현을 마치면 둘째 줄이 "acceptance: 실행 5건, 실패 0건"이 되고, 종료 코드는 0이어야 합니다.

tests: 실행 3건, 실패 0건, 건너뜀 0건, project_code 시험 0건
acceptance: 실행 5건, 실패 3건, 건너뜀 0건(정한 수 5건)

표 7-6 둘째 행의 검토 하위 에이전트(Subagent)는 Chapter 3에서 읽기 도구만 사용하도록 정의한 검토자입니다. 결과를 만든 구현 에이전트와 다른 새 컨텍스트에서, CR의 수용 기준을 기준표로 삼아 변경 내용을 대조합니다. 판정값은 기준마다 충족, 미충족, 확인 불가와 근거 파일, 줄 번호이고, 통과 조건은 표 7-6처럼 채점 전에 정합니다. 예시 답안은 두지 않습니다.

표 7-6의 첫째 행을 믿으려면 에이전트가 수용 시험을 수정하지 못해야 합니다. 에이전트는 시험 통과를 목표로 삼아, 실패하는 시험 쪽을 수정할 수 있습니다. 그래서 검증 기준(Chapter 3에서 정한 수용 시험과 check.py)은 권한 설정의 금지 규칙으로 수정을 막습니다(Chapter 2의 지시와 강제). Claude Code 문서에 따르면 파일 수정 금지 규칙은 파일 편집 도구와, 셸에서 Claude Code가 인식하는 파일 명령(sed, tee 등)과 출력 저장 대상에 적용됩니다. 에이전트가 Python 스크립트를 만들어 실행하고, 그 스크립트가 시험 파일을 여는 식으로 간접으로 수정하는 경우에는 적용되지 않습니다(Anthropic, 2026c). 그래서 확인 방법에서 git status로 두 파일에 변경이 없는지 다시 확인합니다.

그림 7-1의 다시 작업은 훅(Hook)으로 자동화할 수 있습니다. check.py는 작업 단위를 마칠 때 사용자가 판정하려고 실행하는 검사이고, 에이전트가 작업하는 동안에는 훅이 검사를 자동으로 실행합니다. 예제의 훅은 파일을 편집한 뒤마다 단위 테스트를 실행하고, 실패하면 종료 코드 2로 끝나 실패 출력을 모델에 돌려줍니다(Chapter 3). 편집은 이미 실행된 뒤이므로 훅이 편집을 막지는 못하고, 다시 작업하게 합니다(Anthropic, 2026d). 이 훅은 단위 테스트만 실행하므로, 수용 시험은 단위를 마칠 때 check.py로 확인합니다. 검사가 통과할 때까지 에이전트가 응답을 끝내지 못하게 하는 Stop 훅(Chapter 1)도 있으며, Claude Code 문서는 이를 결정적인 관문으로 설명합니다(Anthropic, 2026b). 훅과 검토 하위 에이전트를 직접 만드는 실습은 부록 실습의 실습 4에 있습니다.

실패와 막는 장치

CR의 검증을 설계하지 않으면, 보고만 믿고 동작하지 않는 결과를 완료로 처리합니다. 표 7-7은 CR에서 생길 수 있는 실패와 원인, 막는 장치입니다.

확인 방법

판정은 보고가 아니라 출력 원문으로 합니다. 명령은 실습 폴더(examples/expense-app/)에서 실행합니다. 표 7-8은 CR의 완료를 판정할 때 확인할 것과 확인 위치입니다.

원칙과 점검 질문

완료 기준은 작업을 맡기기 전에 검사로 변환하고, 완료 보고가 아니라 검사 출력 원문으로 판정합니다.

코드가 아닌 업무에서도 증거를 정할 수 있습니다. 보고서의 수치는 원자료와 대조한 결과표를, 문서의 형식은 검사 출력을 보고와 함께 받습니다. 자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 맡긴 작업의 완료 기준 가운데 문장으로만 있는 것은 무엇입니까?
  2. 에이전트가 검증 기준을 수정할 수 없도록 권한으로 금지되어 있습니까?
  3. 완료 보고를 받을 때 함께 확인할 출력 원문이 정해져 있습니까?
