Chapter 7 검증 설계: 완료 보고 대신 증거 받기

결과를 받아들이는 근거는 완료 보고가 아니라, 검사 출력과 산출물처럼 사용자가 직접 확인할 수 있는 증거입니다.

이 장에서는 에이전트(Agent)가 만든 결과를 무엇으로 받아들일지 정하는 검증 설계를 다룹니다. 에이전트는 작업을 마치면 완료 보고를 작성하는데, 완료 보고는 결과를 만든 에이전트 자신의 판단이어서 결과가 실제로 동작한다는 뜻은 아닙니다. 완료 보고만으로 결과를 받아들이면 동작하지 않는 결과도 완료로 처리될 수 있으므로, 작업을 맡기기 전에 어떤 증거로 완료를 판정할지 정해야 합니다.

검증 설계에서 정할 것은 세 가지입니다. 완료 기준을 통과와 실패로 갈리는 검사로 변환하고, 완료 기준마다 누가 판정하는지에 따라 세 가지 검증 방법(자동 검사, 출력 확인, 독립 검수) 가운데 하나를 정합니다. 코드로 판정하기 어려운 기준은 항목별 판정 방법을 적은 표에 따라 결과를 만들지 않은 쪽이 판정하게 합니다. Chapter 6이 작업 단위마다 완료 기준과 확인 방법을 적었다면, 이 장은 그 확인을 어떻게 설계하고 무엇으로 판정할지를 정합니다.

먼저 완료 보고가 근거가 되지 않는 이유와 완료 기준을 검사로 변환하는 방법을 살펴보고, 검증 방법의 선택과 판단이 필요한 기준을 표로 판정하는 방법을 익힌 뒤, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)의 검증을 설계하는 예제를 다룹니다.

  • 완료 보고는 결과를 만든 쪽의 판단이므로 판정 근거로 사용하지 않고, 검사 출력이나 산출물로 판정합니다.
  • 완료 기준은 작업을 맡기기 전에 통과, 실패로 갈리는 검사로 변환합니다.
  • 완료 기준마다 스크립트, 사용자, 결과를 만들지 않은 쪽 가운데 판정할 쪽을 하나 정하고, 판단이 필요한 기준은 항목별 판정 방법을 적은 표로 채점합니다.

완료 보고가 근거가 되지 않는 이유

완료 보고는 일을 한 쪽이 작성한 글이므로, 결과가 실제로 동작한다는 근거가 되지 못합니다. 에이전트는 자기 결과에 오류가 있어도 알아차리지 못한 채 완료를 보고할 수 있습니다. 그래서 완료 보고와 증거를 구분해야 합니다. 완료 보고는 에이전트가 작업을 마쳤다고 알리는 글이고, 증거는 검사 출력이나 산출물(에이전트가 만든 코드, 문서, 화면)처럼 사용자(에이전트에 일을 맡기고 결과를 확인하는 사람)가 직접 확인할 수 있는 것입니다.

이 구분을 뒷받침하는 공개 사례로 Claude Code의 장기 실행 글이 있습니다. 글의 실험에서 에이전트는 충분한 시험 없이 기능을 완료로 표시하는 경향을 보였습니다. 에이전트는 단위 테스트(Unit Test)나 개발 서버(만드는 중인 웹 앱을 실행해 둔 프로그램)에 웹 요청을 보내 응답을 받아 오는 curl 명령으로 시험했지만, 기능이 처음부터 끝까지 동작하지 않는다는 사실은 알아차리지 못했습니다. 단위 테스트는 프로그램의 부품 하나가 정해진 대로 동작하는지를 확인하는 시험이어서, 부품을 이어 사용하는 흐름 전체는 확인하지 못합니다. 브라우저 자동화 도구(프로그램이 브라우저를 열어 사람 대신 누르고 입력하는 도구)로 사람이 사용하는 방식 그대로 시험하라고 명시하자, 에이전트가 기능을 처음부터 끝까지 확인했습니다.

이 사례에서 두 가지를 읽을 수 있습니다. 결과를 만든 에이전트의 판단은 완료의 근거가 되지 않습니다. 사람처럼 시험하라고 명시하면 에이전트도 기능을 처음부터 끝까지 확인합니다.

출력으로 판정하는 방식은 코드가 아닌 업무에도 적용됩니다. 원고 작업을 에이전트에게 맡길 때도 완료 보고 대신 출력 원문, 곧 실행한 명령이 출력한 내용을 수정하거나 줄이지 않은 그대로를 근거로 받을 수 있습니다. 원고를 수정했다는 보고에 빌드(원고나 코드로 결과물을 만드는 일), lint, 배포한 사이트의 쪽이 모두 열리는지 확인하는 명령의 출력을 함께 받는 방식입니다. lint는 원고나 코드의 형식 오류를 정해진 규칙으로 자동 검사하는 도구입니다. 저장소에 반영된 뒤에는 지속적 통합(Continuous Integration, CI)의 검사 결과로 다시 확인할 수 있습니다. Chapter 1에서 본 것처럼 지속적 통합은 저장소에 변경이 올라올 때 자동으로 검사를 실행하는 장치입니다.

에이전트가 시험을 실행했다고 보고해도 같은 문제가 남습니다. 앞의 장기 실행 글의 실험에서 에이전트는 시험을 실행하고도 기능이 동작하지 않는 사실을 알아차리지 못했습니다. "확인했습니다"라는 보고 문장과, 어떤 명령을 실행해 무엇이 출력되었는지를 담은 출력 원문은 다른 정보입니다. 출력 원문으로 판정하려면 무엇을 확인할지가 맡기기 전에 정해져 있어야 하므로, 다음 절은 완료 기준을 검사로 변환하는 방법을 다룹니다.

완료 기준을 검사로 변환

완료 기준이 문장으로만 있으면 판정하는 사람마다 결과가 달라지므로, 맡기기 전에 검사로 정해 둡니다. 완료 기준은 일이 끝났다고 판정하는 조건이며, Chapter 6의 작업 단위 분할에서는 작업 단위 목록에 단위마다 적었습니다. 완료 기준 가운데 사람이 업무의 요구로 정한 것을 수용 기준(Acceptance Criteria)이라고 합니다(Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성). 검사는 미리 정한 통과 조건(통과로 판정하는 조건)에 따라 결과를 통과나 실패로 가르는 확인이며, 스크립트가 실행할 수도 있고 사용자나 다른 검토자가 할 수도 있습니다. 완료 기준을 이런 검사로 만드는 일을 이 장에서는 변환이라고 합니다.

변환한 기준은 누가 판정해도 같은 결과가 나와야 합니다. 표 7-1은 문장으로 작성된 완료 기준을 검사로 변환한 예입니다. 수용 시험(Acceptance Test)은 수용 기준을 충족하는지 확인하는 시험입니다. 둘째 행의 구조 검사 스크립트는 문서의 제목 순서나 필수 항목 같은 형식을 검사해 오류를 찾을 때만 출력하므로, 출력이 비어 있으면 통과입니다. 넷째 행의 응답 코드 200은 웹 서버가 요청을 정상으로 처리했다는 뜻입니다.

새로 만들 결과를 확인하는 검사는 구현 전에는 실패하고 구현 뒤에는 통과해야 합니다. 구현 전에도 통과하는 검사는 작업을 했는지 보여 주지 못하기 때문입니다. 표 7-1의 셋째 행처럼 기존 기능이 유지되는지 보는 검사는 구현 전에도 통과하므로, 그런 검사만 있는 완료 기준에는 새로 생길 결과(추가한 항목, 새 화면의 요소)가 있는지 보는 검사를 하나 더 둡니다. 더한 검사를 구현 전 상태에서 한 번 실행해 실패하는지 확인하면, 그 검사가 작업을 보여 주는지 알 수 있습니다.

변환한 기준을 확인하는 방법은 다음 절에서, 판단이 필요한 기준을 채점하는 방법은 뒤의 기준표와 채점 절에서 다룹니다.

검증 방법의 선택

기준을 검사로 변환해도 모든 기준을 같은 방법으로 확인할 수는 없습니다. 기준을 확인하는 방법을 검증 방법이라고 하며, 누가 판정하는가에 따라 세 가지로 나눕니다. Chapter 6의 작업 단위 목록에 적은 확인 방법은 이 가운데 하나를 그 단위에 맞게 적은 것입니다. 자동 검사는 스크립트나 테스트가 판정합니다. 출력 확인은 사용자가 명령의 출력이나 산출물을 직접 확인합니다. 독립 검수는 결과를 만들지 않은 다른 에이전트나 사람이 검토합니다.

검사로 변환한 완료 기준 하나하나를 기준 항목이라고 하며, 기준 항목마다 가장 알맞은 방법을 하나 선택합니다. 세 방법을 차례로 모두 거칠 필요는 없습니다. 작업 단위의 기준 항목이 모두 통과하면 다음 작업 단위로 넘어가고, 하나라도 미통과면 미통과의 근거(오류 출력, 검토 보고)를 에이전트에 돌려 같은 작업 단위를 다시 수행하게 합니다. 어느 방법을 선택하든 사용자는 마지막에 판정에 사용한 출력 원문(검사 출력, 검토 보고, 승인 기록)을 보고 판정이 실제로 내려졌는지 확인합니다. 출력 확인은 이와 달리 통과와 실패의 판정 자체를 사용자가 내리는 방법입니다.

자동 검사와 독립 검수는 Claude Code 문서의 안내에도 나옵니다. 문서는 에이전트가 실행할 수 있는 검사(테스트, 빌드, 화면 캡처 비교)를 제공하라고 안내합니다. 검사가 없으면 결과가 끝난 것처럼 보이는 것이 유일한 신호가 되고, 사용자가 직접 확인을 되풀이해야 한다는 것이 문서가 드는 이유입니다. 같은 문서는 일을 한 에이전트가 자기 결과를 판정하지 않도록, 앞의 대화 기록이 없는 새 컨텍스트(Context)에서 검토하게 하는 방법도 안내합니다.

그림 7-1은 위에서 아래로 읽습니다. 산출물을 기준 항목으로 나누고, 항목마다 선택한 검증 방법의 출력 원문으로 판정한 뒤, 모든 항목이 통과하면 다음 작업 단위로, 미통과면 오른쪽의 다시 작업으로 가고, 다시 작업은 왼쪽 가장자리를 따라 기준 항목으로 돌아갑니다. 오른쪽 위의 완료 보고는 어느 단계와도 이어지지 않습니다.

표 7-3은 세 방법이 각각 어떤 확인에 알맞은지 보여 줍니다.

반복되는 확인을 자동 검사로 옮긴 사례도 있습니다. Codex의 하네스(Harness) 엔지니어링 글에 따르면, Codex로 제품을 만든 OpenAI 팀은 문서 구조를 전용 lint와 지속적 통합으로 기계적으로 검사했습니다. 사람은 작업의 우선순위를 정하고 결과를 검증하는 역할을 맡았습니다. 이 장의 구분으로 보면, 반복되는 확인은 자동 검사에 맡기고 사람은 판단이 필요한 확인에 시간을 사용하는 구성입니다.

기준표와 채점

표 7-1처럼 코드로 판정하는 검사로 변환할 수 있는 기준만 있는 것은 아닙니다. 문장의 어조나 요약의 충실도처럼 판단이 필요한 기준은 독립 검수로 확인하고, 그 판정 방식을 따로 정해야 합니다. 기준 하나를 정답, 오답이나 점수 같은 판정값으로 만드는 일을 채점이라고 합니다. 채점 방법은 코드 기반, 대규모 언어 모델(Large Language Model, LLM) 기반, 사람의 세 가지입니다.

채점 방법은 앞 절의 검증 방법과 다음처럼 대응합니다. 코드 기반 채점은 자동 검사에 해당하고, LLM 기반 채점과 사람 채점은 결과를 만들지 않은 쪽이 판정하는 독립 검수에 해당합니다. 출력 확인은 사용자가 산출물을 직접 보고 판정하는 방법이어서 채점 방법에 포함하지 않습니다.

채점할 때 항목마다 무엇을 보고 어떻게 판정할지 적은 표를 기준표(Rubric)라고 합니다. 채점하는 쪽이 결과와 비교할, 기준이 되는 답은 예시 답안이라고 합니다.

모델의 출력을 시험하는 평가를 만드는 방법을 설명한 Anthropic의 평가 문서는 채점 방법을 세 가지로 나누고, 가장 빠르고 신뢰할 수 있으며 확장하기 쉬운 방법을 선택하라고 안내합니다. 코드 기반 채점은 결과가 정답과 정확히 일치하는지, 특정 문구가 들어 있는지를 확인합니다. 문서는 LLM 기반 채점은 신뢰도를 먼저 시험한 뒤 확대하고, 사람 채점은 가능하면 피하라고 안내합니다. 표 7-4는 세 방법을 비교합니다. 표의 입력 열, 코드 기반과 사람 채점의 판정 형식은 평가 문서에 없는 내용으로, 이 장에서 정리했습니다.

LLM 기반 채점의 결과는 기준표에 따라 달라집니다. 평가 문서는 상세하고 명확한 기준표를 작성하라고 안내하고, 답변의 첫 문장에 특정 회사 이름이 없으면 오답으로 처리하는 기준을 예로 듭니다. 판정 결과는 정답과 오답 또는 1~5점처럼 구체적인 형태로 받습니다. 점수나 정답 없이 글로만 남기는 평가는 빠르게, 대량으로 판정하기 어렵기 때문입니다.

문서의 예제는 기준이 되는 정답을 예시 답안으로 두고, 채점하는 모델이 결과를 예시 답안과 비교하게 합니다. 이와 별도로 문서의 다른 LLM 기반 채점 예제 코드 주석에는 결과를 만든 모델과 다른 모델로 평가하는 편이 일반적으로 좋다는 안내도 있습니다. 다른 모델로 채점하면 결과를 만든 모델이 자기 결과를 채점하지 않으므로, 앞 절의 독립 검수에 해당합니다. 1~5점처럼 점수로 받으면, 몇 점부터 통과인지 정한 통과 조건(예: 4점 이상)도 채점 전에 정합니다. 그림 7-2는 왼쪽의 입력 셋이 채점으로 들어가고, 채점이 낸 판정값을 오른쪽 가운데의 통과 조건과 비교해 통과와 다시 작업으로 갈리는 순서를 보여 줍니다.

표 7-5는 그림 7-2의 구성 요소를 설명합니다.

기준표로 채점할 때 정할 것은 세 가지입니다.

  • 채점 방법: 항목마다 코드, LLM, 사람 가운데 가장 빠르고 신뢰할 수 있는 방법을 정합니다.
  • 기준표와 통과 조건: LLM 기반 채점과 사람 채점 항목에는 채점 전에 기준표와 통과 조건을 준비하고, 기준이 되는 답이 있으면 예시 답안도 준비합니다.
  • 사람의 확인 지점: 사람 채점은 비용이 크므로, 되돌리기 어려운 결정에 둡니다(Chapter 6의 맡길 업무의 선정).

예제: 변경 요청 사항의 검증 설계

기준마다 검증 방법을 하나 선택하고 출력 원문으로 판정하는 원리를 변경 요청 사항에 적용합니다. 변경 요청 사항은 가상 프로젝트인 경비 정산 시스템 개편에 재무팀이 보낸 요청입니다. 요청 내용은 직원이 경비를 돌려받으려고 올리는 정산 요청에 프로젝트 코드(경비가 속한 프로젝트의 식별 번호)를 목록에서 선택해 입력하게 하는 변경이며, 수용 기준은 다섯 가지입니다(Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성).

  1. 정산 요청 등록 화면에서 프로젝트 코드 목록의 코드를 선택할 수 있습니다.
  2. 프로젝트 코드 목록에 없는 코드로 등록하면 거부하고, 거부 사유에 입력한 코드를 표시합니다.
  3. 목록 화면에 프로젝트 코드를 표시합니다.
  4. 프로젝트 코드가 없는 기존 정산 요청도 이전처럼 목록 화면에 나옵니다.
  5. 등록 처리는 원본 자료(data/projects.csv)를 변경하지 않습니다.

표의 검토 하위 에이전트(Subagent)는 바뀐 내용을 수용 기준과 대조해 보고만 하는 하위 에이전트입니다. 표 7-6은 변경 요청 사항의 기준마다 검증 방법과 통과 조건을 정한 결과입니다.

기준마다 방법 하나를 선택하는 것이 기본입니다. 둘째 행과 셋째 행은 같은 수용 기준을 한 번 더 보는 추가 장치입니다. 둘째 행은 시험이 기준마다 정해진 경우만 확인해서, 시험이 통과해도 시험이 다루지 않는 경우가 남을 수 있기 때문에 둡니다. 검토 하위 에이전트가 근거 파일과 줄 번호로 기준을 다시 대조합니다. 셋째 행은 수용 시험 1이 화면을 그리는 문서(HTML)에 선택 항목이 있는지만 보기 때문에 둡니다. 사용자가 브라우저에서 직접 코드를 선택해 확인합니다. 넷째 행의 통합 테스트 시나리오(여러 기능을 이어서 실행해 확인하는 시험 절차)는 수용 기준에 들지 않습니다. 작업 단위 목록의 작업 5에서 에이전트가 초안을 작성하면 승인자(되돌리기 어려운 동작과 작업 단위의 완료를 승인하는 사람)가 승인하는 단위입니다(Chapter 6의 예제: 변경 요청 사항의 작업 단위 나누기).

첫째 행의 수용 시험을 실행하는 파일은 Chapter 3에서 정한 검사 스크립트 check.py, 곧 단위 테스트와 수용 시험을 명령 한 번으로 실행하는 작은 프로그램입니다. 보고 대신 출력 원문으로 판정하려면 스크립트가 무엇을 출력하는지가 중요하므로, 핵심 부분을 봅니다. 다음은 check.py의 9~10행과 21~37행을 그대로 옮긴 발췌이고, 파일 설명, 모듈을 불러오는 두 줄(import), 시험 이름을 모으는 함수(test_ids)는 생략했습니다. 따라 입력할 필요 없이 읽기만 하면 됩니다.

ACCEPTANCE_COUNT = 5  # docs/CR.md의 수용 기준 수
UNIT_KEYWORD = "project_code"

ok = True
for folder in ("tests", "acceptance"):
    suite = unittest.TestLoader().discover(folder)
    ids = list(test_ids(suite))
    run = unittest.TextTestRunner(verbosity=0).run(suite)
    failed, skipped = len(run.failures) + len(run.errors), len(run.skipped)
    line = f"{folder}: 실행 {run.testsRun}건, 실패 {failed}건, 건너뜀 {skipped}건"
    ok = ok and run.testsRun > 0 and failed == 0 and skipped == 0
    if folder == "tests":
        count = sum(1 for i in ids if UNIT_KEYWORD in i)
        line += f", {UNIT_KEYWORD} 시험 {count}건"
        ok = ok and count > 0
    else:
        line += f"(정한 수 {ACCEPTANCE_COUNT}건)"
        ok = ok and run.testsRun == ACCEPTANCE_COUNT
    print(line)
sys.exit(0 if ok else 1)

앞의 두 줄은 수용 시험의 정한 수(5건)와, 단위 테스트 이름에서 찾을 낱말(project_code)입니다. 반복문은 단위 테스트 폴더(tests)와 수용 시험 폴더(acceptance)에서 시험을 찾아 실행하고, 폴더마다 실행, 실패, 건너뜀 건수를 한 줄로 출력합니다. tests 줄에는 이름에 project_code가 든 시험의 수를, acceptance 줄에는 정한 수를 덧붙입니다. 종료 코드는 명령이 끝날 때 돌려주는 값이며, 0은 성공을 뜻합니다. ok는 조건을 하나씩 모아 두는 값이며, 마지막 줄은 ok에 모은 다음 조건을 모두 충족할 때만 종료 코드 0으로, 아니면 1로 끝냅니다.

  • 두 폴더 모두 실행 건수가 0보다 크고, 실패와 건너뜀이 0건임
  • 수용 시험이 정한 수(5건)만큼 실행됨
  • 단위 테스트에 project_code 시험이 1건 이상 있음

실행 건수가 0건인 폴더를 실패로 판정하는 것은, 시험 파일을 찾지 못해 하나도 실행되지 않으면 실패 건수도 0건이 되어, 통과로 보이기 때문입니다.

다음은 변경 요청 사항을 구현하기 전의 기준 상태에서 python check.py를 실행한 출력입니다(부록의 실습 1. 실습 저장소와 기준 상태).

tests: 실행 3건, 실패 0건, 건너뜀 0건, project_code 시험 0건
acceptance: 실행 5건, 실패 3건, 건너뜀 0건(정한 수 5건)

기준 상태에서는 project_code 시험이 0건이고 수용 시험의 실패가 3건이므로 종료 코드는 1입니다. 실패한 시험의 번호는 이 두 줄에 나오지 않고, 출력 가운데 FAIL로 시작하는 줄의 시험 이름(예: FAIL: test_1_form_offers_project_codes)에 나옵니다. 이 예제의 예상 결과에서는 구현을 마치면 acceptance 줄이 "실행 5건, 실패 0건, 건너뜀 0건(정한 수 5건)"이 되고, tests 줄의 project_code 시험이 1건 이상이며 실패가 0건이면 종료 코드가 0입니다.

Chapter 6에서 본 것처럼 작업 단위 목록의 작업 2(데이터 모델에 프로젝트 코드 항목 추가)와 관련된 수용 시험 4, 5는 구현 전에도 통과하므로, 작업 2의 확인 방법은 사람의 commit 확인입니다. 앞의 완료 기준을 검사로 변환 절의 방법대로라면, 정산 요청 데이터에 project_code 항목이 있는지 보는 시험을 더해 구현 전에 실패하게 만듭니다. 이 예제는 그런 시험을 두지 않았으므로, 작업 2의 구현은 표 7-6 둘째 행의 대조와 commit 확인, 곧 사람이 commit을 승인하기 전에 바뀐 파일과 변경 내용을 보는 일로 확인합니다. 시험을 더한다면 검증 기준에 속하므로 사람이 작성하고, 수용 시험 폴더에 둘 때는 check.py의 정한 수(5건)도 함께 수정합니다.

표 7-6 둘째 행의 검토 하위 에이전트는 읽기 도구(Read, Grep, Glob)만 사용하도록 정의되어 있습니다(Chapter 3의 명세서를 옮길 하네스 설정 파일). 결과를 만든 구현 에이전트(작업 단위를 처리하며 코드를 수정하는 주 에이전트)와 다른 새 컨텍스트에서, 변경 요청 사항의 수용 기준을 기준표로 삼아 변경 내용을 대조합니다. 판정값은 기준마다 충족, 미충족, 확인 불가 가운데 하나이고, 근거 파일과 줄 번호를 함께 보고합니다. 통과 조건은 표 7-6처럼 채점 전에 정합니다. 기준마다 맞는 코드가 하나로 정해지지 않으므로 예시 답안은 두지 않습니다.

표 7-6의 첫째 행을 믿으려면 에이전트가 수용 시험을 수정하지 못해야 합니다. 에이전트는 시험 통과를 목표로 삼아, 실패하는 시험 쪽을 수정할 수 있습니다. 그래서 검증 기준(수용 시험과 check.py)은 권한 규칙(Permission Rule)의 금지 목록(deny)으로 수정을 막습니다. 금지 규칙은 에이전트의 판단과 관계없이 Claude Code가 적용하는 강제 수단입니다(Chapter 2의 다섯 구성 요소가 만드는 흐름). Claude Code 문서에 따르면 파일 수정 금지 규칙은 파일 편집 도구와, 셸 명령(터미널에 입력하는 명령) 가운데 Claude Code가 알아보는 파일 명령(sed, tee 등)과, 명령의 출력을 > 기호로 저장하는 대상 파일에 적용됩니다. 에이전트가 Python 스크립트를 만들어 실행하고, 그 스크립트가 시험 파일을 여는 식으로 간접으로 수정하는 경우에는 적용되지 않습니다. 문서는 실행되는 모든 프로그램의 접근을 막으려면 샌드박스(Sandbox), 곧 운영 체제 수준에서 명령이 접근할 수 있는 파일과 네트워크를 제한하는 기능을 켜라고 안내합니다. 이 예제는 샌드박스를 켜지 않고, 확인 방법에서 바뀐 파일과 commit 기록으로 수용 시험 폴더와 check.py에 변경이 없는지 확인해 보완합니다.

그림 7-1의 다시 작업은 훅(Hook), 곧 정해진 시점에 자동으로 실행되는 명령으로 자동화할 수 있습니다. check.py는 작업 단위를 마칠 때 구현 에이전트가 실행하고 사용자가 그 출력 원문으로 판정하는 검사이고, 에이전트가 작업하는 동안에는 훅이 검사를 자동으로 실행합니다. 예제의 훅은 파일을 편집할 때마다 그 뒤에 단위 테스트를 실행하고, 실패하면 종료 코드 2로 끝나 실패 출력을 모델에 돌려줍니다. 편집은 이미 실행된 뒤이므로 훅이 편집을 막지는 못하고, 다시 작업하게 합니다. 이 훅은 단위 테스트만 실행하므로, 수용 시험은 단위를 마칠 때 check.py로 확인합니다.

검사가 통과할 때까지 에이전트가 응답을 끝내지 못하게 하는 Stop 훅(Chapter 1의 에이전트 루프와 종료 조건)도 있으며, Claude Code 문서는 이를 모델의 판단과 관계없이 검사 결과로만 종료를 정하는 관문으로 설명합니다. 그러나 연속으로 막을 수 있는 횟수에는 상한이 있어(기본 8회, 도구를 호출하면 다시 셈), 상한에 닿으면 검사가 통과하지 않아도 응답이 끝날 수 있습니다. Stop 훅은 종료 코드 2일 때만 종료를 막으므로, 실패하면 종료 코드 1로 끝나는 check.py를 Stop 훅에서 사용할 때는 훅 명령이 종료 코드 2로 끝나게 합니다. 훅과 검토 하위 에이전트를 직접 만드는 실습은 부록의 실습 4. 검증 장치에 있습니다.

실패를 예방하는 장치

변경 요청 사항의 검증을 설계하지 않으면, 보고만 믿고 동작하지 않는 결과를 완료로 처리할 수 있습니다. 표 7-7은 변경 요청 사항의 검증에서 생길 수 있는 실패와 원인, 방지 장치를 정리합니다.

설정과 결과의 확인 방법

명령은 부록 실습 1에서 복사하고 git init(폴더를 Git 저장소로 만드는 명령)으로 기록을 시작한 실습 폴더(expense-practice)의 터미널에서 실행합니다. 표 7-8의 위 네 행은 사용자가 명령과 브라우저로 직접 확인하고, 아래 두 행은 검토 하위 에이전트의 보고와 승인자의 승인 기록을 확인합니다. python app.py는 서버를 띄운 채 다음 입력을 받지 않으므로, 확인을 마치면 Ctrl+C로 종료합니다.

설계 원칙과 점검 질문

완료 기준은 작업을 맡기기 전에 검사로 변환하고, 완료 보고가 아니라 검사 출력 원문으로 판정합니다.

코드가 아닌 업무에서도 보고서의 수치는 원자료와 대조한 결과표를, 문서의 형식은 검사 출력을 보고와 함께 받습니다. 자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 맡긴 작업의 완료 기준 가운데 문장으로만 있는 것은 무엇입니까?
  2. 완료 기준마다 판정하는 쪽(스크립트, 사용자, 결과를 만들지 않은 쪽)이 하나씩 정해져 있습니까?
  3. 완료 보고를 받을 때 함께 확인할 출력 원문이 정해져 있습니까?
