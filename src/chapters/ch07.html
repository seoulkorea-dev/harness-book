Chapter 7 검증 설계: 완료 보고 대신 증거 받기

에이전트(Agent)는 작업을 마치면 완료 보고를 작성하며, 그 보고는 에이전트 자신의 판단입니다. 결과를 받아들이는 근거는 완료 보고가 아니라, 검사 출력과 산출물처럼 사용자가 직접 확인할 수 있는 증거입니다. 그래서 완료 보고만으로 결과를 받아들이면, 실제로 동작하지 않는 결과가 완료로 처리됩니다. 따라서 작업을 맡기기 전에 어떤 증거로 완료를 판정할지 정해야 합니다. 이 장에서는 완료 기준을 검사로 변환하는 방법과 검증 방법의 선택 기준을 다룹니다.

  • 완료 보고는 결과를 만든 쪽의 판단이므로 판정 근거가 아닙니다.
  • 검증 방법은 자동 검사, 출력 확인, 독립 검수의 세 가지입니다.
  • 완료 기준은 작업을 맡기기 전에 검사 가능한 형태로 작성합니다.

완료 보고가 근거가 되지 않는 이유

Anthropic은 장시간 실행 에이전트 실험에서 에이전트가 충분한 시험 없이 기능을 완료로 표시하는 실패를 보고했습니다. 에이전트는 코드를 수정하고 단위 테스트까지 실행했지만, 기능이 처음부터 끝까지 동작하지 않는다는 사실은 인식하지 못했습니다. 브라우저 자동화 도구로 사람이 사용하는 방식 그대로 시험하도록 지시하자, 에이전트는 코드만으로는 드러나지 않던 오류를 발견하고 수정했습니다(Young, 2025).

이 사례는 두 가지를 보여 줍니다. 결과를 만든 에이전트의 판단은 완료의 근거가 되지 않습니다. 확인 수단을 제공하면 에이전트도 오류를 발견합니다.

이 책의 작가는 에이전트의 완료 보고 대신 검사 명령의 출력 원문을 근거로 받습니다. 원고를 수정했다는 보고에는 빌드, lint, 사이트 검증 명령의 출력이 함께 있어야 합니다. lint는 원고나 코드의 형식 오류를 정해진 규칙으로 자동 검사하는 도구입니다. 저장소에 반영된 뒤에는 CI(Continuous Integration) 도구인 GitHub Actions의 검사 결과로 다시 확인합니다. CI는 저장소에 변경을 반영할 때마다 빌드와 검사를 자동으로 실행하는 방식입니다.

검증 방법의 선택

검증 방법은 세 가지입니다. 자동 검사는 스크립트나 테스트가 결과를 판정합니다. 출력 확인은 사용자가 명령의 출력이나 산출물을 직접 확인합니다. 독립 검수는 결과를 만들지 않은 다른 에이전트나 사람이 검토합니다. 그림 7-1은 산출물이 세 가지 검증을 거쳐 통과하거나 재작업으로 돌아가는 구조를, 표 7-1은 방법별 적합한 대상을 보여 줍니다.

OpenAI는 Codex로 제품을 개발하면서 문서 구조를 전용 lint와 CI로 기계적으로 검사했다고 밝혔습니다. 사람은 작업의 우선순위를 정하고 결과를 검증하는 역할을 맡았습니다(Lopopolo, 2026). 반복되는 확인은 자동 검사로 옮기고, 사람은 판단이 필요한 확인에 시간을 사용하는 구성입니다.

완료 기준을 검사로 변환

완료 기준이 문장으로만 있으면 판정하는 사람마다 결과가 달라집니다. 완료 기준은 작업을 맡기기 전에 검사할 수 있는 형태로 작성합니다. 표 7-2는 문장으로 작성된 완료 기준을 검사로 변환한 예입니다.

기준표와 예시 답안

완료 기준 가운데에는 코드로 판정하기 어려운 것이 있습니다. 문장의 어조나 요약의 충실도처럼 판단이 필요한 기준입니다. Anthropic의 평가 문서는 채점 방법을 세 가지로 나누고, 가장 빠르고 신뢰할 수 있으며 확장하기 쉬운 방법을 선택하라고 안내합니다(Anthropic, 2026).

  • 코드 기반 채점: 가장 빠르고 신뢰할 수 있지만, 규칙으로 표현하기 어려운 판단에는 맞지 않습니다. 결과가 정답과 정확히 일치하는지, 특정 문구가 들어 있는지를 확인합니다.
  • LLM 기반 채점: 빠르고 유연해 복잡한 판단에 적합합니다. 문서는 먼저 신뢰도를 시험한 뒤 확대하라고 안내합니다.
  • 사람 채점: 가장 유연하고 품질이 높지만, 느리고 비용이 큽니다. 문서는 가능하면 피하라고 안내합니다.

LLM 기반 채점의 핵심은 기준표입니다. 문서는 상세하고 명확한 기준표를 작성하라고 안내하고, 첫 문장에 회사 이름이 없으면 오답으로 처리하는 기준을 예로 듭니다. 판정 결과는 정답과 오답 또는 1~5점처럼 구체적인 형태로 받습니다. 순수한 정성 평가는 빠르게, 대량으로 판정하기 어렵기 때문입니다.

문서의 예제는 기준이 되는 정답을 예시 답안으로 두고, 채점 모델이 결과를 예시 답안과 비교하게 합니다. 예제의 설명에는 결과를 만든 모델과 다른 모델로 평가하는 편이 일반적으로 좋다는 안내도 있습니다. 그림 7-2는 세 가지 채점 방법의 입력, 판정 형식, 장점과 주의점입니다.

표 7-3은 Chapter 3의 CR-07 예제의 완료 기준을 채점 방법별로 나눈 기준표입니다.

기준표를 만들 때 정할 것은 세 가지입니다.

  • 채점 방법: 항목마다 코드, LLM, 사람 가운데 가장 빠르고 신뢰할 수 있는 방법을 정합니다.
  • 기준표와 예시 답안: LLM 기반 채점 항목에는 통과 조건과 예시 답안을 준비합니다.
  • 사람의 확인 지점: 사람 채점은 비용이 크므로, 되돌리기 어려운 결정에만 둡니다.

수용 시험 검사 예제

Chapter 3의 CR-07 예제는 검증 단계로 검사 스크립트 check.py를 사용합니다. 이 스크립트는 에이전트가 수정할 수 있는 단위 테스트와, 사람이 작성하고 에이전트가 수정할 수 없는 수용 시험을 함께 실행합니다. 다음은 스크립트의 핵심 부분입니다.

import sys, unittest

results = {}
for folder in ("tests", "acceptance"):
    suite = unittest.TestLoader().discover(folder)
    run = unittest.TextTestRunner(verbosity=0).run(suite)
    results[folder] = (run.testsRun, len(run.failures) + len(run.errors))

for folder, (count, failed) in results.items():
    print(f"{folder}: 실행 {count}건, 실패 {failed}건")
sys.exit(0 if all(count > 0 and failed == 0 for count, failed in results.values()) else 1)

스크립트는 판정 근거인 실행 건수와 실패 건수를 폴더별로 출력합니다. 사용자는 "검증을 통과했다"는 보고가 아니라, 두 폴더의 실행 건수와 실패 건수가 출력된 원문을 확인합니다. 스크립트는 실행 건수가 0건인 폴더도 실패로 판정합니다. 시험이 하나도 실행되지 않으면 실패 건수도 0건이 되어, 통과로 보이기 때문입니다. 검사 스크립트와 수용 시험은 권한 설정으로 수정을 금지해서, 에이전트가 판정 기준을 변경하지 못하게 합니다.

에이전트가 스스로 확인했다고 보고하면 충분하다는 의견이 있습니다. 앞의 Anthropic 사례에서 에이전트는 단위 테스트를 실행하고도 기능이 동작하지 않는 사실을 인식하지 못했습니다. 확인을 했다는 보고와 확인의 결과는 다른 정보입니다.

검증 설계는 작업을 맡기기 전에 완료 기준을 검사로 변환하고, 그 출력 원문을 판정의 근거로 정하는 일입니다.
