Chapter 2 하네스의 구성 요소

도구를 연결하는 것만으로는 에이전트의 결과를 믿을 수 없고, 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소를 정해야 합니다.

도구를 연결하면 에이전트(Agent)는 파일을 읽고, 코드를 수정하고, 테스트를 실행할 수 있습니다. 요청을 받은 에이전트는 저장소를 살펴보고, 필요한 파일을 찾아 코드를 수정한 뒤 변경 결과를 확인합니다. 그러나 결과를 받아 보면 도구만으로는 정할 수 없었던 네 가지가 남습니다.

  • 에이전트가 수정해도 되는 범위
  • 사람이 확인해야 할 일과 에이전트가 진행할 일의 경계
  • 다음 세션이 이어 갈 지점
  • 완료했다는 보고를 믿을 근거

이 네 가지의 답은 모델 안에 있지 않습니다. 모델은 주어진 정보와 도구로 판단합니다. 판단의 범위, 허용되는 동작, 남길 기록, 결과를 믿을 근거는 모델 바깥의 하네스(Harness)가 정합니다(Chapter 1의 에이전트와 하네스의 정의). 하네스에서 정할 것은 역할, 도구, 권한, 기록, 검증의 다섯 가지이며, 이 다섯 가지를 하네스의 다섯 구성 요소라고 합니다.

이 장에서는 먼저 하네스에서 정할 다섯 구성 요소가 각각 어떤 문제를 다루는지 살펴봅니다. 이어서 규칙을 규칙 문서에 적을지 제품이 강제하게 할지 판단하는 기준을 다룹니다. 이 순서로 읽으면 마지막 예제인 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)에서 정한 값마다 그렇게 정한 이유가 보입니다.

  • 도구만으로 정할 수 없는 수정 범위, 사람과의 경계, 이어 갈 지점, 완료의 근거를 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소로 정합니다.
  • 하네스는 미리 정한 도구만 모델에 보여 주고, 보여 준 도구도 호출할 때마다 실행해도 되는지 평가합니다.
  • 어기면 되돌리기 어려운 규칙은 규칙 문서에만 두지 않고, 제품이 직접 적용하는 설정으로 강제합니다.

도구를 연결한 뒤 남는 질문

도입부의 네 가지는 하네스의 설정에서 정합니다. Chapter 1에서 본 대로, 하네스는 제품이 제공하는 실행 장치와 사용자와 팀이 정하는 설정으로 나뉩니다. 작업마다 무엇을 허용하고, 무엇을 사람에게 넘길지는 제품이 자동으로 정해 주지 않습니다. 사용자와 팀이 정해야 합니다.

설정에서 정할 항목이 다섯 구성 요소입니다. 역할은 에이전트가 무엇을 책임지는지, 도구는 무엇을 할 수 있는지, 권한은 어디까지 허용할지, 기록은 무엇을 남기고 이어 갈지, 검증은 결과를 무엇으로 믿을지 정합니다. 표 2-1처럼 하나라도 비면 그 구성 요소에 해당하는 실패가 생길 수 있습니다.

같은 모델을 사용해도 다섯 구성 요소를 어떻게 정하느냐에 따라 에이전트가 하는 일의 범위와 결과를 믿을 근거가 달라집니다. 다음 절부터 구성 요소를 하나씩 살펴보며, 에이전트가 실제로 할 수 있는 일을 정하는 도구와 권한은 더 자세히 다룹니다.

역할: 무엇을 맡기는가

역할은 에이전트가 담당하는 작업과 책임 범위를 정합니다. "코드를 수정해 줘"라는 요청만으로는 역할이 정해지지 않습니다. 대상 저장소, 허용하는 변경의 종류, 테스트와 문서까지 맡는지, 배포나 외부 시스템 변경을 제외하는지가 함께 정해져야 합니다.

역할이 명확하면 도구와 권한의 범위도 좁아집니다. 코드 수정을 맡긴 에이전트에는 파일 읽기, 파일 수정, 테스트 실행이 필요합니다. 배포 승인이나 운영 환경 변경은 역할에서 제외할 수 있습니다. 역할은 사용자가 에이전트에게 맡기려는 책임을 정합니다.

역할은 규칙 문서(Claude Code의 CLAUDE.md)에 에이전트가 할 일과 사람에게 넘길 일로 적습니다. 역할이 비어 있으면 에이전트는 요청된 문제를 해결하는 데 필요하다고 판단한 일까지 넓게 수행할 수 있습니다. 그 판단이 맞더라도, 결과가 사용자가 의도한 범위 안에 있다는 보장은 없습니다.

도구: 무엇을 할 수 있는가

도구는 에이전트가 실제로 수행할 수 있는 작업을 정합니다. 파일을 읽고, 코드를 수정하고, 테스트를 실행하는 능력이 모두 도구에서 나옵니다. 도구를 많이 연결할수록 에이전트에게 맡길 수 있는 작업의 범위도 넓어집니다.

도구에는 비용이 따릅니다. 연결한 도구의 정의는 모델의 컨텍스트(Context)를 차지합니다. 기능이 비슷한 도구가 많아지면 모델은 어느 도구를 사용할지 판단하기 어려워집니다. 그래서 도구는 작업에 필요한 최소한만 연결하는 것이 좋습니다.

코드 수정 작업에는 파일 읽기, 파일 수정, 테스트 실행이 필요합니다. 이메일 발송 도구나 외부 시스템의 데이터를 삭제하는 도구는 이 작업에 필요하지 않습니다. 필요 없는 도구까지 연결하면 컨텍스트만 차지하고, 에이전트가 잘못된 도구를 선택할 가능성도 커집니다.

외부 시스템의 기능을 에이전트의 도구로 연결하는 개방형 표준을 MCP(Model Context Protocol)라고 하고, 이를 구현한 프로그램을 MCP 서버라고 합니다. Claude Code는 기본 설정에서 MCP 서버의 도구 설명을 처음부터 모두 불러오지 않습니다. 도구 이름과 서버 안내만 컨텍스트에 두고, 상세 설명은 필요할 때 불러옵니다. 환경 변수, 모델, MCP 서버 설정에 따라 도구 설명을 처음부터 불러오기도 합니다. 그래도 도구 이름과 안내는 컨텍스트에 남으므로, 사용하지 않는 MCP 서버는 /mcp에서 비활성화하는 것이 좋습니다.

도구 연결 기준

도구는 다음 기준으로 연결합니다.

  • 작업 완료에 필요한 도구만 연결하고, 사용하지 않는 도구는 목록에서 제외합니다.
  • 기능이 겹치는 도구는 줄이고, 사용 빈도가 낮은 도구는 제외합니다.
  • 조회만 필요한 작업에는 수정 도구를 목록에서 제외해, 읽기 도구만 사용하게 합니다.
  • 외부 시스템의 도구는 작업 범위에 맞는 것만 연결합니다.
  • 하위 에이전트(Subagent)는 특정 작업을 맡도록 따로 정의한 에이전트입니다. 하위 에이전트의 정의 파일에는 맡긴 작업에 필요한 도구만 적습니다.

이 기준에는 예외가 하나 있습니다. 하위 에이전트의 정의 파일에서 도구 목록을 생략하면, 하위 에이전트는 하위 에이전트에 허용되는 도구를 모두 물려받습니다.

도구는 에이전트가 무엇을 할 수 있는지를 정합니다. 그러나 할 수 있다는 것과 해도 되는 것은 다릅니다. 이 차이는 권한이 결정합니다.

권한: 어디까지 허용하는가

권한은 에이전트에게 허용하는 동작의 범위를 정합니다. 도구를 연결하면 에이전트는 그 작업을 할 수 있습니다. 실행해도 되는지는 권한이 정합니다. 같은 명령 실행 도구(Bash)라도 저장소 상태를 확인하는 git status와 원격 저장소에 변경을 올리는 git push는 결과의 무게가 다릅니다. 같은 파일 수정 도구라도 테스트 파일을 수정하는 일과 인증 로직을 수정하는 일은 위험이 다릅니다.

그래서 권한은 도구를 연결할 때 한 번 정하고 끝내지 않고, 모델이 도구를 호출할 때마다 평가합니다. 모델은 도구 호출을 요청할 뿐이고, 실행은 하네스가 맡습니다. 따라서 하네스는 요청과 실행 사이에서 그 동작을 허용할지, 사람에게 확인을 요청할지, 거부할지 판단할 수 있습니다.

가용성과 권한 평가

도구를 다루는 설정은 표 2-2처럼 가용성과 권한 평가로 나뉩니다. 가용성은 작업 전에 한 번 정하고, 권한 평가는 도구를 호출할 때마다 합니다.

권한 규칙

Claude Code는 권한 규칙(Permission Rule)을 금지, 확인 요청, 허용의 순서로 대조하고, 처음 일치한 규칙이 결과를 정합니다. 권한 규칙은 설정 파일(settings.json)에 금지, 확인 요청, 허용의 세 목록으로 나누어 적습니다.

  • 금지 규칙: 해당 호출은 실행되지 않습니다.
  • 확인 요청 규칙: 실행 전에 사람에게 확인을 요청합니다.
  • 허용 규칙: 별도 확인 없이 실행할 수 있습니다.

규칙에는 도구 이름만 적을 수도 있고, 도구 이름 뒤 괄호에 대상을 함께 적을 수도 있습니다. 웹 문서를 가져오는 WebFetch처럼 도구 이름만 적은 금지 규칙은 그 도구를 목록에서 제외하므로, 모델은 그 도구를 볼 수 없습니다. Bash(git push *)처럼 대상을 적은 금지 규칙은 Bash 도구를 목록에 남겨 두고, 명령 가운데 git push로 시작하는 부분이 있는 호출만 거부합니다.

어느 규칙에도 일치하지 않는 호출은 권한 모드(Permission Mode)가 처리합니다. 모드에 따라 사람에게 묻거나, 자동으로 승인하거나, 거부합니다.

사람과 프로그램의 승인

대화형 세션에서는 확인 요청 규칙에 일치한 호출을 실행 전에 사람이 승인합니다. 사람이 거절하는 방식에 따라 그 뒤의 진행이 다릅니다. 이유를 적고 거절하면 그 이유가 모델에 전달되어 에이전트는 작업을 계속합니다. 주 대화에서 이유를 적지 않고 거절하면 그 차례의 응답이 멈춥니다.

Claude Agent SDK는 Claude Code의 에이전트 루프를 Python이나 TypeScript 프로그램에서 실행하게 하는 라이브러리입니다. 이렇게 프로그램이 에이전트 루프를 실행하는 경우에는, 기본 권한 모드에서 허용 규칙에 없는 확인 대상 호출을 승인 처리 프로그램 코드가 판단합니다. 프로그램이 거부하면 그 호출은 실행되지 않고, 모델은 거부 메시지를 도구 결과로 받습니다. 승인 처리 프로그램이 없으면 확인이 필요한 호출은 거부됩니다. 권한은 실행 직전에 작동하는 판단 장치입니다.

도구 호출 한 번의 흐름

그림 2-1은 도구 호출 한 번이 가용성과 권한 확인을 거치는 흐름입니다. 위쪽은 컨텍스트 구성 단계에서 정하는 가용성이고, 아래쪽은 도구 호출이 권한 확인을 거쳐 실행되거나 거부되는 과정입니다. 실행 결과와 거부 결과는 대화 이력에 추가되어 다음 판단의 입력으로 사용됩니다.

호출이 허용되어 도구가 실행되었다고 해서 작업이 끝난 것은 아닙니다. 그림 2-1의 4번 도구 실행은 실행 결과를 대화 이력에 돌려줄 뿐이고, 모델은 그 결과를 읽고 다음 행동을 정합니다. 작업이 끝났는지 판정하는 일은 검증이 맡습니다. 표 2-3은 그림 2-1의 구성 요소를 정리하며, 맨 아래 한 줄로 적은 권한 모드는 3번 권한 확인 행에 풀었습니다.

기록: 어떻게 이어 가는가

기록은 작업 과정과 결과를 남겨 다음 판단과 인수인계를 가능하게 합니다. 에이전트의 작업은 한 번의 대화로 끝나지 않습니다. 코드를 수정한 뒤 테스트를 실행하고, 실패하면 원인을 찾아 다시 수정합니다. 여러 세션에 걸쳐 작업할 때는 이전 작업에서 무엇을 했고, 왜 그렇게 했으며, 무엇이 남아 있는지 알아야 합니다.

한 세션 안에서는 대화 이력이 이 역할을 합니다. 실행 결과와 거부 결과는 대화 이력에 추가되어 다음 판단의 입력이 됩니다. 그러나 새 세션은 이전 대화를 담지 않은 컨텍스트로 시작합니다. 긴 대화는 자동으로 압축되어 앞의 내용이 그대로 남지 않을 수 있습니다. 그래서 이어받을 결정과 진행 상황은 파일에 남깁니다.

기록이 없으면 에이전트는 매번 처음부터 작업을 다시 이해해야 합니다. 사람도 에이전트가 왜 그런 변경을 했는지, 어디까지 진행했는지, 무엇이 남았는지 확인할 수 없습니다. 기록은 에이전트와 사람이 작업을 이어 가는 공유된 근거입니다.

남겨야 할 기록

파일에 남기는 기록은 무엇을 왜 정했는지 남긴 결정 기록과, 어디까지 진행했는지 남긴 진행 기록으로 나뉩니다. 두 기록에는 다음 항목을 남깁니다.

  • 작업 목표와 요구 조건
  • 사용한 도구와 호출 결과
  • 사람 승인 여부
  • 수정한 파일과 변경 사유
  • 검증 결과
  • 남은 작업과 다음 단계

검증: 무엇을 믿는가

검증은 결과가 요구 조건을 충족하는지 확인합니다. 에이전트가 "완료했습니다"라고 보고했다고 해서 작업이 끝난 것은 아닙니다. 완료는 확인할 수 있는 근거로 판단합니다. 테스트가 통과했는지, 요구 조건을 충족하는지, 변경 범위가 역할과 권한 안에 있는지를 확인해야 합니다.

검증 기준은 작업을 시작하기 전에 정하는 것이 좋습니다. 무엇을 테스트할지, 어떤 결과를 통과로 볼지, 어떤 변경을 사람이 확인할지 미리 정하면, 에이전트는 자기 판단만으로 작업을 끝내지 않습니다.

검증에는 테스트 실행, 결과 비교, 정책 확인, 사람 검토를 사용할 수 있습니다. 검증에 실패하면 작업을 중단하거나 사람에게 넘깁니다. 검증 결과는 기록에 남겨 다음 판단과 인수인계에 사용합니다.

정해진 시점마다 실행할 검사는 훅(Hook)으로 설정 파일에 적습니다. 훅은 도구 실행 전후처럼 제품이 정한 때에 자동으로 실행되는 명령입니다. 파일을 수정할 때마다 테스트를 실행하는 훅을 두면, 모델이 테스트 실행을 잊어도 검사가 실행됩니다.

검증 기준

완료를 판정할 때는 다음을 확인합니다.

  • 요구 조건 충족 여부
  • 테스트 통과 여부
  • 변경 범위가 역할과 권한 안에 있는지 여부
  • 사람 확인이 필요한 작업의 수행 여부
  • 결과의 재현과 추적 가능 여부

다섯 구성 요소가 만드는 흐름

다섯 구성 요소는 하나의 작업 흐름에서 서로를 보완합니다. 역할이 작업의 경계를 정하고, 도구가 그 경계 안에서 가능한 행동을 만들며, 권한이 실행을 통제합니다. 기록은 과정을 이어 가게 하고, 검증은 결과를 신뢰할 수 있게 합니다. 그래서 한 요소가 비면 다른 요소도 제 기능을 하지 못합니다.

다섯 구성 요소는 작동하는 시점과 방식에 따라 세 영역으로 나뉩니다. 판단 전에는 모델이 읽는 정보와 모델이 선택할 수 있는 수단이 판단의 조건을 정하고, 판단 뒤에는 제품이 그 결과를 통제합니다.

  • 지시 영역: 역할과 기록이 속합니다. 모델이 판단할 때 읽는 정보이며, 규칙 문서와 기록 파일에 적습니다.
  • 실행 수단 영역: 도구가 속합니다. 모델이 판단할 때 선택할 수 있는 수단입니다.
  • 강제 영역: 권한과 검증이 속합니다. 판단이 나온 뒤 권한은 요청된 동작을 실행해도 되는지 정하고, 검증은 결과가 완료 조건을 충족하는지 확인합니다.

영역 이름의 지시와 강제는 규칙을 처리하는 두 수단에서 왔습니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단(규칙 문서)이고, 강제는 에이전트의 판단과 관계없이 제품이 적용하는 수단(권한 규칙, 훅)입니다. 역할과 검증은 영역과 처리 수단이 일부 다르며, 그 차이는 다음 절에서 다룹니다.

그림 2-2는 세 영역과 가운데의 "판단과 응답"을 보여 줍니다. 위의 두 영역에서 판단과 응답으로 들어가는 화살표가 판단의 조건이고, 판단과 응답에서 아래 강제 영역으로 나가는 화살표가 판단 결과의 통제입니다. 카드의 단계 이름은 그림 1-2의 루프 단계 가운데 그 구성 요소가 주로 작동하는 곳입니다.

다섯 구성 요소에는 저마다 한계가 있습니다. 역할과 기록은 모델이 읽고 따라야 지켜지고, 도구는 연결할수록 컨텍스트를 차지하며, 권한과 검증은 정해진 범위와 시점에서만 작동합니다. 표 2-4는 그림 2-2의 요소를 주요 역할과 기능적 제약으로 정리합니다.

지시 기반 규칙과 강제 적용

규칙 문서에 "원본 자료는 수정하지 않는다"라고 적어 두면 충분할까요? 규칙 문서에 적은 규칙은 모델이 읽고 따라야 지켜지지만, 권한 절의 금지 규칙은 모델이 따르지 않아도 제품이 적용합니다. 권한 규칙을 적용하는 주체는 Claude Code이고, 프롬프트나 CLAUDE.md의 지시는 에이전트가 시도하는 동작에 영향을 줄 뿐 허용되는 동작 자체를 변경하지 않습니다. 그래서 규칙마다 지시(규칙 문서)와 강제(권한 규칙, 훅) 가운데 어디에 맡길지 정해야 합니다.

강제 수단 가운데 훅은 실행되는 시점에 따라 할 수 있는 일이 다릅니다. 훅에는 셸 명령을 실행하는 훅 외에 프롬프트나 에이전트로 판단하는 훅도 있습니다. 이 장은 셸 명령을 실행하는 훅만 다룹니다.

  • PreToolUse 훅: 도구 실행 전, 권한 규칙 대조보다 먼저 실행되어 호출을 막을 수 있습니다.
  • PostToolUse 훅: 도구 실행 뒤에 실행되어 이미 실행된 편집은 되돌리지 못하지만, 검사 결과를 모델에 알릴 수 있습니다. 명령이 끝나며 성공이나 실패를 알리는 숫자를 종료 코드라고 합니다. 훅 명령이 종료 코드 2로 끝나면 오류 출력이 모델에 전달되어, 모델이 이어서 수정할 수 있습니다.

훅에 지정한 편집 도구(예제에서는 Edit, Write)를 실행할 때마다 PostToolUse 훅으로 검사를 실행하면, 모델이 잊어도 검사가 실행됩니다. 이 용도의 훅을 편집 뒤 훅이라고 합니다.

어떤 규칙을 강제에 둘지는 어기면 되돌리기 어려운지, 모델이 잊어도 정해진 시점마다 실행되어야 하는지의 두 질문으로 정합니다.

  • 되돌리기 어려움: 원본 자료 손상이나 외부 발송처럼 되돌리기 어려운 결과가 생기는 규칙은 권한 규칙으로 막습니다. 다시 작업하면 되는 규칙은 지시로 충분합니다.
  • 정해진 시점의 실행: 파일을 수정할 때마다 실행할 검사가 여기에 해당하며, 훅에 맡깁니다.

표 2-5는 두 질문에 따른 처리 수단입니다.

이 기준을 적용하면 그림 2-2의 영역과 실제 처리 수단이 다른 경우를 설명할 수 있습니다. 그림 2-2에서 역할은 지시 영역에 있지만, 경계 가운데 되돌리기 어려운 것은 표 2-5의 둘째 줄처럼 권한 규칙으로 막거나 사람에게 확인을 요청합니다. 검증은 강제 영역에 있지만, 제품이 강제하는 것은 훅이 검사를 실행하는 부분입니다. 그 출력과 검토 하위 에이전트의 보고는 완료를 판단하는 증거이고, 그 증거를 보고 결과를 받아들이는 승인은 사람이 합니다.

강제 수단에도 적용 범위가 있습니다. PreToolUse 훅이 호출을 허용해도 금지 규칙과 확인 요청 규칙은 그대로 적용됩니다. 파일 수정 금지 규칙은 수정 도구, Bash가 인식하는 파일 명령(cat, sed, tee 등), 출력을 > 기호로 파일에 기록하는 리다이렉션에는 적용되지만, Python 스크립트가 파일을 직접 수정하는 경우는 막지 못합니다. Bash 규칙은 명령 문자열이 일치할 때만 적용되므로, Bash(git push *)는 폴더를 지정하는 -C 옵션을 추가한 git -C . push처럼 같은 동작을 다르게 표기한 명령과 일치하지 않습니다. 훅도 실행되지 않거나 실패하면 막지 못합니다. 이 빈틈을 운영 체제 수준에서 보완하는 격리 환경인 샌드박스(Sandbox)는 Chapter 9의 격리와 샌드박스에서 다룹니다.

예제: 변경 요청 사항의 하네스 구성 정하기

지금까지의 기준을 실제 작업에 적용하면 어떤 값이 될까요? 예제는 Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성에서 자세히 설계할 변경 요청 사항입니다. 작업은 다섯 개의 작업 단위로 나누어 두었습니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다.

  • 작업 1(프로젝트 코드 조회 방식 합의): 사람이 마침
  • 작업 2~4(데이터 모델, 단위 테스트, 화면 변경): 에이전트가 하나씩 구현
  • 작업 5(통합 테스트 시나리오): 에이전트가 초안을 작성하고 사람이 승인

다음 두 표를 읽으려면 예제에서 사용하는 기록 파일과 시험, 자료 다섯 가지를 알아야 합니다.

  • 진행 기록: 작업 단위 목록 파일(tasks.json)이며, 작업 단위마다 완료 여부를 통과 값(true 또는 false)으로 적습니다.
  • 단위 테스트: 프로그램의 부품 하나가 정해진 대로 동작하는지 확인하는 시험이며, tests/ 폴더에 있습니다.
  • 수용 기준과 수용 시험: 수용 기준은 완료 기준 가운데 사람이 정한 것으로, 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 수용 시험은 그 조건을 확인하는 시험이며, 사람이 작성하고 에이전트는 수정하지 않습니다.
  • 원본 자료: 인사 시스템이 갱신하는 프로젝트 코드 목록 파일(data/projects.csv)입니다.
  • 검사 스크립트: 단위 테스트와 수용 시험을 한 번에 실행해 결과를 출력하는 파일(check.py)입니다.

표 2-6은 변경 요청 사항에서 다섯 구성 요소를 정한 값입니다. 운영 기준은 부록 실습의 예제 파일(examples/expense-app/reference/)과 같고, 2026년 10월에 확인한 Claude Code 문서에 맞습니다. 표의 기본 도구는 파일 읽기와 검색(Read, Grep, Glob), 파일 수정(Edit, Write), 명령 실행(Bash)이고, 웹 접근 도구는 웹 문서를 가져오는 WebFetch와 웹을 검색하는 WebSearch입니다.

표 2-6의 역할 행에서 사람의 몫은 수용 기준 확정, 작업 1 합의, 작업 5 승인, commit 확인, push입니다. commit 확인은 규칙 문서의 작업 순서에 적혀 있고, push는 규칙 문서에 적지 않고 권한 규칙으로만 막습니다. 기록 행의 결정 기록은 사람이 적고 에이전트는 읽기만 하며, 진행 기록의 통과 값과 인계 메모는 에이전트가 적습니다.

검증 행의 편집 뒤 훅은 PostToolUse 훅이고, 훅이 반응할 도구를 정하는 조건은 Edit|Write입니다. |는 둘 중 하나라는 뜻이므로, 수정 도구(Edit)나 파일 작성 도구(Write)를 실행한 뒤에 훅이 단위 테스트를 실행하고, 실패하면 종료 코드 2로 오류 출력을 모델에 전달합니다. 검사 스크립트는 수용 시험을 지우거나 건너뛰어 만든 통과를 막기 위해 실행 건수를 다시 셉니다.

표 2-6의 검증 행에 Chapter 1에서 본 Stop 훅(모델이 응답을 마치려 할 때 완료 기준을 검사하는 훅)이 없는 것은, 작업 단위의 완료를 검사 스크립트의 출력과 사람의 commit 확인으로 판정하기 때문입니다. 완료 판정까지 훅에 맡기려면 Stop 훅을 더합니다.

예제의 기록은 사람이 정한 파일에 남깁니다. Claude Code에는 모델이 스스로 정한 내용을 기록해 다음 세션에 읽는 자동 메모리도 있고, 로컬 세션에서는 기본으로 켜져 있습니다. 그러나 무엇을 남길지를 모델이 정하므로, 예제는 이 기능을 기록 구성 요소로 삼지 않습니다.

표 2-7의 일곱 규칙 가운데 다섯은 강제 수단을 사용하고, 나머지 둘(세 번 연속 실패하면 중단, commit 전 검토 요청)은 다시 작업하면 되므로 규칙 문서에만 둡니다. 표 2-7은 규칙마다 지시 수단과 강제 수단을 나눕니다. 표의 Edit(./data/**)는 data 폴더 아래 모든 파일의 수정을 가리킵니다.

표 2-7의 첫 두 줄은 실습으로 비교할 수 있습니다. 규칙 문서만 있을 때는 수용 시험을 수정하려는 시도를 막지 못할 수 있고(부록의 실습 2. 규칙 문서 작성), 금지 규칙을 더하면 수정 도구로 수용 시험과 원본 자료를 수정하려는 시도가 거부됩니다(부록의 실습 3. 권한 설정).

파일 수정 금지 규칙은 스크립트가 파일을 직접 수정하는 경우를 막지 못하므로, 검사 스크립트의 건수 확인과 사람의 commit 확인이 보완합니다.

  • 검사 스크립트는 수용 시험이 정한 수(5건)만큼 실행되었는지와 건너뛴 시험이 없는지 다시 세고, 다르면 실패로 봅니다.
  • 시험의 비교를 약하게 변경한 수정과 원본 자료의 변경은, 사람이 commit을 확인할 때 git status와 git diff로 acceptance/와 data/가 변경 목록에 없는지 보고 찾습니다.

Python 스크립트로 파일을 수정하는 명령처럼 허용 목록에 없는 명령은 권한 모드가 처리합니다. 사람에게 묻는 모드에서는 실행 전에 사람에게 확인을 요청하지만, auto 모드처럼 사람 대신 별도 모델이 검토하는 모드에서는 그 모델이 실행 여부를 판단합니다.

실패를 예방하는 장치

구성 요소 하나를 정하지 않아도 에이전트는 작업을 수행합니다. 그러나 그 구성 요소가 막았을 실패가 생길 수 있고, 생겨도 알아차릴 근거가 남지 않습니다. 표 2-8은 변경 요청 사항에서 구성 요소별로 생길 수 있는 실패와 그 방지 장치를 정리한 것입니다. 방지 장치는 표 2-6, 표 2-7의 이름을 그대로 사용합니다.

설정과 결과의 확인 방법

설정 파일을 읽는 것만으로는 구성 요소가 정한 대로 적용되는지 알 수 없습니다. 설정은 사용자, 프로젝트, 로컬 등 여러 파일에서 합쳐집니다. 훅이 실제로 실행되는지는 동작을 일으켜야 알 수 있습니다. 그래서 제품의 화면과 실행 결과로 확인합니다.

Claude Code 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다.

확인은 실습 폴더에서 Claude Code를 시작한 상태로 합니다. 프로젝트 설정 파일(.claude/settings.json)은 Claude Code를 시작한 폴더를 기준으로 읽히기 때문입니다. 표 2-9의 /로 시작하는 명령은 대화 입력창에 입력합니다.

표 2-9의 역할 행은 부록의 실습 2. 규칙 문서 작성, 권한 행은 실습 3. 권한 설정, 도구 행과 검증 행은 실습 4. 검증 장치를 마친 폴더에서 확인합니다. 기록 행은 실습 5. 작업 단위로 구현과 실습 6. 기록과 인계를 마친 뒤 확인합니다.

도구가 컨텍스트를 차지하는 크기는 /context의 System tools 항목에서 볼 수 있고, MCP 서버를 연결했다면 MCP 도구의 크기는 MCP tools 항목에 표시됩니다.

훅 목록에 있다는 것과 훅이 실행되었다는 것은 다릅니다. /hooks는 등록된 훅을 보여 주는 읽기 전용 목록입니다. 실행 여부는 일부러 테스트가 실패하는 편집을 해서 대화 기록 보기(Ctrl+O)의 훅 오류 메시지로 확인합니다. 성공한 훅의 출력은 대화에 나타나지 않으므로, 실행 기록을 자세히 보려면 claude --debug로 실행합니다.

설계 원칙과 점검 질문

다섯 구성 요소를 모두 정하고, 어기면 되돌리기 어려운 규칙은 규칙 문서에만 두지 않고 권한 규칙과 훅으로 강제합니다.

도구로 넓힌 가능성은 권한으로 좁히고, 작업은 기록으로 이어 가며, 완료는 확인할 수 있는 근거로 판단합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트의 하네스에서 다섯 구성 요소 가운데 정하지 않은 것은 무엇입니까?
  2. 지시로만 처리하는 규칙 가운데 원본 손상이나 외부 발송처럼 어기면 되돌리기 어려운 것은 무엇입니까?
  3. 연결한 도구 가운데 이 작업에 필요하지 않은 도구는 무엇입니까?
