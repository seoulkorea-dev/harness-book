Chapter 2 하네스의 구성 요소

도구 연결만으로는 부족합니다: 에이전트 신뢰를 위한 다섯 가지 구성 요소

도구를 연결하면 에이전트(Agent)는 파일을 읽고, 코드를 수정하고, 테스트를 실행할 수 있습니다. 그러나 도구만으로는 다음 네 가지를 정할 수 없습니다.

  • 에이전트가 수정해도 되는 범위
  • 사람이 확인해야 할 일과 에이전트가 진행할 일의 경계
  • 다음 세션이 이어 갈 지점
  • 완료했다는 보고를 믿을 근거

이 네 가지는 모델 바깥의 하네스(Harness)에서 정합니다. 모델은 판단을 맡고, 하네스는 판단에 필요한 정보와 도구를 제공하며 그 결과를 실제로 실행할지 정하기 때문입니다(Chapter 1의 에이전트와 하네스의 정의). 하네스에서 미리 정해 둘 것은 역할, 도구, 권한, 기록, 검증의 다섯 가지이고, 이것을 하네스의 다섯 구성 요소라고 합니다. 같은 모델을 사용하더라도 다섯 구성 요소를 어떻게 정하느냐에 따라 에이전트가 할 수 있는 일의 범위와 결과를 신뢰할 근거가 달라집니다.

이 장에서는 먼저 다섯 구성 요소가 각각 무엇을 정하는지 살펴봅니다. 이어서 에이전트의 실제 작업 범위를 정하는 도구와 권한을 살펴보고, 규칙을 규칙 문서에 적을지 제품이 강제하게 할지 판단하는 기준을 다룹니다. 이 순서로 읽으면 마지막 예제인 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)에서 정한 값마다 그렇게 정한 이유가 보입니다.

  • 도구만으로 정할 수 없는 수정 범위, 사람과의 경계, 이어 갈 지점, 완료의 근거를 역할, 도구, 권한, 기록, 검증의 다섯 구성 요소로 정합니다.
  • 하네스는 미리 정한 도구만 모델에 보여 주고, 보여 준 도구도 호출할 때마다 실행해도 되는지 평가합니다.
  • 어기면 되돌리기 어려운 규칙은 규칙 문서에만 두지 않고, 제품이 직접 적용하는 설정으로 강제합니다.

다섯 구성 요소

다섯 구성 요소는 하네스의 설정에서 정합니다. Chapter 1에서 하네스는 제품이 제공하는 실행 장치와 사용자와 팀이 정하는 설정으로 나뉩니다. 작업마다 무엇을 허용하고, 무엇을 사람에게 넘길지는 제품이 자동으로 정해 주는 것이 아니라 사용자와 팀이 정해야 합니다.

아래에서 함께 드는 값은 이 장 끝의 예제인 변경 요청 사항에서 정한 것입니다. 변경 요청 사항은 정산 요청 화면에 프로젝트 코드를 선택하는 항목을 추가하는 변경이며, 작업을 미리 다섯 개로 나누어 두었습니다.

  • 역할은 에이전트가 할 작업과 사람이 할 작업의 경계입니다. 경계가 없으면 배포나 외부 발송처럼 사람이 판단할 일까지 에이전트가 진행할 수 있으므로, 규칙 문서(Claude Code의 CLAUDE.md)에 에이전트가 할 일과 사람에게 넘길 일을 적습니다. 변경 요청 사항에서 에이전트는 미리 나눈 작업 가운데 아직 끝나지 않은 첫 작업을 하나씩 맡아 구현하고, 마지막 작업은 초안까지만 작성합니다. 수용 기준 확정, 첫 작업의 합의, 마지막 작업의 승인, 변경 확정 전 확인, 원격 저장소 반영은 사람이 맡습니다.
  • 도구는 맡길 업무에 연결할 도구와, 그 가운데 모델에 보여 줄 범위입니다. 변경 요청 사항은 기본 도구(파일 읽기와 수정, 명령 실행)만 사용하고 웹 접근 도구는 금지합니다. 필요한 자료와 코드가 모두 저장소 안에 있기 때문입니다. 도구가 없으면 에이전트는 파일을 읽거나 명령을 실행하지 못하지만, 너무 많아도 도구 정의가 컨텍스트(Context)를 차지하고 어느 도구를 사용할지 선택하기 어려워집니다. 그래서 작업에 필요한 도구만 연결합니다.
  • 권한은 도구로 할 수 있는 동작의 범위이며, 허용, 확인 요청, 금지로 나눕니다. 범위가 없으면 원본 자료(에이전트가 읽기만 해야 하는 입력 자료)와 완료 판정 기준까지 에이전트가 수정할 수 있으므로, 설정 파일의 권한 규칙(Permission Rule)에 동작별로 적습니다. 변경 요청 사항의 권한은 테스트 실행을 허용하고, 변경 확정(git commit)은 확인 요청으로 두며, 원본 자료와 완료 판정에 사용하는 시험과 검사 스크립트(check.py)의 수정, 원격 저장소 반영(git push)은 금지합니다.
  • 기록은 무엇을 왜 정했는지 남긴 결정 기록과, 어디까지 진행했는지 남긴 진행 기록입니다. 새 세션은 이전 대화를 담지 않은 컨텍스트로 시작하고, 긴 대화는 자동으로 압축되어 앞의 내용이 그대로 남지 않을 수 있습니다. 그래서 이어받을 결정과 진행 상황을 파일에 남깁니다. 변경 요청 사항에서는 사람이 정하고 에이전트는 읽기만 하는 결정 기록(DECISIONS.md)을 둡니다. 에이전트는 작업마다 완료 여부를 진행 기록(tasks.json)에 적고, 세션을 마칠 때 다음 세션이 이어받을 상황을 인계 메모(HANDOFF.md)에 남기며, 작업마다 변경을 확정(commit)합니다.
  • 검증은 결과를 받아들이기 전에 확인하는 방법과 기준입니다. 완료 보고만으로는 결과가 기준을 충족했는지 알 수 없으므로, 무엇을 실행해 어떤 출력이 나오면 완료로 볼지 미리 정합니다. 정해진 시점마다 실행할 검사는 훅(Hook)으로 설정 파일에 적습니다. 훅은 도구 실행 전후처럼 제품이 정한 때에 자동으로 실행되는 명령입니다. 변경 요청 사항에서는 수정 도구를 실행할 때마다 훅이 테스트를 실행합니다. 작업을 마치면 에이전트가 모든 시험을 한 번에 실행하는 검사 스크립트(check.py)를 실행하고, 사람은 그 출력을 보고 변경 확정(commit)을 확인합니다.

다섯 구성 요소는 작동하는 시점과 방식에 따라 세 영역으로 나뉩니다. 판단 전에는 모델이 읽는 정보와 모델이 선택할 수 있는 수단이 판단의 조건을 정하고, 판단 뒤에는 제품이 그 결과를 통제합니다.

  • 지시 영역: 역할과 기록이 속합니다. 모델이 판단할 때 읽는 정보이며, 규칙 문서와 기록 파일에 적습니다.
  • 실행 수단 영역: 도구가 속합니다. 모델이 판단할 때 선택할 수 있는 수단입니다.
  • 강제 영역: 권한과 검증이 속합니다. 판단이 나온 뒤 권한은 요청된 동작을 실행해도 되는지 정하고, 검증은 결과가 완료 조건을 충족하는지 확인합니다.

영역 이름의 지시와 강제는 규칙을 처리하는 두 수단에서 왔습니다. 지시는 에이전트가 읽고 따르도록 요청하는 수단(규칙 문서)이고, 강제는 에이전트의 판단과 관계없이 제품이 적용하는 수단(권한 규칙, 훅)입니다. 역할과 검증은 영역과 처리 수단이 일부 다르며, 그 차이는 뒤의 지시 기반 규칙과 강제 적용 절에서 다룹니다.

그림 2-1은 세 영역과 가운데의 "판단과 응답"을 보여 줍니다. 위의 두 영역에서 판단과 응답으로 들어가는 화살표가 판단의 조건이고, 판단과 응답에서 아래 강제 영역으로 나가는 화살표가 판단 결과의 통제입니다. 카드의 단계 이름은 그림 1-2의 루프 단계 가운데 그 구성 요소가 주로 작동하는 곳입니다.

다섯 구성 요소에는 저마다 한계가 있습니다. 역할과 기록은 모델이 읽고 따라야 지켜지고, 도구는 연결할수록 컨텍스트를 차지하며, 권한과 검증은 정해진 범위와 시점에서만 작동합니다. 표 2-1은 그림 2-1의 요소를 주요 역할과 기능적 제약으로 정리합니다.

도구 사용 범위와 제약

다섯 구성 요소 가운데 도구와 권한은 에이전트가 실제로 할 수 있는 일을 결정하므로 더 자세히 살펴봅니다.

도구를 많이 연결할수록 에이전트가 할 수 있는 일은 늘어나지만, 컨텍스트 공간과 도구 선택의 어려움이라는 두 가지 비용도 함께 늘어납니다. 도구의 정의는 컨텍스트를 차지합니다. 기능이 겹치는 도구가 많으면 어느 도구를 사용할지 판단하기 어려워집니다. 따라서 작업에 필요한 최소한의 도구만 두는 것이 좋습니다.

외부 시스템의 기능을 에이전트의 도구로 연결하는 개방형 표준을 MCP(Model Context Protocol)라고 하고, 이를 구현한 프로그램을 MCP 서버라고 합니다. Claude Code는 기본 설정에서 MCP 서버의 도구 설명을 처음부터 모두 불러오지 않고, 도구 이름과 서버 안내만 컨텍스트에 둔 뒤 필요할 때 불러옵니다. 환경 변수 설정이나 모델에 따라서는 처음부터 모두 불러오기도 합니다. 그래도 도구 이름과 안내는 컨텍스트에 남고 선택 대상도 늘어나므로, 사용하지 않는 MCP 서버는 /mcp에서 비활성화하는 것이 좋습니다.

도구와 권한의 차이

도구를 다루는 설정은 두 가지로 나뉩니다.

명령 실행 도구(Bash) 하나로도 저장소 상태를 확인하는 git status와 원격 저장소에 올리는 git push는 위험이 다릅니다. 파일 수정 도구도 대상 파일에 따라 결과의 심각성이 달라집니다. 그래서 권한은 도구를 연결할 때 한 번 정하고 끝내지 않고, 호출할 때마다 평가합니다.

모델은 도구 호출을 요청할 뿐 실행은 하네스가 맡습니다. 따라서 하네스는 요청과 실행 사이에서 해당 동작을 실행해도 되는지 평가할 수 있습니다.

Claude Code의 권한 규칙

Claude Code는 권한 규칙을 금지 → 확인 요청 → 허용 순서로 검사하고, 처음 일치한 규칙이 결과를 정합니다.

  • 금지 규칙: 해당 호출은 실행되지 않습니다.
  • 확인 요청 규칙: 실행 전에 사람에게 확인을 요청합니다.
  • 허용 규칙: 별도 확인 없이 실행할 수 있습니다.

규칙에는 도구 이름만 적을 수도 있고, 도구 이름 뒤 괄호에 대상을 함께 적을 수도 있습니다.

  • 웹 문서를 가져오는 WebFetch처럼 도구 이름만 적은 금지 규칙은 해당 도구 자체를 목록에서 제외합니다. 모델은 그 도구를 볼 수 없습니다.
  • Bash(git push *)처럼 대상을 적은 금지 규칙은 Bash 도구는 남겨 두고, 명령 가운데 git push로 시작하는 부분이 있는 호출을 거부합니다.

어느 규칙에도 해당하지 않는 호출은 권한 모드(Permission Mode)가 처리합니다. 모드에 따라 사람에게 묻거나, 자동으로 승인하거나, 거부합니다.

프로그램이 승인을 처리하는 경우

대화형 세션에서 확인 요청 규칙에 일치한 호출은 실행 전에 사람에게 확인을 요청합니다. Claude Agent SDK처럼 프로그램이 에이전트 루프를 실행하는 경우에는, 확인이 필요한 호출이 승인을 처리하는 프로그램 코드로 넘어갑니다.

이때 프로그램이 거부하면 해당 호출은 실행되지 않고, 모델은 거부 메시지를 도구 결과로 받습니다. 승인 처리 프로그램이 없으면 확인이 필요한 호출은 거부됩니다.

그림 2-2는 이 흐름을 보여 줍니다. 위쪽은 컨텍스트 구성 단계에서 정하는 가용성이고, 아래쪽은 도구 호출 한 번이 권한 확인을 거쳐 실행되거나 거부되는 과정입니다. 위쪽의 하위 에이전트(Subagent)는 특정 작업을 맡도록 따로 정의한 에이전트이며, 하위 에이전트에 줄 도구도 이때 정합니다. 실행 결과와 거부 결과는 대화 이력에 추가되어 다음 판단의 입력으로 사용됩니다. 대화형 세션에서 사람이 이유를 적지 않고 거절하면, 그 차례의 응답이 멈춥니다.

호출이 허용되어 도구가 실행되었다고 해서 작업이 끝난 것은 아닙니다. 그림 2-2의 4번 도구 실행은 실행 결과를 대화 이력에 돌려줄 뿐이고, 모델은 그 결과를 읽고 다음 행동을 정합니다. 작업이 끝났는지 판정하는 일은 검증이 맡습니다. 표 2-3은 그림 2-2의 단계와 요소를 정리하며, 그림에 한 줄로 적은 권한 모드와 하위 에이전트의 도구도 행으로 풀었습니다.

정리하면 도구에 대해 정할 것은 세 가지입니다.

  • 작업에 연결할 도구: 작업에 필요한 도구만 연결하고, 사용하지 않는 도구는 이름만 적은 금지 규칙이나 MCP 서버 비활성화로 목록에서 제외합니다.
  • 읽기와 수정의 구분: 조회만 필요한 작업에는 수정 도구를 금지 규칙으로 막거나 도구 목록에서 제외해, 읽기 도구만 사용하게 합니다.
  • 하위 에이전트의 도구: 하위 에이전트의 정의 파일에 맡긴 작업에 필요한 도구만 적습니다. 도구 목록을 생략하면 하위 에이전트가 사용할 수 있는 도구를 모두 물려받습니다.

지시 기반 규칙과 강제 적용

규칙 문서에 "원본 자료는 수정하지 않는다"라고 적어 두면 충분할까요? 규칙 문서에 적은 규칙은 모델이 읽고 따라야 지켜지지만, 앞 절의 금지 규칙은 모델이 따르지 않아도 제품이 적용합니다. 권한 규칙을 적용하는 주체는 Claude Code이고, 프롬프트나 CLAUDE.md의 지시는 에이전트가 시도하는 동작에 영향을 줄 뿐 허용되는 동작 자체를 변경하지 않습니다. 그래서 규칙마다 지시(규칙 문서)와 강제(권한 규칙, 훅) 가운데 어디에 맡길지 정해야 합니다.

강제 수단 가운데 훅은 실행되는 시점에 따라 할 수 있는 일이 다릅니다. 이 장은 셸 명령을 실행하는 훅만 다룹니다.

  • PreToolUse 훅: 도구 실행 전, 권한 규칙 대조보다 먼저 실행되어 호출을 막을 수 있습니다. 그러나 훅이 호출을 허용해도 금지 규칙과 확인 요청 규칙은 그대로 적용됩니다.
  • PostToolUse 훅: 도구 실행 뒤에 실행되어 이미 실행된 편집은 되돌리지 못하지만, 검사 결과를 모델에 알릴 수 있습니다. 명령이 끝나며 성공이나 실패를 알리는 숫자를 종료 코드라고 합니다. 훅 명령이 종료 코드 2로 끝나면 오류 출력이 모델에 전달되어, 모델이 이어서 수정할 수 있습니다.

훅에 지정한 편집 도구(예제에서는 Edit, Write)를 실행할 때마다 PostToolUse 훅으로 검사를 실행하면, 모델이 잊어도 검사가 실행됩니다. 이 용도의 훅을 편집 뒤 훅이라고 합니다.

어떤 규칙을 강제에 둘지는 어기면 되돌리기 어려운지, 모델이 잊어도 정해진 시점마다 실행되어야 하는지의 두 질문으로 정합니다.

  • 되돌리기 어려움: 원본 자료 손상이나 외부 발송처럼 되돌리기 어려운 결과가 생기는 규칙은 권한 규칙으로 막습니다. 다시 작업하면 되는 규칙은 지시로 충분합니다.
  • 정해진 시점의 실행: 파일을 수정할 때마다 실행할 검사가 여기에 해당하며, 훅에 맡깁니다.

표 2-4는 두 질문에 따른 처리 수단입니다.

이 기준을 적용하면 그림 2-1의 영역과 실제 처리 수단이 다른 경우를 설명할 수 있습니다. 그림 2-1에서 역할은 지시 영역에 있지만, 경계 가운데 되돌리기 어려운 것은 표 2-4의 둘째 줄처럼 권한 규칙으로 막거나 사람에게 확인을 요청합니다. 검증은 강제 영역에 있지만, 제품이 강제하는 것은 훅이 검사를 실행하는 부분입니다. 그 출력과 검토 하위 에이전트의 보고는 완료를 판단하는 증거이고, 그 증거를 보고 결과를 받아들이는 승인은 사람이 합니다.

강제 수단에도 적용 범위가 있습니다. 파일 수정 금지 규칙은 수정 도구, Bash가 인식하는 파일 명령(cat, sed, tee 등), 출력을 > 기호로 파일에 기록하는 리다이렉션에는 적용되지만, Python 스크립트가 파일을 직접 수정하는 경우는 막지 못합니다. Bash 규칙은 명령 문자열이 일치할 때만 적용되므로, Bash(git push *)는 폴더를 지정하는 -C 옵션을 추가한 git -C . push처럼 같은 동작을 다르게 표기한 명령과 일치하지 않습니다. 훅도 실행되지 않거나 실패하면 막지 못합니다. 이 빈틈을 운영 체제 수준에서 보완하는 격리 환경인 샌드박스(Sandbox)는 Chapter 9의 격리와 샌드박스에서 다룹니다.

예제: 변경 요청 사항의 하네스 구성 정하기

지금까지의 기준을 실제 작업에 적용하면 어떤 값이 될까요? 예제는 Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성에서 자세히 설계할 변경 요청 사항입니다. 작업은 다섯 개의 작업 단위로 나누어 두었습니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다.

  • 작업 1(프로젝트 코드 조회 방식 합의): 사람이 마침
  • 작업 2~4(데이터 모델, 단위 테스트, 화면 변경): 에이전트가 하나씩 구현
  • 작업 5(통합 테스트 시나리오): 에이전트가 초안을 작성하고 사람이 승인

표 2-5와 표 2-6을 읽으려면 예제에서 사용하는 기록 파일과 시험, 자료 다섯 가지를 알아야 합니다.

  • 진행 기록: 작업 단위 목록 파일(tasks.json)이며, 작업 단위마다 완료 여부를 통과 값(true 또는 false)으로 적습니다.
  • 단위 테스트: 프로그램의 부품 하나가 정해진 대로 동작하는지 확인하는 시험이며, tests/ 폴더에 있습니다.
  • 수용 기준과 수용 시험: 수용 기준은 완료 기준 가운데 사람이 정한 것으로, 결과물이 받아들여지기 위해 충족해야 하는 조건입니다. 수용 시험은 그 조건을 확인하는 시험이며, 사람이 작성하고 에이전트는 수정하지 않습니다.
  • 원본 자료: 인사 시스템이 갱신하는 프로젝트 코드 목록 파일(data/projects.csv)입니다.
  • 검사 스크립트: 단위 테스트와 수용 시험을 한 번에 실행해 결과를 출력하는 파일(check.py)입니다.

표 2-5는 변경 요청 사항에서 다섯 구성 요소를 정한 값입니다. 운영 기준은 부록 실습의 예제 파일(examples/expense-app/reference/)과 같고, 2026년 10월에 확인한 Claude Code 문서에 맞습니다. 표에 나오는 도구 이름과 표기는 다음을 가리킵니다.

  • Edit|Write: 훅이 반응할 도구를 정하는 조건입니다. |는 둘 중 하나라는 뜻이므로, 수정 도구(Edit)나 파일 작성 도구(Write)를 실행한 뒤에 훅이 실행됩니다.
  • WebSearch: 웹 검색 도구
  • Read, Grep, Glob: 파일 읽기, 파일 내용 검색, 파일 이름 찾기 도구

표 2-5의 검증 행에 Chapter 1에서 본 Stop 훅(모델이 응답을 마치려 할 때 완료 기준을 검사하는 훅)이 없는 것은, 작업 단위의 완료를 검사 스크립트의 출력과 사람의 commit 확인으로 판정하기 때문입니다. 완료 판정까지 훅에 맡기려면 Stop 훅을 더합니다.

예제의 기록은 사람이 정한 파일에 남깁니다. Claude Code에는 모델이 스스로 정한 내용을 기록해 다음 세션에 읽는 자동 메모리도 있고, 로컬 세션에서는 기본으로 켜져 있습니다. 그러나 무엇을 남길지를 모델이 정하므로, 예제는 이 기능을 기록 구성 요소로 삼지 않습니다.

표 2-6의 일곱 규칙 가운데 다섯은 강제 수단을 사용하고, 나머지 둘(세 번 연속 실패하면 중단, commit 전 검토 요청)은 다시 작업하면 되므로 규칙 문서에만 둡니다. 표 2-6은 규칙마다 지시 수단과 강제 수단을 나눕니다. 표의 Edit(./data/**)는 data 폴더 아래 모든 파일의 수정을 가리킵니다.

표 2-6의 첫 두 줄은 실습으로 비교할 수 있습니다. 규칙 문서만 있을 때는 수용 시험을 수정하려는 시도를 막지 못할 수 있고(부록의 실습 2. 규칙 문서 작성), 금지 규칙을 더하면 수정 도구로 수용 시험과 원본 자료를 수정하려는 시도가 거부됩니다(부록의 실습 3. 권한 설정).

파일 수정 금지 규칙은 스크립트가 파일을 직접 수정하는 경우를 막지 못하므로, 검사 스크립트의 건수 확인과 사람의 commit 확인이 보완합니다.

  • 검사 스크립트는 수용 시험이 정한 수(5건)만큼 실행되었는지와 건너뛴 시험이 없는지 다시 세고, 다르면 실패로 봅니다.
  • 시험의 비교를 약하게 변경한 수정과 원본 자료의 변경은, 사람이 commit을 확인할 때 git status와 git diff로 acceptance/와 data/가 변경 목록에 없는지 보고 찾습니다.

스크립트 실행처럼 허용 목록에 없는 명령은 권한 모드가 처리합니다. 사람에게 묻는 모드에서는 실행 전에 사람에게 확인을 요청하지만, auto 모드처럼 사람 대신 별도 모델이 검토하는 모드에서는 그 모델이 실행 여부를 판단합니다.

실패를 예방하는 장치

구성 요소 하나를 정하지 않아도 에이전트는 작업을 수행합니다. 그러나 그 구성 요소가 막았을 실패가 생길 수 있고, 생겨도 알아차릴 근거가 남지 않습니다. 표 2-7은 변경 요청 사항에서 구성 요소별로 생길 수 있는 실패와 그 방지 장치를 정리한 것입니다. 방지 장치는 표 2-5, 표 2-6의 이름을 그대로 사용합니다.

설정과 결과의 확인 방법

설정 파일을 읽는 것만으로는 구성 요소가 정한 대로 적용되는지 알 수 없습니다. 설정은 사용자, 프로젝트, 로컬 등 여러 파일에서 합쳐지고, 훅이 실제로 실행되는지는 동작을 일으켜야 알기 때문입니다. 그래서 제품의 화면과 실행 결과로 확인합니다.

Claude Code 설치와 실행 방법은 부록 실습의 실습 준비에 있습니다. 확인은 실습 폴더에서 Claude Code를 시작한 상태로 합니다. 프로젝트 설정 파일(.claude/settings.json)은 Claude Code를 시작한 폴더를 기준으로 읽히기 때문입니다. 표 2-8의 /로 시작하는 명령은 대화 입력창에 입력합니다. 표 2-8의 역할 행은 부록의 실습 2. 규칙 문서 작성, 권한 행은 실습 3. 권한 설정, 도구 행과 검증 행은 실습 4. 검증 장치를 마친 폴더에서 확인합니다. 기록 행은 실습 5. 작업 단위로 구현과 실습 6. 기록과 인계를 마친 뒤 확인합니다. 도구 행을 확인할 때 도구가 컨텍스트를 차지하는 크기는 /context의 System tools 항목에서 볼 수 있고, MCP 서버를 연결했다면 MCP 도구의 크기는 MCP tools 항목에 표시됩니다.

훅 목록에 있다는 것과 훅이 실행되었다는 것은 다릅니다. /hooks는 등록된 훅을 보여 주는 읽기 전용 목록이므로, 실행 여부는 일부러 테스트가 실패하는 편집을 해서 대화 기록 보기(Ctrl+O)의 훅 오류 메시지로 확인합니다. 성공한 훅의 출력은 대화에 나타나지 않으므로, 실행 기록을 자세히 보려면 claude --debug로 실행합니다.

설계 원칙과 점검 질문

다섯 구성 요소를 모두 정하고, 어기면 되돌리기 어려운 규칙은 규칙 문서에만 두지 않고 권한 규칙과 훅으로 강제합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 사용하는 에이전트의 하네스에서 다섯 구성 요소 가운데 정하지 않은 것은 무엇입니까?
  2. 지시로만 처리하는 규칙 가운데 원본 손상이나 외부 발송처럼 어기면 되돌리기 어려운 것은 무엇입니까?
  3. 연결한 도구 가운데 이 작업에 필요하지 않은 도구는 무엇입니까?
