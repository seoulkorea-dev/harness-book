Chapter 5 컨텍스트 엔지니어링: 에이전트가 읽는 정보 설계

요청 문장을 다듬는 것만으로는 결과가 정해지지 않고, 에이전트가 판단하는 시점에 어떤 정보를 읽고 있는지에 따라 결과가 달라집니다.

이 장에서는 에이전트(Agent)가 판단할 때 읽는 정보를 설계하는 컨텍스트 엔지니어링(Context Engineering)을 다룹니다. Chapter 1에서 정한 대로 컨텍스트(Context)는 모델이 응답을 생성할 때 입력되는 정보 전체입니다. 컨텍스트 엔지니어링은 모델이 응답을 생성하는 동안 필요한 정보를 선별하고 유지하는 전략입니다. 에이전트는 작업을 시작할 때마다 읽는 규칙 문서(작업 규칙을 적어 프로젝트에 두는 파일)와 요청, 작업 중에 연 파일과 도구 결과를 근거로 판단합니다. 그래서 필요한 자료가 없거나 오래된 자료가 남아 있으면, 같은 요청에도 에이전트가 다른 자료를 근거로 판단해 결과가 달라질 수 있습니다.

컨텍스트는 한정된 자원이어서 자료를 많이 제공한다고 결과가 나아지는 것은 아닙니다. 에이전트가 읽는 정보는 제공 경로와 활용 시점에 따라 상시 규칙, 필요할 때 읽는 문서, 작업 입력, 작업 중 생성 정보의 네 가지 종류로 나뉩니다. 자료는 작업 전에 미리 제공하거나 작업 중에 에이전트가 찾게 할 수 있고, 작업이 길어지면 컨텍스트를 요약하거나 컨텍스트 밖으로 덜어 내는 세 가지 기법을 사용합니다. 네 종류 가운데 작업을 시작할 때마다 읽히는 규칙 문서는 작성과 관리 방법을 따로 정합니다. Chapter 4가 요청 한 건을 설계했다면, 이 장은 요청과 함께 에이전트가 무엇을 언제 읽게 할지를 정합니다.

먼저 컨텍스트가 한정된 자원인 이유와 정보의 종류, 제공 시점을 살펴봅니다. 이어서 규칙 문서를 작성하고 관리하는 방법을 익히고, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)을 구현하는 에이전트가 읽을 정보를 정하는 예제를 다룹니다.

  • 컨텍스트는 한정된 자원이므로 작업에 필요한 자료를 선별하고, 미리 제공할 자료와 작업 중에 찾게 할 자료를 나눕니다.
  • 에이전트가 읽는 정보를 상시 규칙, 필요할 때 읽는 문서, 작업 입력, 작업 중 생성 정보로 나누고, 종류마다 들어오는 시점과 관리 방법을 정합니다.
  • 규칙 문서에는 모든 작업에 해당하는 규칙만 짧게 두고, 같은 실수가 반복되면 항목을 더하며, 맞지 않게 된 항목은 수정하거나 삭제합니다.

컨텍스트는 한정된 자원

선별이 필요한 것은 컨텍스트가 한정된 자원이기 때문입니다. Chapter 1에서 본 것처럼 토큰(Token)은 모델이 텍스트를 나누어 처리하는 단위이고, 컨텍스트 윈도(Context Window)는 모델이 한 번에 처리할 수 있는 토큰의 범위입니다. Anthropic의 컨텍스트 엔지니어링 글은 컨텍스트를 한정된 자원으로 다뤄야 한다고 설명합니다. 글은 그 이유로, 컨텍스트의 토큰이 늘수록 모델이 그 안의 정보를 정확히 떠올리는 능력이 떨어진다는 점을 듭니다.

그래서 자료를 많이 제공한다고 결과가 항상 나아지는 것은 아닙니다. 관련 없는 자료는 관련 있는 자료가 차지할 자리를 줄이고, 오래된 자료는 지금 상태와 맞지 않는 근거가 됩니다. 정할 것은 자료의 양뿐 아니라 작업과의 관련성, 최신성, 제공 시점입니다.

Claude Code에서는 입력창에서 실행하는 /context 명령이 컨텍스트에서 무엇이 공간을 차지하는지 보여 줍니다. 화면에는 사용량을 나타내는 색 격자와 항목별 토큰 수가 나오고, 규칙 문서는 Memory files 항목에 보입니다. /clear 명령은 새 대화를 시작하고, 긴 대화는 /compact 명령으로 요약해 공간을 확보할 수 있습니다. /compact 뒤에 요약에 남길 내용을 적으면 요약을 안내할 수 있습니다. 컨텍스트가 한도에 가까워지면 Claude Code가 오래된 도구 출력을 먼저 지우고, 필요하면 대화를 자동으로 요약합니다. 대화를 요약해 공간을 확보하는 일을 압축이라고 합니다. 압축은 뒤의 미리 제공하는 정보와 필요할 때 찾는 정보 절에서 긴 작업의 기법으로 다시 봅니다.

에이전트가 읽는 정보의 종류

컨텍스트 윈도에 한도가 있으므로, 어떤 정보가 어떤 경로로 언제 들어가는지 구분해야 선별할 수 있습니다. 에이전트가 읽는 정보는 제공 경로와 활용 시점에 따라 네 종류로 나뉩니다.

  • 상시 규칙: 모든 작업에 해당하는 규칙
    • 어디에서 오나: 규칙 문서(Claude Code의 CLAUDE.md)
    • 언제 들어오나: 세션(에이전트와 대화를 한 번 시작해 끝낼 때까지)이 시작될 때마다
  • 필요할 때 읽는 문서: 위치와 읽힐 조건만 안내해 두고 필요할 때 읽는 세부 지침과 자료
    • 어디에서 오나: 규칙 문서에 위치를 안내한 세부 설계 문서, Skill(필요할 때 읽히는 지침 묶음), 경로별 규칙(지정한 경로의 파일에만 적용되는 규칙), 하위 폴더의 규칙 문서
    • 언제 들어오나: 그 작업이나 파일을 다룰 때, 또는 규칙 문서의 안내를 읽은 에이전트가 열 때
  • 작업 입력: 이번 작업을 위해 사람이 주는 정보
    • 어디에서 오나: 사용자가 입력하는 요청과 요청에 함께 첨부하는 자료
    • 언제 들어오나: 요청할 때마다
  • 작업 중 생성 정보: 작업하면서 에이전트가 얻은 정보
    • 어디에서 오나: 에이전트가 열어 모은 파일 내용, 명령이나 도구를 실행해 얻은 출력
    • 언제 들어오나: 도구를 실행할 때마다

위 목록의 시점은 Claude Code 문서의 컨텍스트 설명을 바탕으로 정리한 것입니다.

Skill은 기본 설정에서 이름과 설명만 늘 컨텍스트에 있고 본문은 필요할 때 읽힙니다. 경로별 규칙은 지정한 경로의 파일을 다룰 때 함께 읽힙니다.

네 종류는 제품이 직접 추가하는 정보와 함께 같은 컨텍스트 윈도를 나누어 사용합니다. 제품이 직접 추가하는 정보에는 Chapter 1에서 본 시스템 프롬프트와 도구 정의가 있습니다. 같은 문서라도 사용자가 요청에 첨부하면 작업 입력이고, 규칙 문서에 위치만 안내해 두고 에이전트가 필요할 때 읽게 하면 필요할 때 읽는 문서가 됩니다. 분류의 기준이 문서의 종류가 아니라 제공 경로와 활용 시점인 이유입니다. 필요할 때 읽는 문서와 작업 중 생성 정보는 둘 다 에이전트가 작업 중에 도구로 열어 들어옵니다. 앞의 것은 사람이 미리 작성하고 위치와 읽힐 조건을 안내해 둔 문서이고, 뒤의 것은 에이전트가 작업 대상에서 찾거나 명령을 실행해 얻은 정보입니다.

그림 5-1은 왼쪽에 정보가 오는 곳(규칙 문서, 세부 문서, 사용자, 도구 실행)을, 오른쪽에 컨텍스트 윈도의 네 칸을 두고, 둘을 잇는 화살표에 정보가 들어오는 시점을 적었습니다. 칸마다 관리 방식을 한 줄로 적었고, 표 5-1은 종류별 대표 자료와 관리 방식을 정리합니다.

표 5-1이 종류별 관리 방식이라면, 표 5-2는 그림 5-1의 영역과 선이 맡는 역할과 제약을 정리합니다.

상시 규칙과 필요할 때 읽는 문서를 나누어 사용한 공개 사례도 있습니다. Codex로 제품을 개발한 OpenAI의 팀은 지침을 AGENTS.md 한 파일에 모두 담는 방식이 기대만큼 작동하지 않았다고 밝히고, 약 100줄의 AGENTS.md가 세부 문서의 위치를 안내하는 구성을 쓴다고 설명했습니다.

미리 제공하는 정보와 필요할 때 찾는 정보

앞 절이 정보를 들어오는 경로와 시점으로 나누었다면, 이 절은 같은 자료를 작업 전에 미리 포함해 둘지, 작업 중에 에이전트가 찾아 읽게 할지 선택하는 방법을 다룹니다. 자료를 주는 방법은 두 가지입니다.

  • 미리 제공: 작업 전에 관련 자료를 찾아 컨텍스트에 포함해 두는 방법
    • 예: 임베딩 기반 검색(문장의 뜻을 수치로 변환해 비슷한 자료를 찾는 검색)으로 찾아 둔 자료
    • 앞 절의 종류에서 가까운 것: 상시 규칙, 요청에 첨부한 작업 입력
  • 필요할 때 찾기: 자료의 위치를 가리키는 짧은 정보(식별자)만 두고, 실행 중에 도구로 자료를 불러오는 방법
    • 예: 파일 경로, 저장된 쿼리(미리 저장해 둔 검색 조건), 웹 링크
    • 앞 절의 종류에서 가까운 것: 필요할 때 읽는 문서

두 방법의 설명은 Anthropic의 컨텍스트 엔지니어링 글을 바탕으로 합니다. 글은 AI 모델을 중심으로 만든 많은 애플리케이션이 어떤 형태로든 임베딩 기반 검색으로 중요한 자료를 모델이 추론하기 전에 찾아 둔다고 설명합니다.

두 방법에는 각각 장점과 한계가 있습니다. 같은 글에 따르면 미리 제공하는 방법은 실행 중에 탐색하지 않으므로 빠를 수 있습니다. 반면 미리 찾아 둔 범위 밖의 자료가 작업 중에 새로 필요해지면, 그 자료는 컨텍스트에 담겨 있지 않습니다.

필요할 때 찾는 방법은 에이전트가 탐색하며 관련 자료를 단계적으로 좁혀 가지만, 미리 찾아 둔 자료를 사용하는 것보다 느릴 수 있습니다. 도구와 탐색 기준이 없으면 관련 없는 탐색을 이어 가며 컨텍스트를 낭비할 수도 있습니다.

두 방법은 섞어 사용할 수 있습니다. 같은 글은 혼합 방식의 예로, Claude Code가 CLAUDE.md를 작업 전에 컨텍스트에 포함하고, 파일은 이름 패턴으로 찾는 glob과 내용으로 찾는 grep 같은 검색으로 필요할 때 찾는다고 설명합니다. 어느 방법이든 목표는 원하는 결과가 나올 가능성을 높이는 정보만 가장 작은 묶음으로 선별하는 것이라고 글은 정리합니다.

어느 방법을 쓰든 가져온 자료와 대화 이력은 작업이 길어질수록 쌓이므로, 긴 작업에서는 컨텍스트 윈도에 다 담기지 않는 정보를 다뤄야 할 수 있습니다. 같은 글은 이런 작업을 위한 세 기법과 각 기법이 맞는 작업을 소개합니다.

  • 압축: 앞에서 본 것처럼 한도에 가까운 대화를 요약해 새 컨텍스트로 이어 가는 기법
    • 맞는 작업: 대화를 길게 주고받는 작업
  • 구조화된 노트: 에이전트가 컨텍스트 밖의 파일에 진행 상황을 적어 두고 나중에 다시 읽는 기법
    • 맞는 작업: 단계별 목표를 정해 두고 조금씩 진행하는 개발
  • 하위 에이전트(Subagent): 특정 작업을 맡도록 따로 정의한 에이전트에게 분리된 컨텍스트에서 일을 맡기고 요약만 돌려받는 기법
    • 맞는 작업: 여러 갈래를 나누어 동시에 탐색하는 조사와 분석

하위 에이전트는 새 컨텍스트에서 시작해 주 대화(사람과 에이전트가 주고받는 세션의 대화)의 내용을 보지 못하고, 위임할 때 받은 지시와 규칙 문서(CLAUDE.md)를 근거로 작업합니다. 그래서 위임할 때는 필요한 내용이나 그 내용이 있는 파일의 위치를 지시에 담습니다.

이 동작에는 두 가지 예외가 있습니다. Claude Code에 처음부터 들어 있는 하위 에이전트 가운데 Explore와 Plan, 그리고 정의 파일에 규칙 문서를 읽지 않게 하는 설정(omitClaudeMd)을 둔 하위 에이전트는 규칙 문서도 읽지 않습니다. 반대로 포크(Fork)는 주 대화 전체를 이어받아 시작하는 하위 에이전트라 주 대화의 내용을 봅니다.

그림 5-2는 위에서 아래로 읽습니다. 위쪽에는 자료를 주는 두 방법(미리 제공, 필요할 때 찾기)과 둘을 섞는 혼합이 있고, 두 영역을 잇는 화살표는 어느 방법을 쓰든 작업이 컨텍스트 윈도를 넘을 만큼 길어지면 아래쪽의 세 기법이 필요해진다는 뜻입니다. 표 5-3은 그림의 구성 요소를, 표 5-4는 기법별 역할과 제약을 정리합니다.

Anthropic의 컨텍스트 엔지니어링 글은 지나치게 압축하면 미묘하지만 중요한 맥락을 잃을 수 있다고 설명합니다. 같은 글은 Claude Code가 작업 중에 할 일 목록을 만들어 두고 다시 보는 것을 구조화된 노트의 예로 듭니다.

압축 뒤에 무엇이 남는지는 제품마다 다르므로 사용하는 제품의 문서로 확인합니다. Claude Code 문서에 따르면 대화로 준 지시는 압축 뒤 요약에서 누락될 수 있지만, 프로젝트 루트(프로젝트의 맨 위 폴더)의 규칙 문서(CLAUDE.md)는 압축 뒤에 디스크에서 다시 읽혀 들어갑니다. 반면 경로별 규칙과 하위 폴더의 규칙 문서는 압축 직후에는 다시 읽히지 않고, 그 경로나 폴더의 파일을 다시 열 때 읽힙니다. 그래서 세션 내내 지켜야 할 지시는 대화로 주기보다 프로젝트 루트의 규칙 문서에 둡니다.

규칙 문서의 작성

규칙 문서는 상시 규칙으로 읽혀 모든 세션의 컨텍스트를 차지하므로, 작성 방법이 결과에 영향을 줍니다. Claude Code는 CLAUDE.md를, Codex는 AGENTS.md를 읽습니다.

버전 주석 (2026년 10월) Claude Code 문서는 v2.1.277 이상에서 작업 폴더와 그 위 폴더에 CLAUDE.md가 없고 AGENTS.md만 있으면 AGENTS.md를 읽는다고 안내합니다. Amazon Bedrock(Amazon의 클라우드에서 모델을 사용하는 서비스)을 거치는 세션이나, 사용 정보 전송(텔레메트리)을 끈 일부 세션은 v2.1.281 이상이 필요합니다. 두 제품의 규칙 문서 비교는 Chapter 10의 규칙 문서 비교에 있습니다.

Claude Code 문서의 CLAUDE.md 작성 안내를 다음 네 가지 기준으로 정리합니다.

  • 구체적으로: 확인할 수 있을 만큼 구체적으로 적음
    • 이유: 모호한 지침은 지켰는지 확인할 수 없음
    • 예와 한계: "파일을 정돈해 둔다" 대신 "API 처리 파일은 src/api/handlers/에 둔다"
  • 짧게: 파일 하나를 200줄 미만으로 유지하는 것이 권장 목표
    • 이유: 길수록 컨텍스트를 더 차지하고 지침을 지키는 비율이 낮아질 수 있음
    • 예와 한계: 200줄은 제품이 강제하는 제한이 아니고, 짧다고 준수가 보장되지 않음
  • 일관되게: 같은 대상에 대한 지침이 겹치지 않게 함
    • 이유: 두 지침이 모순되면 에이전트가 둘 중 하나를 임의로 따를 수 있음
    • 예와 한계: 한 절에서 수정할 수 있다고 적은 폴더를 다른 절에서 수정하지 않는다고 적지 않음
  • 나누어서: 여러 단계의 절차는 Skill로, 일부 파일의 지침은 경로별 규칙으로 옮김
    • 이유: 상시 규칙을 짧게 유지함
    • 예와 한계: 규칙 문서에 @docs/CR.md처럼 @ 뒤에 경로를 적은 파일은 시작할 때 함께 읽혀 상시 규칙이 되므로, 필요할 때 읽게 할 문서는 @ 없이 경로만 적음

뒤의 예제 절에서는 Chapter 3의 예제에서 구현을 맡은 에이전트의 규칙 문서를 이 네 기준에 비추어 봅니다. 규칙 문서를 직접 작성하는 실습은 부록의 실습 2. 규칙 문서 작성에 있습니다.

규칙 문서의 관리

규칙 문서는 한 번 작성하고 끝나는 문서가 아닙니다. 규칙 문서의 관리에는 항목을 추가하는 일뿐 아니라, 사실이나 결정이 변경되어 맞지 않게 된 항목을 수정하거나 삭제하는 일도 포함됩니다. 오래된 지침이 남으면 장 첫머리에서 본 것처럼 에이전트가 다른 근거로 판단할 수 있기 때문입니다. Claude Code 문서는 항목을 추가할 시점으로 네 가지를 제시합니다.

  • 에이전트가 같은 실수를 두 번째로 했을 때
  • 코드 리뷰에서 에이전트가 알았어야 할 내용이 지적되었을 때
  • 지난 세션에 입력한 정정 내용을 다시 입력하고 있을 때
  • 새로 합류한 팀원에게도 같은 설명이 필요할 때

수정하거나 삭제할 항목은 폴더 구조나 명령이 변경되었을 때, 같은 내용이 다른 문서에 생겼을 때, 문서가 권장 길이를 넘었을 때 찾아봅니다.

항목을 추가해도 에이전트가 반드시 따르는 것은 아닙니다. Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 다룬다고 설명하고, 에이전트의 판단과 관계없이 막아야 하는 동작은 도구를 실행하기 전에 작동하는 훅(Hook)으로 막으라고 안내합니다. Chapter 2에서 본 것처럼 규칙 문서는 에이전트가 읽고 따르도록 요청하는 지시이고, 권한 규칙(Permission Rule, 도구 호출을 허용, 확인 요청, 금지로 나눠 정한 규칙)과 훅은 에이전트의 판단과 관계없이 제품이 적용하는 강제입니다. 그래서 규칙 문서의 금지 항목 가운데 어기면 되돌리기 어려운 항목은 권한 규칙이나 훅으로도 막을지 검토합니다. 규칙마다 지시와 강제 가운데 무엇에 맡길지는 Chapter 2의 지시 기반 규칙과 강제 적용에서 다루었습니다.

예제: 변경 요청 사항의 구현 에이전트가 읽을 정보 정하기

변경 요청 사항은 가상 프로젝트인 경비 정산 시스템 개편에 재무팀이 보낸 요청입니다. 직원이 경비를 돌려받으려고 올리는 정산 요청 화면에 프로젝트 코드(경비가 속한 프로젝트의 식별 번호)를 선택하는 항목을 추가해 달라는 내용입니다. 이 절에서는 Chapter 3에서 설계한, 변경 요청 사항을 구현하는 에이전트가 무엇을 언제 읽는지를 앞의 네 종류와 작성 기준으로 정합니다.

예제에는 Chapter 3에서 정한 파일과 역할이 나옵니다.

  • 수용 기준: 완료 기준 가운데 사람이 정한 것입니다. docs/CR.md에 다섯 가지가 있습니다.
  • 수용 시험(acceptance/)과 검사 스크립트(check.py): 수용 시험은 수용 기준을 자동으로 확인하는 시험이고, 검사 스크립트는 단위 테스트와 수용 시험을 한 번에 실행하는 프로그램입니다. 둘 다 사람이 작성하고 에이전트는 수정하지 않습니다.
  • 진행 기록(tasks.json): 작업 단위(한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업)마다 확인 방법과 통과 값(true 또는 false)을 적은 파일입니다.
  • 편집 뒤 훅: 파일을 수정할 때마다 단위 테스트(프로그램의 부품 하나가 정해진 대로 동작하는지 확인하는 시험)를 자동으로 실행하는 훅입니다.
  • 검토 하위 에이전트: 바뀐 내용을 수용 기준과 대조해 보고만 하는 하위 에이전트로, 읽기 도구만 사용합니다.

작업 단위로 나누는 방법은 Chapter 6의 작업 단위 분할에서 다룹니다.

이 에이전트는 부록 실습 2에서 예시 규칙 문서(examples/expense-app/reference/CLAUDE.example.md)를 본떠 실습 폴더(이 예제의 프로젝트 루트)에 작성한 CLAUDE.md를 상시 규칙으로 읽습니다. reference/ 폴더의 예시 파일은 Claude Code가 자동으로 읽지 않습니다. 이 규칙 문서는 목적, 읽는 순서, 작업 순서, 수정 범위, 중단 규칙, 명령의 여섯 절로 이루어지며, 빈 줄을 포함해 32줄입니다. 다음은 그 가운데 이 장과 관련된 두 절의 발췌입니다.

## 읽는 순서
1. docs/CR.md(수용 기준)
2. DECISIONS.md
3. tasks.json
4. HANDOFF.md(있으면)

## 수정 범위
- 수정할 수 있음: expense/, app.py, tests/, tasks.json의 "통과" 값, HANDOFF.md
- 수정하지 않음: data/, acceptance/, check.py, CLAUDE.md, DECISIONS.md, .claude/

읽는 순서 절은 필요할 때 읽는 문서의 위치와 순서만 안내하고, 문서의 내용은 규칙 문서에 옮기지 않습니다. 변경 요청 사항 문서(docs/CR.md)는 표 5-1의 분류로는 작업 입력인 변경 요청서에 해당합니다. 그러나 이 예제에서는 요청에 첨부하지 않고 읽는 순서 절에 위치만 적어 에이전트가 작업 단위마다 직접 열게 하므로, 필요할 때 읽는 문서로 다룹니다. Chapter 3의 표 3-3이 세션을 시작할 때 처음 읽는 자료로 적은 것도 이 네 파일입니다. 이 파일들은 작업을 시작할 때마다 읽지만, 제품이 자동으로 포함하지 않고 규칙 문서의 안내를 읽은 에이전트가 도구로 열어야 컨텍스트에 들어오므로 필요할 때 읽는 문서에 해당합니다. 표 3-3이 필요할 때 찾는 자료로 적은 앱 코드와 테스트는 이 장의 분류로 작업 중 생성 정보입니다.

수정 범위 절은 에이전트가 수정할 수 있는 파일과 수정하지 않을 파일을 나누고, 뒤의 확인 방법 절에서 바뀐 파일 목록과 대조하는 기준이 됩니다. 수정하지 않음의 경로는 권한 설정 예시(reference/settings.example.json)를 옮겨 만드는 권한 설정(.claude/settings.json)의 금지 규칙에도 들어 있습니다. 그래서 규칙 문서는 지시를 맡고 권한 설정은 도구 호출의 강제를 맡습니다(부록의 실습 3. 권한 설정).

규칙 문서의 작성 절에서 본 네 기준으로 보면, 이 규칙 문서는 수정 범위를 폴더와 파일 이름으로 적어 바뀐 파일과 대조할 수 있고(구체적으로), 32줄로 권장 목표보다 짧습니다(짧게). 또 수정할 수 있음과 수정하지 않음에 겹치는 경로가 없고(일관되게), 수용 기준과 결정의 내용은 각 파일에 두고 위치만 안내합니다(나누어서). 표 5-5는 네 종류의 정보를 이 예제에서 어떻게 정했는지 보여 줍니다. 운영 기준 가운데 진행할 작업 단위와 완료 보고의 내용은 발췌하지 않은 작업 순서 절에 있고, 작업 입력의 요청 문장은 부록의 실습 5. 작업 단위로 구현에서 입력하는 요청과 일치합니다.

긴 작업의 기법도 이 예제에 쓰입니다. 규칙 문서의 중단 규칙은 세션을 마칠 때 다음 세션이 이어받을 상황을 적는 인계 메모(HANDOFF.md, Chapter 8의 인계 메모 작성)에 현재 상태, 읽을 문서, 미결정, 다음 작업, 확인 명령을 적게 합니다. 직전 세션을 다시 여는 claude --continue 명령을 사용하지 않고 새로 시작한 세션에는 지난 대화가 컨텍스트에 없으므로, 인계 메모가 다음 세션이 읽을 구조화된 노트 역할을 합니다. tasks.json의 통과 값도 어느 작업 단위까지 끝났는지를 남기는 노트입니다. 수용 기준 대조를 검토 하위 에이전트에게 맡기는 것은 하위 에이전트 기법의 예입니다. 압축은 이 예제에서 따로 정하지 않았으며, 자동 압축이 일어나도 프로젝트 루트의 규칙 문서는 다시 읽힙니다.

규칙 문서에 위치와 순서만 두고 내용은 각 문서에서 읽게 하는 방식은 Chapter 11에서 다루는 작가의 원고 저장소에도 쓰입니다. 원고를 작성하는 에이전트는 작업을 시작할 때 원고 저장소 루트의 규칙 문서(CLAUDE.md)를 읽습니다. 이어서 거기 적힌 순서대로 원고 기준 문서(원칙과 규칙을 모은 플레이북, 책마다 정한 선택을 적은 책 설계서), 작업 진행 방식 문서, 인계 메모(HANDOFF.md), 작가에게 묻는 질문 목록과 결정 기록을 읽습니다.

실패를 예방하는 장치

표 5-5가 예제에서 읽을 정보를 정한 결과라면, 표 5-6은 정보가 누락되거나 넘치거나 오래되었을 때 실패를 예방하는 장치를 정리합니다. 행은 상시 규칙(첫째 행), 필요할 때 읽는 문서(둘째, 셋째 행), 작업 입력(넷째 행), 작업 중 생성 정보(다섯째 행)의 순서이고, 표의 읽는 순서와 수정 범위는 예제 절에서 보인 규칙 문서의 두 절을 가리킵니다. 셋째 행의 결정 기록은 예제 규칙 문서의 읽는 순서에 이미 있습니다. 다섯째 행의 시험 실행 하위 에이전트는 예제의 검토 하위 에이전트가 읽기 전용이라 시험을 실행하지 않으므로 따로 정의해야 합니다.

설정과 결과의 확인 방법

에이전트가 무엇을 읽고 있는지는 제품의 화면과 대화 기록으로 확인합니다. 규칙 문서가 컨텍스트에 들어 있다는 것과 에이전트가 규칙을 실제로 지킨다는 것은 다른 문제입니다. 그래서 규칙 문서가 보여도 지켜진다고 판정하지 않고, 규칙을 이해했는지는 응답으로, 실제로 지켰는지는 바뀐 파일로 따로 확인합니다. 표 5-7은 변경 요청 사항을 구현하는 에이전트에서 확인할 항목입니다. /context는 실습 폴더에서 시작한 Claude Code의 입력창에, 나머지 명령은 터미널에서 실습 폴더로 이동한 뒤 입력합니다. wc -l은 파일의 줄 수와 파일 이름을 출력하고(예: 32 CLAUDE.md), 규칙 문서를 만들기 전에는 파일이 없다는 오류를 냅니다. git show --stat HEAD는 마지막 commit(HEAD)에서 바뀐 파일 이름과 바뀐 줄 수만 보여 줍니다. 어느 값이 변경되었는지는 git show HEAD -- tasks.json이 보여 주는 바뀐 줄(-가 붙은 지운 줄과 +가 붙은 더한 줄)로 확인합니다. commit 전이면 git status가 바뀐 파일 목록을, git diff -- tasks.json이 아직 commit하지 않은 바뀐 줄을 보여 줍니다.

설계 원칙과 점검 질문

상시 규칙 문서에는 모든 작업에 필요한 내용만 짧게 두고, 나머지는 필요할 때 읽도록 위치만 안내합니다.

자기 업무에 적용할 때는 다음 세 질문으로 점검합니다.

  1. 지금 규칙 문서에 특정 작업에만 필요한 지침이 섞여 있지 않습니까?
  2. 지난 세션에 입력한 정정 내용을 이번 세션에 다시 입력하고 있지 않습니까?
  3. 에이전트가 대체된 결정이나 오래된 자료를 읽고 근거로 삼을 수 있는 경로가 남아 있습니까?
