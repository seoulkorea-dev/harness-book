Chapter 3 하네스로 에이전트 설계하기

에이전트의 동작은 요청 문장뿐 아니라, 업무의 목적부터 승인 지점까지 하네스에 정의한 아홉 항목에 따라 달라집니다.

이 장에서는 에이전트(Agent)를 설계하는 출발점인 에이전트 명세서를 다룹니다. 에이전트는 요청을 받으면 하네스(Harness)에 정의된 규칙 문서, 도구, 권한을 바탕으로 작업합니다. 정의되지 않은 항목은 모델의 추측이나 제품의 기본값으로 채워질 수 있습니다. 이로 인해 결과가 업무 의도와 달라지거나, 판단의 근거가 남지 않을 수 있습니다.

이를 방지하려면 업무에 필요한 아홉 항목, 곧 목적, 역할, 입력, 도구, 권한, 기록, 검증, 종료 조건, 승인 지점을 하나의 에이전트 명세서에 정리하고, 그 내용을 Claude Code가 읽는 하네스 설정 파일로 옮겨야 합니다. 아홉 항목 가운데 역할, 도구, 권한, 기록, 검증은 2장의 다섯 구성 요소입니다.

이 장에서는 에이전트 명세서의 구성 항목을 살펴보고, 변경 요청 사항을 구현하는 에이전트에 적용한 뒤, 명세서를 Claude Code가 읽는 하네스 설정 파일로 옮기는 방법을 다룹니다.

  • 에이전트 명세서는 다섯 구성 요소(역할, 도구, 권한, 기록, 검증)에 목적, 입력, 종료 조건, 승인 지점을 더한 아홉 항목의 값을 적는 문서입니다.
  • 수용 기준을 판정하는 시험과 스크립트(검증 기준)는 사람이 작성하고, 에이전트가 수정해 통과한 것처럼 꾸미지 못하게 금지 규칙과 사람의 확인으로 보호합니다.
  • 명세서의 값은 규칙 문서, 권한 규칙과 훅을 담은 설정 파일, 하위 에이전트 정의처럼 Claude Code가 읽고 적용하는 하네스 설정 파일로 옮깁니다.

에이전트 명세서의 아홉 항목

업무를 맡길 때마다 정할 항목을 기억에 의존하면 누락이 생기기 쉽습니다. 이를 방지하려면 항목을 목록으로 정리하고, 업무마다 해당 값을 채워야 합니다. 업무에 필요한 항목과 값을 기록한 문서를 에이전트 명세서라고 합니다.

에이전트 명세서는 아홉 항목으로 구성됩니다. 하네스는 모델이 에이전트로 일할 수 있게 하는 모델 바깥의 실행 체계 전체이고, 그 가운데 사용자와 팀이 정하는 층을 설정이라고 합니다. 아홉 항목 가운데 다섯은 Chapter 2의 다섯 구성 요소에서 살펴본 설정의 구성 요소인 역할, 도구, 권한, 기록, 검증입니다. 나머지 네 항목인 목적, 입력, 종료 조건, 승인 지점은 맡기는 업무가 바뀔 때마다 값을 새로 정하므로 업무 항목이라고 합니다.

다섯 구성 요소는 에이전트가 일하는 환경을 정하고, 업무 항목은 에이전트가 무엇을 위해, 무엇을 가지고 일하며, 언제 끝내고, 어디서 사람이 개입하는지를 정합니다. 승인 지점은 권한 규칙(Permission Rule)의 확인 요청으로 구현하는 경우가 많지만, 어느 동작에서 사람이 개입할지는 업무마다 달라 업무 항목에 둡니다. 표 3-1은 업무 항목마다 정할 값, 값을 정하는 기준, 비워 두었을 때 생기는 일을 정리합니다.

업무 항목 가운데 종료 조건에는 값이 여러 개 들어갑니다. 작업이 끝났는지 판정하는 완료 기준, 같은 실패가 반복될 때 멈추는 규칙, 그리고 턴 상한과 비용 상한입니다. 턴 상한과 비용 상한은 루프가 도는 횟수와 사용하는 비용에 두는 한도입니다. 사람이 지켜보는 대화형 세션처럼 상한을 두지 않는 업무에서는 완료 기준과 중단 규칙이 종료 조건을 맡습니다.

아홉 항목 가운데 검증은 기준을 정하는 것만으로는 충분하지 않고, 그 기준을 누가 수정할 수 있는지도 정해야 합니다. 완료를 판정하는 시험(결과가 맞는지 자동으로 확인하는 코드)을 에이전트가 수정할 수 있으면, 기능을 구현하지 않고 실패하는 시험을 수정해서 통과시킬 수 있기 때문입니다.

완료 기준 가운데 사람이 업무의 요구로 정한 것을 수용 기준(Acceptance Criteria)이라고 합니다. 수용 기준을 자동으로 판정하는 시험과, 시험을 실행하는 작은 프로그램(스크립트)을 묶어 검증 기준이라고 합니다. 검증 기준은 사람이 작성하고, 에이전트의 수정은 금지 규칙으로 막으며, 금지 규칙이 막을 수 없는 경우는 사람의 확인으로 보완합니다.

명세서는 사람이 읽는 문서여서 Claude Code가 그대로 적용하지 않습니다. 그래서 명세서의 값은 Claude Code가 정해진 위치에서 자동으로 읽어 들이는 파일로 옮겨야 작동합니다. 이런 파일을 하네스 설정 파일이라고 합니다. 이 장에서 다루는 하네스 설정 파일은 규칙 문서(CLAUDE.md), 권한 규칙과 훅(Hook)을 담는 설정 파일(.claude/settings.json), 하위 에이전트(Subagent) 정의 셋입니다. 진행 기록, 결정 기록, 인계 메모, 검증 기준처럼 에이전트가 읽거나 실행하는 저장소의 다른 파일도 명세서의 값을 담습니다. 다음 예제에서 명세서의 값을 정하고, 그 뒤에 하네스 설정 파일로 옮깁니다.

예제: 변경 요청 사항의 에이전트 명세서 작성

이 절은 명세서를 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)에 적용합니다. 경비 정산 시스템 개편은 가상 프로젝트이고, 변경 요청 사항은 이 프로젝트에 들어온 변경 요청 한 건입니다. 재무팀은 2026년 10월 5일, 직원이 경비를 돌려받으려고 올리는 정산 요청 화면에 프로젝트 코드(경비가 사용된 프로젝트를 가리키는 코드) 선택 항목을 추가해 달라고 요청했습니다. 프로젝트별 경비 집계를 월말 결산에 반영하기 위해서입니다.

대상은 정산 요청을 등록하고 목록으로 보여 주는 작은 웹 앱이며, 따로 설치할 것 없이 Python만 있으면 실행됩니다. 앱 코드는 expense/ 폴더와 app.py에 있고, 앱이 맞게 동작하는지 확인하는 시험 코드는 tests/와 acceptance/ 폴더에 있습니다. 등록할 수 있는 프로젝트 코드 목록은 인사 시스템이 하루 한 번 갱신하는 data/projects.csv에 있으며, 앱은 이 파일을 읽기만 합니다. 이 파일을 원본 자료라고 합니다.

변경 요청 사항은 다섯 작업 단위로 나뉩니다. 작업 단위는 한 세션 안에 끝나고 완료 여부를 확인할 수 있는 크기로 나눈 작업입니다.

  • 작업 1: 인사팀과 프로젝트 코드 조회 방식을 합의합니다. 사람이 맡고, 합의 결과는 결정 기록(DECISIONS.md, 정한 내용과 이유를 적는 문서)의 12번 결정(D-012)으로 확인합니다.
  • 작업 2: 정산 요청의 데이터 모델(정산 요청 한 건을 어떤 항목으로 저장할지 정한 코드)에 프로젝트 코드 항목을 추가합니다. 에이전트가 맡습니다.
  • 작업 3: 바뀐 데이터 모델에 맞춰 단위 테스트(코드의 작은 부분이 의도대로 동작하는지 확인하는 시험, tests/ 폴더)를 갱신합니다. 에이전트가 맡습니다.
  • 작업 4: 정산 요청 화면에 프로젝트 코드 선택 항목을 추가하고, 프로젝트 코드 목록에 없는 코드는 거부합니다. 에이전트가 맡습니다.
  • 작업 5: 프로젝트별 집계를 확인하는 통합 시나리오(여러 기능을 이어서 실행해 확인하는 시험 절차)의 초안을 작성합니다. 에이전트가 초안을 작성하고, 사람이 승인해 완료를 확정합니다.

작업 2~4는 앞 작업의 결과 위에서 이어지므로, 앞 작업이 제대로 끝났는지 확인하지 않으면 잘못이 뒤로 번집니다. 그래서 작업 단위마다 무엇으로 확인하고, 어디서 멈추고, 어디서 사람이 승인할지를 미리 정합니다. 확인하려면 완료 기준이 먼저 있어야 하므로, 사람이 변경 요청 사항의 수용 기준을 정합니다. 수용 기준은 다섯 가지이고, 변경 요청 사항 문서(docs/CR.md)에 있습니다.

  • 정산 요청 등록 화면에서 프로젝트 코드 목록의 코드를 선택할 수 있습니다.
  • 프로젝트 코드 목록에 없는 코드로 등록하면 거부하고, 거부 사유에 입력한 코드를 표시합니다.
  • 목록 화면에 프로젝트 코드를 표시합니다.
  • 프로젝트 코드가 없는 기존 정산 요청도 이전처럼 목록 화면에 나옵니다.
  • 등록 처리는 원본 자료(data/projects.csv)를 변경하지 않습니다.

수용 시험은 수용 기준을 충족하는지 자동으로 확인하는 시험 코드이며, acceptance/ 폴더에 기준마다 하나씩 다섯 건이 있습니다. 수용 시험은 사람이 작성하고 에이전트는 수정하지 않습니다. 반면 단위 테스트는 데이터 모델이 변경되면 함께 수정해야 하므로 에이전트가 수정합니다. 검사 스크립트(check.py)는 두 시험을 명령 한 번으로 실행하는 작은 프로그램입니다. 종료 코드는 명령이 끝날 때 돌려주는 값이며, 0은 성공, 0이 아닌 값은 실패를 뜻합니다. 검사 스크립트가 종료 코드 0으로 끝나는 조건은 셋입니다. 두 시험에서 실패한 시험과 실행하지 않고 넘어간 시험(건너뜀)이 0건이고, 수용 시험이 정한 수(5건)만큼 실행되고, 이름에 project_code가 든 단위 테스트가 1건 이상 있어야 합니다. 셋째 조건은 시험의 이름만 세고, 시험이 무엇을 확인하는지는 보지 않습니다. 이 예제의 검증 기준은 수용 시험과 검사 스크립트입니다.

이 예제에는 에이전트가 둘입니다. 구현 에이전트는 작업 단위를 처리하며 코드를 수정하는 주 에이전트이고, 검토 하위 에이전트는 바뀐 내용을 수용 기준과 대조해 보고만 하는 하위 에이전트입니다.

진행 기록(tasks.json)에는 작업 단위마다 완료 기준을 무엇으로 판정할지 적은 확인 방법(예: 맡은 수용 시험 통과)과, 그 확인 방법을 충족했는지를 true 또는 false로 적는 통과 값이 있습니다. 작업 1은 합의가 이미 결정 기록(D-012)에 있어 통과 값이 처음부터 true이고, 작업 2~4의 통과 값은 구현 에이전트가, 사람이 승인하는 작업 5의 통과 값은 사람이 변경합니다. tasks.json은 에이전트가 수정할 수 있는 파일이므로, 작업 5의 통과 값과 확인 방법 문구가 그대로인지는 사람이 commit 확인에서 봅니다.

구현 에이전트는 세션을 마칠 때 인계 메모(HANDOFF.md, 한 일과 다음 할 일을 적은 메모)를 남깁니다. 변경 확정(git commit)은 바뀐 파일을 저장소의 기록으로 남기는 명령이고, 원격 저장소 반영(git push)은 그 기록을 다른 사람이 보는 저장소에 올리는 명령입니다. 권한 규칙과 훅, 하위 에이전트 정의는 설정 폴더(.claude/)에 둡니다.

표 3-2와 표 3-3은 이 업무에 명세서를 적용한 결과입니다. 표 3-2는 다섯 구성 요소의 값으로, Chapter 2의 예제와 같은 구성을 명세서 형식으로 묶었습니다. 표 3-3은 업무 항목의 값입니다.

이 설계의 핵심 결정은 검증 기준을 보호하는 것입니다. 앞에서 본 것처럼 단위 테스트는 구현 에이전트가 수정할 수 있습니다. 그러나 수용 시험과 검사 스크립트는 사람이 작성하고, 구현 에이전트의 편집 도구로는 수정하지 못하게 금지 규칙으로 막습니다. 작업 4는 사람이 작성한 수용 시험으로 완료를 판정하므로, 단위 테스트의 판정을 변경하는 것만으로는 완료를 꾸밀 수 없습니다. 작업 3은 다릅니다. 작업 3의 근거인 단위 테스트는 에이전트가 작성하므로, 아무것도 확인하지 않는 시험이라도 이름에 project_code만 들어 있으면 작업 3의 확인 방법은 충족됩니다. 그래서 그 시험이 바뀐 데이터 모델을 실제로 확인하는지는, 사람이 commit을 승인하기 전에 바뀐 파일을 보는 commit 확인에서 봅니다.

검사 스크립트도 막을 수 없는 변경이 있습니다. 수용 시험 파일을 지우거나 일부를 건너뛰게 하면 실행 건수나 건너뜀 수가 달라져 검사 스크립트가 실패합니다. 그러나 시험 안에서 결과를 비교하는 줄만 지워 내용을 약하게 변경하면 건수는 그대로입니다. 예를 들어 프로젝트 코드 목록에 없는 코드를 거부하는지 보는 수용 시험에서 거부 여부를 비교하는 줄을 지우면, 검사 스크립트는 통과하고 거부 기능은 없는 채로 완료가 보고됩니다. 검사 스크립트가 건수를 확인하는 것과 별도로, 수용 시험의 수정을 권한 규칙으로 금지하는 이유가 이것입니다.

확인 방법은 구현 전에는 실패하고 구현 뒤에 통과해야 완료의 근거가 되므로, 확인 방법이 기준 전체를 증명하는지도 점검합니다. 작업 2의 확인 방법(수용 시험 4, 5 통과)은 기존 요청의 표시와 원본 자료의 보존이라는 기존 동작만 시험하므로, 구현 전에도 통과합니다. 등록한 요청에 코드가 저장되는지는 작업 4의 수용 시험 3(목록 화면에 코드 표시)에서야 확인됩니다. 이 확인 방법만으로는 작업 2가 끝났다고 판정할 수 없으므로, 작업 2는 사람이 commit 확인에서 데이터 모델의 변경을 직접 보고 승인합니다. 이 예제는 작업 2만을 확인하는 수용 시험을 두지 않았으므로, 그 공백을 사람의 commit 확인이 메웁니다.

종료 조건은 작업 단위마다 판정합니다. 구현 에이전트는 작업 단위를 마칠 때 검사 스크립트를 실행하고, tasks.json에 적은 확인 방법을 충족하면 그 작업 단위의 통과 값을 true로 변경합니다. 작업 2와 작업 3을 마친 시점에는 작업 4가 맡은 수용 시험 1, 2, 3이 아직 실패하므로, 검사 스크립트 전체는 종료 코드 1로 끝납니다. 그래서 확인 방법은 검사 스크립트 전체의 종료 코드로 판정하지 않고, 출력 가운데 그 작업 단위가 맡은 시험의 결과로 판정합니다(작업 3은 tests 줄의 실패 0건과 project_code 시험 1건 이상). 중단 규칙도 작업 단위를 마칠 때 실행한 검사 스크립트에서 그 단위의 확인 방법에 든 시험(확인 대상 시험)이 세 번 연속 실패할 때만 적용하고, 편집 뒤 훅의 실패는 세지 않습니다. 작업 4까지 마치면 검사 스크립트가 종료 코드 0으로 끝나며, 이것이 목표 상태입니다.

작업 단위의 완료가 확정되는 것은 사람이 commit을 승인할 때입니다. 통과 값을 변경한 뒤 구현 에이전트는 검토 하위 에이전트에게 대조를 요청하고, 사람은 그 검토 보고와 바뀐 파일을 보고 commit을 승인하거나 수정을 요청합니다. 수정을 요청받으면 구현 에이전트는 그 작업 단위의 통과 값을 false로 되돌리고 다시 작업합니다. 검토 보고는 완료 판정에 들어가지 않고, 사람이 commit 확인 전에 읽는 참고 보고입니다.

이 예제는 턴 상한과 비용 상한을 두지 않았습니다. Claude Code에서 턴과 비용의 상한을 정하는 명령 줄 옵션(--max-turns, --max-budget-usd)은, 대화 없이 요청 하나를 실행하고 끝내는 -p 실행에서만 사용할 수 있습니다. 이 예제는 사람이 지켜보는 대화형 세션에서 진행하므로 상한 대신 완료 판정과 중단 규칙으로 종료 조건을 정했습니다.

승인 지점과 기록도 정합니다. commit은 실행 전에 사람의 확인을 받게 하고, push는 금지 규칙으로 막아 사람이 실행합니다. 같은 동작을 다른 형태로 작성한 명령은 규칙의 문자열과 일치하지 않을 수 있으며, 그 한계와 보완은 뒤에서 명세서의 값을 설정 파일로 옮길 때 다룹니다. 구현은 부록 실습 5, 6과 같이 두 세션에 나누어 진행합니다(첫 세션은 작업 2, 3, 두 번째 세션은 작업 4). 새로 시작한 세션에 이전 대화가 자동으로 이어진다고 가정할 수 없으므로, 두 번째 세션은 인계 메모와 진행 기록을 읽고 시작합니다.

그림 3-1은 표 3-2와 표 3-3의 값을 하네스에 적용했을 때 주체별로 수정할 수 있는 파일과, 작업 단위 하나의 검증 흐름을 보여 줍니다. 위쪽 두 영역은 수정할 수 있는 파일과 수정할 수 없는 파일이고, 아래는 검증 흐름입니다. 규칙 문서도 하네스의 설정에 속하지만, 설정 폴더(.claude/) 밖에 두고 에이전트가 읽는 지시이므로 그림에서는 설정 폴더와 따로 적었습니다.

검증 흐름에서 실선은 정상 흐름, 점선은 되돌아가거나 멈추는 경로입니다. 훅은 파일을 수정하는 도구(Edit, Write)가 실행될 때마다 그 뒤에 단위 테스트를 자동으로 실행하고, 검사 스크립트는 구현 에이전트가 작업 단위를 마칠 때 실행합니다. 확인 방법을 충족하면 구현 에이전트가 통과 값을 변경하고, 바뀐 파일 목록과 변경 내용을 넘겨 검토 하위 에이전트에게 대조를 요청합니다. 사람은 그 검토 보고를 읽고 commit을 승인하거나 수정을 요청하며, 수정을 요청받으면 구현 에이전트가 통과 값을 false로 되돌리고 파일 수정으로 돌아갑니다.

표 3-4는 그림 3-1의 구성 요소와 주요 역할을 정리합니다.

명세서를 하네스 설정 파일로 옮기기

앞에서 정한 값을 세 종류의 하네스 설정 파일로 옮깁니다. 대화로 전한 지시는 새 세션에 자동으로 이어진다고 가정할 수 없으므로, 세션마다 지켜야 할 값은 파일에 둡니다. 규칙 문서(CLAUDE.md)는 에이전트가 세션을 시작할 때 읽는 지시입니다. 프로젝트의 설정 파일(.claude/settings.json)은 Claude Code가 적용하는 권한 규칙과 훅을 담고, 저장소에 함께 두어 팀이 같은 설정을 사용합니다. 하위 에이전트 정의(.claude/agents/ 폴더의 파일)는 검토 하위 에이전트의 역할과 도구를 담습니다. 표 3-5는 명세서 항목별로 옮길 파일이며, 하네스 설정 파일과 함께 진행 기록, 결정 기록, 인계 메모, 검증 기준 파일도 적었습니다.

권한 규칙은 허용(allow), 확인 요청(ask), 금지(deny)의 세 목록에 둡니다. 규칙은 도구 이름 뒤 괄호에 대상을 적습니다. Edit 규칙은 파일을 수정하거나 새로 작성하는 Claude Code의 편집 도구(Edit, Write) 전체에 적용되고, Bash 규칙은 명령 실행 도구(Bash)에 적용됩니다. Edit(./data/**)는 data/ 폴더 아래 모든 파일의 수정을, Bash(git push *)는 git push로 시작하는 명령을 가리킵니다. 경로의 **는 하위 폴더를 포함한 모든 파일과 일치하고, 명령의 *는 아무 문자열과 일치합니다. ./는 현재 폴더를 기준으로 한 경로이며, 이 예제는 실습 폴더(examples/expense-app/)에서 Claude Code를 시작하고 그 폴더에서 작업한다고 전제합니다.

이 예제는 수용 시험, 검사 스크립트, 원본 자료의 수정을 금지해, 에이전트가 검증 기준과 등록할 수 있는 코드 목록을 변경하지 못하게 합니다. 규칙 문서, 결정 기록, 설정 폴더의 수정도 금지해, 에이전트가 자신에게 적용되는 규칙과 결정을 변경하지 못하게 합니다. 검사 스크립트는 수정만 금지하고 실행(python check.py)은 허용합니다.

금지 규칙이 막는 범위에는 한계가 있습니다. Claude Code 문서에 따르면 Edit 금지 규칙은 Claude Code의 편집 도구와 Claude Code가 알아보는 파일 명령에 적용되고, 에이전트가 실행한 스크립트가 파일을 직접 여는 경우에는 적용되지 않습니다. 명령 규칙은 문자열을 비교하므로, git -C . push처럼 다르게 작성한 명령은 Bash(git push *)와 일치하지 않습니다. 권한 모드(Permission Mode)가 사람에게 묻는 수동 모드(설정 값 default)라면, 허용 목록에 없는 명령은 실행 전에 확인을 요청하므로 사람이 그 자리에서 거절할 수 있습니다. 대화형 세션은 버전에 따라 Claude Code가 호출을 자동으로 판단하는 auto 모드로 시작하며, 문서에 따르면 auto 모드는 작업 중인 저장소로의 push를 기본으로 허용하므로 다른 형태로 작성한 push 명령은 규칙으로는 차단되지 않을 수 있습니다. 이 예제의 설정 파일은 모드를 정하지 않으므로, 수동 모드로 진행하려면 claude --permission-mode default로 시작하거나 설정 파일의 defaultMode에 default를 적습니다. 어느 모드에서든 허용한 단위 테스트 명령과 훅은 에이전트가 작성한 시험 코드를 묻지 않고 실행하며, 그 코드가 금지한 파일을 직접 열어 수정해도 Edit 금지 규칙은 막지 못합니다. 이런 경우는 사람이 commit 확인에서 바뀐 파일 목록으로 찾습니다.

버전 주석 (2026년 10월) Claude Code 문서는 v2.1.283 이상에서 모든 요금제의 대화형 세션이 auto 모드로 시작하고, 그 전 버전에서는 Pro, Max, Team 요금제만 auto 모드로 시작한다고 안내합니다. auto 모드는 작업 중인 저장소로의 push를 확인 없이 허용하지만, 강제 push 같은 동작은 예외로 둡니다.

괄호 없이 도구 이름만 적는 규칙도 있습니다. 웹 페이지를 가져오는 WebFetch와 웹을 검색하는 WebSearch는 Claude Code의 기본 도구이므로, 표 3-2에서 정한 웹 접근 제외를 지키려면 이 형식의 금지 규칙으로 막습니다. Claude Code 문서는 도구 이름만 적은 금지 규칙이 그 도구를 모델의 컨텍스트(Context)에서 없애, 모델이 그 도구를 볼 수 없게 한다고 설명합니다. 이 규칙은 두 도구만 막으므로, curl처럼 웹에 접근하는 셸 명령은 허용 목록 밖에서 권한 모드에 따라 처리됩니다. 아래는 설정 파일의 내용입니다. 실습 파일에는 python 명령이 없는 환경에서 사용하는 python3 허용 규칙 두 줄이 더 있으며, 여기서는 생략했습니다. 그런 환경에서는 훅 명령의 python도 python3로 변경합니다.

{
  "permissions": {
    "allow": [
      "Bash(python -m unittest *)",
      "Bash(python check.py)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(./data/**)",
      "Edit(./acceptance/**)",
      "Edit(./check.py)",
      "Edit(./CLAUDE.md)",
      "Edit(./DECISIONS.md)",
      "Edit(./.claude/**)",
      "Bash(git push *)",
      "WebFetch",
      "WebSearch"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "cd \"$CLAUDE_PROJECT_DIR\" && python -m unittest discover tests -q || exit 2" }
        ]
      }
    ]
  }
}

PostToolUse는 도구가 실행된 뒤에 훅을 실행하는 시점입니다. matcher의 Edit|Write는 파일 수정 도구(Edit) 또는 파일 작성 도구(Write)가 실행된 뒤를 뜻하며, |는 "또는"입니다. 명령은 프로젝트 폴더로 이동한 뒤 단위 테스트를 실행하며, $CLAUDE_PROJECT_DIR은 Claude Code가 프로젝트 폴더의 경로를 담아 주는 환경 변수입니다. 훅의 명령은 세션의 현재 폴더에서 실행됩니다. 세션이 하위 폴더로 옮겨 가면 그 자리에서는 tests 폴더를 찾지 못하므로, 먼저 프로젝트 폴더로 이동하게 했습니다.

명령 끝의 || exit 2는 앞의 테스트가 실패하면 종료 코드 2로 끝내라는 뜻입니다. Claude Code 문서는 PostToolUse 훅이 종료 코드 2로 끝나면 오류 출력(stderr)을 모델에 보여 주지만, 이미 실행된 도구는 막지 못한다고 설명합니다. 단위 테스트를 실행하는 Python의 시험 모듈(unittest)은 결과를 오류 출력에 작성하므로, 실패 내용이 모델에 전달됩니다. 따라서 편집 뒤 훅은 편집을 막지는 못하고, 실패를 알려 다시 작업하게 하는 장치입니다. 파일의 수정 금지는 권한 규칙이 맡습니다.

검토 하위 에이전트는 별도 파일(.claude/agents/reviewer.md)에 정의합니다. 검토하는 쪽이 코드를 수정할 수 있으면 자기가 수정한 결과를 자기가 검토합니다. 그래서 검토 하위 에이전트의 도구를 읽기 도구인 Read(파일 읽기), Grep(내용 검색), Glob(이름 패턴으로 파일 찾기)로 제한합니다. 아래는 그 파일의 내용입니다.

근거 파일과 줄 번호를 함께 보고해 줘. 파일은 수정하지 마.

정의 파일에서 두 줄의 --- 사이는 이름(name), 설명(description), 도구(tools)를 정하는 설정이고, 그 아래는 검토 하위 에이전트에게 주는 지시입니다. Claude Code 문서에 따르면 도구 줄을 생략한 하위 에이전트는 하위 에이전트가 사용할 수 있는 도구를 모두 물려받으므로, 읽기만 할 하위 에이전트는 도구 줄에 읽기 도구만 적습니다. 검토 하위 에이전트는 명령을 실행할 수 없어, 바뀐 내용을 보여 주는 git diff 명령을 직접 실행하지 못합니다. 그래서 규칙 문서의 작업 순서에 "확인 방법을 충족하면 commit 전에 reviewer 하위 에이전트에게 바뀐 파일 목록과 변경 내용(git status, git diff 출력)을 넘겨 수용 기준 대조를 요청한다"라고 적습니다.

검토 보고는 시험을 대신하지 않습니다. 검토 보고는 수용 기준과 코드를 읽고 비교한 결과이고, 실제로 동작하는지는 단위 테스트와 검사 스크립트의 실행 결과가 보여 줍니다.

실패를 예방하는 장치

명세서의 항목이 비어 있거나 하네스 설정 파일로 옮겨지지 않으면, 변경 요청 사항을 구현할 때 실패가 생길 수 있습니다. 표 3-6은 대표 실패 다섯 가지와 원인이 되는 명세서 항목, 방지 장치입니다. 방지 장치는 Chapter 2의 지시 기반 규칙과 강제 적용에서 나눈 강제(에이전트의 판단과 관계없이 제품이 적용하는 수단)와 지시(규칙 문서)에, 기록(진행 기록과 인계 메모)과 승인(사람의 확인)을 더해 나누어 적었습니다.

표 3-6에서 강제는 금지 규칙, 확인 요청 규칙, 하위 에이전트의 도구 제한이고, 지시는 규칙 문서에 적은 구현 수정, 중단, 인계 메모 작성 규칙이며, 승인은 사람의 확인입니다. Claude Code 문서는 CLAUDE.md를 강제 설정이 아닌 컨텍스트로 다루며, 지시를 엄격하게 따른다는 보장은 없다고 설명합니다. 표에는 없지만 검토를 요청하는 시점도 규칙 문서에 적은 지시이므로 모델이 건너뛸 수 있고, 그 공백은 사람의 commit 확인이 메웁니다. 그래서 지시로 막는 두 실패, 곧 같은 시험의 실패 반복과 인계 메모 누락은 모델이 지시를 따르지 않으면 다시 생길 수 있습니다. 이 예제는 두 실패가 생겨도 사람이 멈추거나 되돌릴 수 있어 지시로 두었습니다. 어기면 되돌리기 어려운 동작은 권한 규칙이나, 도구 실행 전에 막는 PreToolUse 훅으로 처리합니다.

설정과 결과의 확인 방법

명세서를 하네스 설정 파일로 옮긴 뒤에는, 파일이 실제로 적용되었는지 Claude Code의 화면과 검사 출력으로 확인합니다. 표 3-7은 변경 요청 사항을 구현하는 에이전트의 확인 방법입니다. /permissions와 /hooks는 실습 폴더에서 Claude Code를 실행한 뒤 입력창에 입력하는 명령이며, 각각 권한 규칙과 훅 설정을 보여 줍니다. python check.py는 터미널에서 실습 폴더(examples/expense-app/)로 이동한 뒤 실행합니다. 직접 실행하는 순서는 구현 전 기준 상태가 부록 실습의 실습 1. 실습 저장소와 기준 상태, 권한 규칙이 부록 실습의 실습 3. 권한 설정, 훅과 검토 하위 에이전트가 부록 실습의 실습 4. 검증 장치, 수용 기준 충족이 부록 실습의 실습 6. 기록과 인계에 있습니다.
