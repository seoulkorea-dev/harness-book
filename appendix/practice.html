실습

본문에서 설명한 하네스의 설정을 직접 구성하고 실행하는 실습을 모았습니다. 실습은 경비 정산 미니 웹 앱 하나를 함께 사용하며, 실습 1부터 차례로 진행합니다. 진행이 멈추면 부록 끝의 막혔을 때를 봅니다.

실습 준비

실습 자료는 저장소의 examples/expense-app/ 폴더에 있고, 실습 1에서 이 폴더를 저장소 밖의 새 폴더(이 부록에서는 expense-practice)로 복사해 사용합니다. 본문에서 "실습 폴더"나 examples/expense-app/이라고 부르는 곳은 실습에서는 이 복사한 폴더입니다.

실습 2부터는 Claude Code를 사용하므로 비용이 듭니다. Claude Code는 Pro 이상의 유료 요금제나 Claude Console 계정으로 사용하며, 무료 요금제에는 포함되지 않습니다43,44. 구독 요금제에서는 Claude Code 사용량이 요금제의 사용 한도 안에 포함됩니다21.

명령은 터미널(명령을 입력해 실행하는 창)에 입력합니다. Windows에서는 Win+X 메뉴에서 PowerShell을, macOS에서는 Cmd+Space로 Spotlight를 열어 Terminal을 찾아 엽니다45. Linux에서는 대부분의 배포판에서 Ctrl+Alt+T를 누르거나 응용 프로그램 메뉴에서 Terminal을 찾아 엽니다45.

실습에는 세 가지 도구가 필요합니다.

  • Python 3: 미니 웹 앱과 테스트를 실행합니다. 실습 코드는 표준 라이브러리만 사용하므로 추가 패키지를 설치하지 않습니다. 설치 파일은 https://www.python.org/downloads/ 에서 받습니다.
  • Git: 실습 저장소를 내려받고 변경 이력을 확인합니다. https://git-scm.com/downloads 에서 설치 파일을 내려받습니다. Windows용은 Git for Windows이며, 터미널 프로그램인 Git Bash가 함께 설치됩니다.
  • Claude Code: 실습에서 에이전트를 실행합니다. 아래 명령 가운데 운영 체제에 맞는 것 하나를 입력해 설치합니다44.

Windows의 PowerShell에서는 다음 명령을 입력합니다.

irm https://claude.ai/install.ps1 | iex

macOS와 Linux의 터미널에서는 다음 명령을 입력합니다.

curl -fsSL https://claude.ai/install.sh | bash

Windows에서는 Git for Windows를 설치한다고 전제하고, Claude Code를 설치한 뒤에는 Git Bash를 터미널로 사용합니다. 이 부록의 명령은 Git Bash와 macOS, Linux 기준이며, PowerShell에서 다른 명령은 따로 적습니다.

Git for Windows가 있으면 Claude Code는 셸 명령을 Git Bash로 실행합니다27. 이때 PowerShell 명령을 실행하는 PowerShell 도구도 함께 켜질 수 있지만, 셸 명령 금지 규칙이 있으면 PowerShell 도구가 꺼지므로 실습 3의 금지 규칙이 그대로 적용됩니다27.

설치를 마친 뒤 터미널에서 다음 세 명령으로 도구를 확인합니다.

python --version
git --version
claude --version

세 명령이 모두 버전 번호를 출력하면 실습을 시작할 수 있습니다. macOS와 Linux에서 python 명령을 찾지 못하면 이 부록의 python을 모두 python3으로 입력합니다. 다른 명령을 찾지 못한다는 메시지가 나오면 설치가 끝났는지 확인하고, 터미널을 닫았다가 다시 엽니다. claude 명령을 처음 실행하면 로그인 화면이 열리므로, 사용할 요금제의 계정이나 Console 계정으로 로그인합니다44.

실습 2~6에서 Claude Code를 시작할 때는 claude 대신 claude --permission-mode default를 입력합니다. Claude Code v2.1.283 이상의 터미널은 auto 모드, 곧 사람 대신 분류기 모델이 실행 전에 동작을 검토하는 모드로 시작하므로, 이 부록의 확인 화면(실행 전에 승인이나 거절을 묻는 화면)이 나오지 않을 수 있습니다. default는 파일 수정, 셸 명령, 네트워크 접근 대부분을 실행 전에 사람에게 묻는 수동 모드입니다11. 직전 세션을 다시 여는 claude --continue에도 같은 옵션을 함께 입력합니다.

실습 1에서 Git으로 첫 commit(바뀐 파일을 저장소의 기록으로 남기는 명령)을 남기려면 Git에 이름과 이메일이 설정되어 있어야 합니다. 설정한 적이 없다면 다음 두 명령을 한 번 실행합니다. --global은 현재 사용자의 모든 Git 저장소에 적용한다는 뜻입니다.

git config --global user.name "이름"
git config --global user.email "이메일 주소"
버전 주석 (2026년 10월) 요금제와 설치 방법은 2026년 10월 20일에 확인한 공식 문서 기준입니다43,44. 도입 시점의 문서에서 다시 확인합니다.

에이전트의 응답은 실행할 때마다 문장이 다를 수 있습니다. 확인 방법에 적은 기준(거부되었는지, 검사가 통과했는지, 파일이 변경되었는지)이 맞으면 응답 문장이 이 부록과 달라도 정상입니다. 저장소의 examples/expense-app/RUNLOG.md는 실습을 실행해 남긴 비교용 기록이며, 실습하는 사람이 기록할 필요는 없습니다.

실습 1의 복사, git init, 첫 commit, 단위 테스트, check.py는 2026년 10월 24일 Linux에서 실행해 확인했고, 실습 2~6의 응답과 화면은 실행 기록을 확인하기 전의 예상입니다.

실습 1. 실습 저장소와 기준 상태

실습 저장소를 내려받아 실습 폴더를 만들고, 경비 정산 시스템 개편 변경 요청 사항(이하 변경 요청 사항)을 구현하기 전의 기준 상태를 확인합니다. 먼저 Chapter 3의 예제: 변경 요청 사항의 에이전트 명세서 작성의 변경 요청 사항 설명을 읽고 시작합니다.

준비물

  • 실습 준비의 세 도구와 Git 이름, 이메일 설정

따라 하기

터미널에서 cd ~를 입력해 홈 폴더로 이동하고, pwd로 현재 위치를 확인합니다. 홈 폴더처럼 다른 Git 저장소 밖에 있는 폴더에서 다음 명령을 차례로 실행하면, harness-book 폴더와 expense-practice 폴더가 이 위치 아래에 생깁니다. 첫 줄은 책 저장소를 내려받고, 둘째 줄은 실습 앱 폴더만 저장소 밖의 새 폴더 expense-practice로 복사합니다. 저장소 밖으로 복사하는 이유는 책 저장소의 규칙 문서와 설정이 실습 폴더에 함께 읽히지 않게 하고, 원격 저장소에 연결되지 않은 연습 폴더를 만들기 위해서입니다.

git clone https://github.com/seoulkorea-dev/harness-book.git
cp -r harness-book/examples/expense-app expense-practice
cd expense-practice
git init
git add -A
git commit -m "실습 시작 상태"

PowerShell에서는 둘째 줄 대신 Copy-Item -Recurse harness-book/examples/expense-app expense-practice를 입력합니다. 셋째 줄은 복사한 폴더로 이동하고, git init부터 세 줄은 그 폴더를 새 Git 저장소로 만들어 시작 상태를 commit으로 남깁니다. 이어서 다음 명령으로 기준 상태를 확인합니다.

python -m unittest discover tests -q
python check.py
python app.py

첫 줄은 단위 테스트를, 둘째 줄은 단위 테스트와 수용 시험을 함께 실행하는 검사 스크립트를 실행합니다. 셋째 줄은 앱을 실행하며, 앱이 실행되는 동안에는 터미널에 다른 명령을 입력할 수 없습니다. 브라우저에서 http://localhost:8000(내 컴퓨터에서 실행 중인 앱의 주소)을 열어 정산 요청 목록을 확인하고, 터미널에서 Ctrl+C를 눌러 종료합니다. 주소가 열리지 않으면 다른 프로그램이 8000번 포트를 사용하고 있는지 확인합니다.

다음은 check.py 출력에서 요약 줄만 뽑은 것입니다(2026년 10월 24일 Linux에서 실행, 실패한 시험의 자세한 출력은 생략). tests 요약 줄은 출력 앞쪽에, FAILED와 acceptance 요약 줄은 맨 끝에 나옵니다. FAILED는 acceptance의 실패 3건 때문입니다. tests 줄의 project_code 시험은 이름에 project_code가 든 단위 테스트의 수이고, acceptance 줄의 정한 수는 실행되어야 할 수용 시험의 수입니다.

tests: 실행 3건, 실패 0건, 건너뜀 0건, project_code 시험 0건
FAILED (failures=3)
acceptance: 실행 5건, 실패 3건, 건너뜀 0건(정한 수 5건)

확인 방법

  • git log --oneline에 "실습 시작 상태" commit 하나가 보입니다.
  • 단위 테스트 명령의 출력 마지막 줄이 OK입니다.
  • check.py의 출력에서 tests(기존 기능의 단위 테스트) 3건은 모두 통과하고, acceptance(변경 요청 사항의 수용 기준을 시험하는 수용 시험) 5건 가운데 3건(test_1, test_2, test_3)은 실패합니다. 종료 코드(명령이 끝나면서 돌려주는 숫자로, 0은 성공, 0이 아닌 값은 실패)는 1입니다. 변경 요청 사항을 구현하기 전이므로 둘 다 정상입니다. 종료 코드는 명령 바로 뒤에 Git Bash와 macOS, Linux에서는 echo $?로, PowerShell에서는 $LASTEXITCODE로 확인합니다(Chapter 7의 설정과 결과의 확인 방법).
  • 이 폴더에는 아직 CLAUDE.md와 .claude/ 폴더가 없습니다. ls -a(PowerShell에서는 dir -Force)로 숨김 항목까지 확인합니다. 홈 폴더의 .claude/는 Claude Code가 사용자 설정을 두는 폴더이므로 있어도 정상입니다. 하네스의 설정은 실습 2~5에서 만듭니다.

실습 2. 규칙 문서 작성

에이전트가 세션마다 읽을 규칙 문서 CLAUDE.md를 작성합니다. 먼저 Chapter 5의 규칙 문서의 작성을 읽고 시작합니다.

준비물

  • 실습 1을 마친 expense-practice 폴더
  • 텍스트 편집기(파일 이름이 CLAUDE.md.txt가 되지 않게 확장자를 확인합니다)

따라 하기

  1. expense-practice 폴더에 CLAUDE.md 파일을 만듭니다. ls(PowerShell에서는 dir)로 파일 이름을 확인합니다.
  2. 목적, 읽는 순서, 작업 순서, 수정 범위, 중단 규칙, 명령의 여섯 절을 작성합니다. 절마다 무엇을 적는지는 expense-practice 안의 reference/CLAUDE.example.md에 예가 있으므로, 처음이라면 먼저 읽고 작성합니다. 수정 범위에는 data/, acceptance/, check.py, CLAUDE.md, DECISIONS.md, .claude/를 수정하지 않는다고 적습니다.
  3. 다 작성하면 예시와 다시 비교해 누락된 항목을 채웁니다.
  4. expense-practice 폴더에서 claude --permission-mode default를 입력해 Claude Code를 시작합니다. 처음에는 이 폴더를 신뢰하는지 묻는 화면이 나오므로 신뢰를 선택합니다46. 요청은 화면 아래의 입력창에 입력합니다. /로 시작하는 입력(슬래시 명령)은 Claude Code의 기능을 부르는 명령입니다.
  5. /context를 입력해 Memory files 항목(Claude Code가 규칙 문서를 표시하는 이름)에 CLAUDE.md가 있는지 확인합니다15.
  6. 다음 두 요청을 차례로 입력합니다. 둘째 요청에서 수정 확인을 묻는 화면이 나오면 선택지 가운데 거절에 해당하는 항목을 선택합니다. 확인 화면 없이 수정이 적용되면 확인 방법의 git restore로 되돌리고, 실습 준비의 권한 모드 옵션을 포함해 시작했는지 확인합니다(Chapter 10의 Claude Code: 도구별 권한 규칙과 추가로 켜는 샌드박스)11.
이 저장소에서 수정하면 안 되는 파일과 폴더를 알려 줘.
acceptance/test_cr07.py의 첫 번째 시험을 삭제해 줘.

확인 방법

  • 첫 요청의 응답이 CLAUDE.md의 수정 범위(data/, acceptance/, check.py 등)를 그대로 따르는지 확인합니다.
  • 둘째 요청에 에이전트가 규칙 문서를 근거로 거절하거나, 수정 확인을 묻는지 확인합니다. 규칙 문서는 에이전트가 읽고 따르도록 요청하는 지시이므로 이 단계에서는 시도를 막지 못할 수 있으며, 막지 못한 경우가 있는지 확인하는 것이 이 단계의 목적입니다. 막는 장치는 실습 3에서 만듭니다.
  • 실습을 마친 뒤 /exit로 Claude Code를 종료하고 git status를 실행해, acceptance/가 변경된 파일 목록에 없는지 확인합니다. 있으면 git restore acceptance/로 되돌립니다. 새로 만든 CLAUDE.md가 목록에 보이는 것은 정상입니다.
  • 응답과 화면은 실행 기록을 확인하기 전의 예상이므로, 문구가 달라도 위 동작이 맞으면 다음으로 진행합니다.

실습 3. 권한 설정

되돌리기 어려운 동작을 권한 규칙으로 막고, commit에는 확인을 거치게 합니다. 먼저 Chapter 9의 권한 규칙을 읽고 시작합니다.

준비물

  • 실습 2를 마친 폴더

따라 하기

  1. expense-practice 아래에 .claude 폴더를 만들고, 그 안에 settings.json을 만듭니다.
  2. reference/settings.example.json의 permissions 부분을 옮깁니다. hooks 부분은 실습 4에서 추가합니다. 옮기면 파일 전체가 다음 내용이 됩니다. 예를 들어 ask의 Bash(git commit *)는 git commit으로 시작하는 셸 명령을 실행 전에 확인 요청으로 돌리고, deny 목록의 Edit(./data/**)는 data 폴더 아래 모든 파일의 수정을 금지합니다. 중괄호와 대괄호의 짝이나 항목 사이의 쉼표가 어긋나면 설정이 반영되지 않을 수 있으므로, 3단계에서 /permissions로 규칙이 보이는지 확인합니다.
{
  "permissions": {
    "allow": [
      "Bash(python -m unittest *)",
      "Bash(python check.py)",
      "Bash(python3 -m unittest *)",
      "Bash(python3 check.py)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(./data/**)",
      "Edit(./acceptance/**)",
      "Edit(./check.py)",
      "Edit(./CLAUDE.md)",
      "Edit(./DECISIONS.md)",
      "Edit(./.claude/**)",
      "Bash(git push *)",
      "WebFetch",
      "WebSearch"
    ]
  }
}

  2. 다음 세 요청을 차례로 입력합니다. 에이전트가 CLAUDE.md의 수정 범위를 근거로 시도하지 않고 답만 하면 금지 규칙이 작동했는지 알 수 없으므로, "금지 규칙을 확인하는 시험이야. 실행을 시도하고, 거부되면 그 메시지를 그대로 보여 줘."라고 이어서 입력합니다. 다른 방법으로 같은 동작을 하겠다는 확인 요청이 나오면 거절합니다.

data/projects.csv에 PRJ-2604 행을 추가해 줘.
원격 저장소에 push해 줘.

확인 방법

  • /permissions 화면에 허용(allow), 확인 요청(ask), 금지(deny) 규칙과 그 출처 .claude/settings.json이 보입니다.
  • 세 요청 모두 실행 전에 거부되고, 금지 규칙으로 거부되었다는 메시지가 화면에 보입니다. 거부되지 않고 확인 요청이 나오면 거절하고, /permissions에서 규칙이 읽혔는지 다시 확인합니다. push는 이 폴더에 원격 저장소가 없으므로 금지 규칙이 없어도 실패하지만, 금지 규칙은 실행 전에 거부한다는 점이 다릅니다.
  • /exit로 종료한 뒤 git status를 실행해 acceptance/와 data/가 변경된 파일 목록에 없는지 확인합니다. 실습 2에서 만든 CLAUDE.md와 이 실습에서 만든 .claude/는 보이는 것이 정상입니다. commit 확인 요청은 실습 5에서 만납니다.
  • 금지 규칙은 명령 문자열이나 파일 경로가 일치하는 시도만 막으므로, 다른 형태로 작성한 명령이나 스크립트를 통한 간접 수정은 막지 못할 수 있습니다(Chapter 9의 격리와 샌드박스). 응답과 화면은 실행 기록을 확인하기 전의 예상이므로, 문구가 달라도 위 동작이 맞으면 다음으로 진행합니다.

실습 4. 검증 장치

편집할 때마다 단위 테스트를 자동으로 실행하는 훅(정해진 시점에 자동으로 실행되는 명령)과, 수용 기준을 대조하는 검토 하위 에이전트(특정 작업을 맡도록 따로 정의한 에이전트)를 만듭니다. 먼저 Chapter 7의 예제: 변경 요청 사항의 검증 설계를 읽고 시작합니다.

준비물

  • 실습 3을 마친 폴더

따라 하기

  1. .claude/settings.json에 reference/settings.example.json의 hooks 부분을 추가합니다. 이 훅은 파일을 수정할 때마다 단위 테스트를 실행하고, 테스트가 실패하면 에이전트에게 알립니다. macOS와 Linux에서 python 명령이 없으면 훅 명령의 python도 python3으로 변경합니다. hooks는 permissions와 같은 단계의 항목이므로, permissions 블록의 닫는 중괄호 뒤에 쉼표를 찍고 이어서 추가합니다. 합친 파일 전체는 다음과 같으며, reference/settings.example.json과 같은 내용입니다.
{
  "permissions": {
    "allow": [
      "Bash(python -m unittest *)",
      "Bash(python check.py)",
      "Bash(python3 -m unittest *)",
      "Bash(python3 check.py)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Edit(./data/**)",
      "Edit(./acceptance/**)",
      "Edit(./check.py)",
      "Edit(./CLAUDE.md)",
      "Edit(./DECISIONS.md)",
      "Edit(./.claude/**)",
      "Bash(git push *)",
      "WebFetch",
      "WebSearch"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "cd \"$CLAUDE_PROJECT_DIR\" && python -m unittest discover tests -q || exit 2" }
        ]
      }
    ]
  }
}
  1. .claude 폴더 아래에 agents 폴더를 만들고, reference/reviewer.example.md를 reviewer.md라는 이름으로 복사합니다(cp reference/reviewer.example.md .claude/agents/reviewer.md). 이 reviewer는 파일을 읽기만 하고 검토 결과를 보고합니다.
  2. Claude Code를 다시 시작하고 /hooks를 입력해 파일 수정 뒤(PostToolUse)에 실행되는 훅이 목록에 있는지 확인합니다.
  3. 다음 세 요청을 차례로 입력합니다. 첫 요청은 목록에 요청자가 보이는지 확인하는 단위 테스트를 일부러 깨뜨려, 훅이 작동하는지 보려는 것입니다. 에이전트가 훅의 실패를 보고 tests/의 시험을 수정하려 하면 거절합니다. 파일 수정 확인 화면이 나오면 수정 대상이 expense/ 안인지 확인하고 승인합니다. 승인해야 수정이 적용되고, 그 뒤에 훅이 실행됩니다. 확인 화면 없이 바로 적용되면 실습 준비의 권한 모드 옵션을 포함해 시작했는지 확인합니다.
expense/views.py의 목록 표에서 요청자 열을 빼 줘.
방금 수정한 내용을 되돌려 줘.
reviewer 에이전트로 현재 코드가 docs/CR.md의 수용 기준을 충족하는지 확인해 줘.

확인 방법

  • /hooks 목록의 PostToolUse 아래에 훅이 있고, 선택하면 단위 테스트 명령이 보입니다. 성공한 훅은 대화에 출력이 보이지 않으며, 첫 요청처럼 테스트가 실패하면 에이전트가 실패 출력을 받아 응답에서 테스트 실패를 언급합니다25.
  • 세 요청을 마친 뒤 /exit로 종료하고 git diff expense/ tests/를 실행해 출력이 없는지 확인합니다. 출력이 있으면 git restore expense/ tests/로 되돌립니다.
  • reviewer 보고가 수용 기준마다 충족, 미충족, 확인 불가를 근거 파일과 함께 제시합니다. 변경 요청 사항을 구현하기 전이므로 docs/CR.md의 기준 1~3은 미충족이며, 이는 실습 1에서 실패한 수용 시험 test_1~test_3과 같은 기준입니다. 기준 4, 5는 구현 전에도 충족되는 기존 동작이므로 충족으로 보고되는 것이 정상입니다.
  • 응답과 화면은 실행 기록을 확인하기 전의 예상이므로, 문구가 달라도 위 동작이 맞으면 다음으로 진행합니다.

실습 5. 작업 단위로 구현

작업 단위 목록을 만들고, 첫 세션에서 작업 단위를 하나씩 구현합니다. 먼저 Chapter 6의 예제: 변경 요청 사항의 작업 단위 나누기를 읽고 시작합니다.

준비물

  • 실습 4를 마친 폴더

따라 하기

  1. reference/tasks.example.json을 expense-practice/tasks.json으로 복사합니다. tasks.json에는 작업 1~5가 있고, 각 항목은 id, 작업, 완료 기준, 확인 방법, 통과 값(작업 단위가 끝났는지를 적는 true 또는 false)으로 이루어지며, 작업 1(프로젝트 코드 조회 방식 합의)은 이미 결정 기록으로 마쳐 통과 값이 true입니다. 복사한 뒤 git add tasks.json과 git commit -m "작업 단위 목록 추가"로 목록을 commit해 둡니다. 이 commit이 있어야 작업 단위의 commit이 쌓인 뒤에도, 확인 방법의 git diff HEAD~2 -- tasks.json처럼 목록을 추가한 시점과 비교해 통과 값의 변경을 볼 수 있습니다.
  2. Claude Code를 다시 시작하고 다음 요청을 입력합니다. 에이전트는 통과 값이 false인 첫 작업 단위인 작업 2를 맡습니다.
CLAUDE.md의 규칙대로 tasks.json의 다음 작업 단위를 수행해 줘.
  1. 파일 수정 확인 화면이 나오면 수정 대상이 CLAUDE.md의 수정 범위(expense/, app.py, tests/, tasks.json의 통과 값, HANDOFF.md) 안인지 보고 승인합니다.
  2. commit 확인 요청이 나오면 승인하기 전에 다른 터미널 창을 열고, expense-practice 폴더에서 git status와 git diff HEAD로 변경된 파일과 내용을 봅니다. 변경된 파일이 수정 범위 안에 있고 data/와 acceptance/가 변경되지 않았으면 승인합니다. 작업 2의 commit에서는 expense/store.py나 expense/service.py에 project_code 항목이 추가되었는지도 봅니다.
  3. 작업 2의 commit을 승인한 뒤 tasks.json에서 작업 2의 통과 값을 true로 변경합니다. CLAUDE.md의 규칙에 따라 에이전트는 이 값을 변경하지 않습니다. 이어서 "CLAUDE.md의 규칙대로 tasks.json의 다음 작업 단위를 수행해 줘."를 다시 입력해 작업 3을 맡기고, 3~4단계와 같은 기준으로 승인합니다. 작업 3을 마치면 작업 4를 요청하지 않고 실습 6으로 넘어갑니다.

확인 방법

  • 완료 보고에 python check.py의 출력 원문이 들어 있습니다. 작업 4를 하기 전이므로 수용 시험 test_1~test_3은 아직 실패하고 종료 코드 1이 정상입니다. 종료 코드 0은 실습 6에서 확인합니다.
  • git diff HEAD~2 -- tasks.json을 실행해 작업 2와 작업 3의 통과 값만 true로 변경되었는지 확인합니다. HEAD~2는 마지막 commit에서 두 commit 앞, 곧 작업 단위 목록 추가 commit을 가리킵니다.
  • git log --oneline에 실습 시작 상태와 작업 단위 목록 추가 뒤로 작업 단위마다 commit이 하나씩, 모두 두 개 더 있습니다. git diff HEAD~2 --stat으로 바뀐 파일이 수정 범위 안인지 확인합니다.
  • 작업 2의 구현은 git diff HEAD~2 -- expense/store.py expense/service.py에서 project_code 항목이 추가되었는지로 직접 확인합니다. 수용 시험 4, 5는 구현 전에도 통과하므로, 그 통과만으로는 작업 2의 구현을 확인할 수 없습니다.
  • 응답과 화면은 실행 기록을 확인하기 전의 예상이므로, 문구가 달라도 위 동작이 맞으면 다음으로 진행합니다.

실습 6. 기록과 인계

첫 세션을 인계 메모로 마치고, 새 세션이 인계 메모만으로 작업을 이어 가는지 확인합니다. 먼저 Chapter 8의 인계 메모 작성을 읽고 시작합니다.

준비물

  • 실습 5를 마치고 종료하지 않은 첫 세션(이미 종료했다면 claude --continue로 직전 세션을 다시 엽니다)

  1. 첫 세션에서 다음 요청을 입력하고, 작성된 HANDOFF.md에 다섯 항목(현재 상태, 읽을 문서, 미결정, 다음 작업, 확인 명령)이 있는지 확인한 뒤 /exit로 종료합니다.

  • 응답과 화면은 실행 기록을 확인하기 전의 예상이므로, 문구가 달라도 위 동작이 맞으면 다음으로 진행합니다.

막혔을 때

  • 처음부터 다시 하려면: expense-practice 폴더를 지우고 실습 1의 복사부터 다시 합니다. 내려받은 harness-book 폴더는 그대로 둡니다.
  • commit이 "Author identity unknown"으로 실패하면: 실습 준비의 git config 두 명령을 실행합니다.
  • 설정 파일을 수정했는데 반영되지 않으면: Claude Code를 /exit로 종료하고 다시 시작합니다. 그래도 /permissions나 /hooks에 보이지 않으면 settings.json의 중괄호와 쉼표를 확인합니다.
  • 권한 화면이 이 부록과 다르면: 실습은 화면 문구와 관계없이 동작으로 판정합니다. 금지한 동작이 실행되지 않았는지 git status와 git diff로 확인합니다. 확인 요청 화면에서 다른 방법으로 같은 동작을 하겠다고 하면 거절합니다.
  • 테스트가 계속 실패하거나 에이전트가 수정 범위 밖의 파일을 수정하려 하면: 확인 요청을 거절하고, 실패 출력이나 CLAUDE.md의 수정 범위를 함께 알려 다시 맡깁니다. 그래도 같으면 git restore로 되돌리고 작업 단위를 처음부터 다시 맡깁니다.
